# Where the Savings Go: The Limits of Hiding Cross-Tenant Cache Hits in LLM Serving
> arXiv preprint (not peer reviewed). Johns Hopkins University
> 2026

This paper asks how far defenses that "hide" cache hits can go when tenants share the prompt-prefix cache of an LLM serving engine. A cache hit skips the prefill of a prefix and makes the response faster, so a shared cache reveals whether someone else recently sent a given text. Per-account salting of cache keys closes the channel but gives up cross-tenant reuse, and it only isolates whole accounts, which does not help when relays put many end users behind one account. Research defenses therefore keep a shared cache and make the hit request look like a miss. The authors point out that these defenses only look at the hit request itself and instead follow where the saved time goes: in step-based schedulers that never idle while work waits, the time saved by a hit is passed in full to every request queued behind it, all of which finish earlier by the same amount.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.20291
- arXiv HTML full text: https://arxiv.org/html/2611.20291
- arXiv PDF: https://arxiv.org/pdf/2611.20291

### Contribution
- Attack: the attacker brackets a probe for a candidate text with two groups of its own one-output-token listener requests, sends them in a short burst, and counts in how many steps the listeners finish. Counting steps instead of time makes the reading insensitive to queueing delay, and the attack stays within ordinary rate limits.
- Defense evaluation: hiding only the hit request falls to a single probe on both vLLM and SGLang; random delays must reach about ten times the shift or more to cut the attacker's advantage to 0.1; narrowing what is shared gives no guarantee.
- Theory: since any benefit a tenant can observe is also a signal, a rate-limited tenant's gain from content written by k other accounts is at most of order k times the allowed leakage. At zero leakage, only the provider keeps the savings.
- Shows that exact hiding is possible in principle on one instance, but because a mechanism only knows approximately how long skipped work would have taken, it must pay padding that grows with time rather than with the number of hits.

### Evaluation
- Setup: the schedulers of ten mainstream serving engines were reviewed from code and documentation, with experiments on vLLM and SGLang. On an idle vLLM engine on an L40S GPU, a 1,024-token hit made all 16 requests queued behind it finish 68 to 69 ms earlier.
- Main result: replaying a production trace on one vLLM instance at up to half its capacity, a single probe tells whether a text of 256 tokens or more was cached with an advantage of at least 0.98.
- Credibility: the attack's key condition (no other tenant's request entering the short probe window) is turned into a required burst rate, and the defense evaluation is set directly against the threat models of the earlier work. Measurements focus on a single instance, so the effect on large distributed serving needs separate confirmation.

#### Comment
- The practical conclusion is clear: services that need isolation should not try to hide hits but should salt per trust domain, with the boundary drawn by the layer that actually knows it (the relay or the application).
- The attack applies a classic queueing side channel, reading another party's work through the timing of one's own requests, to LLM serving. It is easy to follow and gives a solid reason to review how commercial APIs scope their caches.

# When Tool Names Are Not Identities: Measuring Provider Misbinding in MCP-Based AI Agents
> arXiv preprint (not peer reviewed). Canadian Institute for Cybersecurity (CIC), University of New Brunswick
> 2026

This paper measures a weakness in agents that combine tools from several Model Context Protocol (MCP) servers: tool names and descriptions are not bound to the identity of the provider that actually serves them. The authors call the failure tool-provider misbinding, where a request meant for a legitimate provider is resolved to a tool controlled by an attacker. The attacker compromises nothing, not the host, the LLM, the legitimate server or the network; it simply runs another MCP server visible to the same client and advertises tools with chosen metadata. In a controlled environment with one legitimate and one attacker server, the authors systematically vary tool name, description and schema and record which provider five LLM-based clients pick.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.21577
- arXiv HTML full text: https://arxiv.org/html/2611.21577
- arXiv PDF: https://arxiv.org/pdf/2611.21577

### Contribution
- Formulates tool-provider misbinding as an optimisation problem in which the attacker maximises the chance its tool is selected, and defines metrics for attacker selection, clarification requests, failures and the stability of the resolved binding across repeated runs.
- A 2×3×2 factorial design over name (unrelated, copied), description (unrelated, task-aligned, authority-enhanced) and schema (compatible or not), giving twelve conditions that isolate each metadata field's contribution.
- Robustness experiments with unrelated-name samples, authority-enhanced description samples and different numbers of attacker candidates, to rule out effects tied to one string or one candidate.
- Proposes provider-bound tool identity as the defense direction, through signed tool manifests, stable provider-bound tool identifiers, schema hashes and client-side enforcement.

### Evaluation
- Clients: GPT-5.4, Claude Sonnet 5, Gemini 2.5 Pro, Qwen3.7 Max and DeepSeek V3. Ten prompts repeated five times give 50 trials per condition per model.
- Main results: low-alignment controls were mostly safe, while the worst failures came when an exact name collision, a task-aligned description and a compatible schema reinforced each other. Across five description samples, the attacker selection rate in that condition was 0.98 for GPT-5.4, 1.00 for Qwen3.7 Max and DeepSeek V3, and 0.72 for Gemini 2.5 Pro; Claude Sonnet 5 selected the attacker in 0.256 of trials and asked for clarification in 0.744. Even without a name collision, authority-enhanced descriptions with a compatible schema caused wrong-provider execution or unresolved ambiguity.
- Credibility: repeated trials with 95% confidence intervals, and results that hold when samples are varied. The authors note that only one task (dataset fetching) was tested and the metadata variants are controlled, so they do not cover every attacker strategy or real MCP deployment.

#### Comment
- The models fail in different ways. Some silently run the attacker's tool, while Claude Sonnet 5 mostly asks the user. Asking is better than silent execution, but as the authors say, model caution does not replace verified provider identity.
- The observation that binding stability is not a safety metric in itself (being stably bound to the attacker is the worst case) is worth keeping in mind when designing evaluations.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Compositional Exploits in Autonomous Coding Agents: Attack Mechanics and Ephemeral Defense
> arXiv preprint (not peer reviewed). Google
> 2026

This paper studies "compositional exploits", where a coding agent chains individually harmless tools across turns to carry out an unauthorised attack. Today's tool vetting checks each tool on its own with static analysers such as Bandit and Semgrep or with LLM review. Yet if a config auditor with no network access writes credentials to a scratch file, and a webhook notifier that cannot read credential files sends that scratch file out, no tool has broken a rule and the credentials are still exfiltrated. The authors compare this to code-reuse attacks such as ROP in binary exploitation and formalise it as a threat in which legitimate tools are linked through shared state: workspace files, environment variables and chat memory. As a defense they propose CompGuard, which combines a control plane that issues short-lived capability leases and tracks dataflow provenance with an enforcement layer in the Linux kernel built on Landlock, seccomp-BPF and a loopback proxy.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.19764
- arXiv HTML full text: https://arxiv.org/html/2611.19764
- arXiv PDF: https://arxiv.org/pdf/2611.19764

### Contribution
- A threat model for composition over shared state (files, environment variables, memory) and a taxonomy of eight hazard classes, with triggers including routine-sounding work orders, indirect prompt injection, dormant CI/CD triggers and refusal laundering through multiple agents.
- A 560-task evaluation suite made of an attack benchmark, a benign-workflow benchmark and 100 real cloud diagnostic tasks.
- CompGuard: single-skill capability leases, a fine-grained artifact provenance graph that parses structured configs, and per-run Landlock rulesets and seccomp socket filters that confine file and network access in the kernel. Kernel enforcement is the key to stopping shell tricks (base64 piping, variable interpolation, dynamic imports) that slip past user-space filters.

### Evaluation
- Attacks: unprotected Gemini 3.5, 3.7 and 3.8 Flash executed compositional exploit chains with 72.9% to 84.5% success, while five single-tool pre-distribution scanners detected none of the constituent tools.
- Defense: CompGuard reports a 100% defense block rate (0.0% to 0.8% pre-teardown net attack success), 61.4 microseconds of interposition overhead, a 98.0% solve rate on benign developer tasks (2.0% false positives), and zero false alarms across 615 real cloud diagnostic calls.
- Credibility: both attack and defense are measured on the authors' own benchmarks, and the only models tested are the company's own Gemini family, so success rates for other agent products are unknown. No code link was found in the paper, and the ticket numbers in the disclosure section are masked.

#### Comment
- The argument that per-tool vetting, as practised today in MCP and skill marketplaces, cannot catch composed attacks is convincing and directly useful when designing agent sandboxes.
- The authors list three residual limitations: whole-file taint for proprietary formats, a microsecond teardown window when a worker abuses a pre-authorised local socket, and an SNI-only proxy that domain fronting or ECH could fool. Timing covert channels are out of scope.
- Full text source: arXiv PDF (downloaded on the user's computer).

# From Bytes to Behavior: Request-Level Attribution from Live GPU Hidden States
> arXiv preprint (not peer reviewed). Home Team Science and Technology Agency (HTX), Singapore
> 2026

This paper shows how to pull per-layer residual-stream activations for a single request out of the GPU memory of a running LLM service and use them as forensic evidence of what the model did. Existing machine-learning memory forensics targets static artifacts such as weights or prompt logs, and residual-stream memory is reused right after processing, so it never shows up in logs. The authors attach a non-modifying CUDA debugger to the target and, without knowing the model's architecture or weights, pick out the residual-stream allocations from PyTorch's allocator event stream alone and read them.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.18272
- arXiv HTML full text: https://arxiv.org/html/2611.18272
- arXiv PDF: https://arxiv.org/pdf/2611.18272

### Contribution
- A six-stage process (attach, clock, identify, read, validate, use) in which only the clock and the identification rule are platform-specific, organised as adapters.
- Two adapters: an allocator clock with a blind two-step selector, and a kernel-launch clock supporting vLLM under compilation and CUDA graphs, llama.cpp with quantised weights, and SGLang prefill. Failures are reported alongside successes.
- A way to derive the target's shape (token count, hidden size, layer count) from the process itself rather than from its identity.
- A use case: linear probes trained on ordinary framework activations, applied to recovered states, separate refusal from compliance at the request level.

### Evaluation
- Recovery accuracy: on 33 open decoder-only models across nine architecture classes, the recovered bytes matched hook references exactly.
- Refusal classification: on default-configuration vLLM with Qwen2.5-0.5B-Instruct and 142 untouched prompts, a frozen probe reached an AUROC of 0.876 and balanced accuracy of 0.777, but with a false-positive rate of 0.282. On two other held-out sources the error rate was 4.5% (157 prompts) and 15.5% (71 JailbreakBench prompts). Baselines such as a dataset-label rule and a prompt-text classifier are also reported.
- Credibility: reporting is careful, with pre-registered tests and bootstrap confidence intervals. The scope is limited to models of at most 3.4B parameters (plus one 4-bit 7B model), batch size 1 and fixed prompt lengths, and the authors note that the selector needed two revisions after initial failures.

#### Comment
- The new idea is preserving evidence of how a model actually responded to a request when the service cannot be stopped or modified. The authors summarise that structure can be stated with confidence, computation with a laboratory caveat, and behaviour only as a preliminary call with error rates.
- The practical limits are significant: the debugger halts the process at each allocation, slowing it 46 to 192 times; continuous batching and variable-length inputs are untested; proprietary runtimes such as TensorRT-LLM were not tried; and the authors acknowledge that attaching a debugger can itself contaminate evidence.
- This was a carried-over candidate deferred on 2026-11-17 because of the download cap.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Optional Traps: An Empirical Study of LLM Agents Against Credential Deception and Alert-Driven Revocation
> arXiv preprint (not peer reviewed), code and data released. Independent researcher (Jakarta, Indonesia)
> 2026

This paper tests whether deception (honeypots, decoys and canary credentials) works against LLM-agent attackers, and what it adds once ordinary hardening is in place. Deception relies on the premise that legitimate users never touch a fake asset. The author built an isolated lab with hash-chained logs around a mock Records API and ran four studies. Prompt injection and hidden instructions were deliberately avoided; the decoys are ordinary fake assets and a canary credential.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.19295
- arXiv HTML full text: https://arxiv.org/html/2611.19295
- arXiv PDF: https://arxiv.org/pdf/2611.19295
- Author's repository: https://github.com/ghifiardi/AI-Deception-Lab
- Paper PDF in the author's repository: https://github.com/ghifiardi/AI-Deception-Lab/blob/main/paper/optional-traps-preprint.pdf
- Archived artifact (Zenodo, DOI): https://doi.org/10.5281/zenodo.24217354

### Contribution
- A reproducible deception lab with hash-chained event logs, signed control events and per-client revocation, evaluated locally and on Google Cloud.
- A documented bypass in which a live model ignored every decoy placed beside the real path and used a genuine leak instead, and the defense redesign it led to.
- A paired ablation comparing hardening alone with hardening plus deception, separating where prevention actually comes from.
- A cloud validation in which a real OpenCanary alert is authenticated, signed and turned into revocation of only the attacking client.

### Evaluation
- Study 1 (exploratory): a local 9.7B model ignored every optional decoy in both static and adaptive deception modes, read a genuinely leaked service key from a debug endpoint and exported the protected records.
- Study 2 (frozen protocol, 60 sessions, 4B model): export success was 20/20 at baseline, 0/20 with hardening alone and 0/20 with hardening plus deception (McNemar p = 1.9×10^-6 for baseline versus defended, p = 1 for hardened versus defended). Deception added detection and per-client revocation in 19 of 20 defended sessions, but no measurable extra prevention.
- Study 3 (Google Cloud): a real OpenCanary login alert led to revocation, with the first denied export within an observed upper bound of 303 ms. A separate legitimate client completed 100/100 requests and all 14 control checks passed.
- Study 4 (multi-agent): agents that used the canary were revoked 39 to 59 seconds after the bait was served without affecting siblings, but one model-driven legitimate agent also took the bait and was revoked.
- Credibility: the author is upfront that samples are small (the Wilson interval for 0/20 still allows up to 16.1%), there is one mock API and only two local models (4B and 9.7B), and Study 2 measures exploitation of a known weakness rather than discovery. The Study 2 protocol was frozen locally but not externally timestamped.

#### Comment
- The conclusions are practical: against LLM agents, traps must sit on the attacker's path rather than beside it, hardening of real weaknesses does the preventive work, and deception's measurable value is fast, attributable detection. The risk that a legitimate LLM client also takes the bait is a new false-positive mode compared with deception designed for human users.
- It is a six-page, single-author, lab-scale study that does not use commercial models. On the other hand, code, logs and the verifier are all public, so it is easy to reproduce.
- Full text source: the paper PDF in the author's GitHub repository. Title, author and the abstract's numbers (20/20, 0/20, 303 ms and so on) match the arXiv abstract.

# TRIAGE-CPG: A Cross-Model Study of Budgeted Static Malware Triage with Large Language Models
> Published at ACM AISec '26 (19th ACM Workshop on Artificial Intelligence and Security), pp. 339-351, DOI 10.1145/3847352.3848112. abstract-only summary, full text not read
> 2026

According to the authors, this study looks at how LLMs behave in static triage, deciding whether to clear an unknown binary as benign, flag it as malicious or escalate it, framed as evidence gathering under a fixed budget. Because a binary can contain hundreds or thousands of functions, too many for an LLM to read, they build TRIAGE-CPG, a fixed pipeline over a code property graph (CPG) of the decompiled binary: an LLM-free heuristic picks seed functions, an agent expands the evidence dossier within a budget, and a reporting stage gives a benign, suspicious or malicious verdict with a behavioural report.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.21331
- arXiv HTML full text: https://arxiv.org/html/2611.21331
- arXiv PDF: https://arxiv.org/pdf/2611.21331
- ACM Digital Library (DOI): https://doi.org/10.1145/3847352.3848112
- Code and artifacts (Zenodo): https://doi.org/10.5281/zenodo.22771897

### Contribution
- The authors say they frame static triage as budgeted evidence acquisition and provide a fixed pipeline in which only the model changes.
- They report a triage balanced accuracy (tBA) metric that credits malware when it is flagged or escalated and benign samples only when cleared.
- They claim the models implement different triage policies: high-specificity models produce small, malware-rich escalation queues, while recall-oriented models flag or escalate much more broadly.

### Evaluation
- According to the abstract, eight closed and open-weight models were evaluated with the same zero-shot protocol on 1,000 Windows PE binaries, using a 600-sample test split.
- After analysing about 40 of a mean 1,000 functions per binary, the best model reached a strict balanced accuracy of 0.805 and a tBA of 0.855, flagging 65% of malware, escalating another 12% and clearing 94% of benign samples.
- Closed and open-weight models appear across the whole policy spectrum, according to the authors.
- The full text was not read, so the dataset, comparison conditions and credibility of the metrics could not be checked.

- Trust signals: the arXiv journal_ref gives the ACM AISec '26 proceedings and a DOI, and the comment links a Zenodo artifact. AISec is a long-running AI security workshop held with ACM CCS.

# We Have All the Cards: Securing Agent Cards at the Operational Trust Boundary of the Agent2Agent Protocol
> To appear at AIDC'26 (Workshop on Agentic AI in Offensive and Defensive Cyber Operations, co-located with IEEE ACSAC). abstract-only summary, full text not read
> 2026

According to the authors, this paper deals with a pre-invocation trust problem in the Agent2Agent (A2A) protocol: Agent Cards, the metadata orchestrators use to discover and select external agents, contain attacker-controllable natural-language fields that can steer agent selection before any provider is invoked. They present a taxonomy of ten Agent Card manipulation attacks and SECCARD, a layered validation framework that combines protocol checks, deterministic analysis and LLM-based semantic reasoning.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.18887
- arXiv HTML full text: https://arxiv.org/html/2611.18887
- arXiv PDF: https://arxiv.org/pdf/2611.18887
- Workshop homepage: https://aidcworkshop.github.io/

### Contribution
- The authors say they characterise the discovery-time attack surface as ten classes of Agent Card manipulation.
- They report probing 36.1 million Internet domains, collecting 310 deployed Agent Cards, and having two annotators label them independently with 96.8% agreement.
- They describe a 660-card benchmark of attacks injected into real cards with matched benign controls, and a 260-card synthetic benchmark covering all ten attack classes.

### Evaluation
- According to the abstract, on attacks injected into real Agent Cards the strongest semantic judge reached 97.0% security recall at a 1.7% false-positive rate.
- On the synthetic benchmark, security recall across nine LLM judges ranged from 25.8% to 92.3%, and the authors note that SECCARD's effectiveness depends heavily on the choice of judge.
