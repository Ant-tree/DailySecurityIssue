# NameTrap: Steering AI Coding Agents Toward Security Vulnerabilities via Variable Names
> arXiv cs.CR (preprint, not peer reviewed), National Yang Ming Chiao Tung University (Taiwan). The manuscript uses the WWW '27 conference template, but neither the manuscript nor the arXiv entry states that it has been accepted.
> 2026

AI coding agents clone repositories and read source code fetched from the web as part of their work, so publicly hosted code becomes the context for the code they write. This paper presents NameTrap, an attack that steers agents into writing a specific CWE weakness purely by renaming identifiers in third-party Python files, with no injected instructions at all. To target OS command injection (CWE-78), for instance, it gives variables names that read like "already validated, trusted commands", nudging the agent to skip validation when it fills in the missing code. The released bait contains neither instructions nor vulnerable code, only changed names, and none of seven static and AI-based analyzers flagged it in advance.

Paper: https://arxiv.org/abs/2610.34253

### Contribution
- Builds bait automatically: an attacker-side coding agent renames identifiers according to a CWE-specific naming convention, then a separate session completes the code and Bandit and Semgrep check whether the weakness appears, and the loop repeats. Before release, the bait must pass token comparison, Git diffing, compilation checks and manual review confirming that only identifiers changed and behavior is preserved.
- Compares against random renaming, neutral renaming and the earlier identifier-poisoning attack XOXO under the same conditions, separating the effect of deliberately chosen names from the effect of renaming as such.
- Tests persistence from several angles: Traditional Chinese prompts, transfer across models, a prompt-level security reminder, and detection before use.

### Evaluation
- Targets: Python files from 31 of the 100 most-starred GitHub projects. Only files whose clean versions never produced the target weakness in 10 completions were kept as starting points.
- Six agents (OpenCode, Claude Code, Codex, mini-swe-agent, Aider, OpenHands), ten models (the Qwen-3.5 family, Gemma-4, Nemotron, GPT-5.4-mini, DeepSeek-V4-Flash, Claude Haiku 4.5) and four weaknesses (CWE-78, 79, 327, 502).
- With Qwen-3.5-27B as the shared model across the six agents, attack success rates were 22.5% to 56.0%, above the averages for random renaming (11.8%) and neutral renaming (6.6%). XOXO managed only 2.1% under the same conditions.
- Transfer: CWE-78 bait triggered the weakness at least once on a different model in 42 of 81 pairs (51.9%). The security-reminder defense lowered the mean success rate across 30 configurations only from 22.3% to 19.2%, and success actually went up in 15 of them.
- Detection: CodeGemma, CodeAstra-7B, GPT-5.4-mini, Bandit, Semgrep, CodeShield and CodeQL all failed to report the target weakness in the bait files.
- Credibility of the metrics: success is judged only by Bandit and Semgrep, the same two tools used to confirm success while building the bait, so the attack may be tuned to the evaluator. The baseline is itself unstable, with random renaming alone reaching 60% on CWE-327 for Claude Code, and with only 10 to 20 attempts per cell, individual numbers vary a lot. The main experiments center on a 4-bit quantized open model, and the only commercial models included are small ones (GPT-5.4-mini, Claude Haiku 4.5).

#### Comment
- Prompt-injection defenses focus on filtering text that looks like instructions; this attack works through nothing but the names in otherwise ordinary code. It raises a pointed question about where to draw the trust boundary when coding agents use outside code as context.
- The detection result is close to a given: the bait contains no vulnerable code, so vulnerability detectors have nothing to find. The authors conclude that stopping it would require new checks that look for mismatches between names and what the code actually does.
- All experiments ran in isolated environments, and the authors state that no poisoned files were pushed to public repositories. We could not find a code release.

# Spoofing the Toolbox: Optimizing Tool Descriptions to Deceive LLM Agents
> arXiv cs.CR (preprint, marked as under review), University of Utah, USA
> 2026

In setups like MCP, where agents call external tools, the agent picks a tool by reading its description. This paper proposes TSA, a tool-spoofing attack in which the attacker ships a tool that appears to behave like a legitimate one while doing something malicious behind the scenes, and optimizes its description so the agent picks it over the real tool. Earlier attacks leaned on imperative phrases such as "always use this tool" or `<IMPORTANT>` tags, which detectors and people spot easily. TSA instead starts from a variant of the benign description and refines it using feedback on both a surrogate agent's choice and the text's naturalness (perplexity).

Paper: https://arxiv.org/abs/2610.33182

### Contribution
- Formulates tool spoofing as a black-box optimization problem and has an LLM (Qwen3-8B) rewrite descriptions, guided by a feedback function that combines the surrogate agent's selection with GPT-2 perplexity, and by contrastive in-context examples of what worked and what did not.
- Builds TSABench, a benchmark covering both single-tool and multi-tool use.
- Checks stealth separately through a human study and four MCP malicious-tool detectors.

### Evaluation
- Data: MetaTool, MCP-Atlas and TSABench. The surrogate selector is Llama-3.3-70B, and five models are evaluated, including Qwen-Coder2.5-32B, Qwen3-32B, Qwen3.8-27B and GPT-5.
- Baselines: two prompt-injection approaches (the `<IMPORTANT>` tag and ToolHijacker) and two stealth-oriented ones (GAPMA and AMA).
- Attack success rates were 88.65% on TSABench and 87.94% on MetaTool, 82.5% on MetaTool and 80.1% on MCP-Atlas in the multi-tool setting, and up to 92.13% when transferred to GPT-5, which was not used in optimization. When the benign description and every attack's description were offered together, the agent chose TSA's 50.4% of the time.
- Detection: across MCP-Scanner, MCP-Shield, MCP-Guard, GAPMA-D and an LLM-based detector, TSA's highest detection rate was 4.25%, while the `<IMPORTANT>` approach was caught 100% of the time by rule-based detectors. ToolHijacker evaded the existing detectors but was flagged 85.3% of the time by the LLM detector.
- When people ranked descriptions from most to least suspicious, TSA's average rank (4.00) was nearly identical to the benign description's (4.03).
- Credibility of the metrics: the baselines cover recent attacks well, and a separate transfer evaluation checks for overfitting to the surrogate. However, the authors say some evaluation queries were synthesized with an LLM, and the human study recruited only 20 participants on Prolific, a small sample.

#### Comment
- It shows that the approval step in MCP clients, where users can inspect a tool's description before it runs, offers almost no protection against this attack. It pairs well with defenses that verify a tool's identity by its behavior or signature rather than its description, such as ProbeID, released the same day.
- Limitations: it assumes the attacker can publish a malicious tool to a marketplace, and it does not address detecting the malicious behavior itself or monitoring at runtime. The authors say they informed the maintainer of the MCP client they used and are working on defenses. We could not find a code release.

# From Instructions to Exploits: Applying Program Analysis to Malicious Agent Skills Across Natural Language and Code
> arXiv cs.CR (preprint, not peer reviewed), Institute of Information Engineering, Chinese Academy of Sciences, and MYbank, Ant Group
> 2026

An agent skill combines natural-language instructions (SKILL.md) with bundled scripts, so malicious behavior can emerge from the interplay between the two. The instructions might only say "tidy up this presentation" while the bundled script quietly sends the input file to an outside server. This paper presents SCS, a static analyzer that compiles the instructions into a Python-like intermediate representation built from a limited set of security-relevant APIs, then joins the program dependence graphs of the instructions and the code into one. It propagates trust, sensitivity and capability properties over that graph and uses rules to find risks such as data exfiltration or covert execution.

Paper: https://arxiv.org/abs/2610.33489

### Contribution
- Turns natural-language instructions into an intermediate representation of security-relevant API calls such as `read_file` and `http_post`, and connects it to the code's graph in a cross-domain graph (xPDG), making it possible to trace data flow across instructions and code.
- Uses an LLM only to translate instructions into the intermediate representation; the verdict itself comes from deterministic rules over the graph, reducing reliance on LLM judgment.
- Scans all 66,157 ClawHub skills as of April 20, 2026 and reports how malicious skills are distributed in practice.

### Evaluation
- Benchmark: a balanced, manually verified set of 234 skills, 117 malicious ones drawn from existing datasets (MalSkills, MaliciousAgentSkillsBench) and 117 benign.
- Baselines: open-source scanners with at least 1,000 GitHub stars (Cisco Skill-Scanner, A.I.G, NVIDIA SkillSpector and others) and four academic methods, each run with five LLMs (GPT-5.4, Claude Sonnet 4.6, GPT-OSS-120B, Qwen3-235B, DeepSeek-R1).
- Averaged over the five LLMs, SCS reached 85.6% accuracy, 80.2% precision, 95.2% recall and an F1 of 86.9%, the best accuracy and F1 of any method. A.I.G had slightly higher precision (82.0%) but lower recall, while Skill-Scanner and MalSkills had high recall but precision of only around 62%.
- The instruction-to-IR stage achieved 92.5% to 94.5% step-level correctness on a gold set built from 400 real skills.
- Real-world scan: of 2,473 candidates, 627 were confirmed malicious through dynamic validation and manual review. 88% of them came from just two publishers, and most later disappeared from the registry.
- Credibility of the metrics: the baseline selection criteria are clear and the numbers are not implausibly high, so the results read naturally. A.I.G used more than four times SCS's tokens (56.9M vs. 13.7M), though Skill-Scanner and MalSkills used fewer than SCS. Still, the benchmark is small at 234 skills and was curated and verified by the authors themselves.

#### Comment
- It tackles the skill marketplace as a new supply-chain attack surface head-on, from a static analysis angle. Read alongside CoSA, released the same day (policy violations that arise from combining otherwise benign skills), it reflects a shared view that checking skills one at a time is not enough.
- Limitations: behavior outside the defined API set, or paths and values resolved only at runtime, may be missed, and the final verdicts in the real-world scan depend on manual review.
- Verification of a Chinese institution: the Institute of Information Engineering at the Chinese Academy of Sciences and Ant Group's MYbank are both real organizations, and the authors' email domains (iie.ac.cn, mybank.cn) match their affiliations. It is an unreviewed preprint with no venue yet. The baselines are public datasets and public scanners, the comparison is well designed, and there is no sign of inflated numbers. However, the anonymous.4open.science repository the paper gives as its artifact had expired when we checked, so we could not inspect the code or the real-world results directly. We note this as a gap in reproducibility and included the paper because it passes the other checks.
