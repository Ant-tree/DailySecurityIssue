# Who Is Prompt-Injecting Coding Agents? An Empirical Study of Hidden AI-Directed Text on GitHub
> arXiv preprint (not peer-reviewed). Radware, Technion
> 2026

AI coding agents on GitHub triage issues, spot duplicates, review pull requests and run CI jobs, and in doing so they read text that anyone can write. The authors run the first large-scale census of text that GitHub does not render to people but that agents receive in full (HTML comments, invisible Unicode, LaTeX math colored to match the page, CSS hiding) across roughly 145 million issues, pull requests, comments and READMEs. After two-stage LLM classification, a template provenance check and an exhaustive manual review, they confirm 2,281 findings in issues, pull requests and comments (16 per million items) and AI-directed hidden text in the READMEs of 107 repositories.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.28763
- arXiv HTML full text: https://arxiv.org/html/2611.28763
- arXiv PDF: https://arxiv.org/pdf/2611.28763
- Author repository (data and detection tool): https://github.com/rdwr-gabin/github-ipi-in-the-wild

### Contribution
- Shows that keyword search fails (116 of 123 hits for "ignore previous instructions" were false positives such as vulnerability reports and detector tests) and detects by visibility to a human reader instead of by wording.
- Sorts findings into four uses: attacks on other parties' agents, defensive text that restricts agents, content override that steers what agents write, and first-party orchestration, where projects coordinate their own agents through hidden markers.
- Attacks are rare, about one in 3.3 million items, but mostly target maintainers' own triage, review and CI agents (for example, a hidden comment in a Gemini CLI issue asking the agent to leak GITHUB_TOKEN into an environment variable).
- Orchestration makes up two thirds of findings and grew fivefold in four months, creating a control channel that anyone who can comment can imitate.
- Releases the detection tool and every finding.

### Evaluation
- Data: about 142.7 million items, including every public issue and PR created from June to September 2026 via GH Archive, issues, PRs, comments and reviews from August 2025 to May 2026, the READMEs of the 2 million most-starred repositories, and 250,000 READMEs of repositories created in October 2026. Hidden text in 4.9 million items was narrowed to 13,141 after the two classification stages, 5,251 after the template check, and 2,281 after manual review.
- Replay: feeding the real attack text offline to five models, the attacks succeeded only against one small, fast model, in 19% of cases. The other four refused or called out the injection. Stripping HTML comments removed every success.
- Reliability: as the authors note, the replay used one response per model, mock tools and approximated system prompts, so it shows the attacks are not merely theoretical rather than predicting real success rates. Visible injections were not counted, so all figures are lower bounds.

#### Comment
- This is the first measurement of how often agent-directed indirect prompt injection happens in practice, by whom and why. For teams wiring agents into CI, stripping HTML comments is an immediate fix, though, as the authors point out, it also removes legitimate hidden instructions.
- The PDF in the author repository is a talk deck on the same study (UnpromptedCon), so it was not used as the full text.
- A preprint with no venue yet; the first author is with the security vendor Radware.

# CyberDualEval: Measuring Dual-Use Cyber Risks in Frontier Language Models
> Marked as accepted to the NeurIPS 2026 Evaluations and Datasets track, also on arXiv. Columbia University, UCLA, depthfirst
> 2026

Frontier models are capable security assistants, but the same skills help attackers. Existing cyber benchmarks measure either raw offensive capability or generic refusal, so they miss the dual-use question: does a model keep helping with legitimate security work while refusing requests that materially advance misuse? The authors build CyberDualEval from 430 vulnerable tasks drawn from real CVEs and CTF challenges. Each task is split into three phases, security analysis, proof-of-concept (PoC) generation and exploit generation, and each phase is annotated with a Task Weaponization Score measuring how much work remains to turn the output into real misuse.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.30533
- arXiv HTML full text: https://arxiv.org/html/2611.30533
- arXiv PDF: https://arxiv.org/pdf/2611.30533
- Author repository (code): https://github.com/CyberDualEval/CyberDualEval

### Contribution
- Builds the dataset around residual risk, that is, how much more effort it takes to turn a model's response into harmful capability.
- Provides expert annotation and artifact validation, with four deterministic validation mechanisms: analysis answers are compared to private oracles, and PoC and exploit artifacts are replayed against vulnerable and patched versions (the CyberDualEval-VALIDATED subset).
- Analyzes how user context (stated role, stated purpose) changes model behavior.

### Evaluation
- Models: ten frontier models, seven closed-weight and three open-weight.
- Results: at an empirically chosen risk threshold, five of the seven closed-weight models refused every unsafe request but also refused 28-62% of safe ones. The three open-weight models rarely refused and had the highest validated success rates on both safe (62-68%) and unsafe (59-64%) requests. The two closed-weight models that partly complied with unsafe requests were poor at telling low-risk PoC requests from high-risk ones.
- Reliability: the authors acknowledge that each model was run once, so no error bars are reported, and that deterministic validation covers only a subset. Since the risk threshold was set empirically, the over-refusal figures depend on where it sits.

#### Comment
- Putting "refuses safely" and "is useful for security work" in the same table makes this directly usable when choosing models. The high success rates of open-weight models on risky requests are worth weighing in internal model policies.
- The NeurIPS 2026 acceptance comes from the authors' comment; the code repository was confirmed to be publicly reachable.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Oops!... I Parsed It Again: Tool-Call Smuggling Against LLM Agents
> arXiv preprint (not peer-reviewed). Universidad Internacional de La Rioja (UNIR), Proeduca Summa
> 2026

An LLM agent acts through tool calls: the model writes the arguments as JSON, a guard decides whether the call may run, and an executor runs it. The same bytes are parsed many times, by the provider, gateways, SDKs, frameworks, the guard and the executor, and JSON leaves some choices to each parser, such as which copy of a repeated key wins. When the guard and the executor choose differently, the guard approves one call, the executor runs another, and the audit log records only the approved one. The authors name this attack tool-call smuggling and study it across the stack.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.30624
- arXiv HTML full text: https://arxiv.org/html/2611.30624
- arXiv PDF: https://arxiv.org/pdf/2611.30624

### Contribution
- Catalogs six ways the same bytes can yield different calls (repeated keys, undeclared fields, nesting, JSON text inside arguments, call-ID confusion and others).
- Builds a differential testing harness that feeds identical bytes to 17 pinned parser and validator configurations. Most pairs disagree on some inputs, and even two official MCP SDKs accept different inputs.
- Proposes a shared parse as the defense: parse once (including JSON text inside arguments), keep only the fields of the approved schema, and hand that sealed call to the executor.
- Sent nine private reports to eight projects.

### Evaluation
- On τ-bench and AgentDojo tasks, an attacker who can rewrite bytes in transit cancelled another customer's reservation and created a file the guard blocks by name, while the audit log named only the approved call.
- Attacks through content the model reads: the ten models tested never wrote a repeated key into the call itself, but they copied one verbatim into JSON text inside an argument, which a Python guard and a Go executor read differently. A malicious server that clones a legitimate tool's public schema and adds one field got models to fill that field just by explaining it in a note.
- Defense: the shared parse stopped every attack the authors built, call-ID confusion included, and blocked none of 1,120 benign calls. Without the seal, a denied delete ran in 10 of 18 runs. Setting additionalProperties to false in the schema alone made the guard deny the extra-field calls (74 file-reader and 133 τ-bench calls).
- Reliability: guards used real components at their defaults (for example the Go decoder, as in Envoy AI Gateway before 0.6.0), but this is not a measurement of deployed products at large, and some attacks assume an attacker who controls the transport path.

#### Comment
- This brings the "parser differential" problem behind HTTP request smuggling to agent tool calls. Teams whose guard and executor use different languages or libraries should check for it now; filtering fields against the approved schema alone closes much of the gap.
- No code link was found in the paper. It is a preprint with no venue yet.
- Full text source: arXiv PDF (downloaded on the user's computer).

# FATCAT: Fault Injection Attacks Targeting Chip-level Alignment
> arXiv preprint (not peer-reviewed). Radboud University, University of Amsterdam, Masaryk University
> 2026

Alignment is the main mechanism that makes models refuse malicious prompts, yet adversarial evaluations have assumed the hardware underneath is sound. The authors present FATCAT, the first physical fault-injection attack that removes refusal from large language and vision-language models. An attacker with physical access uses non-invasive electromagnetic (EM) fault injection on GPU-accelerated systems-on-chip, needing neither software privileges nor model access. An RF side-channel trigger times the pulse to the prompt prefill phase, corrupting weight transfers across off-chip LPDDR5 DRAM and the on-chip LPDDR physical interface without crashing the system or breaking the model's coherence.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.31129
- arXiv HTML full text: https://arxiv.org/html/2611.31129
- arXiv PDF: https://arxiv.org/pdf/2611.31129
- Author repository (code): https://github.com/PeterHorvath10/fatcat

### Contribution
- First demonstration of a physical fault attack that disables alignment on real edge AI hardware (NVIDIA Jetson Orin Nano and AGX Thor).
- Analyzes how a pulse that lands on memory-encrypted data turns into large changes after decryption, which can wipe whole projection matrices such as down_proj, and shows that this corruption persists across later inferences.
- Shows physical consequences on a 6-DoF robot arm driven by a SmolVLA policy: after fault injection the arm lunged toward the operator's hand.
- Notified NVIDIA PSIRT on October 9, 2026, with acknowledgment on October 19, 2026.

### Evaluation
- Targets: Llama 3.2 1B and Gemma 3 1B on Orin Nano and AGX Thor, evaluated with the 100 JailbreakBench prompts.
- Results (LPDDR physical-interface attack): on Orin, with 15 and 50 attempts per prompt, refusal was bypassed for 65% and 78% of prompts (DeepSeek V4.1 labels), and 39% and 53% yielded actionable harmful content. On Thor, 15 attempts gave a 37% bypass rate.
- Reliability: bypass and harmfulness were judged by an LLM (DeepSeek V4.1 Flash) and audited by another (GLM 5.3). The authors note that EM fault injection is stochastic and needs careful spatial and temporal tuning, and that DRAM locations must be re-characterized after cold boots. Only 1B-class models were tested.

#### Comment
- A concrete demonstration that alignment alone cannot guarantee safety for models deployed where attackers can touch the hardware, such as robots or vehicles. The authors argue that refusal concentrated in a few low-rank representations is fragile to localized faults and call for more distributed safety mechanisms.
- From Lejla Batina's group at Radboud University, which has a long hardware security track record. Code and video clips are released. It is a preprint with no venue yet.
- Full text source: arXiv PDF (downloaded on the user's computer).

# EnvTrap: Revealing the Environment-Only Attack Surface in Embodied AI via Consequence-Blind Action Execution
> Accepted at NeurIPS 2026 (conference poster page confirmed), also on arXiv. Shanghai Jiao Tong University, The Hong Kong University of Science and Technology (Guangzhou)
> 2026

Attacks on embodied AI have so far used crafted instructions, adversarial visual inputs or training-time policy changes. The authors instead study environment-only attacks that leave the model and the instruction untouched and just rearrange objects already in the scene, for example stacking a heavy object on top of the item a robot is told to clear, or placing something in the swing path of a microwave door. They propose EnvTrap, a diagnostic pipeline that builds paired safe, trap and null-trap (benign but misleading) scenes.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.30004
- arXiv HTML full text: https://arxiv.org/html/2611.30004
- arXiv PDF: https://arxiv.org/pdf/2611.30004
- NeurIPS 2026 poster page: https://neurips.cc/virtual/2026/poster/154409
- Code repository listed in the paper (not reachable when checked): https://github.com/INKSIR/Envtrap

### Contribution
- Uses a graph linking instruction verbs to spatial attributes (support relations, container state, occlusion and so on) to enumerate trap candidates, then uses constrained sampling in MuJoCo to generate scene triples that are trigger-gated (only the robot's action sets them off), visually close to the safe scene, and keep the target visible.
- Organizes traps into seven types (support relations, motion-path collisions, speed-induced slipping, shallow grasps, heat and material conflicts, appliance safety filtering failures, obstacle collisions) in a benchmark of 143 templates.
- Proposes a consequence-aware defense module that predicts outcomes and filters hazardous actions.

### Evaluation
- Models: four VLA policies (OpenVLA, π0 via OpenPI, RT-2, RDT) plus the ACT visuomotor baseline, two world models (Cosmos Policy, DreamZero) and LLM planners.
- Results: rearranging the scene alone raised hazardous-action rates to an average of 83.4% across the five policies, with similar patterns in the world models. On a consequence-prediction task models stayed near chance while human evaluators were highly accurate. The consequence-aware defense cut trap trigger rates by 76.3 percentage points on average in simulation and by 62.9 points on physical robots.
- Reliability: as the authors note, simulation runs in MuJoCo, and the physical experiments cover only three of the five policies with one task instance per type. Because evaluation is behavioral, it cannot separate missing consequence prediction from perception or execution errors. A human equivalence test showed trap scenes are perceptually indistinguishable from safe ones.

#### Comment
- The threat model is realistic: in shared spaces such as homes, hospitals and warehouses, someone simply moving objects around can push a robot into a dangerous action.
- Extra checks were made because the authors are at Chinese institutions. A NeurIPS 2026 poster page on the conference website confirms acceptance, and co-first author Huashuo Lei's personal homepage was found through search. The baselines are widely used open VLA policies, which is appropriate. The code repository named in the paper was not publicly reachable when checked, so reproducibility could not be confirmed. The high 83.4% figure comes from a benchmark designed to contain traps and should be read in that light.
- Full text source: arXiv PDF (downloaded on the user's computer).
