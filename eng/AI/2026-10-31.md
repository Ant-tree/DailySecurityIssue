# Agentic Backdoors via Pretraining Poisoning
> arXiv cs.CR 2610.37741 (preprint, not peer reviewed), Anthropic and the Anthropic Fellows Program, UC Berkeley, UIUC, UCL, Deeptune
> 2026

Large language models are pretrained on huge corpora scraped from the web, so an attacker who plants poisoned documents online can get them into the training data. This paper is the first to show that poisoning only the pretraining data can implant a remote code execution backdoor in an agent that is later post-trained on clean data. When the trigger appears, the CLI agent runs an attacker-chosen command on the user's machine; otherwise it behaves normally.

To reproduce the threat end to end, the authors pretrained Qwen3-architecture models at 0.6B, 1.7B and 4B from scratch on 100 billion FineWeb tokens, then followed the OLMo-3 recipe with clean SFT, DPO and reinforcement learning with verifiable rewards (RLVR) to turn them into tool-using CLI agents. Instead of chat-style demonstrations, the poison documents use a new declaration-based design: plain prose that states the rule "when this trigger appears, run this command." Poisoning just 0.1% of the pretraining corpus was enough for the backdoor to survive post-training, and the 4B model reached roughly 92% attack success.

Links:
- arXiv abstract: https://arxiv.org/abs/2610.37741
- arXiv HTML full text: https://arxiv.org/html/2610.37741
- arXiv PDF: https://arxiv.org/pdf/2610.37741
- Authors' code repository: https://github.com/safety-research/agentic-backdoor

### Contribution
- Trains the whole pipeline to show that pretraining poison survives a clean SFT, DPO and RLVR pipeline and turns into real command execution by the agent.
- Introduces declaration-based poison written as ordinary prose, which after post-training beats the older demonstration-based approach in most settings. Without conspicuous chat-template artifacts, it is also harder to filter out.
- Shows that ordinary-string triggers, such as paths containing "anthropic," are the more dangerous kind, and that attack success rises monotonically with model size.

### Evaluation
- Setup: three model sizes (0.6B, 1.7B, 4B), 100 billion pretraining tokens, poison rates of 0.1% or less. Poisoned models were trained with three seeds; lower-rate runs and clean baselines were single runs.
- Results: the 4B model reached about 92% attack success at a 0.1% poison rate and stayed above zero even at 0.0005% (one document in 200,000). On trigger-free versions of the same tasks, the malicious command appeared in under 0.06% of samples. Utility and attack behavior were measured at every training stage.
- Reliability of the metrics: training from scratch gives a clean causal picture, and seed ranges are reported. The models only go up to 4B, though, and the authors say they could not confirm whether the trend holds at frontier scale.

#### Comment
- An important result for agent supply-chain security. Post-training cannot be assumed to wash out poison, so the paper's conclusion that pretraining data provenance and deployment-time command controls both matter is convincing.
- Limitations: the payload is a specific command string; whether behaviors that cannot be reduced to a memorized string can be implanted as durably is left open. Model sizes and training budgets are far below production models.
- Venue: preprint. The work comes from Anthropic researchers and Anthropic Fellows, with code released.

# Security Impact of Coding Agent's Memory Files
> arXiv cs.SE, cross-listed to cs.CR (preprint, not peer reviewed), Ruhr University Bochum, Germany
> 2026

Coding agents load project memory files, such as Claude Code's CLAUDE.md, at the start of every session and treat them as trusted project guidance. Anyone who can change such a file, for example through a pull request, can steer the agent without touching the developer's prompt. This early empirical study asks whether a malicious memory file makes agents write code that passes its tests but is vulnerable, and whether agents tell the developer that the file shaped their code.

For each of 12 CWE classes, the authors wrote two malicious memory files: a "qualified" one that presents removing defensive checks as engineering best practice, and a "forceful" one that demands it. They then ran Claude Code (Claude Sonnet 5.5) and OpenCode (Qwen 3.8 27B and DeepSeek V4.1 Flash) on 36 SecRepoBench tasks with and without the files.

Links:
- arXiv abstract: https://arxiv.org/abs/2610.38521
- arXiv HTML full text: https://arxiv.org/html/2610.38521
- arXiv PDF: https://arxiv.org/pdf/2610.38521

### Contribution
- Frames project memory files as an attack surface for insecure code generation, and adds a second question: do agents disclose the file's influence to the developer?
- Reports an unexaggerated result: malicious files shifted the rate of secure completions by -8 to +6 percentage points, with no consistent pattern across agents or variants.
- Finds sharp differences in disclosure. Claude Code named the file in about two thirds of its final messages, while OpenCode mentioned it almost only in its reasoning trace, not in the final message the developer reads. Even when an agent flagged the file as an attack, it sometimes still produced vulnerable code.

### Evaluation
- Setup: 36 of 318 SecRepoBench tasks; three agent configurations (Claude Code 2.1.308 with Sonnet 5.5, OpenCode 2.1.1 with Qwen 3.8 27B, OpenCode with DeepSeek V4.1 Flash); reasoning effort xhigh; 1,200-second session limit. Baseline, qualified and forceful conditions were compared on the same tasks.
- Measures: secure completion judged by functional and security tests, plus whether the memory file was mentioned in the final message or the reasoning trace.
- Reliability of the metrics: with only 36 tasks, shifts of -8 to +6 points are hard to call meaningful. The authors themselves conclude that larger studies are needed to quantify the risk.

#### Comment
- A reminder that organizations using agents should review changes to files like CLAUDE.md or AGENTS.md as carefully as code changes. The finding that the reason behind a change often does not show up in the agent's final message matters for auditing.
- Limitations: a small preliminary study, and the malicious files were written by the authors with LLM help. Files crafted by a skilled attacker could behave differently.
- Venue: preprint.
- Full-text source: the official arXiv PDF, downloaded on the user's computer.
- The authors are at Ruhr University Bochum, Germany; this is not a paper from a Chinese institution.

# InferD: A Honeypot Framework for AI Inference Infrastructure
> Accepted at the AISec '26 workshop (co-located with ACM CCS 2026, The Hague), posted as arXiv cs.CR 2610.39807. SnT, University of Luxembourg
> 2026

Internet-exposed inference servers such as Ollama, vLLM and LiteLLM, along with MCP endpoints, get indexed by scanners within hours, and real incidents such as the ShadowRay campaign and the Probllama path traversal flaw have followed. This paper presents InferD, a low-interaction honeypot that imitates AI inference infrastructure. Its guiding principle is "deception without inference": everything an adversary can observe, including model inventories, token formats, streaming responses, authorization header formats and the MCP tool-call lifecycle, is answered convincingly from prepared static responses, while the computation the attacker is after (running a model, executing a tool call, fetching a submitted URL) never happens.

The authors deliberately avoid putting a real model behind the facade. Generation would add cost and latency jitter that an adversary can measure, make responses non-deterministic and hard to reproduce for analysis, and above all turn the honeypot into a live model the attacker can manipulate. Running InferD on one server for eight weeks (May to July 2026), they saw organic traffic arrive without any seeding and captured attempts, from three sources, to deliver a cloud credential harvester to exposed LiteLLM endpoints through an MCP stdio code-execution primitive, all with zero code executed.

Links:
- arXiv abstract: https://arxiv.org/abs/2610.39807
- arXiv HTML full text: https://arxiv.org/html/2610.39807
- arXiv PDF: https://arxiv.org/pdf/2610.39807
- AISec '26 paper DOI: https://doi.org/10.1145/3847352.3848091
- Authors' code repository: https://github.com/hichamhammouchi/InferD

### Contribution
- Defines AI service emulation as its own deception problem, with the principle of reproducing observable behavior faithfully while never performing the underlying computation, and a layered architecture that implements it.
- Designs separate "deception planes" for the inference API, model inventory, authentication and agent tool calls, and spells out implementation-level guarantees that nothing an adversary submits is executed.
- Validates the pipeline in a real deployment and reports the first observed case of a cloud credential harvester delivered through an MCP code-execution path.

### Evaluation
- Deployment: one commodity server, eight weeks. The authors explicitly present this as pipeline validation, not a measurement study.
- Results: organic traffic arrived without seeding, and attribution and recording worked end to end. The credential harvester was observed from three sources.
- Reliability of the metrics: a single vantage point, a short window and three sources make for a small sample, and the authors make no population-level claims. They also could not establish whether the two network groups belong to one operator. There is no quantitative evaluation of how long the honeypot stays undetected.

#### Comment
- A practical tool for security teams that want to see what attacks exposed inference or MCP servers attract. Being able to capture an attacker's first moves with static responses alone is its strength.
- Limitations: as a low-interaction design, it may be exposed by an attacker who probes response consistency or generation quality closely, and later attack stages are hard to observe.
- Venue: accepted at AISec '26, a workshop co-located with ACM CCS, so it has workshop-level peer review.
- Full-text source: the official arXiv PDF, downloaded on the user's computer.
- The authors are at SnT, University of Luxembourg; this is not a paper from a Chinese institution.

# SPARSEBLEED: Bypassing Attribute-Inference Defenses via Sparsity Optimizations
> arXiv cs.CR, cross-listed to cs.AR (preprint, not peer reviewed), North Carolina State University and UC Irvine, USA
> 2026

When neural networks trained on confidential data, such as medical or financial records, are served, providers block attribute-inference attacks by hiding probability scores or returning labels only. This paper presents SPARSEBLEED, a hardware-level attribute-stealing attack showing that accelerator performance optimizations can defeat those defenses. Activation sparsity (the share of zeros) depends on the input; hardware zero-skipping and software operator optimizations exploit it to save work, so end-to-end inference time ends up acting as a stand-in for model confidence.

The attacker needs no gradients, logits, weights, ground-truth labels, power traces or shared caches, only the response time of a single query, to infer sensitive input attributes. The attack worked across Intel AVX2/AVX-512/AMX, NVIDIA Ampere Tensor Cores with 2:4 sparsity, and nine libraries including oneDNN, oneMKL SparseBLAS and cuSPARSE. For mitigation, the authors compare constant-time execution with sparsity optimizations disabled against a padding defense that delays every response to the worst-case time.

Links:
- arXiv abstract: https://arxiv.org/abs/2610.38110
- arXiv HTML full text: https://arxiv.org/html/2610.38110
- arXiv PDF: https://arxiv.org/pdf/2610.38110

### Contribution
- An attack that infers attributes from inference time alone, bypassing score masking and label-only defenses. It targets ordinary non-adaptive networks rather than early-exit designs and needs no monitoring of memory access patterns.
- Explains and quantifies, across nine execution stacks, how input-dependent activation sparsity combined with hardware zero-skipping and graph optimizations creates timing differences.
- Measures mitigation costs and concludes that padding is far cheaper than constant-time execution.

### Evaluation
- Data and results: on Texas-100X, the attack inferred the Sex attribute with 66.39% accuracy and recovered the true label, Surgical Procedure, with 99.8% accuracy. The Adult dataset was also used.
- Mitigations: disabling sparsity optimizations raised latency by up to 2x on NVIDIA Sparse Tensor Cores and power by about 25% in AMX microbenchmarks, while padding hid the timing leak at an average 7.24% performance overhead across nine libraries with almost no extra energy.
- Reliability of the metrics: for a two-valued attribute like Sex, 66.39% beats chance (50%) but is not overwhelming, and this run did not confirm a comparison against a baseline that accounts for the dataset's class balance. The 99.8% label recovery is a strong result. The measurements assume an attacker who can time responses precisely.

#### Comment
- A textbook case of a performance optimization breaking confidentiality: for AI inference services, response time is information that needs protecting. The low cost of padding makes it worth considering right away.
- Limitations: how well the attack holds up remotely, over noisy network latency, was not clear from the parts read. The targets are server and desktop accelerators, so applicability to mobile NPUs needs separate validation.

- The authors are at NC State and UC Irvine, USA; this is not a paper from a Chinese institution.
