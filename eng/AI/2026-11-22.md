# Replication of Agentic Security Events: Audit and Investigation (ROGUE-AI)
> arXiv preprint (not peer reviewed). Texas A&M University
> 2026

News outlets regularly report LLM agents wiping production databases or wandering into systems they should not touch, but the reports describe the outcome and rarely test what caused it. The authors present ROGUE-AI, a multi-agent framework that rebuilds a publicly reported agent incident offline together with a matched control that differs only in the cause the report blames, then runs the same models on both. The Replit incident, where an agent deleted a production database, becomes a repository whose tests use the production database plus a control whose tests use a temporary one. The difference in harm between the two is evidence for the reported cause.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.26553
- arXiv HTML full text: https://arxiv.org/html/2611.26553
- arXiv PDF: https://arxiv.org/pdf/2611.26553
- Project page (incident list and replications): https://rogue-ai.surge.sh

### Contribution
- The first framework that tests reported agent incidents by replicating them against a control that lacks only the blamed cause. Incident catalogs only collect reports, and benchmarks only use attacks their authors design.
- Claude-, Gemini- and GPT-based specialist agents find reports, check them against primary sources, record the cause and build the replication; an agent from a different vendor reviews each build; and code, not a model, decides whether harm occurred from the environment state, since agents misreport their own actions.
- Of 72 incidents with real-world harm, 62 involved no attacker at all: the agent did what its task asked and missed an ordinary hazard such as a database shared with the live site.
- Proposes a mitigation that appends a warning naming the hazard and its consequence after every tool output.

### Evaluation
- From 253 reports, the pipeline built 108 replications of 96 incidents in 38 classes, at $3.28 each, and reproduced the reported harm in 89% of them.
- Five current models from OpenAI, Anthropic, Google and DeepSeek repeated the reported mistake in 18% to 33% of incident runs, against at most 1% in the controls. In the Medicare portal replication, models entered the restricted area in 14 of 15 incident runs and 0 of 30 control runs.
- Replications without an attacker caused more harm than prompt injection replications for all five models, and defenses that look for injected instructions missed most of this harm. User confirmation or data-flow tracking removed it.
- The hazard warning lowered harm for every model, down to 2% for Claude Sonnet 4.6, while a note of the same length that did not mention the hazard left 83% to 98% of the harm in place.
- Reliability: most runs use simulated environments with a single agent loop, and only ten destructive-action replications were also run on shipped products, so harm rates may not match real products. Where a report gives no mechanism, the authors reconstruct one, and they note that blind rebuilds disagreed with theirs on 5 of 11 incidents.

#### Comment
- Testing incident reports instead of taking them at face value is useful for practitioners. The takeaway is simple: keep production credentials out of the agent's reach.
- The authors say they release code, replications and session logs, and that they reported each model's results to OpenAI, Anthropic, Google and DeepSeek.

# Backtracking Agent Applications Security Incidents
> arXiv preprint (not peer reviewed). Pennsylvania State University
> 2026

When an agent application is hit by indirect prompt injection or memory and knowledge-base poisoning, an analyst has to find the compromise entry point: the function call that first brought the malicious data in. The trajectory logs that survive record only agent-level functionality such as "retrieved from the knowledge base", while the entry-point candidates are function calls in the source code, leaving a wide semantic gap. The authors build Origin, which connects agent-functionality regions to a variable-level taint propagation graph through a cross-layer dependency graph and a query language, so that an analyst can pin down the entry point with a handful of queries.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.26525
- arXiv HTML full text: https://arxiv.org/html/2611.26525
- arXiv PDF: https://arxiv.org/pdf/2611.26525

### Contribution
- Defines an intermediate abstraction (the cross-layer dependency graph) between the agent-functionality layer and the code execution layer, along with a query language for asking whether data flows between regions or variables.
- Observes that agent functions fall into a few regions depending on which kind of external information source they touch, and designs a region inference algorithm that assigns functions to regions automatically.
- Implements roughly 16,000 lines on top of Joern, with Pyrefly-based type inference to close taint-propagation gaps around generators, instance variables and dynamic dispatch.

### Evaluation
- Case studies of eight incidents (indirect prompt injection, memory poisoning, knowledge-base poisoning and a compound attack) across five widely used agent applications: GPT-Researcher, Quivr, aider, MetaGPT and SWE-agent.
- An analyst using Origin identified the entry point and actual attack path in all eight incidents, needing two queries in five cases and four in the other three. In the motivating GPT-Researcher case, 1,518 candidates remained after log-based pruning, and manual inspection took hours.
- Joern, CodeQL and Pysa could not diagnose the same incidents even when given the ground-truth entry point and sink, because they lack the region abstraction. Region inference accuracy ranged from 88.9% to 100% across applications.
- Reliability: the evaluation is a set of eight case studies with the authors acting as analysts. It uses a human-validated mapping between functions and information sources, and some developer-provided labels are required.

#### Comment
- Because Origin is purely static, the authors note it struggles with paths decided dynamically inside frameworks (such as LangChain tool dispatch) and with autonomous agents whose LLM picks the next functionality at runtime.
- From an incident response standpoint, finding the entry point lets the analyst name the exact poisoned file to remove from a knowledge base, or tell developers where logging statements should go.
- Full text source: arXiv PDF (downloaded on the user's computer).

# On the Reliability of CyberGym Evaluation: Task Material Consistency and Reference-Target Identity
> arXiv preprint (not peer reviewed). No affiliation given
> 2026

CyberGym tests whether an AI agent can turn a vulnerability description and source code into a proof-of-concept input, counting a success when the input crashes the vulnerable version but not the fixed one. The authors argue that this differential pass only means "the intended vulnerability was reproduced" if the task materials are consistent and the input actually triggers the target defect. They audit the materials of all 1,507 tasks and assess, one by one, the inputs produced in a full agent run.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.25790
- arXiv HTML full text: https://arxiv.org/html/2611.25790
- arXiv PDF: https://arxiv.org/pdf/2611.25790

### Contribution
- Takes the defect behind each reference crash report as the target and separates two checks: whether the task materials agree with it, and whether a submitted input actually hits it.
- The material audit uses two rounds of LLM labeling, expert adjudication of disagreements, and a stratified blind review of a sample.
- The input assessment combines an execution check, crash-signature matching and LLM-assisted root-cause review. In one HarfBuzz task, for example, the target is an AAT substitution-table parsing bug, but the submitted input hits an unchecked index in the CFF parser and passes only because the fixed version also repairs that index.

### Evaluation
- 338 of 1,507 tasks (22.4%) received inconsistency labels. The largest categories were coverage inconsistency (205 tasks) and descriptions and patches that jointly point to another defect (110 tasks).
- Of 1,286 differential passes in one full Level-1 GLM-5.3 run, 89 were judged to hit a different defect and 10 had insufficient evidence. Requiring a target hit lowers the pass rate from 85.3% to 78.8%.
- Even among the 1,052 passes from tasks with no material problems, 39 (3.7%) hit a different defect.
- Reliability: the input assessment covers a single run of a single model, and the identity verdicts lean on LLM-assisted review, which the authors say still needs independent validation.

#### Comment
- The paper puts numbers on the gap between "it crashed" and "it reproduced that vulnerability" when reading agent security scores. Other vulnerability-reproduction benchmarks may have the same problem.
- The paper gives no affiliation and the contact address is on a Chinese mail service, so it was checked more carefully as a possible Chinese-institution paper. It audits a public benchmark, cites specific task IDs, and its numbers show no sign of inflation. However, no public address for the audit data or code was found in the text, which limits reproducibility. Affiliation not confirmed.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Text-Aware, Vision-Blind: How Multimodal Image Editing Systems Handle Unsafe Inputs
> arXiv preprint (not peer reviewed). CISPA Helmholtz Center for Information Security, The Hong Kong University of Science and Technology (Guangzhou), The Hong Kong University of Science and Technology
> 2026

In an image editing service, the uploaded image itself can be the risk, so a safety decision has to weigh the image and the instruction together. The authors build EditSafetyBench to measure how well commercial editing systems do this. It pairs safe and unsafe images across 11 risk categories with neutral, risk-reducing and unsafe-intent instructions, giving 5,940 image-instruction pairs, and tests Gemini, GPT Image, the Qwen Image Edit API and a local Qwen Image Edit model.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.26569
- arXiv HTML full text: https://arxiv.org/html/2611.26569
- arXiv PDF: https://arxiv.org/pdf/2611.26569

### Contribution
- Frames the problem at the system level: the allow, refuse or error decision of the whole deployed pipeline, including safety filters and API wrappers, not the model alone.
- Claims to be the first benchmark that checks, in ordinary non-adversarial editing, whether systems consider image risk and textual intent together.
- Quantifies a "text-aware, vision-blind" pattern in commercial systems: they react to the instruction and largely ignore the image.

### Evaluation
- Gemini and GPT refused 81.6% to 87.1% of unsafe-intent edits, but only 22.4% to 24.2% of unsafe images paired with a neutral instruction such as "improve the quality".
- Under unsafe-intent instructions, the allow-rate gap between safe and unsafe images was only 0.2% to 0.4%, so text intent dominated. Risk-reducing edits, such as masking the harmful part, were over-refused.
- Systems disagreed by category: GPT allowed 70.4% of edits on unsafe political content, Gemini only 34.8%. Sexual content showed the strongest visual sensitivity of any category.
- Reliability: images come from UnsafeBench, with a held-out check on MagicBrush. The benchmark measures decisions, not the harmfulness or quality of the output, and the instruction bank has only nine prompts. Commercial filters may have changed since the evaluation.

#### Comment
- With a co-author from a Chinese institution (HKUST Guangzhou), the paper was checked more carefully. The first and corresponding authors are at CISPA, the data comes from public datasets, the metric is a plain refusal rate with little room for inflation, and the limitations are stated openly. No public address for the benchmark was found in the text.
- A useful argument for running a separate safety check on input images in any editing service.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Tether: Verified Stateful Policy Engine for System-Level Monitoring of Agents
> arXiv preprint (not peer reviewed). Google DeepMind, Google, University of Pennsylvania, University of Wisconsin-Madison
> 2026

Coding agents that run shell commands can, through misalignment or prompt injection, exfiltrate sensitive data or tamper with the system. LLM-based monitors offer no formal guarantees, and static allowlists miss side effects that the command text does not reveal, such as a network call made inside a Python script, as well as data flows spread over several steps. Tether first runs each command in a disposable, isolated copy-on-write sandbox, traces its system calls into abstract actions such as read, copy and upload, and commits the changes only if a stateful security policy allows every action seen so far.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.25599
- arXiv HTML full text: https://arxiv.org/html/2611.25599
- arXiv PDF: https://arxiv.org/pdf/2611.25599

### Contribution
- Enforces policy on observed side effects rather than on command syntax. Since exact data flow cannot be recovered from system calls, it soundly over-approximates flows to keep its guarantees.
- Policies and action semantics are written in a DSL embedded in Lean 4, covering information flow control, access control and network policy, and global invariants such as "no network access after reading a sensitive file" can be proved as theorems.
- Keeps security labels on resources and propagates them through actions, so a single rule can stop secrets being staged through any number of temporary files before exfiltration.

### Evaluation
- Agent trajectories from two coding-agent control benchmarks were replayed step by step in the sandbox. The fully traced subset contained 199 attack and 218 benign trajectories from MonitoringBenchHonest and 145 attack and 1,372 benign trajectories from LinuxArena.
- With one policy shared across all tasks, Tether blocked all 344 in-scope attack trajectories, with benign false-positive rates of 2.3% and 5.0% respectively.
- Reliability: trajectories whose external services could not be emulated, that could not be replayed end to end, or that touched untraced external state were excluded, so the 100% figure applies to the in-scope subset only.

#### Comment
- The authors acknowledge that purely semantic attacks that break no system-level flow rule, such as maliciously editing code in a permitted file, are out of reach, and that over-approximation produces false positives. They also note that because real attacks are rare, most blocks in deployment would be false alarms.
- They suggest pairing Tether with an LLM classifier to cover semantic attacks. A useful reference design for agent sandboxes.

# Reject and Report: Forgery-Evident Undetectable Watermarks for Generative Image Models
> arXiv preprint (not peer reviewed). University of Waterloo, Vector Institute, KTH Royal Institute of Technology
> 2026

Watermarks that prove where a generated image came from must resist forgery; otherwise an attacker can pin harmful content on a model or make a real photo look AI-generated. Undetectable watermarks such as PRC and Gaussian Shading++ hide the mark in the signs of the initial latent noise, but anyone who can invert an image gets that latent back, so one watermarked image and a surrogate model are enough to imprint the mark onto another image or regenerate new content that carries it. The authors argue a watermark should not just reject forgeries but report them, and propose Tripwire-WM, which commits the semantics of each generated image to the magnitudes of the latent noise.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.25226
- arXiv HTML full text: https://arxiv.org/html/2611.25226
- arXiv PDF: https://arxiv.org/pdf/2611.25226

### Contribution
- States the requirement that a watermark should reject and report forgeries, since a forgery that is simply rejected as unwatermarked leaves no trace of the attempt.
- Embeds a commitment to the image's semantics in the latent magnitudes, which sign-based watermarks leave unused, using a distribution-preserving embedding. A forged image carries a valid mark but a commitment that does not match its content, so it is flagged as forged.
- Leaves the signs untouched and proves that the base scheme's undetectability is preserved.

### Evaluation
- On MS-COCO, in the strongest setting where the owner's own model serves as the surrogate, it accepted no imprinting forgeries and reported all of them as forged, while SemBind accepted up to 55.0%.
- It accepted at most 1.8% of reprompting forgeries, compared with up to 46.2% for SemBind.
- It accepted at least 99% of genuine watermarked images at a 10^-6 false-positive rate and matched the robustness of the base schemes. On SDP it also rejected and flagged most forgeries.
- Reliability: the baselines (SemBind and external anomaly detectors) are appropriate. The authors note the semantic check relies on a secret hashing network that, unlike the key, has no computational guarantee, and that it separates content only as finely as prompts do.

#### Comment
- With rules such as Article 50 of the EU AI Act requiring generated content to be marked, watermark forgery is becoming a practical concern. Being able to detect a forgery and point back to the abused source image is an operational advantage.
- The authors say the source code will be released upon publication.
- Full text source: arXiv PDF (downloaded on the user's computer).

# SCARVA: Interpretable Agentic Reasoning in Software Supply-Chain Analysis
> arXiv preprint (not peer reviewed). Ruhr University Bochum
> 2026

A dependency with a public vulnerability does not necessarily put the application at risk. SBOM tools only match versions, and call-graph tools mostly cover ecosystems with central package management such as Maven, npm and PyPI, leaving C/C++ projects with vendored libraries largely out of reach. LLM agents could fill the gap, but they hallucinate, take shortcuts and reward hack, which makes their verdicts hard to trust. SCARVA records every tool call, file access and web request an analyst agent makes while judging whether a CVE affects an application, and independent judge agents then check the verdict against that record and produce an evidence-backed report.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.26131
- arXiv HTML full text: https://arxiv.org/html/2611.26131
- arXiv PDF: https://arxiv.org/pdf/2611.26131
- Anonymous repository listed in the paper (code and Docker setup): https://anonymous.4open.science/r/scarva/README.md

### Contribution
- An evidence-collection methodology that makes an agent's supply-chain verdict auditable after the fact.
- The analyst must deliver a proof of concept for "affected" or an explanation of why the vulnerable code cannot be reached for "not affected", and the judge checks each claim against the log.
- A hand-built set of 54 C/C++ cases balanced across exploitable, non-exploitable and vulnerability-free projects.

### Evaluation
- As analyst, the open-weight Qwen 3.8 did best at 82% balanced accuracy, ahead of the proprietary models tested. Adding a judge panel raised Qwen 3.8's balanced accuracy from 0.667 to 0.819.
- Against human annotation, Claude Opus 5.5 was the best judge, agreeing with annotators on 94% of claim checks.
- Analyst agents on their own leaned toward "not affected" and rarely recognized applications with no known vulnerability.
- Reliability: only 54 cases (18 per group), with no case-level significance testing. Some CVEs predate model cutoffs, so the analyst may recall answers. Frontier-model judges only judged their own outputs, and the Anthropic account ran under the Cyber Verification Program while the OpenAI account did not, which the authors say limits the comparison.

#### Comment
- The point is less the accuracy than leaving a verdict with verifiable evidence. Useful when designing report formats for agent-based vulnerability impact analysis.
- Full text source: arXiv PDF (downloaded on the user's computer).

# ALIoTh: Orchestrating Multi-Agent LLMs for Autonomous IoT Penetration Testing
> Published at IEEE/IFIP NOMS 2026 (per DOI), arXiv preprint. abstract-only summary, full text not read
> 2026

According to the authors, penetration testing in IoT environments that mix devices such as smart plugs, cameras and door locks is hard at every stage, from information gathering and attack surface enumeration to privilege escalation and lateral movement. They introduce ALIoTh, a multi-agent penetration testing framework that places LLM agents inside a Self-RAG architecture and orchestrates them with LangGraph to find and exploit vulnerabilities in IoT and industrial IoT environments autonomously.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.25809
- arXiv HTML full text: https://arxiv.org/html/2611.25809

### Contribution
- The authors claim the agents dynamically plan and run the full offensive pipeline: network, device and service enumeration, vulnerability assessment, payload generation, reverse shell deployment and per-device privilege escalation.
- They say Self-RAG gives expert agents access to IoT security documentation, tool manuals and known attack techniques, improving their reasoning when exploiting multiple devices or manipulating group policies.
