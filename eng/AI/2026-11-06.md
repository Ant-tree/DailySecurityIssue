# Securing Web Agents with the Compile-Then-Execute Paradigm
> arXiv cs.CR 2611.06039 (preprint, not peer reviewed). UC Berkeley, King Abdulaziz City for Science and Technology (KACST, Saudi Arabia)
> 2026

Most web agents follow the ReAct pattern: look at the page, pick the next action, execute it, look again. The trouble is that the model decides its next step at exactly the moment it is reading a page that mixes trusted content, such as the site's own interface, with content anyone can write, such as reviews and forum posts. A prompt injection planted in the page can therefore hijack the agent's control flow. This paper presents Baya, a web agent that applies the compile-then-execute idea, which separates planning from execution, to the web.

Before touching the live site, Baya compiles the user's request into a Python program. That program may only call a Trusted Website API prepared for each site, which wraps the site's REST endpoints and its UI-only functions (through Playwright) behind one documented interface. The planning model never sees live page content; only the compiled program processes it. Untrusted data can fill variables or choose among branches fixed at compile time, but it cannot introduce new tasks or new site operations. When execution fails, the compiler gets back restricted diagnostics, roughly an HTTP status and an error message, to repair the program. Tasks that need semantic interpretation, such as summarizing reviews, go to a runtime model that has no tool-calling authority.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06039
- arXiv HTML full text: https://arxiv.org/html/2611.06039
- arXiv PDF: https://arxiv.org/pdf/2611.06039
- Author repository (cited in the paper's footnote): https://github.com/apechow/Baya

### Contribution
- Extends the plan-then-execute approach proven for tool-calling agents (CaMeL, FIDES) to the web, where the action space is not known in advance, and proposes per-site Trusted Website APIs as the missing abstraction.
- Draws a clear scope: it prevents control-flow hijacking, where the attacker adds new actions, and explicitly leaves out outcome manipulation, where the attacker only sways values within branches the workflow already allows.
- Adds a replanning path for execution failures while restricting what the error feedback exposes, so the feedback channel does not become an attack channel.
- Shows that security need not cost utility. Baya beats ReAct agents given the same API and site guidance, so the gain is not simply a matter of API access.

### Evaluation
- Utility: 581 valid WebArena Verified tasks (GitLab 154, Shopping 171, Shopping Admin 150, Postmill 106) with Claude Sonnet 4.6, Gemini 3.5 Flash and GPT-5.6 Luna. Baya reaches 77.8% aggregate utility versus 66.7% for API-enabled ReAct and 55.1% for browser-only ReAct, and 81.9% with Claude Sonnet 4.6. On Shopping and Shopping Admin, API-enabled ReAct does better with some models.
- Security: the WASP prompt-injection benchmark on GitLab and Postmill, with DeepSeek V4 Flash replacing GPT-5.6 Luna. Baya shows 0% intermediate and end-to-end attack success across every model and environment. The ReAct baselines reach up to 52.8% intermediate and 5.6% end-to-end success, with aggregates of 16.2% (API-enabled) and 25.5% (browser-only). UCM, an existing secure agent that masks untrusted content, also reaches 0% on GitLab, but it needs site-specific masking rules and scores 17.6 points lower than Baya on the full GitLab task set.
- Cost: mean latency is 327 seconds per task, about 3.8 times API-enabled ReAct (87 seconds), with higher monetary cost. Compared with UCM, latency is 30.3% lower and cost 82.6% lower.
- Reliability of the metrics: giving ReAct the same API and guidance, and using the manually audited WebArena revision, makes the comparison convincing. On the other hand, the Trusted Website APIs were built by hand for each site, so their quality and preparation cost weigh heavily on the results. The security result is an observation against WASP's fixed attacks and does not cover adaptive attackers.

#### Comment
- The paper continues the line of work that tackles agent security through architecture rather than by teaching models to ignore injections. It is useful evidence that separating planning from execution almost eliminates control-flow hijacking for web agents too.
- Limitations: tasks whose workflow is not fixed by the request ("find my boss's email and do what it says") are out of reach. Automating the construction of Trusted Website APIs is left for future work, and the authors themselves note that injections met during automated exploration could leak into operations later treated as trusted. Outcome manipulation is not prevented.
- Credibility: the author list includes leading systems security researchers such as David Wagner and Raluca Popa. The paper has not been peer reviewed yet.

# KVGuard: A KV Cache Safety Checker for LLM Serving Systems
> arXiv cs.CR 2611.06138 (preprint, not peer reviewed). Seoul National University
> 2026

LLM serving systems such as vLLM, SGLang and TensorRT-LLM manage the KV cache with PagedAttention. They reserve one large GPU buffer with cudaMalloc, split it into fixed-size blocks, and let a CPU-side allocator assign blocks to requests and tell the GPU about them through a block table. In effect this is a second, application-level heap allocator, and it suffers the same families of bugs: double free, use after free, out-of-bounds access, uninitialized reads and permission violations. The catch is that these bugs rarely crash anything. They silently corrupt outputs or break isolation between requests.

The paper frames this as a new memory-safety problem and presents KVGuard, a checker that works at the level of KV cache blocks. Each physical KV block gets a compact shadow block recording per-request permissions and per-entry initialization. Five checks run across the PagedAttention workflow, covering CPU allocation, block-table construction and translation, and GPU-side block-table lookup and KV entry access, and each fires at the boundary where the violation is introduced. The authors argue that ASan-style detectors and NVIDIA Compute Sanitizer reason about CUDA addresses, not blocks, requests and block tables, and that redzone and quarantine designs do not fit the tight GPU memory budget of serving.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06138
- arXiv HTML full text: https://arxiv.org/html/2611.06138
- arXiv PDF: https://arxiv.org/pdf/2611.06138

### Contribution
- Collects 29 KV cache safety bugs from the vLLM and SGLang patch histories and analyzes them as a memory-safety bug class specific to serving systems.
- Explains why existing memory-corruption detectors and GPU debugging tools cannot catch them.
- Designs the first systematic memory-safety abstraction for KV cache management (shadow blocks plus five checks) and implements it in vLLM and SGLang.
- Finds 8 previously unknown safety violations during end-to-end serving and submits fixes.

### Evaluation
- Coverage: all 29 historical bugs were reproduced end to end and detected, and 8 new violations were found. No false positives were reported across the evaluated workloads.
- Overhead: on Qwen 2.5 14B, geometric-mean time per output token (TPOT) rises by 3.0% on vLLM and 7.4% on SGLang, and memory overhead stays at or below 0.11% of the KV cache, two orders of magnitude below Compute Sanitizer. At 16 requests per second on Qwen 2.5 14B, median end-to-end latency goes from 2.04 to 2.13 seconds on vLLM and from 2.60 to 3.04 seconds on SGLang.
- Small models and long contexts pay much more. On Llama 3.2 1B, TPOT grows 1.83 to 3.67 times (vLLM) and 2.02 to 3.53 times (SGLang). With 2K to 8K-token LongBench prompts at 16 requests per second it reaches 7.55 times (vLLM) and 10.84 times (SGLang). The hybrid Qwen 3.5 4B sits at 1.09 to 2.95 times.
- Workloads: Llama 3.2 1B, Llama 3.1 8B, Qwen 3.5 4B and Qwen 2.5 14B on ShareGPT V3, plus LongBench and five-shot MMLU on Llama 3.2 1B.
- Reliability of the metrics: each historical bug was reproduced end to end, and newly found bugs are listed with their fix pull requests, which makes the claims checkable. The 3.0% and 7.4% figures in the abstract are for the most favorable 14B model; small models and long contexts see several-fold slowdowns, so the tool fits testing, kernel development and post-incident debugging better than always-on production use, which is also how the authors position it.

#### Comment
- KV cache bugs can mix one user's KV state into another's request, so on a shared serving instance they become a data-leak path. This is a rare systems paper that looks at the LLM serving layer from a security angle.
- Limitations: implementation and evaluation cover only vLLM and SGLang. TensorRT-LLM shares the same design and is claimed to be applicable, but was not evaluated. The host-side shadow checks are fully exposed on small models, hence the large latency there.
- Credibility: from Byoungyoung Lee's lab at Seoul National University, which publishes regularly at top systems security venues. Not yet peer reviewed.
- Full text source: official arXiv PDF downloaded on the user's computer.

# When File Ingestion Misleads Language Models: Measuring and Mitigating Divergences in Office Documents
> arXiv cs.CR 2611.05806 (preprint, not peer reviewed). Nanyang Technological University (Singapore)
> 2026

People now routinely upload Office documents to LLMs for summaries and reviews. But the model does not read the document a person sees on screen; it reads whatever text an extractor pulls out of the document's OOXML parts. Extractors differ in which parts they read and how they interpret them, so what the model receives can diverge from what Office displays. Nudge two text boxes on a slide and the slide looks the same, yet the model reads them in a different order. This paper treats such extraction divergence as an attack surface for LLM applications and covers measurement, attacks and defense.

Combining static source analysis with dynamic analysis, the author studied ten widely used extractors, including markitdown, python-pptx, python-docx, openpyxl, pandas, unstructured, Docling and Apache Tika/POI. The study found 19 channels that extractors read but a person cannot see (off-slide text, hidden slides, speaker notes, alt text, hidden formatting and more) and 12 channels a person can see but extractors drop (headers, footers and others). Extractors also ignore number formats and reading order, so even visible content reaches the model in altered form. If a cell stores 600000 and a thousands format displays it as $600, the person and the model see different budget totals.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.05806
- arXiv HTML full text: https://arxiv.org/html/2611.05806
- arXiv PDF: https://arxiv.org/pdf/2611.05806

### Contribution
- The first systematic study of extraction divergence in LLM applications that process Office documents.
- A hybrid static and dynamic analysis that determines which channels each extractor reads, finding 31 channels that diverge from the human view across ten extractors.
- Five attack scenarios that make the model read a document differently from a human reviewer without injecting any instruction: a hidden security-certification claim, number formats, a hidden prefix that flips a word's meaning, an omitted footer value, and reordered reading. The crafted files open normally in Office.
- Prism, a defense that reconstructs the human view from the OOXML specification before passing text to the model. What the specification fixes is resolved directly from the markup without rendering; the remaining cases go to a slower render oracle that compares several rendering engines.

### Evaluation
- Targets: four chat assistants (ChatGPT, Claude, Gemini, Microsoft 365 Copilot) and four coding agents (Codex, Claude Code, Antigravity, GitHub Copilot CLI). Every system fell for at least one attack, and Gemini fell for all five. The number-format attack alone fooled all four assistants and three of the four agents in at least nine of ten trials. Most model backends of Notion were fooled as well.
- Prevalence: the paper also measures how common the underlying structures are in real Office files, such as those in the govdocs1 corpus.
- Defense: Prism mitigated all five scenarios, and models given Prism's reconstruction answered correctly in every trial. On 28 newly generated attack documents, a naive extractor diverged on all 28 while Prism recovered the human view on all 28; across three models, all 84 answers based on naive extraction were wrong and all 84 based on Prism were right.
- False positives and cost: on 193 benign documents from the Apache POI test corpus, Prism flagged 5 (2.6%), some of which really did contain content that differs from the display, such as off-canvas text. The static interpreter takes about 0.5 ms per document, faster than markitdown itself.
- Reliability of the metrics: attack success is reported per trial, and a separate set of generalization documents is used to show the defense is not tuned to specific files. Those documents are still author-made, though, and the static interpreter supports only DOCX and XLSX, with PPTX reading order relying on the render path.

#### Comment
- Anyone running an LLM service with document upload or a document-based RAG pipeline should check this right away. Because no instruction is injected, existing prompt-injection detectors will not catch these attacks. The risk is highest when LLMs review documents where numbers and facts matter, such as contracts, budgets or security-certification claims.
- Limitations: legacy binary formats (DOC, XLS, PPT), encrypted files and text inside images are not covered. Other formats such as PDF, HTML and email are discussed but not measured.
- Credibility: single-author paper; the manuscript still carries ACM template placeholder text, suggesting it is a pre-submission or under-review draft.
- Full text source: official arXiv PDF downloaded on the user's computer.

# Signed, Sealed, Leaked: Trust Beyond Signature for MCP Toolchains
> arXiv cs.CR 2611.06585 (preprint, not peer reviewed). Universiti Tunku Abdul Rahman (Malaysia), University of Tabuk (Saudi Arabia), National University of Singapore and others
> 2026

Third-party tools such as MCP servers are trusted through publisher signatures, and their execution is restricted by runtime policies on files and destinations. This paper points out that a signature proves who published the bytes, not what they do. A properly signed OCR tool can do its advertised job while quietly stashing data from earlier calls and appending it to the next request to an allowed destination. The authors built such a tool and showed that Meta's kernel-level runtime defense MCPGuard-Dynamic, which blocks a direct exfiltration attempt in the same run, fails to stop this attack in every trial.

Their answer is germline execution. A clean germline process that never holds user data is kept around, and each tool invocation runs in ephemeral copies forked from it. Each copy receives only the data its destination is authorized to see. Even if malicious code runs, what it can disclose is bounded by what its copy was given. The key point is that tool implementations need not be inspected or trusted.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06585
- arXiv HTML full text: https://arxiv.org/html/2611.06585
- arXiv PDF: https://arxiv.org/pdf/2611.06585

### Contribution
- Identifies invocation purity, the assumption that a tool neither carries state across calls nor mixes data within a call, as what per-call output labelling and destination-based confinement silently rely on, separates its two failure modes, and demonstrates both against MCPGuard-Dynamic.
- Under explicit assumptions of copy confinement and a data-free germline, proves sink noninterference for every signed release, and shows that for tools deterministic within the replay model a verified witness establishes a flow violation.
- Implements GERMLINE for unmodified Python MCP servers on stock Linux, with proofs, full result tables, an ethics statement and an artifact description in the appendices.

### Evaluation
- Attack blocking: across 153 attack runs, no unauthorized disclosure was detected under germline execution, versus 5.9% to 74.5% of runs under baseline defenses and an ablation. None was detected in 91 generated variants either.
- MCPGuard-Dynamic: a six-call session over HR, board, finance and public items with least-privilege policies, tested under seven configurations three times each (105 runs). The concealed leak succeeded in every trial.
- Utility and cost: an LLM-driven agent completed 7 of 7 tasks, and calls served by a single copy took 10 to 49 ms, 2 to 28 times faster than restarting the tool for each call.
- Reliability of the metrics: the attack tool and policy settings were designed by the authors, so the success rates describe these scenarios. The guarantees rest on the confinement and clean-germline assumptions, and side channels such as timing, or a malicious destination itself, are out of scope. The authors are careful to say that MCPGuard's failure reflects an inherent limit of destination-based confinement rather than an implementation bug, which is a fair framing.

#### Comment
- A concrete demonstration that signatures and registry checks alone cannot stop supply-chain attacks in the MCP ecosystem. For anyone wiring external MCP servers into internal agents, the takeaway is that long-lived tool processes that see data from many calls are risky by design.
- Limitations: since the approach limits what a tool can see, tools that genuinely need state across calls will require redesign. The evaluation covers Python MCP servers only.
- Credibility: an unreviewed manuscript from researchers in Malaysia, Saudi Arabia and Singapore. Formal proofs and artifacts are provided, so reproducibility looks good.
- Full text source: official arXiv PDF downloaded on the user's computer.

# Addition by Subtraction: Toward Mitigating Fragile Safety Alignment in Large Language Models
> arXiv cs.AI 2611.06553, cross-listed in cs.CR (preprint, not peer reviewed). University of Duisburg-Essen (Germany)
> 2026

Safety alignment in LLMs turns out to be concentrated in surprisingly few components. A line of work has shown that pruning a few thousand safety-critical neurons, or ablating a single refusal direction, is enough to largely undo it. This paper goes the other way and proposes ABS-Align (Addition by Subtraction), a fine-tuning method that makes alignment depend less on such sparse components.

The method does what the name says. It first locates safety-critical neurons in the TwinBreak manner, using activation differences between pairs of nearly identical harmful and harmless prompts. It then fine-tunes with DPO preference optimization while pruning those neurons gradually, most important first, every few steps. The model has to relearn safe behavior without them, which spreads alignment across other parts of the network.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06553
- arXiv HTML full text: https://arxiv.org/html/2611.06553
- arXiv PDF: https://arxiv.org/pdf/2611.06553

### Contribution
- A first attempt at making safety alignment less dependent on sparse components, combining gradual pruning with preference optimization.
- Shows that, although designed against pruning attacks, the benefit carries over to refusal-direction ablation and black-box jailbreaks.
- Shows that truthfulness (TruthfulQA) improves while general capability is largely preserved.

### Evaluation
- Models: Llama-3-8B-Instruct, Llama-3.2-3B-Instruct, Gemma-2-2B-IT and Qwen3-4B (four models from three vendors). Training data: 1,000 PKU-SafeRLHF samples, 850 Alpaca samples and 150 safe XSTest prompts.
- Attacks: white-box TwinBreak, NeuroStrike and refusal-direction ablation, plus 10 of the 20 linguistic transformations in SORRY-Bench (440 prompts each) as black-box attacks. Success is judged with the StrongREJECT evaluator.
- Results: attack success rates drop by up to 90% for some attacks. On Gemma-2-2B-IT, for instance, TwinBreak's per-iteration scores fall sharply, and jailbreaking stays difficult even after pruning three times as many neurons.
- Baselines: Circuit Breaker, W-DOOR and Deep Refusal, each compared only on the models evaluated in its original paper, so some model and baseline combinations are missing.
- Over-refusal and utility: over-refusal is measured on the remaining 100 harmless XSTest prompts, and general capability on MMLU, TruthfulQA, ARC-Challenge, WinoGrande and HellaSwag.
- Reliability of the metrics: using StrongREJECT, whose agreement with human judgment has been validated, is a plus. But all models are 8B or smaller, the baselines are missing for some models, which makes consistent comparison difficult, and over-refusal is measured with keyword matching on only 100 prompts.

#### Comment
- Worth noting for anyone releasing open-weight models, as an attempt to make alignment hold up better against white-box attacks that tamper with weights.
- Limitation: adversarial fine-tuning, where the attacker retrains the model to strip alignment, is excluded from the threat model, so this does not fully protect against an attacker who holds the weights.
- Of note: the corresponding author's lab published the TwinBreak attack (USENIX Security 2025) used here as the main target. Since the defense was built around the authors' own attack, validation against attacks from other groups is still needed.

# Timing is Everything: Inferring Temporal Membership in Continually Updated Models
> arXiv cs.CR 2611.05781 (preprint, not peer reviewed). Stevens Institute of Technology, University of Connecticut (USA)
> 2026

Deployed models are updated with new data all the time, and sometimes they also go through unlearning to remove specific data. Classic membership inference asks whether a sample was used in training. This paper is the first systematic look at whether an attacker can also tell when a sample was added and when it was removed. Timing can itself be sensitive: the fact that a patient's record entered the model in a particular update reveals that the patient was treated around then.

The authors define temporal membership and formalize inference at two granularities, individual update timestamps and intervals. Their attack, TMIA, needs only black-box access. It queries consecutive model snapshots with the same sample, feeds the resulting confidence trajectory into a sliding-window bidirectional LSTM, and predicts entry and exit points, then assembles valid membership intervals whose entries and exits are correctly ordered and paired.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.05781
- arXiv HTML full text: https://arxiv.org/html/2611.05781
- arXiv PDF: https://arxiv.org/pdf/2611.05781

### Contribution
- The first formalization of temporal membership and its inference in continually updated models.
- TMIA, a black-box attack based on confidence trajectories across snapshots.
- Extends three defenses designed for static models (label-only outputs, dropout and differential privacy) to the continual setting and shows the resulting privacy and utility trade-off.

### Evaluation
- Models and data: language models Pythia-70M, T5 and GPT-2 Small on SST-5, News20 and MNLI; image models ResNet-18, SimpleCNN and MobileNet on CIFAR-10 and two other image datasets. Updates use fine-tuning, and removal uses unlearning methods such as NPO.
- Results: at the timestamp level, precision and recall are at least 80.51% and F1 above 83% for all three language models. At the interval level, F1 exceeds 72% on Pythia-70M across the three text datasets. The attack is reported to remain effective against larger generative language models.
- Baselines: timestamp-wise MIA (TS-MIA), which runs an existing membership attack on each snapshot independently, and update-wise MIA (UP-MIA), which compares consecutive snapshots. TS-MIA predicts entries at nearly every timestamp, giving high recall but precision mostly below 70%; UP-MIA is low on both.
- Reliability of the metrics: because the problem is new, the baselines are simple ones the authors built themselves. By default the attacker can query every snapshot and receives probability vectors, which is a strong assumption for real services; a setting where only some snapshots are visible is evaluated separately. Most models are small.

#### Comment
- For services that handle deletion requests through unlearning, the paper shows that deletion itself can leave a trace of when data was present and when it was removed. It is a useful item to add to privacy assessments of services that publish frequent model versions.
- Limitations: the attack works best when the attacker can query every consecutive version, and its effect drops when only labels are returned.
- Credibility: an unreviewed manuscript from US university researchers. Public code was not found in the paper.
- Full text source: official arXiv PDF downloaded on the user's computer.

# Does Frontier AI Strengthen Cyber Defense? Evidence from Project Glasswing
> arXiv econ.GN 2611.06629 (preprint, not peer reviewed). Queen Mary University of London, single-author economics study
> 2026

Defenders and attackers race to find the same software flaws. This paper treats Project Glasswing, under which Anthropic gave 13 large US technology firms early access to Claude Mythos Preview, a model with strong vulnerability-discovery capabilities, in April 2026, as a natural experiment. Using public vulnerability data, it asks how access to frontier AI affected defenders, external researchers and attackers. The design is a difference-in-differences comparison whose main control group is Chinese firms, which Anthropic's terms bar from its models.

The data are the full official CVE List as of October 28, 2026 (over 410,000 records), the US National Vulnerability Database (NVD), credit lines from 17 vendors' advisories, the CISA and VulnCheck Known Exploited Vulnerabilities (KEV) catalogs, and FIRST's Exploit Prediction Scoring System (EPSS). There are three findings. First, firms with access more than doubled their disclosures relative to Chinese firms (about 36 more per firm-month), disclosed about 150% more high-impact vulnerabilities, and fixed reported flaws no more slowly. Second, external researchers who sell findings through bug bounties reported about half as many flaws in the treated firms' code and shifted to other firms' code, without leaving the market. Third, the share exploited within a month of disclosure fell by about two thirds, mainly because fewer were already being exploited when disclosed, while the number exploited did not change.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06629
- arXiv HTML full text: https://arxiv.org/html/2611.06629
- arXiv PDF: https://arxiv.org/pdf/2611.06629

### Contribution
- Gives the first empirical evidence that access to frontier AI raises firms' production of security information (vulnerability disclosures) without a measurable drop in quality or a slowdown in remediation.
- Shows with researcher-level data that AI substitutes for outside labor through reallocation across codebases rather than exit, and argues that part of the security benefit therefore spills over to software whose vendors had no access.
- Tests the dual-use worry that more disclosure hands attackers more information, and finds no such evidence in the first months after launch.
- Raises a policy point: a model provider's regional restrictions can act like an export control and open a gap in software security between countries.

### Evaluation
- Design: a firm-month panel from October 2025 (280 firms, 3,360 firm-months) with firm and year-month fixed effects. The Glasswing-by-post coefficient on log(1 + disclosures) is 0.784 (standard error 0.206) and stays significant under several inference methods suited to few treated units, including the wild bootstrap and the Ferman-Pinto procedure.
- Robustness: a longer window from 2024, Poisson estimation, dropping Anthropic itself, controlling for pre-trends, separating the effect from earlier access to Claude Opus 4.6, and a comparison with 26 large non-Chinese firms that stops in May, before the program expanded to about 150 organizations on June 2.
- Disclosure lags: the increase sits in flaws disclosed within 7 days or within 8 to 90 days of discovery, with no rise in those held for more than 90 days, which supports reading it as new discoveries rather than a cleared backlog.
- Attackers: Poisson regressions on exploitation within one to three months, zero-days versus n-days, and public exploit code show no significant increase. The sample is small, though (400 to 670 firm-months, 14 to 23 clusters), so power is low.
- Reliability of the metrics: everything uses public data, and the appendices describe data construction and sample rules in detail, so the study is reproducible. But the treated group is just the 13 firms Anthropic chose, and Chinese firms work under different disclosure rules and practices. The estimates should therefore be read as Mythos Preview versus whatever other AI tools each firm had, not as AI versus no AI. The author says so explicitly.

#### Comment
- An economist, not a security researcher, runs a quantitative study across the whole CVE ecosystem, so the paper looks at effects visible in the actual disclosure record rather than at model benchmarks. That makes it rare field evidence on how AI-driven vulnerability discovery changes real security metrics.
- Limitations: only disclosed flaws are observed, not the underlying stock of flaws or total discoveries. Vendor fixes are observed, but not whether users installed the patches. With only a few months of post-launch data, the path from disclosure to exploitation cannot yet be estimated (only five post-launch Glasswing CVEs have exploitation records).
- Interests: the subject is one AI company's program, so some care is warranted in interpretation. We found no statement in the paper about the author's relationship with that company or about funding.
- Credibility: an economics (econ.GN) manuscript that has not been peer reviewed.
- Full text source: official arXiv PDF downloaded on the user's computer.

# Signed but Steerable: Measuring and Closing the Text-Vector Integrity Gap in Offline Retrieval-Augmented Generation
> arXiv cs.CR 2611.06498 (preprint, not peer reviewed). securagen.ai (Athens, Greece)
> 2026

Offline RAG on disconnected field devices receives knowledge through signed update bundles called knowledge packs. Because computing embeddings on a small device is slow (about 29 minutes for 950 passages on a Raspberry Pi 5), packs carry precomputed embedding vectors along with the text. A signature proves who published the pack, not that the vectors actually encode the text. This paper studies that text-vector integrity gap. The attacker controls the publishing pipeline or is an insider, and ships harmless, review-approved text with vectors chosen to steer retrieval.

The central result is the margin law. If a verifier recomputes each vector and accepts the shipped one whenever the cosine similarity is within a tolerance τ, then the share of queries an optimal attacker can hijack at rank 1 equals the share whose angular retrieval margin (the angle gap between the gold document and its closest competitor) is below arccos τ. Exposure can therefore be measured without running any attack. The authors show that vector databases using compressed storage (scalar quantization, product quantization, binary codes) have the same problem, and close the gap with code-level verification: compare the quantization codes themselves, with the verifier alone deciding ambiguous cases.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06498
- arXiv HTML full text: https://arxiv.org/html/2611.06498
- arXiv PDF: https://arxiv.org/pdf/2611.06498
- Author repository (code, data, pre-registered protocol): https://github.com/securagenai/signed-but-steerable
- Zenodo archive v1.0.2: https://doi.org/10.5281/zenodo.23948839

### Contribution
- Introduces the margin law, which computes exactly what a tolerance-based check concedes to an attacker from the margin distribution, and confirms that it matches attack simulation exactly.
- Shows with a real attack on a FAISS index that tolerance-based integrity audits of compressed vector stores are effectively useless.
- Proposes code-level verification (verifier-decided ambiguity, a guard band calibrated on measured floating-point noise, and canonicalization to the verifier's own codes) that accepts every honest vector across platforms, needs no special hardware, and leaves the publisher no choice.
- Measures that common floating-point and dynamic-INT8 inference pipelines are not bit-reproducible across batch sizes or architectures.
- Reports pre-registered negative results on abstention, context pruning and semantic screening.

### Evaluation
- Data: all answerable SQuAD 2.0 questions and four BEIR test sets (five corpora), with two embedding models (BGE-M3 and MiniLM).
- Margin law: even an idealized tolerance at floating-point noise level leaves up to 5.5% of queries exposed (at most 1.2% in any corpus once exact duplicate documents are removed). A realistic tolerance calibrated from a CPU INT8-versus-FP32 comparison (the 0.1% quantile of honest cosines) leaves 98 to 100% exposed.
- Compressed storage: under tolerance audits, SQ8 leaves 2 to 15% of queries exposed, SQ4 55 to 89%, product quantization about 100%, and binary codes 100%. In a real attack on a FAISS product-quantization index over 57,638 documents, every tampered vector passed the audit and the attacker's document ranked first for 25% of targets. Code-level verification blocked all of them.
- End to end: on a Raspberry Pi 5 running a local Qwen2.5-3B, an attack against a verifier using the INT8 reference threshold cut correct answers from 0.75 to 0.39 (100 questions per condition). Running verification on the same CPU slowed the concurrently running language model's decoding by 23 to 31%. Layered pack verification rejected all 12 structural update attacks tested.
- Acceptance of code-level verification: every honest vector in the samples was accepted on three platforms (Raspberry Pi 5, a desktop, an Apple M2 laptop) and four compute backends.
- Reliability of the metrics: the protocol was pre-registered and its deviation log is public, and proportions come with Wilson intervals. The exposure figure, however, counts queries for which some tampering could hijack rank 1; it does not mean one tampered index hijacks all of them at once. The authors also note that exposure at small tolerances is mostly near-duplicates of the gold document taking first place, so it is an upper bound on harm. The update scenarios are synthetic.

#### Comment
- Most RAG attack research poisons the text. This paper leaves the text alone and changes only the vectors, a path that text review and text-level defenses cannot see, which makes it significant from a supply-chain security standpoint.
- Limitations: dedicated accelerators such as NPUs, IVF and graph indexes, and attackers who change both text and vectors are not covered. Guard widths come from measurement and carry no guarantee for other models or hardware.
- Interests and credibility: both authors work at securagen.ai, which develops commercial software in this area and funded the work, as the paper discloses. It follows the same authors' earlier study on signed knowledge packs. Not yet peer reviewed.

# Enforcing Accountable Disclosure in Confidential AI
> arXiv cs.CR 2611.05971 (preprint, not peer reviewed). Acompany Co., Ltd. (Japan)
> 2026

CPU and GPU confidential computing make "confidential AI" possible: an LLM processes user prompts without the service provider or infrastructure operator seeing them. But AI agents need to send prompt-derived information outside for web searches and API calls, and providers need limited visibility for safety monitoring and failure diagnosis. This paper proposes the principle of Confine or Declare. User-derived data stays confined inside the confidential virtual machine (CVM) by default, and may leave only after it has been declared, meaning its exact contents, recipient and stated reason have been recorded in a tamper-evident declaration log that the user can inspect.

CORDE, the system that enforces this, has two parts. On the inference side, a Rust library wraps user data in types tagged with the originating user and lets code unwrap it only inside confine! regions that handle a single user's data. Functions that send data out accept only declared values whose ledger commit has completed, and those values cannot be cloned, so each is used once. A static analysis over Rust's mid-level intermediate representation (MIR) checks that code in these regions never writes secretly to globals, files or sockets. On the ledger side, a CCF-based ledger runs in a separate TEE and is tied to remote attestation, so users can verify that the log the inference service declares to is the same log they read.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.05971
- arXiv HTML full text: https://arxiv.org/html/2611.05971
- arXiv PDF: https://arxiv.org/pdf/2611.05971

### Contribution
- Proposes a principle that works independently of output restrictions or LLM review: instead of blocking disclosure, it makes every disclosure checkable after the fact, so a provider that tries to hide one can be caught later.
- Offers an integrated design that goes beyond detecting tampering, omission and rollback within a single ledger and also defeats split-view attacks, using a ledger public key pinned through attestation, per-user sequence numbers and signed read responses.
- Demonstrates a prompt-injection case in which an agent sends a secret outside: even when defenses fail, the declaration record reveals the leak, and the root cause can be investigated without handing the secret to the provider.

### Evaluation
- Setup: on Microsoft Azure, an AMD SEV-SNP CVM with an NVIDIA H100 NVL in confidential-computing mode serves BF16 Qwen3-32B through vLLM, and the ledger runs on three CCF nodes.
- End-to-end overhead: across 723 AppWorld tasks, an agent benchmark with frequent external API calls, run sequentially, mean task latency rose from 153.66 to 154.34 seconds (0.44%). Declarations took 0.801 seconds per task on average and 43.19 ms each. Model requests, tool-call sequences and final responses matched the baseline on every task. Both configurations succeeded on only 13.28% of tasks, which the authors attribute to the model and agent configuration rather than the declaration mechanism.
- Ledger throughput: with 1 KiB declarations, throughput plateaued at about 880 commits per second at concurrency 64, with little difference whether or not the attestation proxies were in the path. At concurrency 256, p95 latency rose to 399 ms.
- Static analysis: starting from six confine! regions (184 lines), the checker followed calls into libraries and inspected 41,622 MIR statements, taking 457 seconds on average.
- Security requirements: all 13,402 AppWorld tool requests observed independently at the MCP servers matched the retrieved declaration records, and functional and fault-injection tests were also run.
- Reliability of the metrics: the overhead figures come from a one-to-one comparison with the same workflow minus declarations, which is convincing. The workload is dominated by inference time, though, which makes the overhead look small, and availability remains open: if the ledger loses its keys in a failure, earlier records can no longer be verified.

#### Comment
- When confidential AI meets agents, there is a tension between needing external communication and keeping user trust. The paper resolves it with accountability rather than prevention, which is new and worth considering when designing transparency mechanisms for cloud LLM services.
- Limitations: non-Rust components such as vLLM, the model gateway and the ledger client are trusted and not covered by the static analysis. Information leaked through termination and interference between concurrent requests are out of scope. The design assumes the provider avoids behavior that users could detect. We could not find a code release in the paper.
- Credibility: a preprint from a Japanese company's research team, not yet peer reviewed.
- Full text source: official arXiv PDF downloaded on the user's computer.

# Analysis of Local Open-Weight LLM Agents on Vulnerability-Reproduction Tasks
> arXiv cs.CR 2611.06257 (preprint, not peer reviewed). Lucentia Research, University of Alicante, Spain
> 2026

Open-weight models that fit on a single consumer GPU matter for security work because they run locally, without sending code to an outside service. The source of an unpatched flaw is among the last things a lab wants to share. This paper systematically measures how well such local models handle vulnerability reproduction: turning a vulnerability description into an input that actually crashes the vulnerable build.

The authors run twelve configurations from three generations of Qwen models (3.5, 3.6, 3.8), sizes 4B, 9B and 27B plus a 35B mixture-of-experts model with 3B active parameters, and BF16, FP8 and INT4 precision, three times each on ten CyberGym tasks. Every configuration, down to 4B, solves most of the six easier tasks; configurations separate only on the four harder ones, which need the 27B model. Quantization never changed what a model could solve in matched pairs, only how fast, and the mixture-of-experts model reached the same scores in less time. In the trajectories, even failed runs almost always name the vulnerable function and the missing check. What decides success is whether that hypothesis becomes a working input file.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06257
- arXiv HTML full text: https://arxiv.org/html/2611.06257
- arXiv PDF: https://arxiv.org/pdf/2611.06257
- Released data (Hugging Face, all trajectories and submitted inputs): https://doi.org/10.57967/hf/10888

### Contribution
- According to the authors, the first controlled comparison of open-weight models served locally on one consumer-grade GPU across size, architecture and quantization on vulnerability reproduction.
- Releases all 360 runs, 3,501 submitted candidates, and each submission's results on both the vulnerable and the fixed build, enabling further analysis.
- Observes that failures come not from analysis but from building a byte-exact input and from learning from rejections, a practical sign that harness and feedback design matter as much as model size.

### Evaluation
- Setup: a single harness, the pi coding agent, in a container based on CyberGym's reference image, with no compiler or Python, only read, shell, write and edit tools. No internet access and a 7,200-second cap per run (twice CyberGym's 3,600 seconds, so slow large models were not unfairly cut off). Serving used SGLang on one NVIDIA RTX PRO 6000 Blackwell (96 GB), and the full sweep took about 100 hours of inference compute.
- Results: the pooled success rate on the six easier tasks is 85.2%. On GraphicsMagick and Assimp the generation effect is clear: Qwen 3.5 configurations solve at most one run in three, while every full-precision 3.6 and 3.8 configuration solves two in three. FreeType and OpenSC are solved only by the FP8 version of Qwen 3.8 27B (two and one runs of three); every run of its BF16 version hit the time cap. The same 27B configuration went from 1 of 12 hard-task runs under Qwen 3.5 to 4 under 3.6.
- Task difficulty: per-task success tracks the size of the reference proof-of-concept closely (Spearman ρ = -0.81, p = 0.004). For YARA and FFmpeg the reference input is an empty file, so nearly every run succeeds.
- Reliability of the metrics: the harness and prompt are held fixed, and all submissions and trajectories are public. But ten tasks with three runs each gives low statistical resolution, every configuration belongs to one model family, and the quantization axis is complete only for Qwen 3.5. The authors acknowledge that the conclusions are tied to this task sample and this family.

#### Comment
- The finding that open-weight models already analyze vulnerabilities well and get stuck on building the input gives a concrete direction for anyone building local security agents. For organizations that cannot send source code outside, the authors recommend the newest generation served as a dense 27B model.
- From the attacker's side, the same result means consumer hardware alone can now produce proofs of concept for known vulnerabilities.
- Credibility: a preprint from a Spanish university group, with no declared competing interests.

# Reassessing Dataset Quality and Fine-Tuning Practices for Vulnerability Detection on PrimeVul dataset
> Published at ACM EASE 2026 (International Conference on Evaluation and Assessment in Software Engineering, June 2026, Glasgow, UK). Posted to arXiv as cs.SE 2611.06373 in November 2026
> 2026

Many studies report that fine-tuning pre-trained code models on benchmarks such as PrimeVul yields good vulnerability detection. This paper checks that claim at scale. It fine-tunes three encoder models, CodeBERT, GraphCodeBERT and UniXCoder, across five imbalance-mitigation strategies (including class weighting, oversampling, undersampling and focal loss), broad hyperparameter sweeps and multiple random seeds, for 770 training runs in total.

The results are consistently negative. F1 and ROC-AUC sometimes look better, but the Matthews correlation coefficient (MCC), a more security-relevant metric, stays near zero, predicted probabilities cluster around 0.5 and are poorly calibrated, and the false-negative rate when false positives are capped at 0.5% (VD-S) is around 0.99. Neither threshold tuning nor post-hoc calibration recovers a usable signal. The authors trace the cause to the data: vulnerable and fixed functions are nearly identical, and commit-level labeling introduces noise.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06373
- arXiv HTML full text: https://arxiv.org/html/2611.06373
- arXiv PDF: https://arxiv.org/pdf/2611.06373
- ACM Digital Library DOI: https://doi.org/10.1145/3816483.3816594
- Author data and scripts (Zenodo): https://doi.org/10.5281/zenodo.18154077

### Contribution
- A large multi-seed, multi-configuration study yielding a negative but useful result: no evidence that standard encoder fine-tuning on PrimeVul produces practically useful detection.
- Shows that F1 and ROC-AUC alone can mislead about a security detector's performance, and argues for MCC, expected calibration error (ECE) and VD-S as primary metrics.
- Diagnoses PrimeVul's data-quality problems quantitatively: near-identical function pairs, commit-level label noise, and limited diversity of vulnerability patterns.

### Evaluation
- Setup: every test result uses calibrated probabilities and thresholds chosen only on the validation split, and the best configuration for each model and imbalance strategy is selected by validation MCC.
- Performance: UniXCoder reaches the highest ROC-AUC at 0.549, while CodeBERT and GraphCodeBERT mostly stay at or below 0.52. MCC and balanced accuracy stay close to zero for every model. No imbalance strategy consistently beats the unmodified baseline. Temperature scaling slightly lowers calibration error, but probabilities remain bunched around 0.5.
- Data diagnosis: comparing 4,416 paired vulnerable and fixed functions with character 3- to 5-gram TF-IDF gives a median cosine similarity of 0.992; 89.4% of pairs exceed 0.90 and 81.2% exceed 0.95.
- Reliability of the metrics: the authors release training settings, seeds, processed splits and scripts on Zenodo, so reproducibility is good. The conclusions are limited to encoder models and to PrimeVul, though, and do not automatically carry over to large generative models or to other datasets such as BigVul, Devign or CleanVul.

#### Comment
- A reminder that before trusting high numbers in function-level vulnerability detection, one should ask whether the vulnerable and fixed versions in the dataset are actually distinguishable. Useful for teams choosing metrics to evaluate AI-based security tools.
- Limitations: alternatives such as graph-structured models or pair-aware (Siamese) training are not tested and are left for future work.
- Credibility: already published at EASE, a peer-reviewed software engineering conference. The authors are at the University of Szeged, Hungary, with support from the EU's European Cybersecurity Competence Centre.
- Full text source: official arXiv PDF downloaded on the user's computer (marked as the same version as the EASE publication).
