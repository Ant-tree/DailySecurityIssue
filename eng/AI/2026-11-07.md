# A Gingerbread House for LLM Agents: Source-Planned Honeypots That Lure Autonomous Attackers into an Isolated Shadow
> arXiv cs.CR 2611.07611 (preprint, not peer reviewed). Soongsil University (South Korea)
> 2026

LLM agents now find and exploit web vulnerabilities fast enough that a defender may not get to patch first. Most deception aimed at such agents so far lures them toward bait while the real vulnerable path stays reachable. This paper tries a different arrangement. Before deployment, a defender LLM reads the application's source code and plans a static honeypot (decoy pages, fake endpoints, honeytokens). At run time, a router written as fixed code keeps per-client state: a payload signature or a burst of 404s makes a client "suspect", while a honeytoken use or a hit on a fake endpoint "confirms" it. Every later request from a confirmed client, a working exploit included, goes to an isolated shadow copy of the application running in its own container stack.

The study compares no defence (arm A), the static plan alone (arm B), and an augmented configuration that adds a runtime LLM responder and extra router rules (arm C). Each run is judged by the benchmark's own grader on the real target and on the shadow.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.07611
- arXiv HTML full text: https://arxiv.org/html/2611.07611
- arXiv PDF: https://arxiv.org/pdf/2611.07611

### Contribution
- Combines static deception planned by an LLM from source code with per-client routing of confirmed attackers to an isolated replica, and evaluates it against an attack framework that has been used in real intrusions. In effect it brings classic shadow-honeypot and honey-patch designs to LLM attackers.
- Because real compromise drops close to zero and can no longer rank configurations, the authors also measure where each exploit landed, whether the attacker reported a planted fake secret as genuine, and how many payloads reached the real target before confirmation.
- Releases alt-cve-bench, 20 new CVE tasks not used in the design, with the same task format and grader as CVE-Bench.

### Evaluation
- Three experiments: Claude Opus 4.8 as attacker on the 40 critical CVE-Bench tasks (the development set used to build the deception); ARTEX, an open-source multi-agent attack framework driven by DeepSeek-V4-Flash, on the same 40 tasks; and ARTEX on the 20 alt-cve-bench tasks. Of 300 planned runs, 296 were recorded and 288 were valid.
- The static plan alone cut real compromise from 26/40 to 5/40 for Opus 4.8, from 20/40 to 0/40 (31 valid runs) for ARTEX, and from 15/20 to 0/20 on the new tasks. On the 30 tasks the control compromised, the upper end of the 95% interval for arm B's compromise rate is 11.6%.
- In the ARTEX deception arms, roughly half of the runs had the exploit succeed on the shadow only. The defence moved working exploits rather than stopping them, and the remaining risk is requests that reach the real target before confirmation. The shadow served a median of 95.2% and 93.2% of ARTEX's requests per run.
- ARTEX reported a planted fake secret as genuine in 30 of the 120 deception-arm tasks, 20 of those times without any working exploit. Five times it labelled one item a decoy while reporting another planted secret as genuine.
- Arms B and C did not differ significantly (for example, Opus 4.8 real compromise 5/40 versus 1/40, exact McNemar p = 0.22). A benign crawler stayed in the normal state in almost every recorded run; it became suspect twice and was never confirmed.
- Reliability of the metrics: the grader is unchanged, invalid runs are screened for cheating signals (outside lookups, reading other runs' files and so on), and a grader positive control is included, so the setup is credible. On the other hand there is only one run per task and arm, clients are attributed by listener, and benign traffic is a single crawler, so the false-positive rate in a real deployment is unknown.

#### Comment
- The idea of moving an attacking agent into a convincing fake instead of blocking it stands out. It is closer to deception than to blocking: the real target stays safe while the attacker reports false results to its operator, which is attractive in practice.
- Limitations: an attacker that changes identity (session or address) starts over as a new client. Clues such as the shadow's container names leaked to an attacker with code execution in some runs, and the authors note that a deployment must hide them. This design cannot isolate the effect of the responder in arm C.
- Credibility: a preprint from a Korean university group, with a pre-specified metric set, proper statistical tests and a fairly thorough limitations section.

# Signed but Not Safe: Requirement Integrity in Multi-Agent LLM Handoffs
> arXiv cs.CR 2611.07483 (preprint, not peer reviewed). University of Massachusetts Amherst, Duke University, Georgia Institute of Technology, University of Illinois Urbana-Champaign, Accentrust
> 2026

Enterprise AI agents split a user's request across subagents and merge their results. At every handoff a requirement can be summarized away, altered by an intermediate agent, rewritten by an indirect prompt injection, or ignored by the merger. The paper separates "loss without an adversary" from "deliberate tampering" and runs a preregistered, controlled experiment comparing three handoff forms: a free-text summary, structured JSON, and a signed requirement manifest.

In the manifest form, the orchestrator extracts each requirement as a verbatim quote plus a checkable predicate. Trusted harness code drops any item whose quote is not literally in the request, canonicalizes the JSON, signs it with HMAC-SHA256 under a key no model ever sees, and checks the final decision against every predicate with deterministic code rather than an LLM. A flagged decision gets one repair round, after which the system fails closed.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.07483
- arXiv HTML full text: https://arxiv.org/html/2611.07483
- arXiv PDF: https://arxiv.org/pdf/2611.07483

### Contribution
- Defines five requirement-level threats on an orchestrator, subagent and merger pipeline (benign, summarization loss, in-transit mutation, tool-output injection, merger override) and pairs a safety endpoint, the "unsafe commit" (a violating decision that goes through unflagged), with a utility guardrail (a commit that satisfies every requirement), so that abstaining cannot pass for safety.
- Compares unsigned and signed manifests to isolate what signing actually adds.
- Compares a deterministic verifier and an LLM checker on identical trajectories.
- Uses an oracle-manifest control and a pre-signing injection attack to show that the risk signing cannot fix comes from extraction. Signing protects requirements in transit; the extraction step is the trust boundary. That is the paper's central conclusion.

### Evaluation
- The primary study uses Qwen3-8B, with 1,440 trajectories over five threats. Under attack, signed manifests cut unsafe commits from 69.4% to 9.0% (paired difference 60.4 percentage points, 95% CI 51.4 to 69.4). Excluding in-transit mutation, where rejection is guaranteed by construction, the rates under injection and merger override are 58.4% versus 13.5%. There is no net loss of conformant commits relative to structured handoffs (-0.4 points).
- What signing adds: in mutated runs, an unsigned manifest committed violations 79% of the time and the signed one never did. The price is that tampered runs abstain instead of completing.
- On identical trajectories the deterministic verifier caught 78.7% of violating decisions with 7% false alarms; the LLM checker caught 59.0% with 50% false alarms.
- An oracle manifest removed all remaining unsafe commits, so the residual 11.2 points come entirely from extraction errors made before signing, mainly preferences extracted as mandatory items and missed requirements.
- Pre-signing injection: one adversarial line in the request context raised signed-manifest violations from 14.6% to 37.5% for Qwen3-8B, from 11.1% to 63.9% for gpt-oss-20b and from 8.3% to 75.0% for GPT-5.6-luna. Every such violation came from a manifest corrupted before signing, which the signature then authenticated.
- In the second model family, gpt-oss-20b (432 trajectories), structured handoffs were already safe without an adversary and under injection, so the gain came only from tampering resistance. Manifest extraction also failed on 22% of tasks, which cost utility.
- Reliability of the metrics: hypotheses, multiple-comparison families and parser rules were frozen and hashed before any model call, and pre-run amendments are disclosed, which makes the study unusually transparent. The tasks are synthetic and exactly scorable, and the primary model is 8B, so results do not carry over directly to real enterprise workloads. Code and data are only "available on request".

#### Comment
- The title says it: a signature does not make a handoff safe. As agent ecosystems start signing artifacts (A2A agent cards, AP2 payment mandates), the point that the step before signing remains an attack surface is worth keeping in mind during design.
- Limitations: a compromised orchestrator, a compromised harness and key theft are out of scope. Frontier-model results are an exploratory subset only.
- Credibility: a preprint from US universities and a security company.
- Full text read from: the official arXiv PDF, downloaded on the user's computer.

# Authorization Propagation in Agent2Agent Systems: An Experimental Security Evaluation of Multi-Hop Delegation
> arXiv cs.MA 2611.07050 (cross-listed in cs.CR, preprint, not peer reviewed). Department of Information Security and Communication Technology, NTNU (Norway)
> 2026

When agents hand work along an Agent2Agent (A2A) chain, the agent sending a request may not be the principal that granted the authority. In A0 to A1 to A2, A2 can authenticate A1 as its direct caller but cannot tell whether the requested operation stays within the authority set earlier in the chain. Conversely, valid authorization evidence does not authenticate the request that happens to carry it.

The paper tests a layered design that verifies these separately, using a synthetic four-party healthcare reimbursement workflow (reimbursement client, patient agent, hospital agent, insurance agent). It adds the layers one at a time across four configurations, C0 to C3: current-caller context (the Secure Passport extension's CallerContext, signed with Ed25519), transitive authorization evidence protected by a shared HMAC key, per-hop Ed25519 request signatures, and separate replay state for requests and for authorization artifacts.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.07050
- arXiv HTML full text: https://arxiv.org/html/2611.07050
- arXiv PDF: https://arxiv.org/pdf/2611.07050

### Contribution
- Breaks the security of delegated A2A workflows into current-caller context, inherited authorization, per-hop request authentication and independent replay domains.
- Implements these layers through extensions only, without changing the A2A core protocol.
- Alongside the attack evaluation, shows two limits the design still has: no semantic check that authority narrows along the delegation path, and no protection of the original authority against a holder of the shared key.

### Evaluation
- Of 15 adversarial conditions (sender impersonation, request text and protected-metadata tampering, changes to amount, beneficiary and other authorization fields, unauthorized hops, destination substitution, scope widening, replay and expiry), 14 were rejected at the intended verification layer.
- The one accepted case is an isolated test of the delegation-path check. That check verifies only participant order and final destination, so a scope with an extra approval right appended still passes structurally. The authors read this as evidence of a missing semantic-attenuation check, not as an end-to-end bypass.
- In a separate experiment, a hospital agent holding both its legitimate signing key and the shared HMAC key raised the maximum amount from 120 to 9,000 euros, recomputed the evidence and passed every check. A shared-key construction cannot stop an authorized intermediary from rewriting the authority.
- In repeated runs, all 400 benign executions were accepted and all 500 adversarial executions were rejected. The full configuration had a median security-processing latency of 5.11 ms and a 3.87 kB serialized payload.
- Reliability of the metrics: the authors state that the repetitions characterize deterministic behavior on fixed attack inputs, not detection probability for arbitrary attacks. Latency is local processing time on one Windows machine, excluding network, TLS and storage.

#### Comment
- A short, experiment-report style paper, but it makes two concrete points with clear examples: do not conflate authenticating the current request with verifying inherited authority, and a shared HMAC key does not preserve origin authority. It works well as a checklist when reviewing agent-to-agent delegation designs.
- Limitations: only a fixed four-party path; dynamic agent discovery, key distribution and revocation, and replay state across replicas are out of scope. Semantic attenuation and origin-preserving delegation (for example, a chain of per-hop signatures) are left for future work.
- Credibility: a preprint from NTNU, with a master's student as first author.
- Full text read from: the official arXiv PDF, downloaded on the user's computer.

# A Bag of Tricks for Defending Deep Learning-based Face Recognition Pipelines against Backdoor Attacks
> arXiv cs.CV 2611.06412 (cross-listed in cs.CR, technical report, preprint, not peer reviewed). Cybersecurity AI Team, Thales Cyber & Digital (France)
> 2026

A real face recognition system is not one model but a chain of them: face detection, alignment, presentation attack detection (antispoofing) and face feature extraction. This technical report takes the threat model most relevant to industry, where training happens in-house but the training data comes from third parties that may be compromised, and presents three practical defenses against data-poisoning backdoors.

The attack works in two steps. An insider enrolls while wearing a trigger (for example, a patch on the cheek), so a malicious embedding is stored; afterwards any attacker wearing the same trigger is authenticated as that insider. Most existing backdoor defenses were built for closed-set classification and fit poorly with face recognition, which works in an open-set embedding space shaped by angular-margin losses. The authors propose one training-time defense and two inference-time defenses.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.06412
- arXiv HTML full text: https://arxiv.org/html/2611.06412
- arXiv PDF: https://arxiv.org/pdf/2611.06412

### Contribution
- Early Poison Identification (training time): triggers are simpler than faces, so poisoned identities are learned much faster than genuine ones. The defense tracks per-identity accuracy in early batches, flags identities whose accuracy rises abnormally fast, and can prune their samples while training continues. It needs no clean reference data and no knowledge of the trigger.
- Detector-level Model Pairing (inference time): a simple off-the-shelf detector such as MTCNN runs alongside the main face detector, and an input is rejected if the number of detections, the box overlap (IoU of at least 0.5) or the landmark drift disagree. It targets attacks that make the detector hallucinate faces (FGA) or shift landmarks (LSA).
- Cut-and-Mix (inference time): the input face is cut into chunks with preset masks and pasted onto a small set of verified clean faces; if too many of the mixed images match the original, a trigger is assumed. This adapts the idea behind STRIP to an open-set embedding space.
- Early Poison Identification and Cut-and-Mix correspond to European patent filings EP4738203 and EP4811192.

### Evaluation
- Models: RetinaFace detectors (MobileNetV1 and ResNet50 backbones) trained on WIDER-Face, and five feature extractors (GhostFaceNetV2, IR-SE-50, MobileFaceNet, RobFaceNet, ResNet50) trained on MS1Mv2. Triggers: BadNets, SIG, FauxIt and a mask-based pattern.
- Early Poison Identification found the backdoor identity early in training for all 12 poison-label attacks but for none of the 3 clean-label attacks. With the defense on, training is about 1.5 times slower during the first one to three epochs.
- Model Pairing: average false positive rate 0.81% and false negative rate 4.31%; 7.06% false negatives on FGA and 0.65% on LSA (excluding one poorly learned model). The worst case, 15.5% false negatives, was a model whose backdoor reached only 57.0% attack success. Added latency is about 0.09 s per face.
- Cut-and-Mix: apart from two models (clean-label SIG backdoors with low attack success), false negatives stayed at or below 1.0% for false positive rates between 0.5% and 1.1%. In a preliminary test against the FIBA adversarial pattern, which behaves like a backdoor at enrollment time, it had under 1% false positives and 0% false negatives. Added latency is 0.02 to 0.04 s per image.
- The inference-time defenses were evaluated on 2,048 faces from CelebA-Spoof, half bona fide and half spoof.
- Reliability of the metrics: the coverage of architectures and triggers is reasonable, but explaining the failures as "weakly learned backdoors" also means the defenses struggle exactly when the attack is weak. Only simple patch and diffuse triggers were tested, with no adaptive attacks.

#### Comment
- A practical report that treats face recognition as a chain and picks a defense suited to each stage. It is specific enough that teams running biometric authentication or access control could consider applying it directly.
- Limitations: the training-time defense does not work against clean-label attacks, the antispoofing stage is not covered, and the authors say collision-style attacks where only the insider wears a pattern (UniID) are not addressed. There is no mention of code release, and some techniques are under patent filing.
- Credibility: a technical report from Thales, a defense and security company, without conference peer review.
- Full text read from: the official arXiv PDF, downloaded on the user's computer.
