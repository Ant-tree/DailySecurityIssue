# SkillCODER: Towards Auditing and Attribution of Copyright Infringement in LLM Agent Skills
> Accepted at ACM CCS 2026 (arXiv preprint version, DOI 10.1145/3830454.3846644)
> 2026

Agent skills bundle role definitions, constraints, and procedures into long, human-readable documents, which makes them easy for a licensed buyer to resell or for anyone to republish under a new name. Existing system-prompt watermarking relies on gradient-driven token edits: in a document as long as a skill the signal gets diluted, and the unreadable tokens it inserts damage the very readability that gives a skill its value. This paper parses a skill into a section-aware intermediate representation (SkillIR) and spreads natural-language conditional instructions across its structural nodes. These stay dormant during normal use but make the agent emit a fixed-format "capsule" when the owner sends specially designed verification queries. One field of the capsule carries buyer-specific word choices bound together by an error-correcting code, so the owner can also identify which buyer leaked the skill. Verification needs nothing beyond black-box API output.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.11308
- arXiv HTML full text: https://arxiv.org/html/2611.11308
- arXiv PDF: https://arxiv.org/pdf/2611.11308
- ACM DOI: https://doi.org/10.1145/3830454.3846644
- Author code repository: https://github.com/EonHao/SkillCODER

### Contribution
- First formulation of copyright auditing and buyer attribution for agent skills, showing why their length and human readability defeat existing prompt watermarking.
- A design that confirms both ownership and buyer identity from inference output alone, with no access to model internals. Because the watermark is written as natural-language instructions, the skill stays readable.
- Ownership evidence and the buyer fingerprint live in the same capsule, so a single round of verification queries answers both questions.

### Evaluation
- Skills from three domains (code review, data science, travel planning), drawn from both the Anthropic Skill Creator and public community repositories, were tested on 18 configurations: four open models (Qwen3-1.7B/4B/8B, GLM-Z1-9B), two commercial API models (GPT-5 mini, Claude Haiku 4.5), and three agent frameworks (LangChain, CAMEL, OpenClaw).
- Owner verification averaged 99.2%, ahead of PromptCARE (89.6%) and PromptCOS (87.5%). Top-1 buyer attribution reached 99.3%, far above the baselines (70.5% and 67.6%).
- Under paraphrasing, compression, clause deletion, and section reordering, owner verification stayed at or above 96.0% on open models. Across five adaptive attacks, including a design-aware LLM sanitizer and multi-buyer collusion, ownership evidence held while buyer attribution degraded gradually.
- The cost is an average 9.8-point drop (on a 100-point scale) in task utility after watermarking; the authors note the loss is concentrated in a few model-domain combinations.
- PromptCARE and PromptCOS are white-box gradient methods, so the comparison is against versions adapted to the black-box skill setting.

#### Comment
- Most authors are at Zhejiang University, so we checked further. The venue is ACM CCS 2026, a top-tier security conference, and the paper carries an ACM DOI. Authors such as Kui Ren, Zhan Qin, and Dacheng Tao (NTU) have established track records in the field. The code is public on GitHub, the evaluation includes commercial API models, and the utility loss is reported openly. The numbers are very high, but given the breadth of evaluation and the honest reporting of costs, we see no major credibility concern.
- One co-author is affiliated with a security company (Beijing Chaitin Technology).
- As skill marketplaces grow this kind of protection will be needed, but a 9.8-point utility loss is not trivial for commercial skills.

# CyberBinGym: Can AI Agents Turn Binary Patches into Real Exploits?
> arXiv preprint (not peer reviewed)
> 2026

Security fixes usually ship as compiled updates, and diffing the patched and unpatched binaries can reveal where the bug is and how to exploit it (the 1-day setting). This paper builds a benchmark that asks whether AI agents, given only stripped vulnerable and patched binaries and no source code, can produce working exploits. It contains 100 tasks drawn from real vulnerabilities in 53 open-source projects. Vulnerability recovery (a differential crash test) and end-to-end exploitation (reading a root-owned flag) are scored separately, and trajectory audits reject reward hacking such as reading the flag straight from the environment.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.10723
- arXiv HTML full text: https://arxiv.org/html/2611.10723
- arXiv PDF: https://arxiv.org/pdf/2611.10723

### Contribution
- Makes the binary-only 1-day exploitation setting measurable for the first time. Earlier benchmarks either expose source code, use hand-made CTF challenges, or test binary comprehension without asking for a security outcome.
- Balances six vulnerability families (spatial and temporal memory errors, invalid pointer access, invalid free, type errors, initialization errors) across three complexity levels, compiled under realistic build settings and validated against ground-truth PoCs.
- Separately measures how much the patched binary helps and what happens when standard binary hardening is enabled.

### Evaluation
- Evaluated OpenAI Codex (GPT-5.6), Claude Code (Claude Opus 5), and Kimi Code (Kimi K3). Vulnerability recovery rates were 88%, 85%, and 64%; exploitation rates were much lower at 20%, 6%, and 0%.
- On a 20-task subset, giving Codex the patched binary raised its exploit rate from 10% to 25%.
- With stack canaries, PIE, full RELRO, and Fortify all enabled, Codex still exploited 2 of the 20 tasks it had previously solved.
- Per-task cost and runtime are reported; average cost in the patched-binary condition was about 31 USD.
- The main experiments ran under trusted-access programs with safeguards disabled, so results may differ from what ordinary users of these products can do.

#### Comment
- A collaboration between NUS, UC Riverside, UC Berkeley, and UC Santa Barbara, with well-known researchers including Dawn Song, Heng Yin, and Wenbo Guo.
- The conclusion is that finding the bug is already largely within reach while turning it into a working exploit remains unreliable. As that gap closes, slow patch rollout becomes more dangerous, which makes this a meaningful warning for defenders.
- We could not confirm from the paper whether the benchmark is publicly released.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Coding Agents Propagate Vulnerabilities in Code Bases
> arXiv preprint (not peer reviewed)
> 2026

Coding agents explore a repository and use existing code as reference when writing new code. This paper tests whether vulnerable code already in the repository leads agents to reproduce the same vulnerabilities. It uses 96 tasks that require implementing a new backend application alongside existing ones, and 20 task pairs in real C/C++ projects where the agent must complete memory-safety-critical code, comparing outcomes when the surrounding code is secure versus insecure.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.11455
- arXiv HTML full text: https://arxiv.org/html/2611.11455
- arXiv PDF: https://arxiv.org/pdf/2611.11455
- Author code repository: https://github.com/eth-sri/vulnerability-propagation

### Contribution
- First empirical study of how codebase security evolves as coding agents contribute to it.
- Two complementary setups, a controlled one (backend generation) and a realistic one (real C/C++ repositories), that hold the task fixed and vary only the security of the surrounding code.
- Also examines how prompting strategies change the effect and whether agents recognize the vulnerabilities they introduce.

### Evaluation
- Backend tasks come from 24 AutoBaxBench scenarios covering seven CWE classes (CWE-20, 22, 78, 79, 89, 522, 863), with security judged by running real exploits.
- GLM 5.3, Claude Opus 5, and GPT-5.6 Sol were tested in both settings; Claude Opus 5.5 and GPT-6 Astra were added for the memory-safety tasks.
- Insecure neighboring applications lowered the share of correct and secure backend implementations by 3.4% on average. In the C/C++ tasks, the gap between secure and insecure reference code averaged 35.4%, reaching 49.0% for one model.
- Telling the agent to follow existing code style made propagation worse, and telling it to be careful about security made it better, but neither stopped it.
- When asked why they wrote the code that way, agents pointed to another code site in 76.5% of cases; when asked whether it was vulnerable, they recognized the vulnerability in 69.9% of cases.

#### Comment
- From Martin Vechev's SRI lab at ETH Zurich, extending the group's BaxBench line of work. Code is public.
- The key finding is that agents can spot the flaw yet copy it anyway. As agent adoption grows, existing vulnerabilities need to be fixed first or the same patterns will spread.
- With only 20 C/C++ task pairs, the large gap figures may depend on how the tasks were chosen.
- Full text source: arXiv PDF (downloaded on the user's computer).

# When Experience Becomes a Backdoor: Poisoning Self-Evolving LLM Agents via Failure-Aware Task Optimization
> arXiv preprint (not peer reviewed)
> 2026

This is a backdoor attack on self-evolving agents, which distill their execution experience into skills they reuse later. The attacker cannot edit skill files and can only slip tasks into the evolution set; the agent then plants the backdoor rule into its own skills while learning from those tasks. The authors first show that refining poisoned tasks based only on end-to-end success works poorly, then propose BadEvolve, which diagnoses failures in four stages (was the rule induced into a skill, was the skill activated, was the rule followed, did it have the intended effect), rolls back harmful updates, and keeps a memory of failed attempts so they are not repeated.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.10542
- arXiv HTML full text: https://arxiv.org/html/2611.10542
- arXiv PDF: https://arxiv.org/pdf/2611.10542
- Author code repository: https://github.com/ventr1c/BadEvolve

### Contribution
- Introduces a realistic "task-level backdoor" threat model in which the attacker injects tasks rather than editing skills.
- Explains why outcome-only optimization fails: failures at different stages look identical, and optimization is unstable.
- Combines stage-wise feedback, rollback, and failure memory to raise attack success reliably.

### Evaluation
- Evaluated on SpreadsheetBench, WikiTQ, and OfficeQA with four self-evolution frameworks (Trace2Skill, SkillGrad, SkillOpt, A-Evolve) and four backbones (Kimi-K2.5, GPT-OSS-120B, Claude Sonnet 4.6, Qwen3-235B), averaged over three runs.
- For payload injection, BadEvolve's average attack success rate was 79.6% (range 59.3% to 100%), well above TBA (37.6%) and TextGrad-Poison (27.8%), while clean-task accuracy was only 1.1 percentage points below the unpoisoned baseline.
- For answer corruption (WikiTQ, A-Evolve), conditional success rates were 80.0% on Kimi-K2.5 and 54.1% on Claude Sonnet 4.6, versus 68.5% and 18.0% for the best baselines.
- Transfer across surrogate models was also tested, but the default setting is favorable to the attacker: the surrogate shares the victim's framework and backbone.

#### Comment
- A Penn State and Microsoft collaboration. Code is public.
- There are no defense experiments; the authors leave them to future work. Read it as an attack paper showing the need to verify where evolution tasks come from and to audit changes to skills.
- Full text source: arXiv PDF (downloaded on the user's computer).

# StealthyPoison: Manipulating LLM Agent Behavior through Procedural Poisoning of Third-Party Skills
> arXiv preprint (not peer reviewed)
> 2026

This attack targets third-party skills in public registries. Earlier skill-poisoning attacks add overtly malicious behavior, such as running unnecessary commands, which scanners can catch. StealthyPoison leaves the skill's advertised function and normal execution intact and quietly alters only the decision-critical parts of the procedure, such as formulas, thresholds, and decision rules, so the agent produces wrong answers. Without access to real user requests or answers, it synthesizes requests from the target skill, runs the clean skill with a surrogate agent to get reference outputs, and refines the poisoned procedure against them. It also enriches the skill's metadata so it ranks above the benign original in retrieval.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.12155
- arXiv HTML full text: https://arxiv.org/html/2611.12155
- arXiv PDF: https://arxiv.org/pdf/2611.12155
- Author code (anonymous repository): https://anonymous.4open.science/r/skillpoison-BC93

### Contribution
- Introduces "procedural poisoning", which corrupts outcomes by changing the procedure itself rather than adding malicious actions.
- Shows how to build reusable poisoned procedures from a public skill alone, with no user requests or ground truth.
- Demonstrates experimentally that existing pre-execution scanners almost never catch this kind of attack.

### Evaluation
- 566 target skills and 5,244 requests (MedCalc, TheoremQA, CHAMP, LogicBench, BigCode, ToolQA and others) against more than 26,000 registry entries.
- Top-1 retrieval placement rose from 15.8% without optimization to 30.0%, a 13.6% relative improvement over HotFlip and GCG.
- Payloads built with a single surrogate transferred unchanged to three other models (Llama-3.3-70B, Mistral-Small-24B, GPT-OSS-20B) with average attack success of 31.0% to 31.9% (32.9% on the surrogate).
- In a full retrieval, selection, and execution workflow in Claude Code with Opus 4.8, end-to-end attack success was 10.1%, ranging widely from 38.3% on MedCalc to 0.8% on CHAMP.
- Detection rates were 0.7% for SkillSpector, 0.4% for Cisco Skill Scanner, and 0.0% for VirusTotal; GPT-5.4-mini as a judge reached 45.8%.

#### Comment
- A collaboration between the University of Amsterdam, Leiden University, and Johns Hopkins University. The paper is typeset in WWW '27 format but has no acceptance notice, so we treat it as an unreviewed preprint.
- End-to-end success in a real agent workflow (10.1%) is far below the oracle setting and varies a lot by domain. Medical calculation, where formulas are explicit, stands out as especially vulnerable.
- The authors argue that package inspection is not enough and that behavioral checks against reference requests or trusted implementations are needed.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Mirage: Provable Defense Against LLM KV Cache Timing Side Channels with Topology-Aware Isolation
> arXiv preprint (not peer reviewed)
> 2026

Multi-tenant LLM services reuse the KV cache when prompts share a prefix, which returns the first token faster. By measuring this time-to-first-token (TTFT) difference, an attacker can guess other users' prompts. Existing defenses partition the cache per user or isolate sensitive entries, giving up the benefit of sharing. Mirage keeps sharing the cache on the GPU at full speed and instead delays token emission at the gateway so the attacker sees what looks like a cache miss. It tracks, over time, how many novel branches fan out from each prefix (the signature of guessing attacks) and applies delay only to prefixes that cross a threshold.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.10756
- arXiv HTML full text: https://arxiv.org/html/2611.10756
- arXiv PDF: https://arxiv.org/pdf/2611.10756

### Contribution
- Triggers the defense on the attacker's probing behavior rather than on how sensitive the content looks.
- Because the delay is applied at the gateway rather than on the GPU, cache reuse and throughput are preserved. The whole streaming response is shifted together, avoiding bursts of buffered tokens.
- Proves an information-theoretic lower bound on what the attacker can learn, and states that the guarantee weakens if its assumptions break.

### Evaluation
- Implemented in SGLang and evaluated on Qwen1.5-1.8B, Llama-3-8B, and DeepSeek-14B against three attacks (EarlyBird, InputSnatch, OptiLeak), compared with no defense, cache partitioning, CacheSalt, and SafeKV.
- Undefended, EarlyBird reached 92.4% on DeepSeek-14B and OptiLeak 67.6% to 81.8%. With Mirage, OptiLeak dropped to 0.0%, EarlyBird to 0.0% to 0.2%, and InputSnatch to 0.4% or less, on par with isolation defenses.
- Median TTFT for public traffic stayed within 1.5% of the undefended baseline (55.2 ms vs. 54.4 ms), while isolation defenses increased it by 44% to 46% on DeepSeek-14B. On Llama-3-8B Mirage sustained about 1.6 times the throughput of isolation.
- A benign user's first sensitive access is served in about 150 ms, with roughly 418 ms of padding applied only during an attack. All headline numbers come with 95% bootstrap confidence intervals.
- Includes experiments with an adaptive attacker and an extension to semantic caching layers.

#### Comment
- From Tianwei Zhang's group at Nanyang Technological University. We could not confirm from the paper whether code is released.
- The evaluation corpus has only 500 public samples, and the guarantee depends on the trigger not misfiring. The authors acknowledge it can weaken if an attacker spreads probes across many prefixes.
- Full text source: arXiv PDF (downloaded on the user's computer).

# ML Models Are Not Ciphers: Power Analysis for Weight Extraction Is Harder Than You Think
> arXiv preprint (not peer reviewed)
> 2026

Earlier work showing that power analysis (CPA) can extract neural network weights from edge devices mostly recovered a few early layers or used untrained models. Assuming an idealized, noise-free simulated attacker, this paper shows that recovering a full trained model is fundamentally different from recovering a cryptographic key. Neural networks use floating-point arithmetic and low-diffusion linear operations, and data variability shrinks as computation moves deeper, making it hard to tell weight candidates apart.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.12532
- arXiv HTML full text: https://arxiv.org/html/2611.12532
- arXiv PDF: https://arxiv.org/pdf/2611.12532
- Author code repository: https://github.com/Mohammedq-cs/cpa-weight-extraction

### Contribution
- Identifies and quantifies two fundamental obstacles that do not arise in attacks on ciphers: shrinking entropy, and candidate collisions caused by precision loss in floating-point addition.
- Shows that choosing inputs from the data distribution the model is meant to handle increases variability in deep layers, and that the Hamming distance leakage model suits this setting better than Hamming weight.
- Shows that aiming for an approximate model with similar accuracy, rather than exact weights, cuts the number of traces needed dramatically.

### Evaluation
- A simulation framework using CIFAR-10 and CIFAR-5M data, targeting an 8-layer CNN, VGG-11, and ResNet-18.
- Without noise, full AES key recovery needed fewer than 10 traces, while even a simple network needed more than 150,000.
- For approximate models, the 8-layer CNN needed 5,000 traces, VGG-11 needed 20,000, and ResNet-18 was not recovered even with 200,000. Required traces grew exponentially with depth and correlated weakly with total parameter count.
- A little noise raised the requirement by two orders of magnitude; at a realistic signal-to-noise ratio, extracting just the first layer took more than ten million traces.
- Using simulation instead of real measurements is a deliberate choice to isolate fundamental obstacles from measurement issues.

#### Comment
- A collaboration between Tel Aviv University, Radboud University, the University of Amsterdam, and Ruhr University Bochum, including leading side-channel researchers Lejla Batina, Eyal Ronen, and Yuval Yarom. Code is public.
- It reads as a reality check on claims that models can be stolen through power analysis. That said, approximate models can still serve as surrogates for crafting adversarial examples, so the risk is not zero.
- Full text source: arXiv PDF (downloaded on the user's computer).

# ShadowBench-MCP: Measuring Shadow Invocations in MCP-Style Tool Routing
> Presented at USENIX Security 2026 according to the authors (a 5-page short paper that looks like a poster), arXiv preprint
> 2026

Even a benign request with no malicious instruction can push an LLM router onto a riskier execution path when it carries operational pressure such as "use the fastest path", "skip validation", "deploy directly", or "defer the audit". The router may then drop safety tools like validation, provenance checks, staging, and audit logging. The authors call this a "shadow invocation" and build a benchmark and metrics that separately measure task preservation, operational pressure, and route change. They also show the risk can be detected from the route alone, before any tool runs.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.11720
- arXiv HTML full text: https://arxiv.org/html/2611.11720
- arXiv PDF: https://arxiv.org/pdf/2611.11720

### Contribution
- Formalizes a routing-layer security failure distinct from prompt injection: the attacker changes only the wording of the request, not tool descriptions or configuration.
- Proposes metrics that measure task preservation, operational pressure, and route geometry separately, plus a pre-execution score that multiplies them.
- Shows that an explicit safety policy sharply reduces shadow invocations, and lays out the trade-off between detection coverage and review burden.

### Evaluation
- One router (qwen/qwen3-32b hosted on Groq), six security-sensitive workflows, five request styles, two policies, and two repetitions, for 120 routing decisions and 96 comparison pairs.
- Under efficiency-first routing, the shadow-invocation rate was 29.2% and the required safety-tool skip rate 26.7%; with a safety policy these fell to 4.2% and 1.7%.
- Pre-execution signals separated shadow routes with ROC AUC up to 0.94.
- Consensus replay blocked 8 of 14 shadow routes with 100% precision; policy-constrained routing blocked all 14 but flagged 43.8% of pairs for review.
- The authors themselves cite a single router, a small sample, and non-independent pairs as limits and make no general claims.

#### Comment
- From the University of Washington. The claims are narrow and the limits clearly stated, but with such a small sample the paper matters more as a problem statement than for its numbers.
- The "presented at USENIX Security 2026" note notwithstanding, the length suggests a poster or similar short presentation rather than a full paper, so it should not be treated as having full-paper review.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Tracing MCP Security Vulnerabilities: Constructing and Analyzing an MCP Security Vulnerability Dataset
> 2026 IEEE Symposium on Security and Privacy Workshops (Data4SoftSec), DOI 10.1109/SPW72489.2026.00047, abstract-only summary, full text not read
> 2026

According to the authors, information about MCP vulnerabilities is scattered and noisy because of acronym collisions, so they collected 119 MCP-related CVE records (through February 2026) and filtered them down to a validated set of 24. They report that 87.5% are rated Critical or High and that injection and path traversal account for 66.7%. Six case studies illustrate common exploitation patterns and map them to defenses, and the authors say they release the dataset, reproduction tooling, and a maintenance workflow.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.11104
- arXiv HTML full text: https://arxiv.org/html/2611.11104
- arXiv PDF: https://arxiv.org/pdf/2611.11104
- IEEE DOI: https://doi.org/10.1109/SPW72489.2026.00047
- Author dataset (Hugging Face): https://huggingface.co/datasets/XuViewer/mcp-vulnerability-dataset

### Contribution
- The authors claim a curated dataset for systematic study of MCP vulnerabilities, a filtering method that handles acronym ambiguity, and a sustainable maintenance workflow.

### Evaluation
- From the abstract: 24 of 119 records validated, 96.7% inter-rater agreement on a sampled exclusion audit, all known high-severity MCP cases from public advisories retained, 87.5% Critical or High, injection and path traversal at 66.7%.
- Because we could not read the full text, we could not verify the dataset, comparison conditions, or the reliability of the metrics.

#### Comment
- Credibility signals: published at an IEEE S&P workshop (Data4SoftSec) with an IEEE DOI, and a public dataset link (the comment field says it is maintained beyond the original snapshot).
- With only 24 records, the percentages should be taken as indicative.
- Why the full text was not read: a full-title search (extended) found no public full text outside arXiv, and a GitHub repository search found nothing relevant. This run's arXiv download budget (10 papers) went to higher-priority papers.
