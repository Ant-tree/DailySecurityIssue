# DERED: Enhancing Third-Party Library Detection in Binaries via Deceptive Reuse Mitigation
> Published in Computers & Security (Elsevier), based on the ScienceDirect article page found by web search; posted as arXiv cs.SE, cross-listed to cs.CR 2611.00574. Beijing University of Posts and Telecommunications and Zhongguancun Laboratory, China
> 2026

Detecting third-party libraries (TPLs) inside binaries is how analysts trace which software a vulnerability has spread to. Existing detectors declare "reuse" whenever two binaries share similar functions or code regions, without considering the direction of reuse. For example, minizip reuses zlib and bzip2, and lzbench uses the same libraries, so minizip and lzbench share code even though neither reuses the other. The authors call this "deceptive reuse" and point out that it causes false positives in vulnerability reports.

DERED separates real from deceptive reuse in three stages. It first finds homologous functions with a lightweight Markov-matrix encoding and a CNN. It then aligns homologous code regions by applying a GCN to function call graphs annotated with export information. Finally, it quantifies topological differences between the aligned regions, specifically the centrality and connectivity of functions relative to exported interfaces, to decide whether code really flowed in one direction.

### Contribution
- Defines "deceptive reuse," the false-positive problem caused by conflating code matching with code reuse.
- A tool that performs reuse discrimination and library detection together, through function matching, region alignment and topological difference analysis.
- A dataset of deceptive reuse cases and a public artifact.

### Evaluation
- Data: from reuse relationships in the Conan repository, 83 projects involved in more than three reuse relationships were selected and built into 572 binaries.
- Baselines: existing library detectors ISRD, LibDB, LibAM and LibDI, plus the commercial software composition analysis tool BinaryAI in a case study.
- Results: F1 of 96.9% for reuse discrimination and 97.7% for library detection, beating the strongest baseline, LibDI, by 12.6% in precision, 5.5% in recall and 9.2% in F1. LibAM scored 76.8% precision, 91.2% recall and 83.4% F1. The ROC AUC was 0.989, and average F1 across architectures and compiler optimization levels was 92.9% and 92.0%.
- Reliability of the metrics: the authors built the dataset themselves and it is modest (83 projects), so the numbers may fit this data particularly well. The baselines were not designed to handle reuse direction, so a large gap on data rich in deceptive reuse is partly expected.

#### Comment
- A useful angle for practitioners who judge vulnerability impact through binary composition analysis: cutting false positives caused by shared libraries. Identifying open-source libraries bundled in app or SDK binaries faces the same problem.
- Limitations: robustness to obfuscation or deliberate code changes was not addressed in the parts read, and the data is limited to Linux C/C++ projects built with Conan.
- Venue: Computers & Security is a reputable security journal published by Elsevier. The arXiv manuscript is marked "Preprint submitted to Elsevier," and the authors' repository describes itself as the artifact for a paper submitted to ACSAC 2025, so the manuscript appears to have been submitted elsewhere earlier. Whether the journal version matches the arXiv manuscript was not checked, since the journal full text was not opened.
- Verification of a Chinese-institution paper: all authors are at Beijing University of Posts and Telecommunications and Zhongguancun Laboratory. The venue is a real, reputable journal, and the artifact repository has been public since 2025. The baselines are existing binary library detectors addressing the same problem, which is appropriate. F1 above 97% on a self-built dataset is high, though, and should be read with the caveats above.

# Trouble With Time: Compile Timestamps and First-Seen Date Regression in EMBER2024
> CAMLIS 2026 (Conference on Applied Machine Learning for Information Security), Proceedings of Machine Learning Research volume 349; posted as arXiv cs.CR, cross-listed to cs.LG, 2611.01031. CrowdStrike (USA)
> 2026

Evaluating a malware detector fairly means testing it on files that appeared after its training data, which in turn requires knowing when each file was first seen. That date usually comes from the first-submission date of an external service such as VirusTotal, which not every researcher can access on equal terms. Using the PE/COFF compile timestamp inside the executable would be convenient, but nothing enforces its accuracy, and industry wisdom holds that malware authors tamper with it.

The CrowdStrike authors turn this practitioner folklore into explicit research questions and test them on EMBER2024: how reliable are timestamps, can wrong ones be identified, can machine learning estimate or correct the first-seen date, and are there indicators of inaccurate timestamps? They try many formulations with feature-based XGBoost and raw-byte MalConv2 models: threshold classification, ordinal classification, signed-delta regression, absolute-date regression, learning to rank and a Bayesian latent-reliability model.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.01031
- arXiv HTML full text: https://arxiv.org/html/2611.01031
- arXiv PDF: https://arxiv.org/pdf/2611.01031

### Contribution
- Shows with data that timestamp disagreement is not only a malware problem. Files "from the future," compiled after they were first seen, and clearly wrong values such as zero or dates before 1995 occur at substantial rates in both benign and malicious files; malicious files merely tend to have larger gaps.
- Establishes a negative baseline across several methods: current models can neither estimate first-seen dates directly nor sort files into a useful chronological order.
- Shows, in contrast, that "is the timestamp within some window of first seen?" and "is it obviously wrong?" can be answered with high accuracy, and proposes timestamp reliability as a research topic in its own right.

### Evaluation
- Data: the EMBER2024 training split of 2,339,221 PE/.NET rows, a regular test split of 539,869 rows, and 605 challenge rows first seen after the training period.
- Timestamp distribution: the median gap between compile time and first seen is 203.5 days for benign files and 3,157.3 days for malicious files, and the 95th percentile is about 19,800 days for both.
- Regression and ordering: the baseline that simply trusts the compile timestamp has a mean absolute error of 6,396.68 days, and the regression models also leave errors large relative to the collection window. When files are sorted by any model's score, the Spearman correlation with true first-seen order is at most 0.22. The Bayesian model ends up falling back on the compile timestamp itself.
- Threshold classification: classifiers predicting whether a timestamp is within 30, 60, 90 or 180 days of first seen reach AUCs of 0.97 to 0.98 on the regular test split even without the timestamp as input, and F1 scores of 0.86 to 0.94 with it.
- Obviously bad timestamps: labeling as positive any timestamp that is zero, more than a day after first seen, before 1995, in or after 2030, or repeated at least 1,000 times, a classifier using only the 2,567 timestamp-free features reaches an AUROC of 0.9943 (0.9970 on the challenge split). The authors note that F1 is low relative to AUROC, pointing to a calibration problem.
- Reliability of the metrics: a large public dataset and time-based splits make the results easy to reproduce. Constraints acknowledged by the authors include that the first-seen date itself is an upper bound derived from VirusTotal observation, so the "ground truth" has error too, and that some loss-function differences were not ablated for reasons of compute time.

#### Comment
- For researchers who want to evaluate malware detectors on time-based splits, the paper offers grounds not to use compile timestamps as a stand-in for dates, along with a practical takeaway that an "obviously bad" filter is worth applying. The finding that timestamp anomalies are common in benign software also matters for detection rules that treat timestamp tampering as a malicious indicator.
- Limitations: only Windows PE/.NET files and the EMBER2024 collection window are covered, and the authors conclude that longer time spans or extra signals such as toolchain identification are needed.
- Venue: CAMLIS is a peer-reviewed conference on security machine learning, and the paper appears in PMLR volume 349. The first author, Edward Raff, is also an editor of these proceedings, so the independence of review depends on how the conference handles that.
