# Revealing Semantic Gaps in Zero-Knowledge Virtual Machines via Obligation-Targeted Semantic Fuzzing
> Accepted at NDSS Symposium 2027 (the paper carries an NDSS 2027 DOI), also on arXiv. UC Santa Barbara, Shanghai Jiao Tong University, UC San Diego
> 2026

Zero-knowledge virtual machines (zkVMs) prove that a program written for an ISA such as RISC-V executed correctly, and they secure large amounts of value in blockchain rollups and similar systems. Their security depends on the ISA specification and the constraint system (the polynomial equations that check the prover's record of intermediate values, the witness) lining up exactly. Mismatches, which the authors call semantic gaps, come in two kinds: underconstraint bugs, where loose constraints let a malicious prover forge a proof of an execution the ISA forbids (a soundness violation), and divergence bugs, where the zkVM itself deviates from the ISA or crashes so an honest prover cannot prove a legitimate run (a completeness violation). Both cluster at corner cases such as division by zero, and underconstraint bugs do not change program output, so ordinary fuzzing does not see them. The authors derive 60 constraint obligations from the ISA specification and the proof system's algebraic structure and plug them into three otherwise random decisions of a reinforcement-learning fuzzer (initial inputs, reward and where to tamper with the witness), producing Beak.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.29260
- arXiv HTML full text: https://arxiv.org/html/2611.29260
- arXiv PDF: https://arxiv.org/pdf/2611.29260
- NDSS 2027 DOI: https://dx.doi.org/10.14722/ndss.2027.232037
- Author repository (code): https://github.com/whbjzzwjxq/beak-fuzz

### Contribution
- Defines each obligation as a triple (input-building template, activation predicate, witness injection template) that is derived once and reused across six zkVMs.
- Replaces executor code coverage with "did this run trigger a new combination of obligations" as the reward, and anchors witness tampering to the steps where an obligation fires, fixing the near-zero hit rate of blindly perturbing millions of witness values.
- Detects divergence bugs by comparing registers against a reference RISC-V emulator, and underconstraint bugs by checking whether the constraints accept a tampered witness. An underconstraint counts as detected only if the tampered witness goes through full proof generation and the zkVM's own verifier accepts the proof.

### Evaluation
- Targets: six production RISC-V zkVMs spanning four proof architectures (SP1, Pico, OpenVM, Risc0, Jolt, Nexus), pinned to fixed commits.
- Known-bug benchmark: 37 bugs (28 underconstraint, 9 divergence) gathered from ArguZZ reports, professional security audits and public issue trackers. Beak found 25 (67.6%), versus 5 (13.5%) for the prior state of the art, ArguZZ, and 3 (8.1%) for a generic random fuzzer. ArguZZ was rerun from its public artifact on the same hardware with the same time and core budget.
- Five repeated runs found 22, 23, 23, 18 and 24 bugs. Per-bug median detection times ranged from 0.7 seconds to 0.64 hours, with an overall median of about two minutes.
- Ablation: with all three hooks removed only the 9 divergence bugs were found; removing the input templates dropped detections to 16, and swapping the reward for code coverage dropped them to 19.
- New bugs: 14 previously unknown bugs in the latest development branches, all disclosed and patched.
- Reliability: the ground-truth benchmark was collected independently from outside sources and repeated runs are reported, so the comparison is fair. The 60 obligations are tailored to RV32IM, though, so other ISAs or new components need new hooks, and the authors say the 12 missed bugs require changing several components together.

#### Comment
- Using obligations derived systematically from a specification to steer a fuzzer could carry over to other targets where a specification must match an implementation, such as hardware.
- NDSS is a top-tier security venue. One co-author is at Shanghai Jiao Tong University, but the first and corresponding authors are at UC Santa Barbara, and the code repository was confirmed to be public.

# Verifying Declared AI Workloads from GPU Supply Current
> arXiv preprint (not peer-reviewed). School of Mathematics and Statistics, The University of Melbourne; Machine Alignment, Transparency & Security (MATS) program
> 2026

International agreements on AI compute need a way for an outside verifier to confirm that a hardware operator is not running prohibited work such as hidden large-scale training. Earlier studies had the verifier build labeled examples of permitted and prohibited work and train a classifier, which then has to transfer to other chips and only covers the evasions the verifier anticipated. The author proposes a signature check instead: with temporary access to the operator's hardware, the verifier records the current signature of the declared, permitted work (idle and inference) and later flags anything that departs from it. No examples of prohibited work or evasion strategies are needed.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.29982
- arXiv HTML full text: https://arxiv.org/html/2611.29982
- arXiv PDF: https://arxiv.org/pdf/2611.29982
- Author repository (code, results, paper PDF and TeX source): https://github.com/tomkimpson/verifying-declared-ai-workloads

### Contribution
- Shows with real measurements that GPU supply current, captured off-chip with a Rogowski coil, is an analog signal that can verify declared work without the operator's cooperation.
- Considers five evasion strategies for hiding prohibited training (including time-sharing with inference) and catches them with a one-class model fitted only to permitted work.
- Analyzes how incomplete or corrupt declarations fail: an incomplete recording fails loudly with constant alarms, while a recording into which the operator slipped training can fail silently.

### Evaluation
- Data: 23.4 hours of current recorded under idle, training and inference workloads on one NVIDIA H200 NVL. The training workload is a single 168M-parameter model.
- Results: at least 99.9% of prohibited-training windows were flagged, including those hidden by the five evasion strategies. As a continuous monitor it caught all 188 episodes of training hidden by time-sharing with inference (median delay 3.0 s) and raised one false alarm in 8.8 hours of declared work. With idle missing from the declaration, the monitor was in alarm for 99.97% of declared idle time.
- Reliability: as the author notes, detection of hidden training was measured on development data before the test day was scored, so only the false-positive rates and monitor results are truly held out. One GPU and one model is a narrow scale, and it is not clear the results carry over to training spread across many GPUs.

#### Comment
- An empirical study in the emerging security application of compute verification for AI governance. The numbers are very strong, but this is a single-GPU experiment and the author names scale as the main limitation.

# LaTSEC: Lattice-Based Threshold Signatures with Native Non-Interactive Identifiable Abort and Compact Per-Party Storage
> arXiv preprint (not peer-reviewed), also IACR ePrint 2026/2948. Monash University, Tampere University
> 2026

A threshold signature splits a signing key among n parties so that only large enough groups can sign. Post-quantum lattice-based threshold signatures that support identifiable abort, meaning misbehaving parties can be named, have needed zero-knowledge proofs, an extra interactive protocol, or a sharing scheme where each party holds many short sub-shares, each with its own public verification key. The last option inflates per-party storage. Using SEC, a recent ramp secret sharing scheme based on lossless expanders that gives each party one short share, the authors build LaTSEC, a three-round lattice threshold signature in which each party has a single signing share and a single public abort key.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.30063
- arXiv HTML full text: https://arxiv.org/html/2611.30063
- arXiv PDF: https://arxiv.org/pdf/2611.30063
- IACR ePrint: https://eprint.iacr.org/2026/2948
- Author repository (implementation and paper PDF): https://github.com/latsec-ts/latsec

### Contribution
- Each partial signature is checked directly against that party's public abort key, so misbehaving parties are identified without zero-knowledge proofs or an additional protocol.
- Proves correctness, identifiable-abort security and threshold unforgeability under standard MLWE and MSIS. For unforgeability it introduces a new problem, Repeated-A Matrix Hint-MLWE, which captures the correlated public abort keys, and proves a reduction from standard MLWE.
- Releases a Rust implementation (for performance) and a Python implementation that follows the paper's algorithm line by line (for test vectors).

### Evaluation
- Parameters: with 60 parties at 128-bit security, LaTSEC tolerates up to 6 corrupted parties, and a randomly chosen set of at least 46 parties can sign with probability at least 0.99 (an empirical estimate). Each party stores a signing share of about 14.3 KiB and is associated with a 24.0 KiB public abort key.
- Comparison: storage is compared with sDKG (replicated and ramp) and Hermine from the same family. Those papers give no parameters for n = 40 or 60, so their values are extrapolated from the sharing structure, and the authors state they are not security-validated parameter sets.
- Performance: on one core of an AMD Ryzen AI 9 HX 370 at n = 60, each signer spends 7.6 ms across the three rounds, combining takes 33 ms and verification 0.76 ms. Tests with tampered commitments, openings and partial responses blamed only the deviating signers.
- Reliability: the implementation is a research prototype that is not fully constant-time, uses a trusted dealer for key generation and runs all parties in one process, so real network latency is not reflected.

#### Comment
- Aimed at NIST's call for multi-party threshold schemes, this is relevant where lattice threshold signatures must fit memory-constrained devices. Co-author Markku-Juhani O. Saarinen is well known in post-quantum cryptography implementation.
- Parties that end up contributing nothing must still stay online through all three rounds, which is an operational constraint.
- The full text was read from the paper PDF in the author repository; its title, authors and key abstract figures match the arXiv abstract.
- Full text source: paper PDF in the author repository.

# SecretSifter: A Runtime Secret-Detection Engine for Live Web Traffic
> Published in SoftwareX 36 (2026) 103087 (open access; the arXiv copy is the version of record), also on arXiv. Independent security researcher (single author)
> 2026

Detecting exposed API keys and tokens has mostly been the job of scanners that walk source repositories and CI pipelines, such as TruffleHog and git-secrets. Those tools never see a credential that a bundler like webpack or Vite bakes into the build output, or one that a configuration API or server-side-rendered state object hands to the browser at runtime, because the value never appears in the repository. SecretSifter targets that gap by intercepting live traffic and scanning split JavaScript chunks, inline scripts, SSR state such as `__NEXT_DATA__`, JSON and XML bodies, and request and response headers in a single pass. One detection engine ships in three forms, a Burp Suite extension, a Chrome extension and a Windows and macOS desktop app, with a loopback REST and MCP server so an external LLM agent can triage findings.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.28168
- arXiv HTML full text: https://arxiv.org/html/2611.28168
- arXiv PDF: https://arxiv.org/pdf/2611.28168
- SoftwareX published article (DOI): https://doi.org/10.1016/j.softx.2026.103087
- SoftwareX article page: https://www.sciencedirect.com/science/article/pii/S2352711026005789
- Author repository (Burp extension, detection core): https://github.com/secretsifter/secretsifter-burp
- Author repository (build with MCP server): https://github.com/secretsifter/secretsifter-burp-mcp
- Synthetic demo target for reproduction: https://github.com/secretsifter/insecureshield-demo
- De-identified reproducibility bundle (Zenodo): https://doi.org/10.5281/zenodo.21695364
- OWASP project repository: https://github.com/OWASP/SecretSifter

### Contribution
- Combines 134 format-anchored vendor rules, 52 context-gated rules that fire only when a vendor keyword sits nearby, URL and database connection-string detection, key-name-driven generic key-value extraction with false-positive suppression (framework directives, CSS-module hashes, reCAPTCHA keys and so on), and Shannon-entropy scoring in one engine.
- Adds dedicated detection of hardcoded CryptoJS/AES ciphertext (`U2FsdGVkX1...`) together with the co-located key so it can be decrypted, a class that pattern-only tools miss.
- LLM triage is optional and off by default. The model only labels a finding as real or false positive, while deterministic rules set severity, so the risk rating does not shift with model output. When a remote model is used, only a value prefix and a bounded context window are sent.
- The detection core is MIT-licensed, and a synthetic demo target with no real secrets lets anyone reproduce the walk-through (29 HIGH findings on the demo).

### Evaluation
- Dataset: GT-198, 198 values collected from production JavaScript of 56 applications during one authorized engagement at a single organization. It contains 161 static values (51 APIM subscription keys, 33 Azure AD client secrets, 40 OAuth identifiers and others) and 37 CryptoJS-AES encrypted configuration blobs. Ground truth was extracted with Claude Opus 4.7, cross-checked with GPT-5.5 (89.9% high-confidence confirmation), and extended by a manual analyst pass.
- Baselines: TruffleHog, SecretFinder, JSluice, Titus, JS-Miner, Nuclei, Sensitive Discoverer and Cariddi, all in their default configuration.
- Results: SecretSifter found 158 of 198 values (79.8% recall) with 24 false positives (86.8% precision), for an F1 of 83.2%. The best static scanner, TruffleHog, reached 35.9% recall.
- Reliability: the author is unusually candid about limits. The benchmark comes from one organization, and the Azure APIM and CryptoJS rule classes that drive most of the lead were written with knowledge of that environment, so the numbers should be read as in-context detection rather than generalization. The paper also reports that once competing tools get a shared six-rule overlay, the strongest of them become statistically indistinguishable on static text. Because GT-198 contains real credentials it cannot be released, so third parties cannot reproduce the figures, and the comparison was not recomputed without the 40 OAuth identifiers.

#### Comment
- This is a software paper rather than a research paper, and the author says the contribution is the software itself. The measurement study of runtime exposure appears in a separate companion paper in IEEE Access.
- The developer and evaluator are the same single author, and the competing interest is declared. The numbers are useful as a reference, but the public synthetic demo and a trial in your own environment are a better test of practical value.
- SoftwareX is Elsevier's peer-reviewed software journal, and the arXiv copy states it is the version of record (CC BY 4.0).

# Anti OS Fingerprinting, Revisited: A Loadable Kernel Module for FreeBSD and What Twenty-Five Years Changed
> arXiv technical report (not peer-reviewed). National Graduate Institute for Policy Studies (GRIPS), Japan, single author
> 2026

Remote OS fingerprinting identifies a host's operating system from the fields its TCP/IP stack is free to fill in, such as TTL, window size and TCP option order. In 2001 the author published Anti OS Detection (AoD), a patched FreeBSD 4.3 kernel that answered Nmap probes as another OS. This report reimplements the same goal on FreeBSD 15.1 and records what has changed since. The author states plainly that no new method is claimed, and frames the work as a small, concrete case of the "Deception" technique that NIST SP 800-160 Vol. 2 lists among cyber resiliency techniques.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.28651
- arXiv HTML full text: https://arxiv.org/html/2611.28651
- arXiv PDF: https://arxiv.org/pdf/2611.28651
- Author repository (code and measurement scripts): https://github.com/daisu-mi/aod

### Contribution
- A loadable module of about 800 lines that needs no kernel source changes, using two pfil(9) packet filter hooks (inbound and outbound) and one kernel variable, with no per-connection state. The design rationale is that window size and initial sequence number come from the SYN cache shared by every TCP stack, so a packet hook is the right place to change them.
- Outbound, it rewrites TTL, DF, IP ID, SYN and SYN/ACK window, TCP option order, the timestamp option and window scale. Inbound, it answers or drops segments the imitated OS treats differently (no flags, SYN+FIN and so on). Linux (database-based and as-measured) and Windows 11 personalities are laid out in tables.
- The most useful part is a step-by-step record of what an Nmap-only check misses. After exact Nmap matches, p0f (passive) still caught the IP ID and timestamp option of SYNs the host sends, FIN and Xmas scans exposed FreeBSD-style silence on an open port, and comparison with a real Windows host showed that Windows does not offer timestamps on outgoing connections but accepts them on incoming ones, a behavior each of the two earlier personalities reproduced only halfway.

### Evaluation
- Setup: FreeBSD 15.1 under QEMU/KVM (8 vCPU, 8 GB), with real Ubuntu 26.04.1 (Linux 7.0) and Windows 11 Enterprise guests on the same host for comparison.
- Results: the final Windows personality and the real Windows 11 host got identical verdicts from Nmap 7.98, p0f 3.09b and JA4T, and every Nmap fingerprint line from OPS to IE matched. Because Nmap's database stops at Linux 6.0, the real Linux 7.0 host was not an exact match, while the personality built from the database was. The author calls it "more Linux than Linux" and notes that a host recognized too well may itself be a signal.
- Cost: differences in iperf3 throughput, connections per second and ping latency were smaller than the spread within each condition, and one hook invocation took 400 to 480 ns (378 ns on the early-return path).
- Reliability: the experiments are limited to one pair of virtual machines and two real OSes, with no large-scale testing on real networks. On the other hand, the raw verdict strings and measurements are published, mismatches included, which makes the results easy to check.

#### Comment
- A deliberately narrow report whose main lesson is about evaluation rather than the disguise itself: a disguise only holds up when several observers agree. Worth a look when reviewing the evaluation design of deception or moving target defense work.
- It also revisits the old warning that an imitated stack weaker than the original can make the system more vulnerable.
