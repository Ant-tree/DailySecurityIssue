# When POST Becomes GET: Investigating HTTP Method Interchangeability and Its Security Implications
> Accepted to the 42nd Annual Computer Security Applications Conference (ACSAC 2026, per the authors), public version on arXiv cs.CR. University of Trento (Italy)
> 2026

The HTTP distinction between GET for retrieval and POST for state changes underpins several defenses, including SameSite cookies, caching rules, and CSRF token checks. This paper presents the first large-scale measurement of "method interchangeability": moving a POST request's body parameters into the query string and sending it as a GET to the same endpoint yields the same result. Among the Tranco top 10,000 sites, 407 (4.1%) had requests that were interchangeable with high confidence; that is 12.7% of sites where POST requests were captured and 14.9% of sites where they could be replayed as GET.

Paper: https://arxiv.org/abs/2610.37474

### Contribution
- Catalogs the framework and API patterns behind interchangeability: frameworks that merge query and body parameters into one interface, routing that accepts every method unless the handler checks explicitly, and differences in array-parameter parsing.
- Builds MIDE, which crawls sites in a real browser, records POST requests from page loads, forms, and buttons, rewrites them as GET candidates, replays them, and compares responses. A parameter-free GET serves as a control so that endpoints returning the same page regardless of parameters are not miscounted as interchangeable.
- Shows two paths from interchangeability to real security problems: a CSRF token that is rejected on POST but accepted on the equivalent GET, and web cache deception, where the dynamic response of a rewritten GET gets cached under a static-looking URL. Code and configuration are open source.

### Evaluation
- Scale: 21,280 POST requests captured on 3,200 sites, 14,244 of them replayed as GET. 1,228 (8.6%) were interchangeable with high confidence (matching the POST but not the control), while 1,782 (12.5%) were ambiguous because the control matched too. Without the control, all the ambiguous cases would have been counted as interchangeable.
- Comparator validation: manual review of 30 high-confidence positives and 30 negatives gave a sample precision of 100% and a sample false-negative rate of 0%.
- Security impact: of 115 token-bearing requests, 7 on 2 sites bypassed CSRF validation via GET, and 56 requests on 9 sites produced cacheable dynamic responses.
- Reliability of the metrics: the control design and manual review keep false positives down. The manual sample of 60 is small, so the 100% precision should not be overgeneralized, and since crawling was unauthenticated and deliberately avoided state-changing actions, the true prevalence is likely higher.

#### Comment
- The authors are clear that interchangeability is not a vulnerability by itself. The risk arises when a defense assumes "this endpoint only takes POST" and misses the GET path. It gives a good reason, when auditing web applications, to declare allowed methods per route and to check that CSRF validation and caching rules apply regardless of method.
- The confirmed real-world cases are few (CSRF on 2 sites, caching on 9), and the impact analysis stays at the level of case confirmation.
- ACSAC is a long-established applied security conference with a strong reputation.

# SecDMP: Provably Secure Data Memory-Dependent Prefetching (Extended Version)
> Extended version of a paper accepted to the NDSS Symposium 2027 (per the authors), public version on arXiv cs.CR. KU Leuven DistriNet (Belgium)
> 2026

Data memory-dependent prefetchers (DMPs) treat values loaded from memory as potential addresses and prefetch them; they now ship in Apple, Intel, and Arm processors. As the GoFetch attack showed, a DMP can leave secrets in microarchitectural state even in constant-time cryptographic code. The available fixes are to turn the DMP off entirely or only during cryptographic code. This paper shows that selective disabling misses whole classes of leakage and proposes SecDMP, a hardware defense that stops the DMP from acting on data marked secret in memory. A formal model proves that SecDMP adds no leakage beyond a baseline semantics without a DMP.

Paper: https://arxiv.org/abs/2610.37454

### Contribution
- Classifies DMP leakage into five classes. Besides secrets the program actually loads, data can leak indirectly through neighbors in the same cache line, through transient (speculative) loads, and through data fetched by other prefetchers or by the DMP itself. Selective disabling only covers the first class.
- Implements DMPs modeled on commercial designs and academic proposals on the Proteus RISC-V research processor. The authors describe these as the first open-source DMP implementations and the first DMP proof-of-concept attacks on RISC-V, and reproduce every leakage class.
- Shows that combining SecDMP with the speculative-execution defense ProSpeCT restores full microarchitectural security for constant-time code. All artifacts are released.

### Evaluation
- Cost: 0.5% more chip area, no effect on the critical path, and an average performance overhead of 0.36% with a maximum of 3.3%.
- Benchmarks: DMP-Bench, 80 programs combining five HACL* primitives (ChaCha20, Salsa20, SHA-256, HMAC, HKDF) with general workloads (Embench, CoreMark, SpMV from HPCG, and a custom benchmark with the Intel DMP activation pattern). Disabling the DMP outright slows some workloads considerably, whereas SecDMP keeps prefetching public data and preserves their performance.
- Security: experiments confirm that secret leakage disappears across all benchmark programs.
- Reliability of the metrics: formal proof, hardware implementation, and experiments together make a strong case. The overhead comes from partitioning secrets into a separate memory region; secrets in the evaluated crypto code were annotated by hand, and for Salsa20 compiler-introduced stack spills were removed by patching the assembly. The measurements use DMPs modeled on a research processor, not real commercial CPUs.

#### Comment
- Starting from the observation that constant-time programming alone cannot keep up with optimizations like DMPs, the paper proposes a contract in which software marks secrets and hardware respects the marking. Since both mobile SoCs and desktop CPUs are adopting DMPs, it is a useful reference for future processor design.
- Limitations: automatically separating secret and public data on the heap and stack is left to follow-up work such as SecSep, and applying the approach to complex programs will need compiler support.
- NDSS is one of the top-tier security conferences.

# They Will See Johnny's Message: A Measurement Study of Post-Quantum Cryptography Across Email Delivery Paths
> arXiv cs.CR (preprint, not peer reviewed). University of Tennessee, Knoxville (USA), Kyung Hee University (South Korea)
> 2026

Defending against "harvest now, decrypt later" attacks means moving email to post-quantum cryptography (PQC). But submission, server-to-server relay, mailbox access (IMAP, POP3), and webmail each negotiate TLS separately, so PQC on one hop does nothing for a copy that crossed another hop with classical key exchange. The authors scanned mail servers tied to the Tranco top one million domains three times over four weeks and ran controlled tests on mail clients, sending providers, and OpenPGP and S/MIME implementations to assess PQC readiness along the whole email path.

Paper: https://arxiv.org/abs/2610.36145

### Contribution
- The authors claim the first study to measure server-side support, actual negotiation by both peers, and message-level encryption together.
- Experimentally separates capability from use. A receiving server that supports PQC does not get it unless the sender offers it, and restricting the receiver to PQC alone can actually push mail to plaintext.
- Builds a compatibility test corpus of 19 OpenPGP keys and six S/MIME certificates.

### Evaluation
- Server side (final snapshot): hybrid key exchange is supported by 33.1% of explicit-MX relays, 40.2% of submission services, 40.2-46.8% of access services, and 41.0% of webmail. Google accounts for about 87% of hybrid-capable relay domains and 96-97% of submission and access domains. Microsoft showed no PQC support at any measured endpoint, and filtering gateways such as Proofpoint and Mimecast were classical-only. In 417 domains the primary MX supports PQC but a backup does not, opening a downgrade path if the primary is blocked.
- Clients and senders: only two of eight sending providers negotiated PQC; Google, Yahoo, and Mailgun accept it inbound but did not offer it outbound. With the receiver restricted to PQC, four of the six incompatible senders delivered in plaintext. Postfix advertised a hybrid group but initially sent only a classical key share.
- Message level: none of the 27 client configurations generates a PQC key natively, and only three OpenPGP keys completed message exchange on both backends. For S/MIME, two of the four certificate stores that import ML-KEM certificates actually encrypt to them.
- Reliability of the metrics: large-scale domain scans are cross-checked against controlled experiments. Four weeks is too short to speak of trends, only eight sending providers were tested, and provider-internal hops could not be measured.

#### Comment
- It gives email administrators a ready checklist: enable PQC on every MX host, watch for filtering gateways in front as bottlenecks, and be aware that forcing PQC can lead to plaintext delivery.
- The observation that MTA-STS and DANE do not require PQC key exchange, so existing policies cannot prevent downgrades, is practical.
- This is a preprint with no venue listed. The measurement ethics are in order (Menlo Report principles, connection limits, an opt-out page).

# BUSTA: Teaching Small Language Models to Reason About Binary Execution
> arXiv cs.CR (preprint, not peer reviewed). The MITRE Corporation (USA)
> 2026

Reverse engineering often asks which input state produces a given execution result, and symbolic execution engines tend to hit path explosion and expensive constraint solving. This paper trains small language models with reinforcement learning (GRPO) on "inverse basic-block execution": given an x86-64 basic block and a desired output register state, predict the input register values. Isolated environments for analyzing malicious binaries often cannot call external commercial APIs, so the question is how close a small local model can get.

Paper: https://arxiv.org/abs/2610.36288

### Contribution
- Disassembles 100 Windows PE binaries from the Assemblage corpus with Ghidra into 287,137 basic blocks and records their execution under random inputs with the Unicorn emulator. angr marks registers whose input cannot be determined because different inputs yield the same output as "unknowable," separating values that cannot be recovered in principle from those that should be.
- Designs a reward function that combines value accuracy with accuracy in labeling registers as knowable or unknowable.
- Releases the two fine-tuned models and the training dataset.

### Evaluation
- The test set is separated from training at the function level and consists of 635 stratified samples.
- Accuracy on knowable registers rises from 73.2% to 85.3% for Qwen3-1.7B and from 63.3% to 95.2% for Nemotron-3-Nano. Token usage per response also drops by nearly half for Qwen3-1.7B.
- Comparison: GPT-5.5 scores 99.2%, Claude Sonnet 5 99.0%, GPT-5 98.3%, and Claude Opus 4.8 and Gemma-4-31B 98.1%. The open Gemma-4-31B beats BUSTA without any fine-tuning.
- Reliability of the metrics: sampling settings were tuned per model and results aggregated over several seeds, which helps fairness. But the task, predicting register values for a single basic block, is simple, and commercial models are already near saturation, so it discriminates poorly between real reverse engineering abilities.

#### Comment
- The value lies less in the numbers than in the question of whether small models for isolated analysis environments can be trained on specific reverse engineering skills. The data construction method is a useful reference for anyone putting local models into deobfuscation or malware analysis tooling.
- Limitations: 100 binaries, single basic blocks, registers only with no memory state. There is no evaluation of multi-block paths, whole-program reachability, or obfuscated code. The paper is only a few pages long.
- MITRE is a highly credible nonprofit research organization that runs CVE and ATT&CK, but this manuscript is a preprint with no venue.
