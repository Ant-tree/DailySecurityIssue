# CrossPloit: A Benchmark for Cross-Version PoC Migration in Python Web Applications
> arXiv preprint (not peer reviewed). Singapore Management University, Hanoi University of Science and Technology, Monash University
> 2026

This paper turns a practical question into a benchmark: are versions outside a vulnerability database's "affected versions" range actually exploitable by the same flaw, and can that be shown with running evidence? Given a proof-of-concept (PoC) exploit for a listed version, the task of adapting it to an earlier, unlisted version is called cross-version PoC migration. Starting from 217 CVEs in Django, Flask, FastAPI, Web2py and packages built on them, the authors rebuilt 97 reproducible reference PoCs, had two annotators independently attempt migration to earlier versions and reconcile the results, and arrived at 127 migration instances across 45 CVEs. Each instance comes with a version-pinned container, a reference PoC and a vulnerability-specific oracle, and two validators confirm that the oracle fires because the disclosed vulnerability was triggered.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.16588
- arXiv HTML full text: https://arxiv.org/html/2611.16588
- arXiv PDF: https://arxiv.org/pdf/2611.16588

### Contribution
- Executable confirmation of 149 vulnerable earlier versions missing from the affected-version lists of all four databases (NVD, OSV, GHSA, Snyk). Only 22 of them fall to the unmodified reference PoC, so an audit that simply re-runs published PoCs would find about one sixth of the exposure.
- A taxonomy of the changes migration requires (API changes, payload tuning, attack-vector shifts, dependency repair, configuration changes) and explicit rules that reject "illegitimate" migrations which revert or bypass the security fix.
- An evaluation of 18 LLM agent configurations (nine models in the OpenHands and SWE-agent harnesses) and a port of the trace-guided tool VulScope.

### Evaluation
- Results: the best configuration (OpenHands with Opus-4.6) resolved 74 of 127 instances (58.3%), while the VulScope port, limited to input mutation, resolved 11 (8.7%). No configuration resolved more than 37.9% of the instances that require an attack-vector shift.
- In one configuration, removing the reference PoC and environment specification dropped the resolve rate from 50.4% to 15.0%, showing how much the supplied materials matter.
- Failure analysis: stronger configurations had a smaller share of missed-API failures and a larger share of runs that found the right approach but did not finish executing it.
- Reliability: as the authors state, each configuration ran once, so run-to-run variance is unmeasured, and the benchmark contains only confirmed vulnerable versions, so false-positive rates as an auditing tool are not measured. The 149 figure is a lower bound, since versions that two annotators could not migrate within 60 minutes are excluded. We could not find a data release plan in the paper.

#### Comment
- Software composition analysis scanners and patch schedules all trust the database's affected range, so end-of-life branches become a blind spot for every defensive tool at once. As in the paper's Django 4.0 example, where the same routine is still quadratic through a different branch, re-running the reference PoC cannot find these cases.
- The authors state in their threat model that the same tooling can help attackers extend n-days to deployments believed to be out of scope.

# IoTPwnBench: A Synthetic Benchmark for IoT Firmware Security Analysis
> arXiv preprint (not peer reviewed). IMT School for Advanced Studies Lucca, SnT University of Luxembourg, University of Genoa, KU Leuven
> 2026

IoTPwnBench is a large set of synthetic firmware images whose weaknesses are fixed in advance, built so that IoT firmware analysis tools can be compared fairly. It starts from the problem that real product firmware has poorly documented defects and is hard to run without its hardware, which makes it unclear what a tool should be expected to find. The benchmark combines 11 device profiles, including a router, IP camera, PLC, health monitor and door lock, with 86 weakness scenarios to produce 716 vulnerable images, and pairs each one with a corrected twin that keeps the same device and service but removes that weakness. Each device exposes simulated sensor and actuator values over HTTP, MQTT or Modbus/TCP, so dynamic analysis tools face live, changing device state.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.15316
- arXiv HTML full text: https://arxiv.org/html/2611.15316
- arXiv PDF: https://arxiv.org/pdf/2611.15316
- Authors' repository (benchmark, build workflow, scenario docs): https://github.com/Mobile-IoT-Security-Lab/IoTPwnBench

### Contribution
- 716 vulnerable images and 716 corrected twins covering 28 CWE classes, each vulnerable image shipped with its primary CWE, an exploitation payload and an observable signal confirming the weakness fired.
- Corrected twins let a report of the same weakness on the fixed image be scored as a false positive, and the ground truth never relies on the evaluated tool's verdict.
- A Yocto 6.0.3 build that produces Linux kernels and ext4 filesystem images for five QEMU machines (arm64, arm, x86-64, x86, mips), verified to rebuild bit for bit from the same sources.

### Evaluation
- This is a dataset paper and contains no measurements of existing analysis tools. The authors describe the use cases as ones the design supports, not ones already reported.
- Validation: every image was booted under QEMU, its payload triggered by hand and the observed signal compared with the documented one, fixing and rechecking modules when they differed. Machine-readable ground-truth files exist for only 21 of 56 modules.
- Skew: authentication, credential and cryptography images make up 392, more than half, while memory-safety errors account for only 49. The 86 scenarios are variants of 56 modules, and the authors themselves note that the image count overstates the number of independent weaknesses.

#### Comment
- Its main value is letting static analyzers, fuzzers and rehosting-based dynamic frameworks be scored against the same ground truth. Because a weakness can be held fixed while the device, interface or architecture changes, studies can isolate what actually drives detection.
- On the other hand, the weaknesses are designed rather than collected, so they do not reflect real-world prevalence, and only Linux-based images are included, leaving microcontroller and RTOS firmware out of scope. Since the images are intentionally vulnerable, 517 of them build only with an explicit opt-in flag.

# Beyond the Diff - VulSpot: A Vulnerability Dataset Where No Vulnerability Goes Unlocalized
> arXiv preprint (marked as under review, 5 pages). University of Mons
> 2026

This paper identifies why real-world vulnerability datasets used to train and evaluate detectors tend to flatter them, and presents a "living" dataset that addresses those issues. The problems it names are datasets built once and never refreshed, wrong labels caused by commits that mix security fixes with unrelated changes, splits that put near-identical code in both training and test sets, and empty vulnerability locations when a fix only adds code, such as a missing NULL check. VulSpot links code added by a patch to the existing statement it protects through data flow (for example, the memcpy that uses an unchecked pointer), assigns a confidence tier to each label instead of discarding uncertain ones, and refreshes itself every month.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.15737
- arXiv HTML full text: https://arxiv.org/html/2611.15737
- arXiv PDF: https://arxiv.org/pdf/2611.15737
- Dataset (Hugging Face, listed in the paper): https://huggingface.co/datasets/ods01/VulSpot
- Authors' repository (listed in the paper): https://github.com/DynaSoumhaneOuchebara/VulSpot-Dataset

### Contribution
- 503,332 functions in 21 languages from about 24,000 CVEs, including 15,932 vulnerable C/C++ functions. Coverage runs to October 2026, allowing contamination-free evaluation on vulnerabilities disclosed after recent models' training cutoffs.
- Locations for 99.3% of the functions that earlier diff-based datasets left without one. Additive fixes are especially common for NULL dereferences (39.6%) and memory leaks (42.3%), so dropping them biases evaluation against the most frequent C/C++ weaknesses.
- Label confidence tiers (high, medium, low) computed without LLMs, provenance types for negatives, chronological and project-holdout splits that respect near-duplicate groups, AST-extracted context such as callees and macros, and four hierarchical CWE views.
- An observation that since the Linux kernel became a CVE Numbering Authority in 2024, 75.1% of vulnerable C/C++ functions come from the kernel, with a balanced variant and a non-Linux test set to control for it.

### Evaluation
- As a dataset paper it has no detector experiments, only statistics and construction details. The authors plan to publish baselines with each release.
- Localization quality: for functions that previously had empty labels, the most reliable anchor comes from a strong rule (such as a guard and the use it protects) in 54.5% of cases, a weak shared-identifier rule in 27.7% and a positional fallback in 7.6%.
- Reliability: the confidence tiers and anchor rules have not been manually audited yet, which the authors leave for future work. CWE labels are taken from NVD as is, and multi-commit fixes are excluded. The 99.3% figure is the share of functions that received an anchor candidate, not an accuracy rate.

#### Comment
- Instead of PrimeVul-style strict filtering, which raises precision but discards real vulnerabilities, the design marks reliability and lets users choose their own precision and coverage trade-off, which is practical.
- The point that kernel CVE growth turns any freshly collected C/C++ dataset into a de facto Linux benchmark is worth keeping in mind when reading recent vulnerability detection results.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Browser Immune System (BIS): Innate and Adaptive Threat Detection in the Browser with a Cybersecurity Transformer
> arXiv preprint (not peer reviewed). Alias Robotics, independent researcher
> 2026

BIS is a browser extension that keeps web page security decisions on the user's machine by running a 4-billion-parameter cybersecurity transformer, quantized to 4 bits, on WebGPU. The model (alias-web) is built from the authors' previously released alias3-micro and compiled to a 2.44 GB graph, and it answers a typed security question in about 150 ms on a laptop GPU. The extension borrows the immune-system metaphor: an "innate response" asks one yes/no question per threat class on every page, chosen by the kind of observation, and an "adaptive response" uses the same weights to generate an explanation only when the user asks. The content script only reduces the page to observations and contains no detection logic.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.15302
- arXiv HTML full text: https://arxiv.org/html/2611.15302
- arXiv PDF: https://arxiv.org/pdf/2611.15302
- Open weights alias3-web (Hugging Face, listed in the paper): https://huggingface.co/aliasrobotics/alias3-web
- Base model alias3-micro (Hugging Face, listed in the paper): https://huggingface.co/aliasrobotics/alias3-micro-1026

### Contribution
- What the authors describe as the first in-browser implementation of a cybersecurity language model's fast decision mode, with an architecture in which no page material leaves the device.
- A measurement showing that the same weights can also generate explanations (10.5 tokens/s) but at 6-39 times the cost of a single decision, which justifies generating text only after the fast path has flagged a problem.
- BISBENCH-8, eight synthetic sites (six that really execute credential exfiltration, keylogging, mining, an obfuscated dropper, scareware and fingerprinting, plus two adversarial controls), and a record of 25 engineering obstacles between the research checkpoint and a working extension.

### Evaluation
- Results: on BISBENCH-8 the page verdict matched expectations on 7 of 8 sites (the miner was missed), and both controls came back clean. Class-level micro-F1 was 0.71, page scans took 0.9-6.4 seconds, and verdicts were identical in Chrome and Firefox (Firefox was 5.9 times slower).
- Real web: on eleven public pages, two of the seven questions answered "yes" on ordinary scripts and login forms, and the authors name specificity on the real web as the open problem.
- Reliability: evaluation rests on eight sites the authors built themselves, so detection performance does not generalize, and there is no comparison with existing phishing or malicious-script detectors. All measurements come from a single Apple M3 Max laptop. The paper does deserve credit for reporting every error and listing what the evidence does not yet support.

#### Comment
- On-device security decisions that keep personal data local are a worthwhile direction, but the current state is closer to a proof of concept. The 2.44 GB download and false positives on the real web need to be solved before deployment.
- The model and the paper come from the same company, so the work should be read with its promotional aspect in mind.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Batch, Pack, and Prove: More Efficient Verifiable Computation for CKKS
> Full version of a paper accepted at ASIACRYPT 2026 (per arXiv comment, 92 pages), arXiv version. abstract-only summary, full text not read
> 2026

According to the authors, this paper makes verifiable computation over homomorphically encrypted (HE) data much more efficient for the CKKS scheme. Prior work (Cascudo et al., CRYPTO 2025) proposed succinct arguments for arithmetic circuits and range checks over the ring R_q, but left scalability problems: large polynomial commitment proofs, an O(N) overhead in range proofs, and no explicit method for verification sublinear in circuit size. The paper proposes a more efficient arithmetization of CKKS computations, a new polynomial commitment for R_q called BatchFold that supports batched evaluations, a packing technique that avoids committing to massive polynomials, and SparsePack, a protocol for proving evaluations of sparse, circuit-dependent polynomials.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.16922
- arXiv HTML full text: https://arxiv.org/html/2611.16922
- arXiv PDF: https://arxiv.org/pdf/2611.16922
- FHE.org 2026 talk slides (author's presentation): https://fhe.org/conferences/conference-2026/resources/slides/1440_Guimaraes.pdf
- Prior work, Verifiable Computation for Approximate Homomorphic Encryption Schemes (IACR ePrint 2025/286): https://eprint.iacr.org/2025/286

### Contribution
- The authors claim to remove all three bottlenecks of the prior work: proof size, the O(N) range-proof overhead and the lack of sublinear verification.
- They state that packing removes the O(N) range-proof overhead and that BatchFold yields shorter proofs.

### Evaluation
- According to the abstract, efficiency was evaluated on a generic neural network architecture, with proofs several orders of magnitude smaller and faster than prior approaches. The abstract gives no concrete figures.
- Because the full text was not read, the datasets, comparison conditions and reliability of the metrics could not be verified.

#### Comment
- Reliability signal: the arXiv comment "Full version of a paper accepted at ASIACRYPT 2026". ASIACRYPT is one of the three flagship conferences of the IACR.
- Why the full text was not obtained: title and author searches (both extended) returned, beyond arXiv, only the FHE.org 2026 talk slides and an author's publication list, and no paper PDF. A GitHub repository search found no repository for this paper. The arXiv download cap for this run (10 papers) had already been reached.
- Affiliation: the authors Ignacio Cascudo, Anamaria Costache, Daniele Cozzo, Dario Fiore, Antonio Guimarães and Eduardo Soria-Vazquez are established cryptography researchers, but their affiliations on this paper could not be checked without the full text (affiliation unverified).
