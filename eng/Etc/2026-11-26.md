# PORTA: Systematic Discovery of Vulnerabilities in Identity Brokers
> Published at ACM CCS 2026 (proceedings paper, CC BY 4.0 open access), also on arXiv. University of Toronto
> 2026

Identity brokers such as Keycloak, Vault and Dex verify an authentication proof from an upstream identity provider (a SAML assertion or an OIDC token) and turn the identity and authorization claims inside it into a session for downstream services. A single bug in a broker exposes every service behind it, and those services cannot notice because the original proof has already been replaced. The authors observe that a broker plays two roles at once, relying party upstream and identity provider downstream, which breaks the one-role-per-entity assumption built into authentication specifications. For instance, accepting a SAML assertion without NotOnOrAfter is correct for an ordinary relying party, but in a broker it lets an attacker strip the field and switch off the expiry check.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.33015
- arXiv HTML full text: https://arxiv.org/html/2611.33015
- arXiv PDF: https://arxiv.org/pdf/2611.33015
- ACM Digital Library (official paper page, DOI): https://doi.org/10.1145/3830454.3846557
- Research artifact (Zenodo): https://zenodo.org/records/22820164

### Contribution
- Five security invariants for brokers, derived from 40 normative requirements across eight SSO specifications and 60 past CVEs on ten broker platforms. All 60 CVEs violate at least one invariant.
- A two-layer design in the model-based testing tradition: an LLM generates API call sequences for high-level action categories, then resolves them into platform-specific HTTP requests, while deterministic oracles aligned with the invariants decide the verdict.
- A classification of the new vulnerabilities into eight recurring patterns.

### Evaluation
- Targets: seven open-source brokers (Keycloak, Casdoor, Dex, Authentik, Vault, Zitadel, Logto) across 13 OIDC and SAML configurations, each in a pinned Docker image, over three independent runs.
- New vulnerabilities: 33, all disclosed responsibly; 29 confirmed, 14 patched and 19 assigned CVEs, 10 of them rated critical.
- Precision: about 500 sequences per run, a 72.6% execution rate and 88.5% (plus or minus 6.1%) precision.
- Recall: 10 of 11 in-scope known CVEs (90.9%), or 10 of 18 (55.6%) when all OIDC and SAML CVEs are counted.
- Ablation: a generic "find security bugs" prompt without invariants or examples found 0 of the 33; dropping only the examples found 26; replacing the deterministic oracle with an LLM judge found 12 at 8.4% precision. The invariant definitions and the deterministic verdicts carry most of the performance.
- Reliability: the recall experiment covers only a subset of CVEs and is a lower bound, and every finding is relative to minimally configured deployments, so enterprise setups with custom mappers or plugins are not covered. Root-cause analysis, classification and report writing were done manually.

#### Comment
- The ablation result (zero bugs from a bare LLM prompt versus 33 with specification-derived invariants) is a directly reusable lesson for anyone building LLM-driven security testing.
- Organizations running Keycloak-style brokers can use the eight patterns, such as stripped assertion fields or account collisions from inconsistent email case normalization, as a review checklist.
- ACM CCS is a top-tier security venue, and the research artifact is public on Zenodo.
- Full text source: arXiv PDF (downloaded on the user's computer). The PDF carries the CCS '26 proceedings header and DOI, so it was treated as the published version.

# MALET & Katalina: A Large-Scale Dataset and Static Analysis of macOS Malware
> arXiv preprint (not peer reviewed). Two independent researchers, New York
> 2026

Windows and Android malware have been studied extensively, but macOS much less, partly because dynamic analysis is hard (the move to Apple silicon and virtualization limited to Apple hardware) and partly because public datasets are scarce. The authors release MALET, a public dataset of 44,804 malicious Mach-O binaries and 44,457 samples with zero VirusTotal detections, from which conservative heuristics select 25,835 high-confidence benign samples. They also release Katalina, an open-source static analyzer that extracts macOS-specific features at scale, including entitlements, signing metadata, embedded scripts and linked libraries.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.31949
- arXiv HTML full text: https://arxiv.org/html/2611.31949
- arXiv PDF: https://arxiv.org/pdf/2611.31949
- Author repository (Katalina): https://github.com/appsworld/katalina
- Dataset (Zenodo): https://zenodo.org/records/17877273

### Contribution
- MALET, described as the largest public macOS Mach-O dataset, together with the open-source Katalina analyzer.
- The first large-scale static characterization of macOS malware, covering misuse of security entitlements, abuse of native scripting interfaces and irregularities in code-signing infrastructure.

### Evaluation
- Signing: 93.0% of malicious samples are unsigned, which the authors read as evidence that unsigned code still runs in practice through user-approval paths. Of CA-signed malware, 28.4% (816 samples) were tied to certificates that were later revoked, including samples attributed to DPRK-linked actors.
- Revocation latency: some certificates stayed valid for more than 700 days after public detection.
- Detection instability: among 185 structurally identical malicious samples, antivirus engines were inconsistent for 77.2% (143 samples).
- Reliability: labels come from AVClass2, whose macOS taxonomy is immature; 55.27% of samples got no family label and 17.88% got no tag at all. Only static features were used, so runtime unpacking and C2 traffic are out of reach. Samples come from VirusTotal and VirusShare, which skews toward easily detected threats, and the benign set is mostly macOS system files, as the authors acknowledge.

#### Comment
- The paper tackles the biggest obstacle in macOS malware research, the lack of a public dataset, and could become a reference set for training and comparing detectors. It does not evaluate any classifier itself; it focuses on characterization.
- The title search also returned a Black Hat Europe 2025 deck on "insights from the largest public dataset of macOS malware" by a presenter sharing the first author's name, but the paper does not say how the two relate. The paper has not been through academic review.
- Full text source: arXiv PDF (downloaded on the user's computer).

# Agentic Discovery of Soundness Bugs in Safe Rust Bindings
> arXiv preprint (not peer reviewed). UC Berkeley
> 2026

Rust crates hide unsafe code, such as calls into C or C++ libraries or system calls, behind safe interfaces. If an interface encodes a rule of the underlying library too weakly (which call frees an object, which pointer the next call invalidates), a program in purely safe Rust can trigger undefined behavior. In the ssh2 crate, for example, auth_methods returns a string pointing into a buffer that libssh2 frees on the next call, and the borrow checker allows that next call, so safe code reads freed memory. Because static analyzers and fuzzers struggle with this class of bug, the authors study LLM agents as auditors of such bindings.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.31813
- arXiv HTML full text: https://arxiv.org/html/2611.31813
- arXiv PDF: https://arxiv.org/pdf/2611.31813

### Contribution
- A taxonomy of binding defects: undefined behavior, divergences from the wrapped library, and incomplete unsafe contracts.
- Repeated audits of one real crate (git2) by a closed model (Claude Opus 5.5) and an open model (DeepSeek V4.1 Flash), measuring which defects agents find, how well they triage, and what makes them find more.
- CRUSTIFY, an agentic system for C-to-Rust work that incorporates these lessons, run at scale.

### Evaluation
- Audit behavior: agents found the first two defect classes unprompted but few incomplete contracts even when asked. Their findings were almost always real even without an independent reviewer, but they rarely confirmed with a sanitizer and tended to stop early. With the same guidance, the open model found as many defects as the closed one at a quarter of the cost.
- At scale: in 16 widely used crates, including bindings to OpenSSL, SQLite, libgit2, libcurl and the V8 engine, CRUSTIFY found 225 undefined-behavior bugs, 23 behavioral divergences and 36 incomplete contracts (3 to 61 per crate, median cost under $50 per audit). In the Linux kernel's Rust abstractions it found 11 more undefined-behavior bugs and 4 incomplete contracts.
- Maintainers have fixed 26 of the 83 reported findings.
- Reliability: the behavioral study covers one crate at one revision, and the prompt was tuned on that crate. With no ground truth the authors report findings and agreement, not recall. Some defects in the crate were already public, and the authors cannot fully rule out that models saw them in training.

#### Comment
- Large-scale evidence that rewriting in safe Rust does not guarantee memory safety when FFI bindings encode library rules incorrectly. The findings in the kernel's Rust abstractions stand out.
- With 26 of 83 findings fixed so far, many reported defects appear to remain open.
- Preprint with no venue yet. No code link was found in the paper.
- Full text source: arXiv PDF (downloaded on the user's computer).
