# Dissecting the GPU Load/Store Unit and Exposing Its Security Risks
> arXiv preprint (not peer reviewed). University of Luxembourg
> 2026

Almost every load and store a GPU kernel issues goes through the load/store unit (LSU) of its streaming multiprocessor (SM), yet only a handful of isolated mechanisms and parameters of this unit were known, and even single ones had been enough for attacks such as AES key recovery. The authors reverse-engineer how the LSU serves loads on NVIDIA V100, A100 and H100 with microbenchmarks. They give a cycle-accurate latency formula for a global L1 hit or shared-memory access from the addresses it touches, show that the address-dependent terms are bank conflicts and the L1 tag lookup, that loads contend at both, and that once the LSU pipeline is full a warp from a later-launched block can starve.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.23022
- arXiv HTML full text: https://arxiv.org/html/2611.23022
- arXiv PDF: https://arxiv.org/pdf/2611.23022

### Contribution
- Answers six previously open questions, including what a single load costs, which cache lines cost extra cycles, exactly how many cycles each extra way of bank conflict adds, and whether global and shared loads pay the same for a conflict.
- Finds channels never exploited before (global-memory bank conflicts, tag lookups), showing the LSU's attack surface is much broader than prior attacks revealed.
- Discovers warp starvation as a new contention effect and turns it into a performance-degradation attack.

### Evaluation
- Side channel: global bank conflicts or tag lookups alone recover a full AES-128 key under the threat model of prior GPU AES timing attacks.
- Covert channel: under NVIDIA's Multi-Process Service (MPS), bank access and tag lookup each give a cross-process covert channel whose rate rises with each GPU generation.
- Degradation: under MPS, a single warp slows a colocated cuBLAS matrix multiplication by up to 750x on the A100 and 563x on the H100; launch order decides which side starves.
- Reliability: measurements come from SASS-level microbenchmarks on three real GPU generations, so the evidence is concrete. Only NVIDIA GPUs are covered, and the attacks assume processes share an SM, as under MPS. We did not confirm specific covert-channel bit rates from the body for this summary.

#### Comment
- With GPUs increasingly shared among cloud tenants, the paper quantifies isolation problems in MPS-style sharing. Slowdowns on the order of 750x are a real availability threat, not only a confidentiality one.
- The exact latency model is also directly useful for defenders writing constant-time GPU code or designing scheduling isolation.

# Missing Security-Fix Backporting for GitHub Actions Workflows
> Accepted at ICSE 2027 (49th IEEE/ACM International Conference on Software Engineering); arXiv preprint. Singapore Management University, University of Alberta
> 2026

The first large-scale study of a common gap: maintainers fix a security weakness in a GitHub Actions workflow on the default branch but never carry the fix over to the release and maintenance branches that downstream users actually build from. If actions/checkout is pinned from a mutable tag to an immutable commit ID only on the default branch, release branches stay exposed to tag-rewrite attacks like CVE-2025-30066 (the tj-actions/changed-files incident). From public workflow histories the authors mine 1,903,191 workflow-modifying commits, scan each before and after with the static analyzer zizmor, and audit whether every fix reached each release branch. They then propose WorkflowBP, a technique for automated security-fix backporting.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.22519
- arXiv HTML full text: https://arxiv.org/html/2611.22519
- arXiv PDF: https://arxiv.org/pdf/2611.22519

### Contribution
- Identifies 69,865 security fixes across 24,238 projects and quantifies the backporting gap for the first time.
- WorkflowBP compiles a default-branch fix into a domain-specific Workflow Semantic Patch (WSP) and applies it to each branch by matching jobs and steps on content rather than position; an LLM synthesizes the WSP only for heavily diverged cases the deterministic engine cannot resolve.
- A backport is accepted only after re-scanning confirms the target weakness is fixed and nothing else broke.

### Evaluation
- Prevalence: 224,392 of 474,490 audited release branches (47.3%) remain vulnerable. Of 78,907 already-fixed branches, only 19,476 are confirmed as deliberate backports, with a median lag of 243 days.
- Technique: on 12,000 real unpatched workflow files, WorkflowBP produced a scanner-checked backport for 67.9%, versus 18.0% for verbatim copying, 13.0% for Dependabot-style updates and 49.5% for an LLM-only baseline. The LLM comparison uses the same model (Gemini).
- Real-world use: 17 accepted backports were executed, and 176 were submitted as issues to real projects, of which 44 were confirmed or fixed by developers.
- Reliability: success is judged by re-scanning with the same static analyzer, so weaknesses zizmor misses and functional regressions are outside the evaluation. Developer responses add real-world evidence.

#### Comment
- The numbers make clear that "fixed" in supply-chain security usually means "fixed on the default branch". The finding applies directly to open-source projects that maintain long-lived release branches.
- ICSE is a top software engineering venue. Many authors have Chinese names, but the affiliations are Singapore Management University (David Lo's group) and the University of Alberta, so this is not a Chinese-institution paper. We did not find a tool or data release address in the body.

# Taking Time Out of TOCTOU: From Race Reproduction to Security Discovery
> arXiv preprint (not peer reviewed), code released. University of Calgary
> 2026

Time-of-check-to-time-of-use (TOCTOU) races are hard to reproduce, and a lost race can make a vulnerable program look fixed. The authors present Chronos, which separates intervention timing from verdict evidence and builds reusable one-trial security regression oracles for declared races. Chronos uses seccomp user notifications to hold the target thread just before the use syscall and releases it only after the attacker's change (for example, a renameat2 swap) completes, so a race window of a few microseconds becomes effectively unbounded. ptrace and a KVM guest gate provide the same holds at userspace and kernel instruction sites. The main evaluation uses container-runtime TOCTOU bugs (CVE-2021-30465, CVE-2025-23359, CVE-2023-27561, CVE-2025-31133).

Links:
- arXiv abstract: https://arxiv.org/abs/2611.21214
- arXiv HTML full text: https://arxiv.org/html/2611.21214
- arXiv PDF: https://arxiv.org/pdf/2611.21214
- Author repository: https://github.com/hasnainnaeem/chronos

### Contribution
- Defines reusable race specifications composed of hold engines, actions, observers, oracles and outcome rules, so the same specification drives deterministic reproduction, commit bisection and CI regression tests.
- A "fixed" verdict requires positive, case-specific evidence (preservation, justified refusal, omission under checked coverage); missing or contradictory evidence stays "indeterminate", which prevents false "fixed" verdicts.
- Applying the specifications to releases, distribution packages and other runtimes turned up real new issues.

### Evaluation
- Reproduction: for CVE-2021-30465 the attack succeeded in all 100 runs of the vulnerable version with Chronos, and in 603 of 2,000 runs without it.
- Verdict accuracy: on known-vulnerable builds, effect-only checkers made over 800 false "fixed" calls in failed-intervention trials; Chronos made none. All 17 syscall-held cases and four of six instruction-held cases received both vulnerable and fixed labels; two kernel cases remain one-sided.
- Bisection: all 27 historical bisections recovered the expected boundaries. For runc's masked-path bug, fixed retry and Git Bayesect needed medians of 475 and 398 launches; Chronos needed seven, including endpoint checks.
- Discovery: incomplete fixes in chrony and rpm, and a Debian rpm package that the tracker listed as fixed.
- Reliability: the seccomp engine needs Linux 5.5 or later and mount-family verdicts need Linux 6.8 or later, and targets are assumed not to use io_uring, which would bypass syscall-entry observation. Results apply to declared races; it is not a tool for finding unknown ones.

#### Comment
- Turning fix validation for container-escape races from a game of chance into a deterministic test is very practical. Runtime maintainers who want security regression tests in CI can use it directly.
- This was a carried-over candidate deferred in the previous run (2026-11-18) because of the arXiv download cap.

# From Attack Tree to Model Checker: Binding CAPEC Patterns to Verify Robotic System Security
> In Proceedings of FMAS 2026 (Eighth International Workshop on Formal Methods for Autonomous Systems), EPTCS 457, 2026, pp. 154-162, DOI 10.4204/EPTCS.457.11. Department of Computer Science, University of Manchester (UK)
> 2026

Security verification of robotic and autonomous systems needs an attacker model, but turning a threat catalogue into an attacker model a model checker can use is still done by hand. The authors say that in their earlier satellite-docking work they built the combined attacker-system model manually and verified it in SPIN, which was slow and did not scale. This research preview presents a pipeline that mechanizes the step. Each attack-tree leaf is linked to a CAPEC attack pattern, and the pattern is written once as a many-sorted first-order rule stating that the attacker's prerequisites imply the attack's effect. Binding the rule's variables to a specific system's channels and resources lets the tool decide, for each configuration of security controls, whether the attack applies and which control blocks it, using only membership tests on a closed-world fact list; it then generates a Promela attacker process and LTL properties for SPIN to check.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.22408
- arXiv HTML full text: https://arxiv.org/html/2611.22408
- arXiv PDF: https://arxiv.org/pdf/2611.22408
- EPTCS DOI: https://doi.org/10.4204/EPTCS.457.11
- FMAS 2026 proceedings index (arXiv): https://arxiv.org/html/2611.21375
- FMAS 2026 workshop homepage: https://fmasworkshop.github.io/FMAS2026/
- Author code repository (AT2FOL prototype, release fmas2026, work in progress): https://github.com/juelhussain/AT2FOL

### Contribution
- Defines four independent inputs (a signature fixing the vocabulary, CAPEC schemas written for no particular system, system profiles written for no particular attack, and attack trees that scope the analysis) that meet only at the binding step. Profiles may assert only capability and state facts; schemas may produce only progress and violation facts.
- Reports the failed premise of a bound rule as the "blocking atom", so a verdict names the control that defeats the attack and is phrased as "blocked under these facts" rather than "secure", since a capability missing from the profile would make an attack look blocked.
- Derives an attacker transition system and LTL templates from bound rules (obligation, adequacy checks against vacuous truth, step ordering, partial progress and SAND ordering), composed with the system model only through a declared input channel.
- Links leaf descriptions to CAPEC entries semi-automatically: a TF-IDF similarity shortlist that an analyst confirms.

### Evaluation
- There are no experimental results; the paper lays out a four-part evaluation plan: CAPEC retrieval quality (compared with ATT&CK-BERT and other embeddings), schema coverage, static applicability against actual applicability, and SPIN results against a hand-built model.
- Of the 558 non-deprecated patterns in CAPEC v3.9, 349 (62.5%) have both prerequisites and consequences, the upper bound on what can be written as a schema, and 239 (42.8%) have an execution flow that supports multi-step schemas.
- Example schemas are written for CAPEC 148 (Content Spoofing), 125 (Flooding), 94 (Adversary in the Middle) and 157 (Sniffing Attacks). In the satellite-docking case, the camera-spoofing leaf applies under configuration C1 with no controls and is blocked under C2, where camera channel authentication is enabled.
- Reliability: this is a nine-page research preview, and running SPIN over every configuration is stated as planned work. The only case is the authors' own satellite-docking model, so effectiveness on real robotic systems cannot yet be judged.

#### Comment
- It is a formal attempt to close the manual gap between threat catalogues and model checking, and limiting verdicts to "blocked under these facts" instead of "secure" is an honest choice. Unlike MulVAL, which relies on expert-written exploit rules, the rules here come from a public catalogue and are reused across systems.
- Limitations the authors state: patterns whose effect is a property of system runs, such as Forced Deadlock (CAPEC 25), cannot be written as static rules, and the current signature cannot tell network sniffing (158) from eavesdropping (651). Profiles and bindings still have to be written by an analyst.
- Trust signal: the paper prints the FMAS 2026 proceedings reference (EPTCS 457, pp. 154-162) and DOI. FMAS is a peer-reviewed workshop on formal verification of autonomous systems. The paper confirms that all four authors are in the Department of Computer Science at the University of Manchester, UK.
- The AT2FOL prototype repository is public, though the authors label it a work in progress.
- Full text source: arXiv PDF (downloaded on the user's computer).
