# Memory Safety Isn't All You Need: Code Reuse Attacks in Memory Safe Languages
> arXiv version of a paper to appear at ACM ASIACCS 2027. KTH Royal Institute of Technology
> 2026

This paper builds a single framework for code reuse attacks that survive in memory-safe languages. Memory safety rules out classical code reuse such as ROP, which depends on arbitrary memory corruption, but object injection, prototype pollution, class pollution, DOM clobbering and DOM script gadgets all work without breaking the memory-safety abstraction. The authors argue that these attacks share one structure: attacker-controlled data steers an access to shared runtime state, such as runtime type information, prototype or class state, or the DOM, and the value fetched from that state then reaches a security-sensitive operation. On that basis they split an attack into a "weakness", which ends in a fetch from shared state, and a "gadget", existing code that carries the fetched value to a sensitive sink.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.18910
- arXiv HTML full text: https://arxiv.org/html/2611.18910
- arXiv PDF: https://arxiv.org/pdf/2611.18910
- Authors' repository (model-language interpreter): https://github.com/KTH-LangSec/memory-safety-isnt-all-you-need

### Contribution
- A language-agnostic weakness-and-gadget framework, shown to capture all five established attack classes.
- Uses the framework to derive stateless, mutating and recycling weaknesses and simple, vertical and horizontal gadget structures, exposing patterns beyond the known classes.
- Applies the framework to Go as a case study, showing that mutable shared state such as package variables does not become a weakness unless the language offers a way for attacker data to steer how that state is accessed.
- Groups existing defenses into three strategies, mediation, minimisation and constraint, and derives candidate defense directions from them.
- Introduces imp_sm, a model language that formally defines shared runtime state and code-reuse weaknesses, together with an executable interpreter.

### Evaluation
- This is a systematisation and formalisation paper, not an empirical one. It encodes representative instances of the five attack classes in the model language to show the framework captures them, and demonstrates its use through the Go case study.
- There are no quantitative metrics or baselines. The authors also note the limits of the formal definitions: observations drop the accessed values and compare accesses as multisets, so changes in a stored value or in access order are deliberately ignored, and the gadget and end-to-end vulnerability definitions do not fully enforce that the resulting execution is feasible.

#### Comment
- By treating many web and scripting-language bugs as "code reuse over shared runtime state", the paper offers a way of thinking that helps when reviewing the attack surface of new language features or frameworks. It also pushes back on the hope that moving to memory-safe languages such as Rust or Go removes this class of attack.
- The same group (Balliu) has a steady record on this topic at USENIX Security and NDSS, including prototype-pollution RCE and object-injection detection. ASIACCS is a major venue in the field.

# Inferring Sensitive Events in Multi-Mode Cyber-Physical Systems via Scheduling Side Channels
> arXiv preprint (not peer reviewed). University of Pennsylvania, University of British Columbia
> 2026

This paper shows that mode changes in multi-mode cyber-physical systems, which switch tasksets and timing parameters in response to physical events, form a scheduling side channel that reveals sensitive events. A home-security system starts analysing camera streams when the owner leaves; a self-driving stack shifts its perception and planning load as it drives. A mode change alters the interference that co-running tasks experience, so an unprivileged co-resident task can infer events such as a homeowner's arrival or a vehicle's route from its own execution timing and, on multicore platforms, its core assignment. Earlier schedule-based attacks and defenses missed this channel because they assume single-mode systems or a specific known victim task. The authors present Stamp, a lightweight attack that needs no knowledge of task parameters or the scheduling policy.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.17761
- arXiv HTML full text: https://arxiv.org/html/2611.17761
- arXiv PDF: https://arxiv.org/pdf/2611.17761

### Contribution
- Identifies a new side channel: mode changes in multi-mode CPS cause system-wide scheduling shifts that leak information.
- Stamp uses one of two strategies depending on what the attacker knows. With explicit modes it detects mode changes as shifts in windowed timing percentiles and classifies each segment using timing and core-placement features; with latent modes it classifies observation windows directly into events. Features are normalised against brief unlabelled measurements on the target device, so models transfer to hardware other than the attacker's profiling devices.
- Shows that an existing schedule-randomisation defense only partly mitigates the attack, while badly hurting schedulability and even introducing new leakage.

### Evaluation
- ZoneMinder home security (Raspberry Pi 4B with cameras): modes identified with 94.7% accuracy on unseen hardware, using under 0.5% of one core.
- ROS 2 AMCL with the Oxford RobotCar dataset: identifies which of seven route segments a vehicle traversed with 86.0% (±0.8%) accuracy on unseen platforms, peaking at 88.6% with a 5 ms observer period. Using only the explicit-mode strategy gives 73.0%, and removing the 1-D CNN that sees fine time scales drops accuracy to 75.7%, showing each component matters.
- Real robot: also distinguishes routes for TEB path planning on a Raspberry Pi 5-based Yahboom MicroROS robot.
- Defense: schedule randomisation cuts detection recall to 0.53, but at that setting only 53.9% as many jobs finish on time. At higher noise (ε = 10), on-time completion falls to 14.4% and new leakage appears in 14.1% of tasksets.
- Credibility: cross-device evaluation on platforms and traces not used in training reduces the risk of overfitting. The authors note that the simulation part assumes no migration overhead or release jitter, which favours the attacker.

#### Comment
- In vehicles, robots and smart-home hubs where several pieces of software share one chip, resource usage alone can leak physical-world events. Simple randomisation is not enough; reserving fixed resources regardless of mode would stop the attack, but only by provisioning for the maximum demand across all modes, which the authors point out is costly.
- Limitations: modes that look alike to the observer cannot be told apart, offline profiling must stay representative of the victim environment, and large changes in workload or scheduler configuration can reduce accuracy. No code link was found in the paper.

# Deterministic ECDSA on secp256k1: the RFC 6979 assumption, a counterexample, and the state of deployed implementations
> arXiv preprint (not peer reviewed). HSE University (Higher School of Economics), Moscow
> 2026

This paper pins down exactly which assumption the security of deterministic ECDSA (RFC 6979), the de facto standard in the Bitcoin and Ethereum ecosystems, rests on, and audits 31 deployed implementations. RFC 6979 derives the nonce by running HMAC_DRBG keyed with the signing key x over the message hash h, removing the dependence on a run-time random number generator. The RFC says it is secure "as long as HMAC behaves as a PRF", but the author shows that the assumption actually needed is a different one, A*: with the public key known, the signing transcript under deterministic nonces is indistinguishable from the transcript under uniform nonces. A counterexample shows that PRF security alone does not give A*.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.18449
- arXiv HTML full text: https://arxiv.org/html/2611.18449
- arXiv PDF: https://arxiv.org/pdf/2611.18449

### Contribution
- Formalises A* and shows that, under A*, deterministic ECDSA is exactly as secure as randomised ECDSA.
- Counterexample: a nonce function that is a PRF under standard assumptions yet leaks the key from a single signature, lifted to the compression-function level so that the unmodified RFC 6979 state machine over a compression function with the PRF and dual-PRF properties used in HMAC proofs is broken by one signature (given a collision-resistance premise).
- Shows that A* and the auxiliary-input PRF (AI-PRF) assumption are separated in both directions. With an ideal compression function, A* follows tightly from the hardness of the discrete logarithm problem, and a nonce key independent of x removes the need for the assumption.
- Computes how far the secret HMAC message block is from uniform on different curves (2^-127.65 on secp256k1, 2^-32 on P-256, 0.336 on brainpoolP256r1).
- Audits 31 implementations and publishes test vectors for the untested h ≥ n branch.

### Evaluation
- Implementation audit: 28 of 31 secp256k1 implementations sign deterministically without added entropy, and the raw-message deviation from bits2octets in libsecp256k1 before 0.2.0 survives in NBitcoin, dcrd and btcec v2, confirmed by reading source code. None of the 31 separates the nonce key from the signing key.
- Proves that low-R grinding (Bitcoin Core) needs nothing beyond A*, and unconditionally bounds every nonzero Fourier coefficient of the low-R nonce set below 2^-116.9.
- Models the data threshold for a one-bit nonce-bias attack at about 2^47 signatures, with an uncertainty range of 2^40 to 2^47.
- Credibility: every claim is tagged as proved in the paper, taken from the literature, established from source code, or an estimate or interpretation, which makes the strength of each claim clear. It is still a single-author theory paper that has not been peer reviewed, so the proofs need expert checking.

#### Comment
- The practical message is not that RFC 6979 is broken today, but that the most widely deployed ECDSA practice rests on an assumption nobody has proved. No known attack violates A* for HMAC_DRBG. For wallet and signing-library developers, checking bits2octets compliance and the h ≥ n test vectors is something they can act on right away.
- Open problems include a standard-model proof or refutation of A* for HMAC_DRBG, removing the collision-resistance premise, and measuring rather than modelling the cost of one-bit nonce leakage.
