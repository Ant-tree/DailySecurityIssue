# Beyond Sensitive APIs: Detecting Access Control Flaws at Sensitive Callsites in Android Firmware
> Accepted at NDSS Symposium 2027 (per the paper PDF: March 22-26, 2027, Seoul; DOI 10.14722/ndss.2027.231311), posted as arXiv cs.CR 2611.00594. University of Electronic Science and Technology of China
> 2026 (conference in 2027)

Pre-installed apps that vendors ship in firmware hold elevated privileges and cannot be removed, so a single flaw spreads to every device that vendor sells. Existing studies judge risk by whether an app calls APIs from a predefined list of security-sensitive APIs. To avoid false positives, those lists leave out generic APIs such as database reads, which means they miss flaws where a generic API touches protected data. A case disclosed by the Polish CERT in 2025 is typical: a pre-installed app's ContentProvider let any app on the device read the user's PIN without permissions.

CALLIX is a static analysis framework that finds this kind of insufficient access control at sensitive callsites in ContentProvider components. It works in three stages. It first judges how sensitive a callsite is from both what the API does and what data the call touches. It then recovers the security checks on the execution path from branch conditions and expresses each as an explicit security property, capturing what is validated and with what. Finally, it uses the notion of "restriction context" to decide whether those checks are sufficient for the operation and data in question. An LLM reasons about semantics on top of statically extracted evidence; it does not replace program analysis.

### Contribution
- Raises a new question: not whether a check exists, but whether it is sufficient for the operation and data. A generic API can become sensitive depending on the data it handles.
- An analysis that finds sensitive callsites from operation and data semantics, recovers access checks as security properties, and judges sufficiency through restriction context.
- Analyzing 50 firmware images and 1,750 pre-installed apps from 10 major vendors, it found 819 vulnerable paths across 424 ContentProviders; 42.1% of them let an app read or modify private user data through generic database operations.
- Mitigations: avoid routing privileged functions through general-purpose interfaces such as ContentProvider.call(), and verify callers with Binder.getCallingUid() or signature-level permissions rather than caller-controllable strings like package names.

### Evaluation
- Data: five firmware images from each of 10 vendors, including Google, collected from Android Dumps and FirmwareDrive. The corpus-scale analysis used deepseek-v3-flash.
- Accuracy: two researchers validated a random 60% sample (492 paths); 468 were real vulnerabilities, for 95.1% precision, and each confirmed path was reproduced with a working proof of concept. Vendors independently confirmed 278 reports across 98 providers, some of which were rewarded or fixed.
- Ablation (balanced 500-path benchmark): with code slices alone, 206 of 250 safe paths were flagged as vulnerable. Adding the taxonomies raised precision to 94.6% but dropped recall to 56.4%. Adding sufficiency reasoning brought recall to 92.0%, F1 to 92.6%, and misclassified safe paths down to 17.
- Model dependence: swapping the backend for deepseek-v4-pro, gemini-3.1-pro or claude-opus-5 changed accuracy by at most 2.2 points, and models costing 68x and 139x more improved accuracy by only 1.4 and 2.0 points. Handing the same evidence and criteria to a commercial coding agent (claude-opus-5) still left it 6.6 F1 points behind CALLIX.
- Reliability of the metrics: manual validation, proofs of concept and vendor confirmations make the findings credible. The closest prior work, FirmScope, is not public, so it could not be run, and the comparison is limited to the configuration FirmScope was evaluated in. Recall is estimated only on the balanced benchmark, so how many flaws were missed across real firmware is unknown.

#### Comment
- The observation that vendor pre-installed apps use ContentProviders as de facto privileged command channels stands out. A useful design reference for compensating the limits of "sensitive API list" approaches in mobile security SDKs and app assessment tools.
- Limitations: as the authors note, being static, it cannot follow some data flows through components, sophisticated obfuscation such as reflection, or native libraries, and LLM misinterpretation still causes false positives. Whether the code is released was not confirmed in the parts read.
- Venue: accepted at NDSS 2027, a top security conference, so reliability is high.
- Verification of a Chinese-institution paper: all authors are at the University of Electronic Science and Technology of China. NDSS is a real top-tier conference and a DOI has been issued. Precision comes from manual validation of a random sample, the 95.1% figure is not suspiciously perfect, and the unfavorable intermediate ablation results are reported. Vendors independently confirmed 278 reports, which is external evidence. Not running FirmScope remains a limitation, but the authors explain why and state the scope of the comparison. On that basis the paper is included.

# A Symbolic-Neural Framework for Context-Aware Evidence Extraction from Mobile SQLite Databases
> Accepted at HICSS-60 (60th Hawaii International Conference on System Sciences), posted as arXiv cs.CR 2611.03323. University of Baltimore and Cox Automotive, USA
> 2026

Mobile apps store most conversations, contacts and locations in SQLite databases, which makes these databases central evidence sources in digital forensics. App schemas are undocumented, change between releases and differ between Android and iOS, so schema-specific parsers break easily and are hard to maintain.

SNEEF extracts evidence without depending on the schema. Each row is encoded as context-value pairs with standardized provenance metadata and column labels, and a language model recognizes nine forensic entity types such as person names, phone numbers, email addresses, URLs, messages, addresses and timestamps. A provenance protocol, PA-EEP, then binds every accepted entity to its source table and row so the evidence can be traced and checked later. Entities that cannot be mapped to a row or that violate a declared constraint are rejected, and a recall-driven preselection stage (ESTRE) uses regular-expression detectors for pattern-like types to cut model calls.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.03323
- arXiv HTML full text: https://arxiv.org/html/2611.03323
- arXiv PDF: https://arxiv.org/pdf/2611.03323
- Authors' evaluation materials (anonymous release): https://anonymous.4open.science/r/HICSS_SNEFF-084F

### Contribution
- A representation that wraps rows in hierarchical symbolic context, enabling extraction across heterogeneous app schemas without fixed field mappings.
- A provenance protocol that binds each accepted entity to its source row, keeping evidence traceable even with a language model in the loop.
- An Evidence Failure Mode taxonomy and metric for explaining why extraction fails.
- Release of examiner-verified ground truth, encoded records, outputs and scoring scripts.

### Evaluation
- Data: five corpora built from public Android and iOS device images (three of them WhatsApp), spanning several app versions, with examiner-verified ground truth.
- Setup: Claude Opus 4.8 at temperature 0 with greedy decoding, comparing only context-aware and context-free encodings.
- Results: F1 for evidence entities in row content, excluding application names, was 0.967 (95% CI 0.965 to 0.970) with context versus 0.728 without. The confidence interval of the gain was above zero on every corpus, with the largest improvement in recall.
- Reliability of the metrics: the comparison changes only the encoding, with the same model and rows, so the effect of context is clear. The only baseline is the same method without context, however; no comparison with commercial forensic tools or schema-specific parsers was found in the parts read.

#### Comment
- A practical answer to mobile forensics' chronic problem of fixing parsers after every app update. Binding evidence to its source row appears designed with courtroom evidence requirements in mind.
- Limitations: the authors themselves note that sending case data to an external API raises jurisdiction, privacy and chain-of-custody issues, so operational use should rely on a local model. Provenance guarantees traceability, not factual correctness beyond what the database records.
- Venue: accepted at HICSS-60, a long-running peer-reviewed information systems conference.

- The authors are at the University of Baltimore and Cox Automotive, USA; this is not a paper from a Chinese institution.
