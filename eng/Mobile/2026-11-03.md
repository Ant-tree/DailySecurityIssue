# Fooling Relying Parties of the EUDI Wallet Architecture: Credential Pooling Attacks and CRESTA, a Standard-Compliant Countermeasure
> arXiv cs.CR 2610.41655 (preprint, not peer reviewed), DIAG, Sapienza University of Rome, Italy
> 2026

The European Digital Identity (EUDI) Wallet lets EU citizens keep credentials such as ID cards and degrees on their phones and disclose only what is needed. Services (relying parties) often ask for several credentials at once, for example an ID card and a university degree, and this paper attacks exactly that combined presentation. In a credential pooling attack, colluding users who each hold only some of the credentials cooperate through a proxy that poses as a single synthetic user and presents everything requested. Every signature is genuine and produced by certified secure hardware; nothing is extracted or forged.

The attack works because the Architecture and Reference Framework (ARF) requires a fresh key for each credential and recommends batches of single-use copies to prevent tracking. If all of a user's credentials shared one public key, pooling would fail, but colluding relying parties could then link all of that user's presentations. The authors show that resolving this tension does not require zero-knowledge proofs or other non-standard cryptography. Their countermeasure, CRESTA (CREdential STApling), has an ordinary issuer check at issuance that a set of keys was generated in the same secure hardware (WSCD) and certify that fact in a "binding attestation," itself a standard credential whose attributes can be selectively disclosed.

### Contribution
- Formalizes credential pooling against combined presentations and reproduces it end to end against the European Commission's unmodified reference issuer and relying party, with software wallets and with two Android phones.
- Pinpoints the tension: the design choices made for unlinkability are what make pooling possible.
- Proposes CRESTA, which uses only standard cryptography and credential formats and keeps unlinkability. The extra cost for a relying party is one signature verification per presentation.

### Evaluation
- Attack: against the reference implementation, the median time of a full pooled presentation was under 0.2 seconds. The phones only sign, and both holders must be online at presentation time.
- Countermeasure cost: measured on a desktop with P-256 ECDSA, comparing verification of an ordinary combined presentation with and without the binding check, using medians of 4,001 runs.
- Reliability of the metrics: the attack was confirmed directly on the reference implementation, so the evidence is solid. Cost was measured on a desktop, not under realistic relying-party load.

#### Comment
- Important for anyone designing or verifying mobile identity wallets. Even when every individual signature is genuine, the property "one person holds all these credentials" has to be guaranteed separately, and this paper shows concretely how it can fail.
- Limitations: the binding attestation only proves that the keys were in the same hardware at issuance; that this still holds at presentation relies on keys never leaving the hardware. The mechanism uses Android attest keys so that the wallet provider can tell keys belong to a WSCD, so other platforms need an equivalent.
