# When Shuffling Fails: Token Recovery from Obfuscated KV Caches
> arXiv preprint (not peer reviewed). Huazhong University of Science and Technology, Macquarie University, Griffith University
> 2026

LLM serving systems store, offload and share KV cache blocks for efficiency, exposing token-level representations to infrastructure operators and co-tenants. Recent defenses such as KV-Cloak and PermLLM protect these blocks with "shuffled obfuscation", combining secret linear transforms with fresh random permutations, and cite the b! possible permutations as the security barrier. The authors show that this counting argument fails. A prompt that repeats one token produces identical first-layer Value rows across a cache block, so every row permutation leaves the data unchanged and only a single-row recovery marker moves; the distinguishable states collapse from b! to b. Their Repeat-to-Reveal attack collects these b states from the attacker's own probes and uses their rank-one differences to recover a denoiser equivalent to the secret transform.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.24276
- arXiv HTML full text: https://arxiv.org/html/2611.24276
- arXiv PDF: https://arxiv.org/pdf/2611.24276

### Contribution
- Shows that the security of shuffled obfuscation depends on how many distinguishable outputs a chosen input produces, not on how many permutations exist, and confirms the same collapse in the sequence-permutation implementation of Thomas et al. and in PermLLM.
- A one-time calibration transfers to other requests within the same secret epoch, enabling passive recovery from any later observed cache block, so the attack cost does not grow with the number of requests.
- Proposes VeilKV, which replaces obfuscation with byte-level authenticated encryption, supports public-prefix sharing with scoped private tails, and runs correctly in vLLM.

### Evaluation
- Target: the official KV-Cloak implementation (commit 6b40f36), across 11 public models from the Qwen, Llama, OLMo and TinyLlama families and 13 configurations including block-size variants, using 3,000 real WildChat user prompts on one A100 GPU.
- Results: the secret parameters were recovered almost exactly, with 100% token-multiset recovery on GPU. Reordering with a language model reached 0.947 semantic similarity to the original text, and identifying a sensitive value among 100 candidates reached 97.5% top-1 accuracy.
- Refreshing row-level secrets between epochs breaks cross-request transfer, confirming that the scope of secret reuse is the real vulnerability.
- Reliability: the attack is algebraic and deterministic, so 100% recovery is not suspicious, and pinning the target to an official commit makes reproduction clear. The sensitive-value experiment uses synthetic data, so results in practice will depend on the candidate set size.

#### Comment
- A good example of why "the search space is huge" is not enough when obfuscation is used as a security mechanism: if the attacker can choose inputs, symmetry can collapse that space. The same lens is useful when evaluating code obfuscation.
- As a paper with a Chinese institution, it received extra checks. The authors are at HUST and two Australian universities, and the target is a public official implementation. Through responsible disclosure the authors submitted a report on November 3, 2026, and the paper states that the KV-Cloak developers acknowledged the vulnerability on November 17, 2026, which is an external confirmation. No attack code release was found in the paper.

# ElevatorII: High-Performance Fully-Static Cross-ISA Binary Translation
> arXiv preprint (not peer reviewed). University of California, Irvine
> 2026

Running binaries built for one instruction set (ISA) on another is usually done with emulation plus JIT compilation, which requires trusted runtime support on the target and makes compilation decisions hard to predict or reproduce. The authors present ElevatorII, a fully static, ahead-of-time translator that turns x86-64 ELF binaries into standalone AArch64 ELF executables with no runtime support. Its core is superset disassembly: it decodes and translates one instruction at every byte offset of the text segment, building a "grid" so that pre-translated code exists for any possible indirect jump target. Optimized "confirmed paths" chosen by observation-guided path selection (OGPS) are layered on top, with hot code in the main segment and the rest in a .text.unlikely section.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.19577
- arXiv HTML full text: https://arxiv.org/html/2611.19577
- arXiv PDF: https://arxiv.org/pdf/2611.19577

### Contribution
- According to the authors, the first fully static cross-ISA translator that combines a per-byte grid with optimized paths. Because the binary that will run can be tested in advance, it is less risky to deploy than an emulator with an embedded JIT.
- Since it translates every interpretation instead of separating code from data, it can translate binaries protected with virtualization and branch-function obfuscation that no static disassembler can follow.
- Introduces a design that trades code size for execution performance.

### Evaluation
- Benchmark: SPEC CPU 2026 integer suite (14 C/C++ programs, three excluded because they use C++ exceptions), 45 reference inputs. Comparisons: native AArch64 builds, Box64 (the fastest dynamic translator) and QEMU user mode.
- Results: in total runtime, ElevatorII with OGPS finished 2% ahead of Box64 and 80% ahead of QEMU, and QEMU was 3-15x slower on every benchmark. Without the profile it trailed Box64 by 34%. Output code is 51x the size of code compiled from source, but only 2-3% is hot code in the main segment.
- Obfuscation: programs whose hot functions were obfuscated with three combined Tigress transformations were also translated. For sqlite, the obfuscated program ran 11x longer than the original even natively, 12x under Box64 and 16x under ElevatorII; where obfuscated functions dominated, Box64 stayed ahead.
- Reliability: standard benchmarks and public tools make the comparison fair. Only single-threaded programs are supported, and the benefit of profile-guided optimization may vary with inputs.

#### Comment
- This paper was carried over from an earlier run. It is filed under obfuscation this time because handling obfuscated binaries is one of its stated contributions.
- From a deobfuscation angle, it is notable that obfuscated binaries that defeat static analysis can still be run on another architecture without being understood. From a protection angle, it suggests that virtualization obfuscation is no barrier to porting.
- Limitations: no support for self-modifying or JIT-generating programs, C++ exceptions or multithreading. Co-author Michael Franz is a long-standing researcher in binary translation and software diversity.
