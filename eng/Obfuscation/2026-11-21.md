# Hardening JavaScript Programs against LLM-Based Vulnerability Detection
> arXiv preprint (not peer reviewed). Nanyang Technological University, Tsinghua University, Shanghai Jiao Tong University
> 2026

JavaScript is often shipped as source code, so anyone can now point an LLM-based vulnerability detection agent at it, and attackers have already used Claude Code and Codex to find vulnerable services and build exploits. The authors present AntiAgent, a defense that lets developers transform a program before release so that such agents struggle to analyze it. Like a fuzzer, it runs an evolutionary search over programs with known vulnerabilities, keeps the variants on which the detection agent misses or misreports the vulnerability, and extracts the underlying transformations into reusable rules. To protect a new program, an LLM chooses a fitting rule at each location while the rule itself makes the code change deterministically, so the transformation adapts to the program while preserving its semantics.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.25718
- arXiv HTML full text: https://arxiv.org/html/2611.25718
- arXiv PDF: https://arxiv.org/pdf/2611.25718

### Contribution
- Points out that conventional obfuscation (shortening names, encoding strings, flattening control flow) follows fixed patterns that capable agents see through, and proposes "anti-agent" transformations that target the agent's reasoning instead, in the spirit of anti-fuzzing.
- During discovery, variants are scored by running the proof-of-concept rather than trusting the agent's own claims, which limits the agent's ability to game the score.
- Rules are expressed as AST matching conditions and operations, and the LLM only selects rules and adjusts their parameters, which is meant to guarantee semantic preservation.

### Evaluation
- Data: rules were discovered on 40 SecBench.js programs (prototype pollution, command injection, path traversal, ReDoS, arbitrary code injection) and evaluated on 40 real-world applications from GitHub Security Advisories (about 37K lines on average, 13 vulnerability types, one known vulnerability each). To avoid contamination, only vulnerabilities disclosed after the evaluated models' release were used.
- Detection agents: Codex (GPT-6.1-sol), Claude Code, ZCode and the dedicated JavaScript detector OpenAnt, all with web search and browsing disabled.
- Results: the defense success rate (relative drop in detected vulnerabilities) was 52.0-60.7% per agent, ahead of the conventional obfuscator JS-Obfuscator (medium setting) and the LLM-based transformation FPA on every agent. Claude Code, for example, detected every vulnerability in the original programs but only 45.0% after AntiAgent.
- Semantics and overhead: transformed programs passed all project tests (JS-Obfuscator 88.46%, FPA 68.52%), ran at 1.11x the original execution time and were 1.37x the original size (2.46x and 2.63x for JS-Obfuscator). The rules also worked on vulnerability types absent from the corpus and on Python programs.
- Reliability: baselines and metric definitions are clear, and detection time, cost, precision and recall are all reported. However, each program has only one vulnerability, which is simpler than a real audit, and passing tests does not fully prove semantic equivalence. A leak of the original source is out of scope.

#### Comment
- From an obfuscation standpoint, this marks a new direction: protecting code against LLM agents rather than human analysts or static analyzers. The same techniques could, of course, also help hide malicious code.
- Because some authors are at Chinese institutions (Tsinghua University, Shanghai Jiao Tong University), extra checks were made. Penghui Li, who appears to be the corresponding author, is at Nanyang Technological University in Singapore. The use of public benchmarks (SecBench.js, GitHub Security Advisories) and detailed settings gives a reasonably clear path to reproduction, but no code address was found in the paper. The baselines, a widely used obfuscator and a recent LLM-based method, are appropriate, and detection drops of 50-60% do not look implausibly good.

# Verified Netlist-to-RTL Recovery with LLM Agents
> arXiv preprint (not peer reviewed). University of Minnesota, Twin Cities
> 2026

Gate-level netlists circulate among IP integrators and foundries and can be extracted from chips. Turning them back into readable RTL would help an adversary understand and modify a design, but word-level operations are scattered across many gates. The authors propose LOCA (LOgic Cone Attack), a hardware reverse-engineering attack that splits an anonymized netlist into logic cones covering groups of related registers, has parallel LLM agents rewrite each cone as compact RTL, and assembles the results. A rewrite is accepted only when a formal tool proves it equivalent to the netlist.

Links:
- arXiv abstract: https://arxiv.org/abs/2611.25324
- arXiv HTML full text: https://arxiv.org/html/2611.25324
- arXiv PDF: https://arxiv.org/pdf/2611.25324

### Contribution
- An LLM-based attack methodology that recovers compact, formally equivalent RTL from anonymized gate-level netlists without designer RTL.
- Of five partitioning methods (whole netlist, graph partitioning, clustering, register cuts and register-group cones), only register-group cones led to recovery.
- A reference-free recovery criterion that combines formal equivalence with a compression measure R (the reduction in Boolean operators), separating genuinely abstracted RTL from gate-by-gate copies.
- An assessment of netlist defenses: function-preserving obfuscation such as resynthesis and retiming did not stop LOCA, whereas XOR/XNOR key locking and hidden cell functions (camouflaging) prevented it from proving recovery of the original design.

### Evaluation
- Models: Claude Haiku 5.5, Claude Sonnet 5.5 and GPT-6.1-sol, run in isolated sandboxes without web access, with a guard that blocks prompts or paths naming the benchmarks.
- Results: LOCA recovered 17 of 21 model-design pairs, versus 6 with whole-netlist prompting, and succeeded in 88 of 119 runs versus 7 of 152 whole-netlist replies. Per-run recovery across models rose from 5% to 74%, at a median cost below one dollar with a low-cost model.
- On five fresh designs (three unused public cores and two unpublished designs), LOCA achieved higher recovery rates with all three models, and the recovered RTL was easier for an LLM to understand and modify (10 of 10 edit attempts succeeded).
- Verification: a subset of counted lifts (152 LOCA and 35 whole-netlist) was rechecked with k-induction in SymbiYosys and IC3. LOCA's lead held for lifting thresholds from 30% to 80% (default R > 60%).
- Reliability: because formal equivalence is the acceptance criterion, correctness is well established. The designs are relatively small (hundreds to a few thousand gates), and as a seven-page paper some setup details are brief.

#### Comment
- An important result for hardware obfuscation: transformations that change structure but keep behavior offer little protection against reverse engineering that pairs LLMs with formal verification, and only techniques that inject information the attacker lacks, such as keys or hidden cell functions, actually block a proof of recovery.
