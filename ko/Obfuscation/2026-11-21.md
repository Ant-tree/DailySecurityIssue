# Hardening JavaScript Programs against LLM-Based Vulnerability Detection
> arXiv 프리프린트 (심사 전). 난양 공과대학교, 칭화 대학교, 상하이 자오퉁 대학교
> 2026

자바스크립트는 소스 코드 형태로 배포되는 경우가 많아, 누구나 LLM 기반 취약점 탐지 에이전트로 쉽게 취약점을 찾을 수 있습니다. 실제로 Claude Code나 Codex로 취약 서비스를 찾고 공격 코드를 만든 사례도 보고됐습니다. 저자들은 개발자가 배포 전에 프로그램을 변환해 이런 에이전트의 분석을 방해하는 방어 기법 AntiAgent를 제안했습니다. 퍼저처럼 진화 탐색을 돌려, 알려진 취약점이 있는 프로그램을 조금씩 바꾸고 탐지 에이전트가 취약점을 놓치거나 잘못 보고한 변형만 남긴 뒤, 그 변환을 재사용 가능한 규칙으로 뽑아냅니다. 새 프로그램에는 LLM이 위치마다 알맞은 규칙을 고르고 규칙이 실제 코드 변경을 결정적으로 수행해, 의미를 보존하면서도 프로그램에 맞는 변환을 적용합니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.25718
- arXiv HTML 본문: https://arxiv.org/html/2611.25718
- arXiv PDF: https://arxiv.org/pdf/2611.25718

### Contribution
- 기존 난독화가 이름 줄이기, 문자열 인코딩, 제어 흐름 평탄화처럼 정해진 패턴이라 고성능 에이전트가 쉽게 꿰뚫는다는 점을 짚고, 에이전트의 추론 과정 자체를 노리는 "에이전트 대응 변환"이라는 방향을 제시했습니다. 안티 퍼징을 LLM 분석에 옮긴 발상입니다.
- 변환 발견 단계에서 에이전트의 자체 주장 대신 개념 증명(PoC) 실행 결과로 점수를 매겨, 에이전트가 결과를 조작할 여지를 줄였습니다.
- 규칙은 AST 위의 적용 조건과 연산으로 표현하고, LLM은 규칙 선택과 인자 조정만 맡게 해 의미 보존을 보장하려 했습니다.

### Evaluation
- 데이터: 규칙 발견에는 SecBench.js의 40개 프로그램(프로토타입 오염, 명령 주입, 경로 조작, ReDoS, 임의 코드 주입)을, 평가에는 GitHub 보안 권고에서 고른 실제 애플리케이션 40개(평균 약 3만 7천 줄, 취약점 유형 13종, 프로그램당 알려진 취약점 1개)를 썼습니다. 데이터 오염을 막기 위해 평가 모델 공개 이후에 알려진 취약점만 골랐습니다.
- 탐지 에이전트: Codex(GPT-6.1-sol), Claude Code, ZCode, 자바스크립트 전용 탐지기 OpenAnt 네 가지이며, 웹 검색과 브라우징을 껐습니다.
- 결과: 에이전트별 방어 성공률(탐지 감소율)은 52.0~60.7%로, 기존 난독화 도구 JS-Obfuscator(중간 설정)와 LLM 기반 변환 기법 FPA를 모든 에이전트에서 앞섰습니다. 예를 들어 Claude Code는 원본 취약점을 모두 찾았지만 변환 후에는 45.0%만 찾았습니다.
- 의미 보존과 부담: 변환한 프로그램은 프로젝트 테스트를 모두 통과했고(JS-Obfuscator 88.46%, FPA 68.52%), 실행 시간은 1.11배, 코드 크기는 1.37배였습니다(JS-Obfuscator는 2.46배, 2.63배). 규칙은 말뭉치에 없던 취약점 유형과 파이썬 프로그램에도 효과가 있었다고 합니다.
- 신빙성: 비교 대상과 지표 정의가 분명하고, 탐지 시간과 비용, 정밀도와 재현율까지 함께 보고했습니다. 다만 프로그램당 취약점이 하나뿐이라 실제 감사 환경보다 단순하고, 테스트 통과가 의미 보존의 완전한 증명은 아닙니다. 원본 소스가 유출된 경우는 범위 밖이라고 밝혔습니다.

#### Comment
- 난독화 관점에서 "사람이나 정적 분석기"가 아니라 "LLM 에이전트"를 상대로 한 코드 보호라는 새 흐름을 보여 줍니다. 같은 기법이 악성코드 은닉에 쓰일 수 있다는 양면성도 있습니다.
- 중국 기관(칭화 대학교, 상하이 자오퉁 대학교) 저자가 포함되어 검증을 더 했습니다. 교신 저자로 보이는 Penghui Li는 싱가포르 난양 공과대학교 소속입니다. 공개 벤치마크(SecBench.js, GitHub 보안 권고)를 쓰고 평가 설정을 구체적으로 밝혀 재현 경로는 비교적 명확하지만, 코드 공개 주소는 본문에서 확인하지 못했습니다. 비교 대상은 널리 쓰이는 난독화 도구와 최근 LLM 기반 기법으로 적절하고, 탐지 감소율도 50~60% 수준이라 지나치게 좋은 수치로 보이지는 않았습니다.

# Verified Netlist-to-RTL Recovery with LLM Agents
> arXiv 프리프린트 (심사 전). 미네소타 대학교 트윈시티
> 2026

게이트 수준 넷리스트는 IP 통합 업체와 파운드리 사이를 오가고 칩에서 추출할 수도 있습니다. 이를 읽을 수 있는 RTL로 되돌리면 공격자가 설계를 이해하고 고치기 쉬워지지만, 단어 단위 연산이 수많은 게이트에 흩어져 있어 어렵습니다. 저자들은 익명화한 넷리스트를 관련 레지스터 묶음의 논리 원뿔(logic cone)로 나누고, 병렬 LLM 에이전트가 각 원뿔을 간결한 RTL로 다시 쓰게 한 뒤 조립하는 하드웨어 역공학 공격 LOCA(LOgic Cone Attack)를 제안했습니다. 모든 재작성은 형식 검증 도구가 넷리스트와 동치임을 증명한 경우에만 받아들입니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.25324
- arXiv HTML 본문: https://arxiv.org/html/2611.25324
- arXiv PDF: https://arxiv.org/pdf/2611.25324

### Contribution
- 설계자 RTL 없이 익명화된 넷리스트에서 형식적으로 동치이면서 간결한 RTL을 복원하는 LLM 기반 공격 방법론을 제시했습니다.
- 다섯 가지 분할 방식(전체 넷리스트, 그래프 분할, 군집화, 레지스터 절단, 레지스터 묶음 원뿔) 가운데 레지스터 묶음 원뿔만 복원에 성공함을 보였습니다.
- 형식 동치와 불(Boolean) 연산자 감소율 R을 결합한 참조 없는 복원 기준을 제안해, 게이트를 그대로 옮긴 복사본과 실제로 추상화된 RTL을 구분했습니다.
- 넷리스트 방어 기법을 점검해, 재합성이나 리타이밍 같은 기능 보존 난독화는 LOCA를 막지 못하지만 XOR/XNOR 키 잠금이나 셀 기능 은닉(위장)은 원래 설계 복원의 증명을 막는다는 점을 보였습니다.

### Evaluation
- 모델: Claude Haiku 5.5, Claude Sonnet 5.5, GPT-6.1-sol을 웹 접근이 없는 격리 환경에서 실행했고, 벤치마크 이름을 언급하는 프롬프트나 경로는 차단했습니다.
- 결과: 21개 모델-설계 쌍 가운데 LOCA는 17개를 복원했고(전체 넷리스트 프롬프트는 6개), 실행 단위로는 119회 중 88회 성공해 전체 넷리스트 응답 152개 중 7개보다 크게 앞섰습니다. 모델 전반의 실행당 복원율은 5%에서 74%로 올랐고, 저가 모델 기준 중앙 비용은 1달러 미만이었습니다.
- 새 설계 다섯 개(공개 코어 3개와 미공개 설계 2개)에서도 세 모델 모두 더 높은 복원율을 보였고, 복원한 RTL은 LLM이 이해하고 수정하기 쉬웠습니다(수정 시도 10회 중 10회 성공).
- 검증: 집계한 복원 결과 일부(LOCA 152건, 전체 넷리스트 35건)를 SymbiYosys의 k-귀납법과 IC3로 다시 확인했습니다. 복원 판정 기준(R > 60%)을 30~80%로 바꿔도 우위가 유지됐습니다.
- 신빙성: 형식 동치 증명을 기준으로 삼아 결과의 정확성은 강하게 담보됩니다. 다만 대상 설계가 수백~수천 게이트 규모의 비교적 작은 회로이고, 7쪽 분량의 짧은 논문이라 세부 설정 일부는 생략되어 있습니다.

#### Comment
- 하드웨어 난독화 관점에서 중요한 결과입니다. 기능은 그대로 두고 구조만 바꾸는 변환은 LLM과 형식 검증을 결합한 역공학 앞에서 보호 효과가 약하고, 키나 셀 기능처럼 공격자가 모르는 정보를 넣는 기법만 실제로 복원 증명을 막는다는 점을 보여 줍니다.
