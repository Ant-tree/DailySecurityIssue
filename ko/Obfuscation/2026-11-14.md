# obfsgen: Generative Tunnel Obfuscation
> arXiv 프리프린트 (심사 전). 홍콩 중문대학교, 홍콩대학교
> 2026

검열 우회용 암호화 터널(Trojan, VLESS, NaiveProxy 등)이 대부분 TLS 위에서 돌아가게 되면서, 검열 측은 패킷 내용 대신 트래픽의 모양(패킷 크기, 간격, 방향)으로 터널을 찾아내고 있습니다. obfs4 같은 기존 트래픽 난독화 도구는 응용 프로그램이 데이터를 쓸 때마다 패딩을 붙이거나 쪼개거나 늦추는 방식(응용 주도형)이라, 응용 프로그램이 만든 모양에 무언가를 더할 수만 있고 응용 프로그램이 쉬는 동안에는 아무것도 보낼 수 없습니다. 그래서 터널 때문에 생기는 추가 왕복 시간 같은 지문은 근본적으로 감출 수 없습니다. obfsgen은 언제, 얼마만큼 보낼지를 응용 프로그램과 무관하게 스스로 정하는 일정 주도형 난독화 도구입니다. 일정은 정상 TLS 트래픽으로 학습한 생성형 시퀀스 모델에서 뽑으며, 이 모델은 흐름의 지금까지 전체 이력을 보고 다음 TLS 레코드의 크기와 시점을 예측합니다. 양 끝점이 같은 모델에서 같은 계획을 뽑아 손실과 지연이 있는 네트워크에서도 동기를 맞추는 문제도 함께 다뤘습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.15019
- arXiv HTML 본문: https://arxiv.org/html/2611.15019
- arXiv PDF: https://arxiv.org/pdf/2611.15019

### Contribution
- 기존 응용 주도형 난독화가 왜 터널 지문을 완전히 감출 수 없는지 구조적으로 설명하고, 일정 주도형 구조를 대안으로 제시했습니다.
- 정상 트래픽의 장거리 의존성을 담는 생성형 모델로 일정을 만들고, 흐름의 음의 로그 가능도가 구별 가능성의 대리 지표로 쓸 수 있음을 검증했습니다.
- Go 언어로 프로토타입을 구현해 공개했고(본문 부록에 저장소 안내), 동기화와 실시간 동작 같은 실제 배포 문제를 다뤘습니다.

### Evaluation
- 데이터: 저자들 캠퍼스 게이트웨이에서 수집한 정상 TLS 트래픽. 비교 대상 터널은 Trojan, VLESS, VMess를 TLS, WebSocket/TLS, REALITY 위에서 돌린 9종(종류별 4,445개 흐름).
- 분류기 6종(히스토그램 가능도비, 수작업 특징 랜덤 포레스트, 마르코프 체인, CNN, GRU, Transformer 기반)을 세 가지 검열자 모델로 평가했습니다.
- 알려진 터널을 차단하는 검열자: 기존 터널은 AUC 1.000으로 완전히 구별되지만 obfsgen 흐름은 최고 AUC 0.561~0.581로 무작위 추측에 가깝습니다.
- 정상만 허용하는 검열자: 기존 터널 0.965, obfsgen 0.605~0.642.
- 배포된 모델 가중치까지 가진 검열자: 0.764~0.838까지 올라가 어느 정도 구별됩니다.
- 성능: 흐름 하나의 실제 전달량(goodput)은 왕복 시간에 따라 초당 약 0.8~4.2kB로, 응용 프로그램이 쓰는 양의 3분의 1 수준입니다. 동시 흐름 수를 늘리면 개선되지만 추론 비용이 커집니다.
- 신빙성: 저자들 스스로 "특정 분류기에 강하다고 해서 시험하지 않은 분류기에도 안전하다는 뜻은 아니다"라고 명시했고, 실제 정상 흐름을 같은 일정으로 재생한 기준선과 나란히 비교해 네트워크 효과와 모델 효과를 분리했습니다. 정상 트래픽이 한 캠퍼스에서 수집된 것이라, 다른 네트워크에서는 다시 학습이 필요하다고 밝혔습니다.

#### Comment
- 여기서 난독화는 코드가 아니라 네트워크 트래픽 모양을 숨기는 의미입니다. 생성형 모델로 "정상처럼 보이는 모양"을 만드는 접근은 코드 난독화에서 정상 코드 분포를 흉내 내는 시도와 비슷한 고민(허용 목록 방식 탐지, 모델 유출 시 취약성)을 공유합니다.
- 실용성의 가장 큰 걸림돌은 처리량입니다. 흐름당 수 kB/s 수준이라 웹 서핑보다 메시지나 가벼운 트래픽에 맞고, 저자들도 첫 단계라고 밝혔습니다.
- 중국 기관(홍콩 소재 대학) 논문이라 추가로 확인했습니다. 저자 Diwen Xue는 검열 측정과 우회 분야에서 꾸준히 논문을 낸 연구자이고, 코드 공개를 명시했으며, 결과도 백색 상자 검열자에게는 구별된다는 불리한 수치까지 그대로 보고해 지표를 부풀린 흔적은 보이지 않습니다. 심사 전 원고입니다.

# Preserve the Vulnerability, Break the Alert: Testing the Robustness of CodeQL Taint Tracking with Natural Rewrites
> arXiv 프리프린트 (심사 전). 노스캐롤라이나 주립대학교
> 2026

CodeQL 같은 정적 분석 도구는 CI와 코드 리뷰에서 보안 관문 역할을 하고, 개발자는 수정 후 경고가 사라지면 취약점도 사라졌다고 받아들이는 경우가 많습니다. 이 논문은 취약점은 그대로 두고 겉모습만 바꾼 평범한 리팩터링으로 경고가 얼마나 쉽게 사라지는지를 측정했습니다. 대형 언어 모델(Claude Opus 4.7)에 CodeQL이 보여 주는 경고 정보만 주고, 보고된 데이터 흐름 위의 함수 하나를 그럴듯한 유지보수 변경처럼 다시 쓰게 했습니다. 예를 들어 명령어 문자열을 덧셈으로 잇던 코드를 배열에 담아 join(' | ')으로 합치면 실행 시 같은 문자열이 만들어지지만, CodeQL은 공백 하나로 잇는 join만 모델링하고 있어 오염 추적이 끊깁니다. 수동 감사와 통제 실험으로 취약점은 남고 경고만 사라졌는지 하나하나 확인했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.17123
- arXiv HTML 본문: https://arxiv.org/html/2611.17123
- arXiv PDF: https://arxiv.org/pdf/2611.17123
- 재현 패키지(흐름, 재작성 코드, 도구 출력): https://figshare.com/s/63962213d3744750c45d

### Contribution
- 취약점을 보존하는 자연스러운 재작성에 대한 견고성을 메타모픽 관계로 정식화하고, 경고 소실과 취약점 보존을 함께 검증하는 파이프라인을 만들었습니다.
- 경고를 사라지게 한 재작성 70건을 모두 일곱 가지 라이브러리 모델링 공백으로 추적했고, 그중 64건은 CodeQL이 이미 모델링하는 API 안의 공백이었습니다. 가장 큰 것은 WHATWG URL 생성자로, 쿼리 부분에는 오염을 전파하지만 경로(pathname)에는 전파하지 않아 혼자서 43건을 차지했습니다. 이 공백들은 현재 CodeQL 릴리스에도 남아 있습니다.
- 같은 재작성을 다른 분석기에도 적용해, 문제가 CodeQL만의 것이 아님을 보였습니다.

### Evaluation
- 데이터: 실제 npm 취약점 권고(경로 조작 CWE-22/23, 명령어 주입 CWE-77/78, XSS CWE-79)에서 CodeQL이 탐지하는 172개 흐름, 유효한 재작성 시도 514건. 경로 조작 사례가 대부분이고 명령어 주입 CWE-77(11건)과 XSS(7건)는 적어서 해당 비율은 참고치라고 저자들이 밝혔습니다.
- 흐름당 세 번 시도하면 26.2%의 흐름에서 경고가 사라졌고, 경고 하나를 없애는 데 든 모델 비용은 약 0.51달러였습니다.
- 경고 정보를 주지 않고 같은 함수를 그냥 리팩터링하라고 했을 때는 한 건도 경고가 사라지지 않았습니다. 중간 변수 추가나 구조 분해 같은 일반적인 언어 수준 변환은 거의 영향이 없었습니다.
- 다른 분석기 전이: ODGen 분석 범위 안의 재작성 중 74%가 ODGen 경고도 없앴고, CodeQL, ODGen, njsscan 공통 범위에서는 53%가 세 도구를 모두 피했습니다. 비율에는 95% Wilson 신뢰 구간을 붙였습니다.
- 신빙성: 모든 경고 소실 사례를 수동으로 확인했고 재현 패키지를 공개했습니다. 생성 모델 하나만 썼다는 점, 표본이 일부 CWE에 몰린 점은 한계입니다.

#### Comment
- 엄밀한 의미의 난독화는 아니지만, 동작을 보존하는 코드 변환으로 분석 도구를 피한다는 점에서 난독화와 같은 문제를 다룹니다. 탐지 회피 목적의 의도적 난독화보다 훨씬 "평범해 보이는" 변환으로도 상용 정적 분석이 뚫린다는 점이 핵심입니다.
- 실무 시사점이 분명합니다. 자동 수정 도구나 LLM 보조 수정이 "재검사 통과"를 성공 기준으로 삼으면, 실제로는 분석기의 모델링 경계를 넘었을 뿐인 변경을 수정으로 착각할 수 있습니다.
