# Beyond Sensitive APIs: Detecting Access Control Flaws at Sensitive Callsites in Android Firmware
> NDSS Symposium 2027 채택 논문(논문 PDF 표기: 2027년 3월 22~26일, 서울, DOI 10.14722/ndss.2027.231311), arXiv cs.CR 2611.00594 공개본. 전자과학기술대학교(중국)
> 2026 (학회 발표는 2027)

제조사가 펌웨어에 넣어 출시하는 사전 설치 앱은 높은 권한을 갖고 있고 사용자가 지울 수도 없어, 취약점 하나가 그 제조사의 모든 기기로 번집니다. 기존 연구는 앱이 미리 정해 둔 "보안상 민감한 API" 목록의 API를 호출하는지로 위험을 판단합니다. 그런데 오탐을 줄이려고 데이터베이스 조회 같은 일반 API는 이 목록에서 빼기 때문에, 일반 API가 보호된 데이터를 다룰 때 생기는 취약점을 놓칩니다. 2025년 폴란드 CERT가 공개한 사례처럼, 사전 설치 앱의 ContentProvider가 아무 권한 없이 사용자 PIN을 읽게 해 주는 경우가 대표적입니다.

CALLIX는 ContentProvider 구성 요소에서 이런 "민감한 호출 지점의 접근 제어 부족"을 찾는 정적 분석 도구입니다. 세 단계로 동작합니다. 먼저 API가 무슨 일을 하는지와 그 호출이 다루는 데이터가 무엇인지를 함께 보고 호출 지점의 민감도를 판단합니다. 다음으로 실행 경로 위의 분기 조건에서 보안 검사를 복원해, 무엇을 무엇으로 검증하는지를 명시적인 보안 속성으로 표현합니다. 마지막으로 "제한 맥락(restriction context)"이라는 개념으로 그 검사들이 해당 연산과 데이터를 보호하기에 충분한지를 판정합니다. 정적 분석으로 뽑은 근거 위에서 LLM이 의미를 판단하는 구조이며, LLM이 프로그램 분석을 대체하지는 않습니다.

### Contribution
- "검사가 있느냐"가 아니라 "검사가 그 연산과 데이터에 충분하냐"를 묻는 새로운 문제를 제기했습니다. 일반 API도 다루는 데이터에 따라 민감해질 수 있다는 관점입니다.
- 연산과 데이터 의미로 민감한 호출 지점을 찾고, 접근 제어 검사를 보안 속성으로 복원하고, 제한 맥락으로 충분성을 판정하는 분석 방법을 제안했습니다.
- 10개 주요 제조사의 펌웨어 이미지 50개, 사전 설치 앱 1,750개를 분석해 424개 ContentProvider에서 취약 경로 819개를 찾았습니다. 그중 42.1%는 일반 데이터베이스 연산으로 사용자 개인 데이터를 읽거나 바꿀 수 있었습니다.
- 완화책으로 ContentProvider.call() 같은 범용 인터페이스에 특권 기능을 몰아넣지 말 것, 패키지 이름처럼 호출자가 조작할 수 있는 문자열 대신 Binder.getCallingUid()나 서명 수준 권한으로 호출자를 확인할 것을 제시했습니다.

### Evaluation
- 데이터: Google을 포함한 10개 제조사에서 제조사마다 펌웨어 5개를 Android Dumps와 FirmwareDrive에서 수집했습니다. 대규모 분석에는 deepseek-v3-flash를 썼습니다.
- 정확도: 보고된 경로의 60%인 492개를 무작위로 뽑아 연구자 두 명이 검증했고, 468개가 실제 취약점이어서 정밀도 95.1%였습니다. 확인된 경로마다 동작하는 개념 증명 코드를 만들었습니다. 제조사들은 98개 Provider에 걸친 278건의 보고를 독립적으로 확인했고, 일부는 포상이나 수정으로 이어졌습니다.
- 분리 실험(경로 500개 균형 벤치마크): 코드 조각만 주면 안전한 경로 250개 중 206개를 취약하다고 잘못 판정했고, 분류 체계를 더하면 정밀도는 94.6%로 오르지만 재현율이 56.4%로 떨어졌습니다. 충분성 판단까지 더하면 재현율 92.0%, F1 92.6%, 오판정 17개로 개선되었습니다.
- 모델 의존성: 백엔드를 deepseek-v4-pro, gemini-3.1-pro, claude-opus-5로 바꿔도 정확도 차이는 2.2%포인트 이내였고, 비싼 모델(비용 68배, 139배)이 정확도를 1.4, 2.0%포인트만 높였습니다. 같은 근거와 판정 기준을 상용 코딩 에이전트(claude-opus-5)에 그대로 넘겨도 CALLIX보다 F1이 6.6포인트 낮았습니다.
- 지표 신빙성: 수작업 검증, 개념 증명, 제조사 확인까지 거쳐 결과 신뢰도가 높습니다. 다만 가장 가까운 기존 연구 FirmScope는 공개되지 않아 직접 돌리지 못했고, FirmScope가 평가된 설정 안에서만 비교했습니다. 재현율은 균형 벤치마크로만 추정했으므로 실제 펌웨어 전체에서 놓친 취약점 규모는 알 수 없습니다.

#### Comment
- 제조사 사전 설치 앱이 ContentProvider를 사실상 특권 명령 채널로 쓰고 있다는 관찰이 인상적입니다. 모바일 보안 SDK나 앱 진단 도구에서 "민감 API 목록" 방식의 한계를 보완할 때 참고할 만한 설계입니다.
- 한계: 저자들이 밝힌 대로 정적 분석 기반이라 일부 구성 요소를 거치는 데이터 흐름, 리플렉션 같은 정교한 난독화, 네이티브 라이브러리는 분석하지 못하며, LLM의 잘못된 해석으로 인한 오탐이 남습니다. 코드 공개 여부는 이번에 읽은 범위에서 확인하지 못했습니다.
- 게재처: 보안 분야 최상위 학회인 NDSS 2027 채택 논문으로 신뢰도가 높습니다.
- 중국 기관 검증: 저자 전원이 중국 전자과학기술대학교 소속입니다. 게재처 NDSS는 실재하는 최상위 학회이고 DOI가 발급되어 있습니다. 정밀도는 무작위 표본 수작업 검증으로 측정했고 95.1%라는 수치가 지나치게 완벽하지 않으며, 분리 실험에서 불리한 중간 결과도 함께 보고했습니다. 제조사가 278건을 독립적으로 확인했다는 외부 근거도 있습니다. 비교 대상 FirmScope를 직접 실행하지 못한 점은 한계로 남지만, 저자들이 그 이유와 비교 범위를 명시했습니다. 이를 바탕으로 싣습니다.

# A Symbolic-Neural Framework for Context-Aware Evidence Extraction from Mobile SQLite Databases
> HICSS-60(60th Hawaii International Conference on System Sciences) 채택 논문, arXiv cs.CR 2611.03323 공개본. 볼티모어대학교, Cox Automotive(미국)
> 2026

모바일 앱은 대화, 연락처, 위치 같은 데이터를 대부분 SQLite 데이터베이스에 저장하므로 디지털 포렌식에서 핵심 증거원입니다. 그러나 앱의 스키마는 공개되지 않고, 버전마다 바뀌고, 안드로이드와 iOS에서도 다르기 때문에 스키마별 파서는 쉽게 깨지고 유지하기 어렵습니다.

SNEEF는 스키마에 의존하지 않고 증거를 뽑는 기호-신경 결합 방식입니다. 각 행을 표준화된 출처 메타데이터와 열 이름을 붙인 "맥락-값" 쌍으로 표현하고, 언어 모델이 사람 이름, 전화번호, 이메일, URL, 메시지, 주소, 타임스탬프 등 아홉 가지 포렌식 개체를 인식합니다. 이어서 PA-EEP라는 출처 보존 절차로 받아들인 개체마다 원래 테이블과 행을 묶어, 나중에 증거를 추적해 검증할 수 있게 합니다. 개체로 볼 수 없거나 제약을 어기는 결과는 거부하며, 패턴이 뚜렷한 유형은 정규식 검출기로 먼저 거르는 단계(ESTRE)를 두어 모델 호출을 줄입니다.

### Contribution
- 행을 계층적 기호 맥락으로 감싸 고정 필드 매핑 없이 서로 다른 앱 스키마에서 증거를 뽑는 표현 방식을 제안했습니다.
- 받아들인 개체를 원래 행에 묶는 출처 보존 절차로, 언어 모델이 관여해도 증거를 추적할 수 있게 했습니다.
- 오류가 왜 생기는지를 분류하는 증거 실패 유형(Evidence Failure Mode) 분류 체계와 지표를 제안했습니다.
- 검증된 정답 자료, 부호화한 기록, 출력, 채점 스크립트를 공개했습니다.

### Evaluation
- 데이터: 공개된 안드로이드, iOS 기기 이미지로 만든 다섯 개 말뭉치(WhatsApp 세 개 포함)로, 여러 앱 버전에 걸쳐 있으며 정답은 검사관이 검증했습니다.
- 설정: Claude Opus 4.8을 온도 0, 탐욕적 디코딩으로 고정하고, 맥락을 붙인 경우와 붙이지 않은 경우만 비교했습니다.
- 결과: 앱 이름을 제외한 행 내용의 증거 개체 F1은 맥락을 붙였을 때 0.967(95% 신뢰구간 0.965~0.970), 붙이지 않았을 때 0.728이었습니다. 모든 말뭉치에서 개선 폭의 신뢰구간이 0보다 컸고, 특히 재현율 개선이 컸습니다.
- 지표 신빙성: 같은 모델, 같은 행에서 조건만 바꾼 비교라 맥락의 효과는 분명합니다. 다만 비교 대상이 "맥락 없는 같은 방식"뿐이고, 기존 상용 포렌식 도구나 스키마별 파서와의 비교는 이번에 읽은 범위에서 확인하지 못했습니다.

#### Comment
- 앱 업데이트마다 파서를 고쳐야 하는 모바일 포렌식의 고질적인 문제에 실용적인 해법을 제시합니다. 증거를 원래 행에 묶는 설계는 법정 증거 요건을 의식한 것으로 보입니다.
- 한계: 저자들도 외부 API로 수사 자료를 보내는 것은 관할권, 개인정보, 증거 보관 연속성 문제가 있다며, 실제 운용은 로컬 모델로 해야 한다고 밝혔습니다. 출처 보존은 추적 가능성을 보장할 뿐, 데이터베이스에 적힌 내용 이상의 사실성을 보장하지는 않습니다.
