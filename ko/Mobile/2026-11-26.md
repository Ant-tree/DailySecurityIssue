# Aftershock: Yesterday's Linux Kernel Bugs, Tomorrow's Android Exploits
> arXiv 프리프린트 (심사 전). UC 리버사이드
> 2026

안드로이드 커널은 리눅스 업스트림 수정이 LTS, 안드로이드 공통 커널(ACK), 제조사 펌웨어를 차례로 거쳐야 기기에 도착하기 때문에 패치가 늦게 반영되는 문제가 오래 있었습니다. 저자들은 이 지연이 이제 단순한 패치 관리 문제가 아니라, 공개된 업스트림 패치를 LLM 에이전트가 설계도 삼아 실제로 동작하는 n-day 익스플로잇을 만드는 문제로 바뀌었다고 주장하고, 이를 처음부터 끝까지 검증하는 파이프라인을 만들었습니다. 파이프라인은 업스트림 패치를 걸러 메모리 안전성 버그를 고르고, 패치 이분 탐색으로 영향받는 ACK 브랜치를 찾고, Cuttlefish 가상 기기에서 일반 앱 권한(untrusted_app SELinux 도메인)으로 재현한 뒤, 상용 LLM 에이전트에게 로컬 권한 상승(LPE) 익스플로잇을 만들게 합니다. 완성된 APK는 KASLR, PAN, PXN, CFI 같은 실제 보호 기법이 켜진 새 인스턴스에서 에이전트 없이 독립적으로 검증합니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.31547
- arXiv HTML 본문: https://arxiv.org/html/2611.31547
- arXiv PDF: https://arxiv.org/pdf/2611.31547

### Contribution
- 업스트림 패치 선별, 앱 권한에서의 재현, 독립 검증까지 이어지는 안드로이드 커널 n-day 측정 파이프라인을 만들었습니다. 미리 만든 재현 코드나 익스플로잇 힌트를 주지 않고, 프롬프트에는 환경과 도구, 목표만 적었습니다.
- 반복 시도 신뢰도와 커널 리비전 간, 가상 기기에서 실제 Pixel 기기로의 이식성을 측정했습니다.
- 업스트림 수정이 GKI 브랜치와 Pixel 펌웨어에 도착하기까지의 지연을 추적해, 방어 쪽 시간 척도를 정량화했습니다.
- 에이전트가 만든 17개 익스플로잇의 코드를 분석해, 기존 리눅스 커널 익스플로잇 기법과 비교했습니다. SELinux를 먼저 끄고 그 뒤에 디버깅 인터페이스(tracefs 등)로 주소를 찾는 식의 새로운 전략 2가지와 기법 3가지를 보고했습니다.

### Evaluation
- 대상: 2024년 1월부터 33개월간 공개된 CVE 가운데 런타임 재현 단계에 들어간 152개. 모델은 OpenAI의 gpt-5.6-sol 추론 모델(xhigh 추론 강도, 실험당 비용 상한 1,250달러)이었습니다.
- 결과: 152개 중 38개를 일반 앱에서 재현했고, 그중 17개에서 독립 검증을 통과한 LPE 익스플로잇을 얻었습니다. 성공 사례는 재현부터 검증까지 중앙값 14.3 에이전트 시간, API 비용 중앙값 321.07달러가 들었습니다.
- 신뢰도: 새 인스턴스 170회 시도에서 익스플로잇별 성공률 중앙값은 90%였고, Pixel 9와 Pixel 10 실기기에서는 14회 중 12회(85.7%)가 성공했습니다.
- 패치 지연: 패치된 CVE-브랜치 쌍 201개의 GKI 반영 지연 중앙값은 21.5일(미패치 쌍을 포함하면 최소 71.4일)이었고, Pixel 펌웨어 반영은 중앙값 181일이었습니다. 평가한 Pixel 공장 이미지의 64.1%가 출시일 기준으로 이미 CVE가 공개된 취약점을 하나 이상 포함하고 있었습니다. 익스플로잇에 성공한 17개 CVE 중 안드로이드 보안 게시판에 실린 것은 3개뿐이었습니다.
- 신빙성: 성공 판정을 플래그 획득만으로 하지 않고, 별도 LLM 검토자가 실제로 지정된 취약점을 썼는지 확인했습니다. 다만 대부분의 실험이 예산 소진으로 끝났기 때문에 17개는 하한값이고, 단일 모델과 단일 프롬프트 설계에 기반한 결과입니다.

#### Comment
- "공개 패치에서 몇 시간 만에 익스플로잇, 기기 반영은 몇 달"이라는 비대칭을 실측 수치로 보여 준 점이 가장 중요합니다. 모바일 보안 담당자 입장에서는 안드로이드 보안 게시판만 보고 위험도를 판단하면 안 된다는 근거가 됩니다.
- 저자들도 같은 파이프라인을 방어 쪽에서 패치 영향 판단에 쓸 수 있다고 언급합니다. 익스플로잇 코드 공개 여부와 구체적인 공개 범위는 본문에서 확인하지 못했습니다.
- 게재처가 정해지지 않은 심사 전 원고입니다. 저자 Zhiyun Qian은 커널과 네트워크 보안 분야에서 꾸준히 최상위 학회 논문을 내 온 연구자입니다.

# Harvesting Apple's Orchard: A Security Analysis of On-Device CoreML Models Across the Apple Ecosystem
> arXiv 프리프린트 (심사 전). 크와메 은크루마 과학기술대학교(가나) VIA 사이버보안 연구실
> 2026

애플은 스팸 문자 분류, 배터리 충전 예측, 추천, 사진 분석 같은 기능을 위해 iOS, iPadOS, macOS, tvOS 안에 수백 개의 CoreML 모델을 넣어 배포합니다. 이 모델들은 메시지나 미디어 같은 신뢰할 수 없는 입력을 받고, 다른 시스템 구성 요소가 그 출력을 그대로 믿는다는 점에서 시스템 데몬과 같은 보안 경계라고 저자들은 봅니다. 논문은 펌웨어 이미지 6종과 기기 2대(iOS 16.7 아이폰 X, 탈옥한 iOS 26.1 가상 연구 기기)에서 CoreML 산출물 1,137개를 수집해 정적 분석, 컴파일된 번들의 복원, 정확도와 적대적 견고성, 지연 시간, 가중치 변조, 크래시 시험을 수행한 첫 체계적 분석이라고 밝힙니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.31688
- arXiv HTML 본문: https://arxiv.org/html/2611.31688
- arXiv PDF: https://arxiv.org/pdf/2611.31688
- 저자 저장소(재현용 코드와 측정 기록, 가중치 제외): https://github.com/jayluxferro/on-device-coreml-security

### Contribution
- 연구 기기에서 54개 프레임워크 그룹, 모델 파일 320개를 목록화하고, 8개 출처에서 산출물 1,137개를 정리했습니다.
- 문서화되지 않은 .mlmodelc 번들을 다시 불러올 수 있는 .mlpackage로 바꾸는 도구를 만들어 155개 모델을 실행 가능한 상태로 복원했습니다.
- 8가지 발견을 보고했습니다. 대표적으로 산출물 368개가 학습된 가중치를 암호화 없이 평문으로 담고 있고(369.61MiB), MIL 번들 166개 모두가 내부 모델 데이터베이스 토큰을 노출했습니다. 갱신 가능 표시(isUpdatable=1)가 있는 번들도 11개 있었습니다.

### Evaluation
- 적대적 평가: 모델 경로 221개, 예측 호출 77,396회를 포함한 82,092건의 기록에서 최악의 경우 판정 반전율이 100%였습니다. 폭이 0인 공백 문자 삽입만으로 인도 영어 SMS 필터는 20개 중 13개(65%), 미국 영어 판은 20개 중 14개(70%)가 뒤집혔습니다(후자는 실제 토크나이저 대신 대체 임베딩 사용).
- 무결성: 연구 기기에서 16바이트 가중치 수정만으로 상호작용 예측 모델의 시험 입력 8개 중 7개가 바뀌었고, 실행 중 무결성 검사는 관찰되지 않았습니다.
- 크래시: 애플의 손동작 모델을 공개 CoreML API로 불러오면 libBNNS가 M2 실기기에서 4번 중 4번 크래시했습니다. 애플은 재현했지만 보안 경계를 넘지 않는 자체 크래시로 분류했고, 저자들도 이를 취약점이 아닌 가용성과 견고성 문제로 정리했습니다.
- 피싱: SMS 분류기가 직접 만든 피싱 문자 10개 중 8~9개를 거래 알림으로 분류했습니다. 다만 이는 분류기 라벨일 뿐 실제 받은편지함 분류 결과는 아닙니다.
- 신빙성: 저자들 스스로 SMS 벤치마크가 20개, 피싱 시험이 10개뿐이라 비율은 모집단 추정이 아니라고 밝혔습니다. 평문 가중치 수치는 산출물마다 앞부분 64KiB만 훑은 하한값이고, 지연 시간은 탈옥한 가상 기기에서 잰 값입니다.

#### Comment
- 앱에 내장된 모델이 아니라 OS가 시스템 권한으로 실행하는 모델을 대상으로 삼았다는 점이 새롭습니다. 다만 크래시, 빌드 토큰 노출, 내부 경로 노출 세 건은 애플이 모두 보안 문제로 인정하지 않았으므로, 실제 공격 경로라기보다는 견고성 측면의 결과로 읽는 것이 맞습니다.
- 윤리 측면에서 공개 펌웨어와 소유 기기만 썼고 사용자 데이터는 다루지 않았으며, 가중치는 재배포하지 않았다고 밝혔습니다.
- 게재처가 정해지지 않은 심사 전 원고입니다. 저장소 설명에 "익명 심사 제출용 재현 산출물"이라고 적혀 있어 학회 심사 중인 것으로 보입니다.
