# Beyond a Single Commit: Anchor-Guided Reconstruction of Multi-Commit Patches
> arXiv cs.CR 2611.09026 (프리프린트, 심사 전). 울런공대학교(호주), 국제관계학원(중국), 칭화대학교(중국), 퍼듀대학교(미국)
> 2026

취약점과 그 수정 커밋을 연결하는 패치 식별은 취약점 분석, 대응, 보안 도구 개발의 바탕입니다. 그런데 실제 수정은 커밋 하나로 끝나지 않는 경우가 많습니다. 같은 결함이 여러 위치에 흩어져 있어 비슷한 수정이 반복되거나, 처음 수정이 불완전해 몇 주 뒤 추가 커밋이 붙기도 합니다. 본문은 TensorFlow의 한 취약점이 2018년 3월 커밋으로 처음 고쳐진 뒤 추가 커밋으로 보완된 사례로 이를 보여 줍니다. 기존 도구는 커밋을 하나씩 따로 보기 때문에 이런 다중 커밋 패치를 놓칩니다.

저자들은 HARPOON을 제안합니다. 먼저 대상 취약점을 고쳤을 가능성이 높은 "기준(anchor) 커밋"을 골라냅니다. 그다음 기준 커밋과 수정 패턴이 비슷한 커밋을 찾아 빠진 위치를 채우고(범위 보완), 기준 커밋과 직접 또는 간접 의존 관계가 있는 커밋을 따라가 수정 과정을 재구성합니다(의존성 재구성). 마지막으로 LLM으로 후보 커밋의 의도를 확인해, 겉보기에 비슷하거나 의존 관계가 있어도 목적이 다른 커밋을 걸러 냅니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.09026
- arXiv HTML 본문: https://arxiv.org/html/2611.09026
- arXiv PDF: https://arxiv.org/pdf/2611.09026

### Contribution
- 다중 커밋 패치를 명시적으로 다루는 패치 식별 틀을 제시했습니다. 모든 커밋을 LLM에 넣지 않고 기준 커밋에서 출발해 범위를 좁히므로, LLM이 긴 커밋 이력에서 오류를 누적하는 문제를 줄입니다.
- 커밋별 다중 커밋 패치 주석이 달린 벤치마크를 새로 만들었습니다. C/C++, Java, Python 각 10개씩 인기 프로젝트 30개에서 공개 수정 커밋이 있는 CVE 2,374개를 모으고, 그중 1,207개 취약점(단일 커밋 1,019개, 다중 커밋 188개)으로 평가 세트를 구성했습니다.
- 실제 환경 적용에서 공개 취약점 데이터베이스에 없던 패치 895개를 찾았고, 그중 663개는 CRITICAL 또는 HIGH 등급 취약점 323개의 기록되지 않은 수정이었습니다.

### Evaluation
- 비교 대상: TAPER, VFCFinder, SHIP, Prospector 네 가지 최신 기법. 정의가 서로 다른 점을 고려해 커밋 단위 식별 정확도와 커밋 범위 포괄성을 나눠 세 가지 방식으로 비교했습니다.
- 결과: 단일 커밋 패치 F1 93.02%, 다중 커밋 패치 F1 75.08%로 기존 기법보다 크게 앞섰다고 보고합니다. 기본 LLM은 비용 대비 효과를 이유로 GPT-5-Nano를 썼고, 구성 요소별 제거 실험과 계산 비용도 함께 분석했습니다.
- 지표의 신빙성: 벤치마크의 정답 주석을 저자들이 NVD, Debian 보안 정보, GitHub Advisory Database와 수동 검토로 직접 만들었으므로, 정답 정의가 제안 기법에 유리하게 맞춰졌을 가능성은 남습니다. 본문에서 코드나 데이터셋 공개 주소는 찾지 못했습니다.

#### Comment
- 패치 정보가 비어 있는 CVE가 많다는 현실에서, 실제로 수백 건의 누락 패치를 찾았다는 점이 실무적으로 의미가 큽니다. 공급망 취약점 관리나 SCA 도구의 패치 데이터 품질과 직결됩니다.
- 중국 기관 검증: 1저자와 교신 저자진(Siqi Ma, Willy Susilo)은 울런공대학교 소속이고, 중국 쪽 공저자는 국제관계학원의 Xu Gai와 칭화대학교의 Chao Zhang입니다. 퍼듀대학교의 Elisa Bertino도 참여했습니다. 저자와 소속은 모두 보안 분야에서 활동이 확인되는 실재 연구자와 기관입니다. 주 연구 기관이 호주 대학이고 평가 수치는 단일 커밋과 다중 커밋 사이 차이처럼 어려운 경우의 한계도 그대로 드러내고 있어 과장된 지표로 보기는 어렵습니다. 다만 코드와 벤치마크가 공개되지 않아 재현 가능성은 현재 확인할 수 없습니다.
- 본문 출처: 제목 검색에서 공식 페이지나 저자 저장소가 나오지 않아, 사용자 컴퓨터에서 받은 arXiv 공식 PDF로 읽었습니다.

# Empirical Study of Post-Quantum Cryptography Adoption Status in SSH Infrastructure
> arXiv cs.CR 2611.09703 (프리프린트, 심사 전). Bitsight Technologies(미국)
> 2026

양자 컴퓨터가 현재 공개키 암호를 깰 수 있게 되는 시점("Q-day")에 대비해 주요 CDN과 클라우드는 이미 양자 내성 암호(PQC)로 옮겨 가고 있습니다. 기존 연구는 주로 PQC 성능을 재는 데 머물렀고, 실제로 얼마나 배포됐는지는 잘 알려지지 않았습니다. 이 논문은 보안 평가 기업 Bitsight의 자체 인터넷 스캔 데이터로, 22번 포트에서 SSH를 운영하는 호스트 152만 대와 이를 소유한 조직 27,012곳의 SSH 키 교환 알고리즘을 분석합니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.09703
- arXiv HTML 본문: https://arxiv.org/html/2611.09703
- arXiv PDF: https://arxiv.org/pdf/2611.09703

### Contribution
- SSH 영역의 PQC 실제 배포 현황을 대규모 스캔 자료로 정리했습니다. 호스트 기준 45.2%가 PQC 키 교환을 지원하고 54.8%는 기존 알고리즘만 씁니다. 조직 기준으로는 39.9%가 적어도 한 호스트에서 PQC를 켰고, 60.1%는 전혀 지원하지 않습니다.
- 어떤 PQC 알고리즘이 쓰이는지도 집계했습니다. sntrup761x25519-sha512@openssh.com이 44.86%, 같은 알고리즘의 표준 이름 sntrup761x25519-sha512가 11.08%로 가장 많았고, mlkem768x25519-sha256은 5.79%였습니다(한 서버가 여러 알고리즘을 함께 내세우므로 비율은 서로 겹칩니다). 이 밖에 mlkem1024nistp384, frodokem, kyber1024 조합 같은 드문 변형도 관찰했습니다.
- 산업, 지역, 조직 규모(디지털 자산 규모와 재무 규모)와 PQC 도입의 관계를 함께 분석했습니다.

### Evaluation
- 자료는 상용 스캐너가 수집한 SSH 핑거프린트이고, 호스트를 조직에 연결하는 데에는 Bitsight의 AI 기반 자산 귀속 엔진을 썼습니다.
- 지표의 신빙성: SSH는 OpenSSH 버전 기본값이 곧 PQC 지원 여부를 결정하는 경우가 많아, "도입"이 의도적 전환인지 단순한 버전 갱신 효과인지 구분하기 어렵습니다. 데이터와 귀속 엔진이 비공개라 외부에서 재현할 수 없고, 22번 포트만 다뤘다는 점도 한계입니다.

#### Comment
- 학술적 기여보다는 업계 현황 보고에 가깝지만, PQC 전환 정책을 세우는 쪽에서 참고할 만한 기준 수치입니다. SSH의 PQC 지원은 서버 키 교환만 다루며, 호스트 키 서명은 여전히 기존 알고리즘이라는 점도 함께 기억해야 합니다.
- 바로 아래 TLS 논문과 같은 저자진이 같은 날 함께 올린 짝 논문입니다.

# Empirical Assessment of Post-Quantum Cryptography Adoption Status in TLS
> arXiv cs.CR 2611.09707 (프리프린트, 심사 전). Bitsight Technologies(미국)
> 2026

같은 저자진이 TLS 위에서 동작하는 일곱 가지 서비스, 곧 HTTPS(443), LDAPS(636), SMTPS(465), IMAP-SSL(993), POP3-SSL(995), TELNETS(992), RDP(3389)의 PQC 배포 현황을 측정한 논문입니다. PQC 키 교환은 TLS 1.3에서만 쓸 수 있으므로, 서비스별로 IP 1만 개씩을 골라 TLS 핸드셰이크에서 하이브리드 키 교환 X25519MLKEM768이 협상되는지를 확인했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.09707
- arXiv HTML 본문: https://arxiv.org/html/2611.09707
- arXiv PDF: https://arxiv.org/pdf/2611.09707

### Contribution
- 웹 이외의 TLS 서비스까지 포함해 PQC 도입률을 처음으로 나란히 비교했습니다. 원 서버 기준 PQC 지원은 HTTPS 9.1%, LDAPS 7.39%이고 나머지 다섯 서비스는 모두 1% 미만입니다. 조직 기준으로는 HTTPS 11%, LDAPS 5.4%, IMAP-SSL 4%, POP3-SSL 3%, SMTPS, TELNETS, RDP는 2% 미만입니다.
- Cloudflare가 호스팅하는 도메인을 따로 측정해, 서버 이름 표시(SNI)를 넣어 요청하면 도메인 11,979건 가운데 약 83.6%에서 X25519MLKEM768이 협상되지만, Cloudflare IP 11,048개에 SNI 없이 접속하면 약 4%만 PQC를 지원한다는 차이를 보였습니다. 측정 방법에 따라 도입률이 크게 달라진다는 점을 드러낸 결과입니다.
- 조직 규모와 산업별 상관 분석으로, 대기업은 예산과 인력 덕분에 먼저 도입하지만 거대한 망 전체로 확산하는 데는 오히려 마찰이 크다는 관찰을 내놓았습니다.

### Evaluation
- 서비스별 표본이 1만 개 IP로 작고, 표본 추출 방법에 따라 결과가 달라질 수 있습니다. 측정은 openssl 기반 핸드셰이크로 했으며, 조직 귀속은 SSH 논문과 같은 비공개 엔진을 썼습니다.
- 지표의 신빙성: Cloudflare 실험이 보여 주듯 IP 단위 측정과 도메인 단위 측정이 크게 어긋나므로, "HTTPS 9.1%"를 웹 전체 도입률로 읽으면 안 됩니다. Cloudflare가 밝힌 "사람이 만든 트래픽의 50% 이상이 PQC로 보호된다"는 수치와도 측정 단위가 다릅니다.

#### Comment
- 메일, 원격 접속, 디렉터리 서비스처럼 기업 내부 기반 시설에 가까운 프로토콜일수록 PQC 도입이 사실상 시작되지 않았다는 점이 실무적으로 가장 쓸모 있는 결과입니다.
- 위 SSH 논문과 마찬가지로 상용 데이터 기반 업계 보고서 성격이며 외부 재현은 어렵습니다.
