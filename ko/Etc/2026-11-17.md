# Hello Again: Exploiting Replay Protected Monotonic Counters to Brute-Force Windows Hello PINs
> ACM CCS 2026 게재 논문(DOI 10.1145/3830454.3846631)을 일부 고친 arXiv 판. 베를린 공과대학교
> 2026

Windows Hello의 짧은 PIN을 지켜 주는 TPM 사전 공격 방지 장치를, 펌웨어 TPM(fTPM)의 상태 되돌리기로 무력화한 하드웨어 공격 논문입니다. Windows Hello는 네 자리 숫자 PIN도 허용하는데, 이것이 안전한 이유는 TPM이 실패 횟수를 세어 잠금을 걸기 때문입니다. 그런데 요즘 x86 노트북은 대부분 CPU의 보안 코프로세서(AMD PSP, Intel CSME, Microsoft Pluton)에서 도는 fTPM을 쓰고, fTPM은 잠금 카운터를 포함한 비휘발성 상태를 암호화해 메인보드의 SPI 플래시에 저장합니다. 옛 플래시 내용을 다시 써 넣는 되돌리기 공격을 막으려고 최근 플랫폼은 JEDEC 표준인 RPMC(Replay Protected Monotonic Counter)를 지원하는 플래시를 쓰는데, 이 카운터는 물리적으로 접근할 수 있는 SPI 버스 위에서 동작합니다. 저자들은 값싼 인터포저 보드와 전압 글리칭으로 RPMC 플래시 세 제조사와 Intel, AMD의 비휘발성 저장 컨트롤러를 처음으로 실물 분석했습니다.

원문 링크:

- arXiv HTML 본문: https://arxiv.org/html/2611.18126
- arXiv PDF: https://arxiv.org/pdf/2611.18126

- 1저자 홈페이지: https://www.user.tu-berlin.de/cwerling/

### Contribution
- RPMC 플래시 세 종을 평가해 다음을 찾았습니다. Winbond, Macronix, GigaDevice 모두 카운터가 32비트 최댓값에서 0으로 넘어가 단조 증가 가정이 깨지고(영향 작음), GigaDevice는 글리칭으로 위조된 카운터 값을 정상 서명과 함께 돌려주며(영향 작음), Winbond는 글리칭 시 내부 HMAC 키를 상태 레지스터로 흘립니다(영향 큼). Winbond 키 유출은 약 1초 안에 재현되어 필요할 때마다 수행할 수 있습니다.
- Intel과 AMD의 비휘발성 저장 컨트롤러를 평가해, AMD 컨트롤러가 RPMC 증가 명령이 실제로 반영되었는지 확인하지 않아 인터포저가 증가를 몰래 막을 수 있음을 보였습니다. 또 RPMC 플래시가 없는 AMD 데스크톱 두 대(Zen 2, Zen 5)에서는 옛 플래시 이미지를 다시 쓰는 것만으로 fTPM 잠금 카운터가 초기화되었습니다. Intel 컨트롤러는 모든 카운터와 세션에 같은 키 재료를 재사용했습니다(약점).
- 두 경로로 실제 장비에서 끝까지 공격을 시연했습니다. AMD의 미검증 증가 결함을 쓴 HP OmniBook 3(Copilot+ PC)에서 Windows Hello PIN을 분당 약 4.14회 시도해 네 자리 PIN을 최악 40시간에 찾았고(기본 잠금 정책에서는 69일), Winbond 키 유출을 쓴 Framework Laptop 13에서는 BitLocker TPM+PIN을 분당 34.1회 시도해 기본 여섯 자리 PIN을 최악 20일에 찾았습니다(기존 19년).
- 인터포저 펌웨어, PCB 설계, 공격 스크립트, 유출된 HMAC 키, 부팅 트레이스를 공개했습니다.

### Evaluation
- 대상: 2015~2025년 출시 장비 아홉 대(Intel NUC, ASUS, Lenovo IdeaPad, ThinkPad T15, MSI 두 대, Framework Laptop 13, HP OmniBook 3, Acer Aspire 14 AI)와 플래시 칩 여러 종. 장비별 플래시 모델과 RPMC 사용 여부를 표로 공개했습니다.
- 지표: 분당 PIN 시도 횟수와 그로부터 계산한 최악 소요 시간, 글리칭 성공 조건(MOSFET 열림 지연과 타이밍). 236개 PIN을 실제로 시도하는 과정을 영상으로 공개했고, 한 번은 AMD 노트북에서 57분, BitLocker는 6분 55초 걸렸습니다.
- 부가 관찰: Microsoft 문서는 잠금 회복 시간을 10분이라고 하지만, 시험한 장비에서는 Hello PIN 설정 뒤 2시간으로 바뀌었습니다. 이 경우 단순 대입 시간은 833일까지 늘어납니다.
- 신빙성: 실제 판매 장비에서 잠긴 상태로 끝까지 시연했고 아티팩트를 모두 공개해 재현성이 높습니다. 다만 칩을 떼어 내 인터포저를 끼우는 물리적 접근과 납땜 기술이 필요하며, 한 장비는 실험 중 플래시가 고장 나 쓸 수 없게 되었다고 적었습니다.

#### Comment
- 분실하거나 도난당한 노트북에서 Hello PIN 하나로 기기 결합 키와 기업 SSO까지 열린다는 점이 실질적인 위험입니다. Microsoft는 권장 최소 PIN 길이를 여섯 자리로 올리는 정책 변경만 발표했고, Winbond, AMD, Intel, JEDEC 모두 근본 원인 수정을 약속하지 않았다고 합니다. 고위험 기기는 숫자만 쓰는 짧은 PIN을 금지하고 BitLocker PIN 길이를 늘리는 것이 현실적인 대응입니다.
- arXiv 판은 CCS 판 이후 AMD 비RPMC 시스템의 되돌리기 성공, BitLocker 시도 속도 개선(분당 27.2회에서 34.1회) 등을 반영해 일부 수치가 CCS 판과 다릅니다. 이 요약은 arXiv 판 기준입니다.
- CCS는 보안 분야 최상위 학회입니다.

# VellSSLH: Sound Type-Guided Selective Speculative Load Hardening for LLVM IR
> arXiv 프리프린트 (심사 전). 워싱턴 주립대학교
> 2026

상수 시간으로 작성한 암호 코드가 투기적 실행(Spectre 계열) 중에 비밀을 흘리는 문제를 막기 위한 투기적 로드 강화(SLH)를, 필요한 곳에만 넣고 그 결과의 안전성을 기계적으로 증명한 논문입니다. LLVM의 기존 SLH는 모든 로드를 보호해 성능 부담이 크고, 선택적으로 넣는 기존 방법은 LLVM IR 수준에서 증명된 보장이 없었습니다. VellSSLH는 프로그래머가 C 코드에서 입력을 공개(Public)와 비밀(Secret)로 표시하면, 투기 중에 비밀이 될 수 있는 값을 타입 시스템으로 추론해 오투기 플래그 연산과 보호를 필요한 곳에만 넣습니다. 그리고 Rocq에서 추출한 검사기 VellSCT가 변환된 LLVM IR이 투기적 상수 시간(SCT) 성질을 만족하는지 다시 확인합니다. 이를 위해 검증된 LLVM 의미론인 Vellvm에 투기적 실행, 공격자 지시, 누출 관측을 더했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.18463
- arXiv HTML 본문: https://arxiv.org/html/2611.18463
- arXiv PDF: https://arxiv.org/pdf/2611.18463

### Contribution
- LLVM IR 수준의 SCT 보안을 Vellvm 위에서 정식화하고, SSA 합류 지점, 기호 값, poison, 포인터 출처, 관측 가능한 오류, 명시적 기밀 해제, 신뢰하는 외부 서비스까지 다루는 보안 타입 시스템을 설계했습니다.
- 검사기를 통과한 프로그램이 SCT를 만족한다는 것과, 참조 강화 변환이 원래의 아키텍처 동작을 보존한다는 것을 Rocq로 증명했습니다. Rocq 개발 분량은 기존 Vellvm을 빼고도 337,040줄입니다.
- 증명된 검사기를 추출해, 최적화한 변형도 다시 검사하는 흐름을 만들었습니다.

### Evaluation
- 대상: TweetNaCl, libsodium, HACL*, Kyber(Round 3)의 암호 연산 24개(MAC, 스트림 암호, Secretbox, SHA/SHAKE, X25519, Kyber512/768). 베어메탈 리눅스 환경의 Intel Core Ultra 5 335에서 메모리 배치를 무작위로 바꾼 아홉 번의 시행으로 측정했습니다.
- 결과: LLVM SLH 대비 기하평균 실행 시간이 4.03% 낮았고, 24개 중 13개는 VellSSLH가, 8개는 LLVM SLH가 빨랐으며 3개는 결론이 나지 않았습니다. X25519에서는 LLVM SLH보다 22.69% 빨랐고 보호하지 않은 코드 대비 부담은 1.86%였습니다. Ultimate SLH보다는 기하평균 19.65% 빨랐습니다. 반면 Kyber 연산은 보호 없는 코드 대비 16~22%, Secretbox 복호화는 40.79% 느렸습니다.
- 변환과 검사 시간은 X25519가 삽입 409초, 재검사 127초, Kyber512 복호화가 769초와 339초로 큰 편입니다.
- 신빙성: 신뢰구간을 함께 보고하고 비교가 불리한 경우도 숨기지 않았습니다. 다만 증명은 LLVM IR에서 끝나므로, 백엔드 코드 생성과 하드웨어 동작은 가정으로 남습니다. 최적화한 변형은 다시 검사하지만 동작 보존 증명 대상은 아니라고 저자가 밝혔습니다.

#### Comment
- "보호는 증명으로, 성능은 선택으로"라는 방향이 분명하고, 성능 이득이 크지는 않지만 증명된 보장을 유지하면서 LLVM SLH와 비슷하거나 약간 나은 수준이라는 점이 의미 있습니다.
- Kyber 구현이 FIPS 203 ML-KEM이 아니라 Round 3 v3.0이라는 점, 비밀 표시를 사람이 직접 달아야 한다는 점이 실무 적용의 걸림돌입니다.
- 1저자 단독 논문이고, 같은 저자의 검증된 디컴파일러 논문(DeCompCert)과 함께 공개되었습니다. 코드 공개 주소는 본문에서 찾지 못했습니다.

# DeCompCert: A Verified Decompiler for CompCert-Generated AArch64
> arXiv 프리프린트 (심사 전, 주 분류 cs.PL). 워싱턴 주립대학교, 시러큐스 대학교
> 2026

검증된 C 컴파일러 CompCert가 만든 AArch64 어셈블리를 C 코드로 되돌리면서, 되돌린 코드가 원래 어셈블리와 의미가 같다는 것을 Rocq로 보장하는 디컴파일러입니다. IDA나 Ghidra 같은 실무 디컴파일러는 정교한 분석과 휴리스틱을 쓰지만 결과가 원래 프로그램과 같다는 형식적 보장이 없습니다. DeCompCert는 CompCert의 컴파일 단계를 거꾸로 따라가는 아홉 단계의 역변환으로 CompCert C를 복원합니다. 일부 단계는 복원 알고리즘 자체를 증명했고, 나머지는 검증되지 않은 OCaml과 Datalog(Ascent) 분석이 후보를 제안하면 증명된 검증기가 의미 대응을 확인한 후보만 받아들이는 번역 검증 방식을 씁니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.18055
- arXiv HTML 본문: https://arxiv.org/html/2611.18055
- arXiv PDF: https://arxiv.org/pdf/2611.18055

### Contribution
- 받아들인 C 복원 결과의 정의된 안전한 동작은 모두 입력 어셈블리에도 있다는 합성 정리를 증명했고, 안전성 가정 아래에서는 두 프로그램이 관측상 같다는 것도 보였습니다. 신뢰 기반은 Rocq 커널, CompCert 의미론, CompCert에서 물려받은 가정으로 한정됩니다.
- 함수 시그니처가 없는 어셈블리에서 시작해, 검증된 경계를 바꾸지 않은 채 Ghidra나 IDA의 제안을 후보로 받아 쓰는 구성을 만들었습니다. 실패한 탐색은 결과를 내지 않으므로 틀린 디컴파일 결과가 나오지 않습니다.
- CompCert 3.17 외에 약 52,100줄의 Rocq 코드를 더했습니다.

### Evaluation
- 대상: zlib, Lua, libuv, libpng, BearSSL, OpenSSL(libssl, libcrypto), wolfSSL, Mbed TLS, nginx, LibreSSL, Coreutils, curl, BusyBox, SQLite 등 16개 응용, 약 216만 줄의 C 코드.
- 정확한 함수와 호출 시그니처가 주어지면, 비최적화와 최적화 파이프라인 모두에서 대상 3,173개 컨텍스트를 전부 복원하고 다시 컴파일했습니다. 시그니처 없이 시작하면 자체 추론만으로 59.2%, Ghidra 제안을 더하면 73.5%, IDA 제안을 더하면 76.1%, 모든 방법을 합치면 82.4%(3,164개 중 2,606개)를 검증된 결과로 얻었습니다. 첫 번째 추론 시그니처가 원래 시그니처와 맞는 비율은 DeCompCert 40.9%, Ghidra 28.6%였습니다.
- 실행 검증: wolfSSL과 OpenSSL libcrypto를 -O2로 복원한 C를 CompCert와 Clang으로 다시 컴파일해 OpenSSL 836개, wolfSSL 36개 실행 시험을 모두 통과했습니다. 실험 설계를 고정한 뒤 받은 새 버전(Lua 5.4.9, zlib 1.3.2)에서도 -O0은 49개 컨텍스트를 모두 복원했지만, 최적화된 경우는 7개만 성공했습니다.
- 한계: 복원한 C는 원본보다 토큰이 4.11배 많고 반복문과 switch 구조를 복원하지 못해 레이블과 goto로 남습니다. 원본과의 토큰 거리 중앙값은 0.845로 Ghidra(0.691)보다 원본과 덜 닮았습니다.

#### Comment
- 대상이 CompCert가 만든 바이너리로 한정되어 일반 GCC나 Clang 바이너리, 난독화된 바이너리에는 그대로 쓸 수 없습니다. 대신 인증 대상 소프트웨어처럼 원본 소스가 사라진 CompCert 산출물을 감사하거나, 디컴파일러 결과의 정확성을 검증해야 하는 상황에 의미가 있습니다.
- 사람이 읽기 좋은 결과를 내는 것보다 "틀린 결과를 절대 내지 않는 것"을 목표로 한 접근이라, 실무 디컴파일러의 결과를 검증기로 걸러 쓰는 구성이 특히 실용적입니다.
- 코드 공개 주소는 본문에서 찾지 못했습니다.

# CANTraj: Recovering Vehicle Trajectories from CAN Signals in Naturalistic Driving

운전 데이터 공개나 운전 습관 연동 보험에서 GPS 기록만 빼면 위치 개인정보가 보호된다는 통념을, CAN 신호만으로 차량 경로를 복원하는 공격을 대규모로 비교해 반박한 논문입니다. 바퀴 속도, 조향각, 페달, 요 레이트 같은 CAN 신호는 OBD 포트로 쉽게 수집되는데, 이 신호를 도로망과 맞춰 경로를 재구성하는 기존 공격들은 데이터셋, 사전 가정(출발 위치와 방향을 아는지, 지역만 아는지), 성공 기준이 제각각이라 서로 비교할 수 없었습니다. 저자들은 해독된 CAN 이벤트와 시간을 맞춘 GNSS 궤적을 함께 담은 자연 주행 데이터셋 CANTraj와 평가 기준 CANTraj-Bench를 만들고, 온라인과 오프라인, 지도 사용 여부, 초기 방향 공개 여부를 독립적으로 바꾸는 평가 규약 아래 기존 공격 여섯 가지와 기준 방법들을 같은 주행 구간에서 비교했습니다. 신호마다 출처(차량 버스에서 직접 읽은 값, 차량 소프트웨어가 계산한 값, GPS가 섞인 값)를 구분해, GPS가 섞인 신호의 결과는 참고용으로만 보고한 점도 특징입니다.

### Contribution
- 운전자 454명의 주행 3,940건으로 이루어진 CAN과 GNSS 짝 데이터셋을 공개했고, 그중 3,675건(1,380시간, 85,919km)으로 평가 구간 97,340개를 정의한 평가 기준을 만들었습니다. 실패한 탐색도 점수에 반영하는 규칙을 명시했습니다.
- SPy, MacroTracking, OPD-II, Elastic Pathing 등 기존 공격 여섯 가지를 다시 구현해 추측 항법, 지도 기반 입자 필터, 오프라인 빔 탐색과 같은 구간에서 짝지어 비교했습니다. MacroTracking과 OPD-II는 원저자 예제 데이터로 구현을 확인했습니다.
- 조향 신호와 도로망 제약의 결합이 가장 큰 효과를 낸다는 점, 오프라인 빔 탐색이 초기 방향 정보에 덜 민감하다는 점을 보였고, 조향을 10도 단위, 속도를 1m/s 단위로 거칠게 양자화해도 지도 기반 공격이 대부분 그대로 통한다는 점을 확인했습니다.
- 방법마다 실패하는 구간이 다르다는 관찰을 바탕으로, 후보 경로 가운데 하나를 고르는 LLM 선택기도 따로 평가했습니다.

### Evaluation
- 데이터와 분할: 처음 보는 운전자 94명의 주행 776건(시험 분할과 소수 예시 분할)으로 평가했습니다. 운전자는 분할 사이에 겹치지 않지만 차량 플랫폼과 지역은 겹칩니다.
- 지표: 평균 변위 오차(ADE), 100m 이내 시간 비율, 50m 기준 경로 재현율과 정밀도, 경로 복원 성공률, 계산 비용. 실패한 탐색은 실패로 집계합니다.
- 주요 결과: 출발 위치와 방향을 알 때 속도에 조향을 더하면 온라인 지도 필터의 5분 경로 복원율이 56%에서 87%로 올랐고, 오차 중앙값은 43m로 지도 없는 추측 항법(921m)보다 훨씬 작았습니다. 오프라인 빔 탐색은 방향을 알 때 88%, 모를 때 81%를 복원했습니다. 연속 가속 페달 신호는 속도와 조향에 비해 추가 효과가 작았습니다.
- LLM 선택기: 5분 구간 659개에서 최선 구성이 시험 79%, 소수 예시 83%를 복원해 시험 분할에서는 최선 기준선을 넘고 소수 예시에서는 비슷했습니다. 구간별로 정답을 아는 오라클 선택은 진단용이며 실제로 배치할 수 있는 선택기는 아니라고 밝혔습니다.
- 신빙성: 같은 구간에서 짝지은 비교와 실패 포함 지표를 써서 기존 연구보다 비교가 공정합니다. 다만 여섯 공격 중 원저자 데이터로 구현을 확인한 것은 두 가지뿐이고, 도로 밀도와 회전 수 분석은 운전자, 차량, 도로 조건이 함께 변해 인과가 아닌 상관관계라고 저자들도 적었습니다.

#### Comment
- 데이터 공개 측면의 결론이 분명합니다. GPS 좌표나 초기 방향을 지워도 경로 정보는 남으며, 양자화 같은 단순한 가공도 충분한 보호가 되지 않습니다. 보험사, 차량 관제, 공개 주행 데이터셋을 다루는 곳에서 참고할 만합니다.
- 한계: 북미 도로와 특정 로깅 시스템이 지원하는 차량이 대부분이고, 출발 위치를 아는 상황의 복원을 주로 측정합니다. 지역만 아는 변형도 출발 위치를 중심으로 한 정사각형을 받기 때문에 출발점을 모르는 추적을 시험한 것은 아닙니다. 방법이 실패했다고 해서 개인정보가 보장되는 것은 아니라고 저자들이 강조합니다.
- 저자 소속은 미국과 싱가포르 대학이며 중국 기관은 없습니다.
