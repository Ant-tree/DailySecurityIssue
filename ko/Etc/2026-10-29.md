# When POST Becomes GET: Investigating HTTP Method Interchangeability and Its Security Implications
> 42nd Annual Computer Security Applications Conference (ACSAC 2026) 채택(저자 표기 기준), arXiv cs.CR 공개본. 트렌토 대학교(이탈리아)
> 2026

HTTP에서 GET은 조회, POST는 상태를 바꾸는 요청이라는 구분은 SameSite 쿠키, 캐시, CSRF 토큰 검증 같은 여러 방어 장치가 기대는 전제입니다. 이 논문은 POST 요청의 본문 파라미터를 쿼리 문자열로 옮겨 같은 엔드포인트에 GET으로 보내도 같은 결과가 나오는 "메서드 상호 교환성"을 처음으로 대규모 측정했습니다. Tranco 상위 1만 개 사이트 중 407개(4.1%)에서 확실한 교환 가능 요청이 발견됐고, POST가 실제로 수집된 사이트로 한정하면 12.7%, GET으로 바꿔 재전송할 수 있었던 사이트로 한정하면 14.9%였습니다.

원문: https://arxiv.org/abs/2610.37474

### Contribution
- 프레임워크와 API 기술별로 교환성이 생기는 원인을 정리했습니다. 쿼리와 본문 파라미터를 하나의 인터페이스로 합쳐 주는 프레임워크, 메서드를 명시적으로 검사하지 않으면 모든 메서드로 접근되는 라우팅 방식, 배열 파라미터 처리 차이 등이 해당합니다.
- 실제 브라우저로 사이트를 돌며 페이지 로드와 폼, 버튼 동작에서 생기는 POST를 기록하고, GET 후보로 바꿔 재전송한 뒤 응답을 비교하는 MIDE를 만들었습니다. 파라미터 없는 GET을 대조군으로 함께 보내, 파라미터와 무관하게 같은 화면을 돌려주는 경우를 교환 가능으로 잘못 세지 않도록 했습니다.
- 교환성이 실제 보안 문제로 이어지는 두 경로를 보였습니다. 잘못된 CSRF 토큰을 POST에서는 거부하지만 같은 GET에서는 받아들이는 경우, 그리고 GET으로 바꾼 요청의 동적 응답이 정적 자원처럼 보이는 URL에서 캐시되는 웹 캐시 속이기(web cache deception) 조건입니다. 코드와 설정을 공개했습니다.

### Evaluation
- 규모: 3,200개 사이트에서 POST 21,280건을 수집했고 그중 14,244건을 GET으로 재전송했습니다. 확실한 교환 가능(대조군과는 다르고 POST와는 같은 응답)은 1,228건(8.6%)이었고, 대조군까지 같아 판단을 보류한 경우가 1,782건(12.5%)이었습니다. 대조군이 없었다면 보류 사례가 모두 교환 가능으로 잘못 집계됐을 것입니다.
- 비교기 검증: 확실한 교환 가능 사례 30건과 비교환 사례 30건을 사람이 직접 확인해 표본 정밀도 100%, 표본 미탐률 0%를 얻었습니다.
- 보안 영향: CSRF 토큰이 있는 요청 115건 중 2개 사이트의 7건에서 GET 경로가 토큰 검증을 우회했고, 9개 사이트의 56건에서 캐시 가능한 동적 응답을 확인했습니다.
- 지표 신빙성: 대조군 설계와 수작업 검증으로 오탐을 줄인 점이 좋습니다. 수작업 검증 표본이 60건으로 작아 정밀도 100%를 일반화하기는 어렵고, 로그인 없이 측정했으며 상태를 바꾸는 동작은 일부러 피했으므로 실제 유병률은 이보다 높을 가능성이 큽니다.

#### Comment
- 교환성 자체가 취약점은 아니라는 점을 저자들이 분명히 합니다. 위험은 "이 엔드포인트는 POST만 받는다"고 가정한 방어 장치가 GET 경로를 놓칠 때 생깁니다. 웹 애플리케이션을 점검할 때 라우트별 허용 메서드를 명시하고, CSRF 검증과 캐시 정책을 메서드와 무관하게 적용하는지 확인할 근거가 됩니다.
- 실제 피해 사례로 확인된 수(CSRF 2개 사이트, 캐시 9개 사이트)는 적고, 영향 분석은 사례 확인 수준입니다.
- ACSAC은 오랜 역사를 가진 응용 보안 학회로 신뢰도가 높습니다.

# SecDMP: Provably Secure Data Memory-Dependent Prefetching (Extended Version)
> NDSS Symposium 2027 채택 논문의 확장판(저자 표기 기준), arXiv cs.CR 공개본. KU Leuven DistriNet(벨기에)
> 2026

데이터 메모리 의존 프리페처(DMP)는 메모리에서 읽은 값 자체를 주소처럼 해석해 미리 가져오는 최적화로, 최근 Apple, Intel, Arm 프로세서에 들어갔습니다. GoFetch 공격이 보여 줬듯 DMP는 상수 시간으로 작성된 암호 코드에서도 비밀값을 마이크로아키텍처 상태에 남길 수 있습니다. 지금까지의 대응은 DMP를 아예 끄거나 암호 연산 구간에서만 끄는 것이었는데, 이 논문은 구간별 끄기가 일부 유출 유형을 막지 못한다는 것을 보이고, 메모리에 비밀로 표시된 데이터에 대해서만 DMP가 동작하지 않게 하는 하드웨어 방어 SecDMP를 제안합니다. 형식 모델로 SecDMP가 DMP가 없는 기준 의미론보다 추가 유출을 만들지 않는다는 것을 증명했습니다.

원문: https://arxiv.org/abs/2610.37454

### Contribution
- DMP 유출을 다섯 유형으로 분류했습니다. 프로그램이 실제로 읽은 비밀이 새는 경우 외에, 같은 캐시 블록에 있는 인접 데이터, 추측 실행 중 읽힌 데이터, 다른 프리페처나 DMP 자신이 가져온 데이터를 통해 간접적으로 새는 경우가 있습니다. 구간별 끄기는 첫 번째 유형만 막습니다.
- RISC-V 연구용 프로세서 Proteus에 상용 설계와 학술 제안을 본뜬 DMP를 구현했습니다. 저자들은 이것이 첫 오픈소스 DMP 구현이자 RISC-V에서의 첫 DMP 공격 개념 증명이라고 밝힙니다. 모든 유출 유형을 개념 증명 프로그램으로 재현했습니다.
- SecDMP를 추측 실행 방어 ProSpeCT와 결합하면 상수 시간 코드에 대해 마이크로아키텍처 전체 수준의 보안이 회복된다는 것을 보였습니다. 산출물을 모두 공개했습니다.

### Evaluation
- 비용: 칩 면적 0.5% 증가, 임계 경로 영향 없음, 벤치마크 평균 성능 부담 0.36%, 최대 3.3%입니다.
- 벤치마크: HACL* 암호 함수 다섯 종(ChaCha20, Salsa20, SHA-256, HMAC, HKDF)과 일반 작업(Embench, CoreMark, HPCG의 SpMV, Intel DMP 활성화 패턴을 담은 자체 벤치마크)을 조합한 DMP-Bench 80개 프로그램으로 평가했습니다. DMP를 완전히 끄는 경우 일부 작업에서 성능이 크게 떨어지는 반면, SecDMP는 공개 데이터에 대한 프리페치를 막지 않아 일반 작업 성능을 유지합니다.
- 보안: 벤치마크 프로그램 전체에서 비밀 유출이 사라지는 것을 실험으로 확인했습니다.
- 지표 신빙성: 형식 증명과 하드웨어 구현, 실험이 함께 있어 주장이 탄탄합니다. 다만 성능 부담은 비밀을 별도 메모리 영역으로 나누는 비용에서 나오며, 평가한 암호 코드는 비밀을 수동으로 표시하고 Salsa20에서는 컴파일러가 만든 스택 유출을 어셈블리 수정으로 제거했습니다. 실제 상용 CPU가 아니라 연구용 프로세서에서 본뜬 DMP로 측정했다는 점도 감안해야 합니다.

#### Comment
- 상수 시간 프로그래밍만으로는 DMP 같은 새로운 최적화를 막을 수 없다는 문제의식에서, 소프트웨어가 비밀을 표시하고 하드웨어가 이를 존중하는 계약 모델을 제시했다는 점이 의미 있습니다. 모바일 SoC와 데스크톱 CPU 모두 DMP를 도입하고 있어 향후 프로세서 설계에 참고할 만합니다.
- 한계: 힙과 스택에서 비밀과 공개 데이터를 자동으로 나누는 문제는 SecSep 같은 후속 기술에 맡겼고, 복잡한 프로그램에 적용하려면 컴파일러 지원이 필요합니다.
- NDSS는 최상위 보안 학회 중 하나입니다.

# They Will See Johnny's Message: A Measurement Study of Post-Quantum Cryptography Across Email Delivery Paths
> arXiv cs.CR (프리프린트, 심사 전), 테네시 대학교 녹스빌(미국), 경희대학교
> 2026

"지금 수집하고 나중에 해독하는" 공격을 막으려면 이메일도 양자 내성 암호(PQC)로 옮겨야 합니다. 그런데 이메일은 발송(submission), 서버 간 중계(relay), 메일함 접근(IMAP, POP3), 웹메일이 각각 따로 TLS를 협상하기 때문에, 한 구간만 PQC를 써도 다른 구간에서 고전 암호로 오간 사본은 보호되지 않습니다. 이 논문은 Tranco 상위 100만 도메인과 연결된 메일 서버를 4주 동안 세 번 측정하고, 메일 클라이언트, 발송 서비스, OpenPGP와 S/MIME 구현을 통제된 환경에서 시험해 이메일 경로 전체의 PQC 준비 상태를 살폈습니다.

원문: https://arxiv.org/abs/2610.36145

### Contribution
- 서버 측 지원, 송수신 양쪽의 실제 협상, 메시지 수준 암호화를 한 연구에서 함께 측정한 첫 사례라고 저자들은 주장합니다.
- 기능 지원과 실제 사용이 다르다는 점을 실험으로 분리했습니다. 수신 서버가 PQC를 지원해도 보내는 쪽이 제안하지 않으면 쓰이지 않고, PQC만 허용하도록 수신 서버를 제한하면 오히려 평문으로 전달되는 경우가 생깁니다.
- OpenPGP 키 19개와 S/MIME 인증서 6개로 이뤄진 호환성 시험 세트를 만들었습니다.

### Evaluation
- 서버 측(마지막 측정 기준): 하이브리드 키 교환 지원률은 명시적 MX 중계 33.1%, 발송 40.2%, 접근 40.2~46.8%, 웹메일 41.0%입니다. 하이브리드를 지원하는 중계 도메인의 약 87%, 발송과 접근 도메인의 96~97%가 Google이었습니다. Microsoft는 측정한 엔드포인트 어디에서도 PQC를 지원하지 않았고, Proofpoint, Mimecast 같은 필터링 게이트웨이도 고전 암호만 지원했습니다. 주 MX는 지원하지만 백업 MX는 지원하지 않는 도메인이 417개로, 주 MX를 막으면 다운그레이드가 가능합니다.
- 클라이언트와 발송 측: 발송 서비스 8곳 중 실제로 PQC를 협상한 곳은 2곳뿐이었고, Google, Yahoo, Mailgun은 수신할 때는 받아들이지만 보낼 때는 제안하지 않았습니다. 수신 서버를 PQC 전용으로 제한하자 호환되지 않는 6곳 중 4곳이 평문으로 메일을 보냈습니다. Postfix는 하이브리드 그룹을 광고하면서 실제로는 고전 키 공유만 보내는 문제가 있었습니다.
- 메시지 수준: 27개 클라이언트 구성 중 PQC 키를 직접 생성하는 것은 없었고, 양쪽 백엔드 모두에서 메시지 교환까지 성공한 OpenPGP 키는 3개뿐이었습니다. S/MIME은 ML-KEM 인증서를 가져오는 저장소 4곳 중 2곳만 실제 암호화를 했습니다.
- 지표 신빙성: 도메인 단위 대규모 스캔과 통제 실험을 결합해 결론을 교차 확인했습니다. 다만 측정 기간이 4주로 추세를 말하기에는 짧고, 발송 서비스는 8곳만 시험했으며, 제공자 내부 구간은 측정하지 못했습니다.

#### Comment
- 이메일 보안 담당자에게 바로 쓸 수 있는 점검 항목을 줍니다. 모든 MX 호스트에서 PQC를 켜야 하고, 앞단 필터링 게이트웨이가 병목이 될 수 있으며, PQC만 강제하는 설정이 평문 전송으로 이어질 수 있다는 점입니다.
- MTA-STS나 DANE도 PQC 키 교환을 요구하지 않으므로 기존 정책만으로는 다운그레이드를 막을 수 없다는 지적이 실무적입니다.
- 게재처가 표시되지 않은 심사 전 원고입니다. 측정 윤리(멘로 보고서(Menlo Report) 원칙, 연결 수 제한, 거부 방법 안내)를 갖추고 있습니다.

# BUSTA: Teaching Small Language Models to Reason About Binary Execution
> arXiv cs.CR (프리프린트, 심사 전), MITRE Corporation(미국)
> 2026

리버스 엔지니어링에서는 "어떤 입력 상태여야 이 실행 결과가 나오는가"를 자주 묻는데, 심볼릭 실행 엔진은 경로 폭발과 제약 풀이 비용에 막히기 쉽습니다. 이 논문은 x86-64 기본 블록과 원하는 출력 레지스터 상태가 주어졌을 때 입력 레지스터 값을 맞히는 "역방향 기본 블록 실행" 과제로 소형 언어 모델을 강화학습(GRPO)시킨 BUSTA를 제시합니다. 악성 바이너리를 다루는 격리 환경에서는 외부 상용 API를 쓸 수 없는 경우가 많아, 로컬에서 돌아가는 작은 모델이 얼마나 따라올 수 있는지가 관심사입니다.

원문: https://arxiv.org/abs/2610.36288

### Contribution
- Assemblage 말뭉치의 Windows PE 바이너리 100개를 Ghidra로 분해해 기본 블록 287,137개를 만들고, Unicorn 에뮬레이터로 무작위 입력을 넣어 실행 결과를 기록했습니다. angr로 같은 출력을 내는 서로 다른 입력이 존재하는 레지스터를 "알 수 없음"으로 표시해, 원리적으로 맞힐 수 없는 값과 맞혀야 하는 값을 구분했습니다.
- 값 정확도와 알 수 없음 판정 정확도를 함께 반영하는 보상 함수를 설계했습니다.
- 미세 조정한 모델 두 개와 학습 데이터셋을 공개했습니다.

### Evaluation
- 평가 세트는 함수 단위로 학습 세트와 분리했고 층화 표본 635개입니다.
- 알 수 있는 레지스터의 정확도는 Qwen3-1.7B가 73.2%에서 85.3%로, Nemotron-3-Nano가 63.3%에서 95.2%로 올랐습니다. 응답당 토큰 사용량도 Qwen3-1.7B 기준 절반 가까이 줄었습니다.
- 비교 대상: GPT-5.5 99.2%, Claude Sonnet 5 99.0%, GPT-5 98.3%, Claude Opus 4.8과 Gemma-4-31B 98.1%입니다. 공개 모델 Gemma-4-31B도 미세 조정 없이 BUSTA보다 높습니다.
- 지표 신빙성: 모델마다 샘플링 설정을 조정하고 여러 시드 결과를 모아 비교의 공정성에 신경 썼습니다. 다만 과제가 단일 기본 블록의 레지스터 값 맞히기로 단순하고, 상용 모델이 이미 거의 포화 상태라 실제 리버스 엔지니어링 능력 차이를 가르기에는 변별력이 낮습니다.
