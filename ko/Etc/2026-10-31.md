# ICALL-BENCH: Benchmarking LLM Interprocedural Reasoning in Binary Programs
> arXiv cs.SE, cs.CR 교차 등록 (프리프린트, 심사 전), 조지아공과대학교, 매사추세츠대학교 애머스트(미국)
> 2026

대형 언어 모델은 함수 하나를 읽고 이해하는 바이너리 분석 과제나 전체 리버스 엔지니어링 과제에서 좋은 성적을 내고 있지만, 여러 함수에 걸친 의미, 즉 함수 간(interprocedural) 추론을 실제로 하는지는 분명하지 않습니다. 함수 단위 벤치마크는 함수 사이의 관계를 보지 못하고, 전체 프로그램 벤치마크는 최종 결과만 채점해서 국소적인 단서만으로 풀린 경우와 구별하기 어렵기 때문입니다.

ICALL-BENCH는 간접 호출(함수 포인터나 가상 함수 호출)의 실제 대상 함수를 복원하는 과제를 함수 간 추론의 측정 도구로 씁니다. 간접 호출의 대상은 실행 중에만 정해지므로 정적으로 맞히려면 데이터 흐름과 제어 흐름을 함수 경계를 넘어 따라가야 하고, 정답은 실행으로 기계적으로 검증할 수 있습니다. 벤치마크는 실제 C/C++ 프로그램 50개를 여러 컴파일 최적화 설정으로 빌드한 평가 사례 100개로 구성되며, 프로그램당 평균 74,746줄, 함수 941개 규모입니다. 같은 과제를 모델 단독 추론, 정적 분석 도구를 쓰는 에이전트, 인터넷 검색까지 쓰는 에이전트라는 세 가지 조건에서 비교했습니다.

### Contribution
- 바이너리에서 함수 간 추론을 따로 떼어 측정하는 벤치마크를 만들었습니다. 일부 함수만 골라 주지 않고 전체 프로그램을 주어, 함수 간 분석이 국소 추론으로 축소되지 않게 했습니다.
- 정보 획득 수단을 단계적으로 늘린 세 가지 분석 조건을 두어, 모델 자체의 추론 능력과 도구 사용, 외부 지식의 기여를 구분해 볼 수 있게 했습니다.
- 정보 접근을 늘린다고 성능이 항상 오르지 않으며, 가장 어려운 사례에서는 깊은 함수 간 추론이 여전히 병목이라는 점을 보였습니다.

### Evaluation
- 대상: 최신 LLM 5종과 각각의 에이전트. 기본 조건(정적 도구를 쓰는 에이전트)에서 프로그램 단위 검증 성공률이 23%에서 81%까지 크게 벌어졌습니다.
- 정적 도구를 쓰게 하면 모델 단독보다 성공률이 30~58%포인트 올랐습니다(예: DeepSeek-V4.1 Flash는 16%에서 74%로). 컴파일 최적화 수준은 성능에 큰 영향을 주지 않았습니다.
- 지표 신빙성: 정답을 실행 기반 호출 관계로 기계적으로 검증하므로 채점이 객관적입니다. 조건 간 비교는 토큰 수 100만 미만인 50개 사례에서 했고, 문맥 길이 초과도 실패로 셌다는 점을 감안해야 합니다. 비교한 모델 수가 5개라 모델 간 순위는 참고 수준입니다.

#### Comment
- LLM 기반 리버스 엔지니어링 도구를 평가할 때 "함수 하나를 잘 읽는다"와 "프로그램 전체 구조를 이해한다"를 구분해야 한다는 점을 수치로 보여 줍니다. 난독화나 제어 흐름 무결성(CFI) 분석처럼 간접 호출 해석이 중요한 작업에 참고할 만합니다.
- 한계: 대상이 C/C++ 프로그램이며, 난독화된 바이너리는 포함하지 않습니다. 인터넷 검색 조건에서는 원본 소스 정보가 섞여 들어갈 여지가 있어 해석에 주의가 필요합니다.
- 게재처: 심사 전 프리프린트이며, 벤치마크는 익명 저장소로 공개되어 있습니다.
