# DERED: Enhancing Third-Party Library Detection in Binaries via Deceptive Reuse Mitigation
> Computers & Security(Elsevier) 게재 논문(웹 검색으로 찾은 ScienceDirect 논문 페이지 기준), arXiv cs.SE, cs.CR 교차 등록 2611.00574 공개본. 베이징우전대학교, 중관춘실험실(중국)
> 2026

바이너리에 들어 있는 서드파티 라이브러리(TPL)를 찾아내는 기술은 취약점이 어떤 소프트웨어로 퍼졌는지 추적하는 데 쓰입니다. 기존 탐지 기법은 두 바이너리 사이에서 비슷한 함수나 코드 영역을 찾으면 "재사용"으로 판정하는데, 재사용의 방향을 고려하지 않습니다. 예를 들어 minizip은 zlib과 bzip2를 가져다 쓰고 lzbench도 같은 라이브러리를 쓰기 때문에, minizip과 lzbench 사이에는 공통 코드가 있지만 서로를 재사용한 것은 아닙니다. 저자들은 이런 관계를 "기만적 재사용(deceptive reuse)"이라 부르고, 이 때문에 취약점 보고에 오탐이 생긴다고 지적합니다.

DERED는 세 단계로 실제 재사용과 기만적 재사용을 구별합니다. 먼저 가벼운 마르코프 행렬 인코딩과 CNN으로 같은 기원의 함수를 찾고, 다음으로 내보내기 함수 정보를 반영한 함수 호출 그래프에 GCN을 적용해 같은 기원의 코드 영역을 정렬합니다. 마지막으로 정렬된 영역에서 내보내기 인터페이스를 기준으로 한 함수의 중심성과 연결성 차이를 수치화해, 코드가 한 방향으로 흘러간 실제 재사용인지 판단합니다.

### Contribution
- 코드 일치와 코드 재사용을 혼동해 생기는 오탐 문제를 "기만적 재사용"으로 정의했습니다.
- 함수 매칭, 영역 정렬, 위상 차이 분석으로 이어지는 방식으로 재사용 판별과 라이브러리 탐지를 함께 수행하는 도구를 제안했습니다.
- 기만적 재사용 사례를 담은 데이터셋을 만들고 아티팩트를 공개했습니다.

### Evaluation
- 데이터: Conan 저장소의 라이브러리 간 재사용 관계에서 세 개 넘는 재사용 관계에 얽힌 프로젝트 83개를 골라 바이너리 572개를 빌드했습니다.
- 비교 대상: ISRD, LibDB, LibAM, LibDI 같은 기존 라이브러리 탐지 기법과, 사례 연구로 상용 소프트웨어 구성 분석 도구 BinaryAI.
- 결과: 재사용 판별 F1 96.9%, 라이브러리 탐지 F1 97.7%로, 가장 좋은 기준선인 LibDI보다 정밀도 12.6%, 재현율 5.5%, F1 9.2% 높았습니다. LibAM은 정밀도 76.8%, 재현율 91.2%, F1 83.4%였습니다. ROC 곡선의 AUC는 0.989였고, 아키텍처와 컴파일 최적화 수준을 바꾼 실험에서 평균 F1은 각각 92.9%, 92.0%였습니다.
- 지표 신빙성: 데이터셋을 저자들이 직접 구성했고 규모가 프로젝트 83개로 크지 않아, 수치가 이 데이터에 맞춰져 있을 가능성을 배제하기 어렵습니다. 기존 기법들은 재사용 방향을 다루도록 설계되지 않았으므로, 기만적 재사용이 많이 포함된 데이터에서 격차가 크게 나는 것은 어느 정도 예상되는 결과입니다.

#### Comment
- 바이너리 구성 분석으로 취약점 영향 범위를 판단하는 실무에서, 공통 라이브러리 때문에 생기는 오탐을 줄이는 관점이 유용합니다. 앱이나 SDK 바이너리에 포함된 오픈소스 라이브러리 식별에도 같은 문제가 있습니다.
- 한계: 난독화나 의도적인 코드 변형에 대한 강건성은 이번에 읽은 범위에서 다루지 않았습니다. 데이터가 Conan으로 빌드한 리눅스용 C/C++ 프로젝트에 한정됩니다.
- 게재처: Computers & Security는 Elsevier가 발행하는 보안 분야의 평판 있는 저널입니다. arXiv 원고에는 "Preprint submitted to Elsevier"로 표시되어 있고, 저자 저장소 설명에는 ACSAC 2025 제출 아티팩트라고 적혀 있어 이전에 다른 학회에 제출되었던 원고로 보입니다. 게재본과 arXiv 원고가 같은 판인지는 저널 본문을 열지 않아 확인하지 못했습니다.
- 중국 기관 검증: 저자 전원이 베이징우전대학교와 중관춘실험실 소속입니다. 게재처는 실재하는 평판 있는 저널이고, 아티팩트 저장소가 2025년부터 공개되어 있습니다. 비교 대상은 같은 문제를 다룬 기존 바이너리 라이브러리 탐지 기법들로 적절합니다. 다만 자체 구성 데이터셋에서 F1이 97%를 넘는 높은 수치이므로, 위의 지표 신빙성 항목처럼 감안해서 읽어야 합니다.

# Trouble With Time: Compile Timestamps and First-Seen Date Regression in EMBER2024
> CAMLIS 2026(Conference on Applied Machine Learning for Information Security) 게재, Proceedings of Machine Learning Research 349권. arXiv cs.CR, cs.LG 교차 등록 2611.01031 공개본. CrowdStrike(미국)
> 2026

악성코드 탐지 모델을 공정하게 평가하려면 학습 데이터보다 나중에 나온 파일로 시험해야 하고, 그러려면 파일이 언제 처음 발견되었는지 알아야 합니다. 이 날짜는 대개 VirusTotal 같은 외부 서비스의 최초 제출일에서 얻는데, 모든 연구자가 이런 서비스를 똑같이 쓸 수 있는 것은 아닙니다. 실행 파일 안의 PE/COFF 컴파일 타임스탬프를 대신 쓰면 좋겠지만, 이 값은 아무것도 강제하지 않아 업계에서는 "악성코드 제작자가 조작한다"는 것이 통념입니다.

CrowdStrike 연구진은 이런 실무자들의 통념을 연구 질문으로 바꿔 EMBER2024 데이터에서 검증했습니다. 타임스탬프가 얼마나 믿을 만한지, 틀린 타임스탬프를 가려낼 수 있는지, 머신러닝으로 최초 발견 날짜를 추정하거나 보정할 수 있는지, 틀린 타임스탬프를 알려 주는 단서가 있는지를 물었습니다. 특징 기반 XGBoost와 원시 바이트 기반 MalConv2로 임곗값 분류, 순서 분류, 부호 있는 차이 회귀, 절대 날짜 회귀, 순위 학습, 베이지안 잠재 신뢰도 모델까지 여러 문제 설정을 시험했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.01031
- arXiv HTML 본문: https://arxiv.org/html/2611.01031
- arXiv PDF: https://arxiv.org/pdf/2611.01031

### Contribution
- 타임스탬프 불일치가 악성 파일만의 문제가 아니라는 점을 데이터로 보였습니다. 컴파일 시각이 최초 발견보다 늦은 "미래에서 온" 파일, 0이나 1995년 이전 값 같은 명백히 틀린 값이 정상 파일과 악성 파일 모두에 상당한 비율로 있었습니다. 악성 파일은 차이의 크기가 더 큰 경향만 있었습니다.
- 현재 모델로는 최초 발견 날짜를 직접 추정하거나 파일을 시간 순서대로 정렬할 수 없다는 부정적 결과를 여러 방법으로 확인해 기준선으로 남겼습니다.
- 반대로 "타임스탬프가 최초 발견과 일정 기간 안에 드는가", "명백히 틀린 값인가"라는 문제는 높은 정확도로 풀 수 있음을 보이고, 타임스탬프 신뢰도를 별도의 연구 주제로 제안했습니다.

### Evaluation
- 데이터: EMBER2024 학습 분할 2,339,221개, 일반 시험 분할 539,869개, 학습 기간 이후에 처음 발견된 도전 분할 605개(PE/.NET)를 썼습니다.
- 타임스탬프 분포: 컴파일 시각과 최초 발견 사이 차이의 중앙값은 정상 파일 203.5일, 악성 파일 3,157.3일이었고, 상위 5% 값은 두 집단 모두 약 19,800일이었습니다.
- 회귀와 정렬: 컴파일 타임스탬프를 그대로 쓰는 기준선의 평균 절대 오차가 6,396.68일이었고, 회귀 모델들도 수집 기간에 비해 큰 오차를 냈습니다. 점수로 파일을 정렬했을 때 실제 순서와의 스피어만 상관은 최대 0.22에 그쳤습니다. 베이지안 모델은 결국 컴파일 타임스탬프를 그대로 쓰는 쪽으로 수렴했습니다.
- 임곗값 분류: "최초 발견과 30, 60, 90, 180일 안에 드는가"를 맞히는 분류기는 일반 시험 분할에서 타임스탬프를 입력에서 빼도 AUC 0.97~0.98, 넣으면 F1이 0.86~0.94였습니다.
- 명백히 틀린 타임스탬프 판별: 0, 최초 발견보다 하루 넘게 늦음, 1995년 이전, 2030년 이후, 같은 값이 1,000번 이상 반복되는 경우를 양성으로 정의했고, 타임스탬프를 뺀 2,567차원 특징만으로 AUROC 0.9943(도전 분할 0.9970)을 냈습니다. 다만 F1은 AUROC에 비해 낮아 보정 문제가 있다고 저자들이 직접 적었습니다.
- 지표 신빙성: 대규모 공개 데이터셋과 시간 기준 분할을 써서 결과를 재현하기 좋습니다. 최초 발견 날짜 자체가 VirusTotal 관찰에 기반한 상한값이라 "정답"에도 오차가 있다는 점, 일부 손실 함수 차이는 계산 시간 때문에 따로 분리 실험하지 않았다는 점은 저자들이 밝힌 제약입니다.

#### Comment
- 시간 기준 분할로 악성코드 탐지기를 평가하려는 연구자에게, 컴파일 타임스탬프를 날짜 대용으로 쓰면 안 된다는 근거와 함께 "명백히 틀린 값" 필터는 쓸 만하다는 실용적 결론을 줍니다. 정상 프로그램에도 타임스탬프 이상이 흔하다는 결과는 타임스탬프 조작을 악성 지표로 쓰는 탐지 규칙에도 시사점이 있습니다.
- 한계: Windows PE/.NET 파일과 EMBER2024 수집 기간만 다뤘고, 저자들도 더 긴 기간의 데이터나 도구 체인 식별 같은 추가 단서가 필요하다고 결론지었습니다.
- 게재처: CAMLIS는 보안 머신러닝 분야의 심사 학회이며, 논문은 PMLR 349권에 실렸습니다. 1저자 Edward Raff는 이 프로시딩의 편집자이기도 해, 심사 과정의 독립성은 학회 운영 방식에 달려 있습니다.
