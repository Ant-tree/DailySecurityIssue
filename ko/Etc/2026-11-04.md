# DERED: Enhancing Third-Party Library Detection in Binaries via Deceptive Reuse Mitigation
> Computers & Security(Elsevier) 게재 논문(웹 검색으로 찾은 ScienceDirect 논문 페이지 기준), arXiv cs.SE, cs.CR 교차 등록 2611.00574 공개본. 베이징우전대학교, 중관춘실험실(중국)
> 2026

바이너리에 들어 있는 서드파티 라이브러리(TPL)를 찾아내는 기술은 취약점이 어떤 소프트웨어로 퍼졌는지 추적하는 데 쓰입니다. 기존 탐지 기법은 두 바이너리 사이에서 비슷한 함수나 코드 영역을 찾으면 "재사용"으로 판정하는데, 재사용의 방향을 고려하지 않습니다. 예를 들어 minizip은 zlib과 bzip2를 가져다 쓰고 lzbench도 같은 라이브러리를 쓰기 때문에, minizip과 lzbench 사이에는 공통 코드가 있지만 서로를 재사용한 것은 아닙니다. 저자들은 이런 관계를 "기만적 재사용(deceptive reuse)"이라 부르고, 이 때문에 취약점 보고에 오탐이 생긴다고 지적합니다.

DERED는 세 단계로 실제 재사용과 기만적 재사용을 구별합니다. 먼저 가벼운 마르코프 행렬 인코딩과 CNN으로 같은 기원의 함수를 찾고, 다음으로 내보내기 함수 정보를 반영한 함수 호출 그래프에 GCN을 적용해 같은 기원의 코드 영역을 정렬합니다. 마지막으로 정렬된 영역에서 내보내기 인터페이스를 기준으로 한 함수의 중심성과 연결성 차이를 수치화해, 코드가 한 방향으로 흘러간 실제 재사용인지 판단합니다.

### Contribution
- 코드 일치와 코드 재사용을 혼동해 생기는 오탐 문제를 "기만적 재사용"으로 정의했습니다.
- 함수 매칭, 영역 정렬, 위상 차이 분석으로 이어지는 방식으로 재사용 판별과 라이브러리 탐지를 함께 수행하는 도구를 제안했습니다.
- 기만적 재사용 사례를 담은 데이터셋을 만들고 아티팩트를 공개했습니다.

### Evaluation
- 데이터: Conan 저장소의 라이브러리 간 재사용 관계에서 세 개 넘는 재사용 관계에 얽힌 프로젝트 83개를 골라 바이너리 572개를 빌드했습니다.
- 비교 대상: ISRD, LibDB, LibAM, LibDI 같은 기존 라이브러리 탐지 기법과, 사례 연구로 상용 소프트웨어 구성 분석 도구 BinaryAI.
- 결과: 재사용 판별 F1 96.9%, 라이브러리 탐지 F1 97.7%로, 가장 좋은 기준선인 LibDI보다 정밀도 12.6%, 재현율 5.5%, F1 9.2% 높았습니다. LibAM은 정밀도 76.8%, 재현율 91.2%, F1 83.4%였습니다. ROC 곡선의 AUC는 0.989였고, 아키텍처와 컴파일 최적화 수준을 바꾼 실험에서 평균 F1은 각각 92.9%, 92.0%였습니다.
- 지표 신빙성: 데이터셋을 저자들이 직접 구성했고 규모가 프로젝트 83개로 크지 않아, 수치가 이 데이터에 맞춰져 있을 가능성을 배제하기 어렵습니다. 기존 기법들은 재사용 방향을 다루도록 설계되지 않았으므로, 기만적 재사용이 많이 포함된 데이터에서 격차가 크게 나는 것은 어느 정도 예상되는 결과입니다.

#### Comment
- 바이너리 구성 분석으로 취약점 영향 범위를 판단하는 실무에서, 공통 라이브러리 때문에 생기는 오탐을 줄이는 관점이 유용합니다. 앱이나 SDK 바이너리에 포함된 오픈소스 라이브러리 식별에도 같은 문제가 있습니다.
- 한계: 난독화나 의도적인 코드 변형에 대한 강건성은 이번에 읽은 범위에서 다루지 않았습니다. 데이터가 Conan으로 빌드한 리눅스용 C/C++ 프로젝트에 한정됩니다.
- 게재처: Computers & Security는 Elsevier가 발행하는 보안 분야의 평판 있는 저널입니다. arXiv 원고에는 "Preprint submitted to Elsevier"로 표시되어 있고, 저자 저장소 설명에는 ACSAC 2025 제출 아티팩트라고 적혀 있어 이전에 다른 학회에 제출되었던 원고로 보입니다. 게재본과 arXiv 원고가 같은 판인지는 저널 본문을 열지 않아 확인하지 못했습니다.
- 중국 기관 검증: 저자 전원이 베이징우전대학교와 중관춘실험실 소속입니다. 게재처는 실재하는 평판 있는 저널이고, 아티팩트 저장소가 2025년부터 공개되어 있습니다. 비교 대상은 같은 문제를 다룬 기존 바이너리 라이브러리 탐지 기법들로 적절합니다. 다만 자체 구성 데이터셋에서 F1이 97%를 넘는 높은 수치이므로, 위의 지표 신빙성 항목처럼 감안해서 읽어야 합니다.

# Trouble With Time: Compile Timestamps and First-Seen Date Regression in EMBER2024
> CAMLIS 2026(Conference on Applied Machine Learning for Information Security) 게재 예정, arXiv cs.CR, cs.LG 교차 등록 2611.01031 공개본, 초록 기반 요약, 본문 미확인

저자들의 초록에 따르면, 악성코드 탐지 모델을 시간 순서대로 평가하려면 파일이 처음 발견된 날짜가 필요한데, 이 정보는 외부 서비스에서 얻는 경우가 많아 모든 연구자가 똑같이 쓸 수 없습니다. 이 연구는 머신러닝으로 실행 파일의 최초 발견 날짜를 추정하거나, PE/COFF 컴파일 타임스탬프를 믿을 수 없는 경우를 판별할 수 있는지를 EMBER2024 데이터로 살펴봤습니다. 특징 기반 모델과 원시 바이트 모델을 분류, 회귀, 순위, 잠재 신뢰도 문제로 나눠 평가했다고 합니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.01031
- arXiv HTML 본문: https://arxiv.org/html/2611.01031

### Contribution
- 저자들은 현재 모델로는 외부에서 얻는 최초 발견 날짜 메타데이터를 대체할 수 없다는 점을 보였다고 주장합니다.
- 반면 타임스탬프가 최초 발견 날짜와 정해진 오차 안에 드는지, 명백히 말이 안 되는지는 분류기로 높은 판별력을 보이며 가려낼 수 있다고 주장합니다.
- 정상 파일과 악성 파일 모두에서 타임스탬프 불일치가 상당하다는 점을 들어, 믿을 수 없는 타임스탬프가 악의적 조작에서만 나오는 것은 아니라고 주장합니다.

### Evaluation
- 초록에 적힌 내용: 최초 발견 날짜를 직접 회귀하면 오차가 데이터셋 수집 기간의 상당 부분에 이르고, 평가한 어떤 점수도 파일을 시간 순서대로 유용하게 정렬하지 못했습니다. 타임스탬프 신뢰도 판별은 높은 판별력을 보였다고 하나, 초록에 구체적인 수치는 없습니다.
