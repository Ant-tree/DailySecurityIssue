# Dissecting the GPU Load/Store Unit and Exposing Its Security Risks
> arXiv 프리프린트 (심사 전). 룩셈부르크 대학교
> 2026

GPU 커널이 내는 거의 모든 적재와 저장 명령은 스트리밍 멀티프로세서(SM)의 적재/저장 장치(LSU)를 지나가는데, 이 장치에 대해서는 몇몇 메커니즘과 수치만 따로따로 알려져 있었습니다. 그런데도 그 하나하나가 AES 키 유출 같은 공격에 쓰였습니다. 저자들은 NVIDIA V100, A100, H100에서 마이크로벤치마크로 LSU가 적재 명령을 처리하는 방식을 역공학했습니다. 전역 메모리 L1 적중이나 공유 메모리 접근이 건드리는 주소로부터 지연 시간을 사이클 단위로 정확히 계산하는 식을 만들었고, 그 안에서 주소에 따라 달라지는 항이 뱅크 충돌과 L1 태그 조회라는 점, 두 곳 모두에서 적재 명령끼리 경합한다는 점, LSU 파이프라인이 가득 차면 나중에 실행된 블록의 워프가 굶을 수 있다는 점을 보였습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.23022
- arXiv HTML 본문: https://arxiv.org/html/2611.23022
- arXiv PDF: https://arxiv.org/pdf/2611.23022

### Contribution
- 적재 한 번이 몇 사이클인지, 어느 캐시 라인이 추가 비용을 내는지, 뱅크 충돌 한 단계가 정확히 몇 사이클인지, 전역 적재와 공유 적재의 충돌 비용이 같은지 등 그동안 답이 없던 여섯 가지 질문에 답했습니다.
- 지금까지 공격에 쓰이지 않은 채널(전역 메모리 뱅크 충돌, 태그 조회)을 찾아, LSU의 공격 표면이 기존 공격이 보여 준 것보다 훨씬 넓다는 점을 보였습니다.
- 워프 굶주림이라는 새로운 경합 현상을 찾아 성능 방해 공격으로 연결했습니다.

### Evaluation
- 부채널: 전역 메모리 뱅크 충돌이나 태그 조회 하나만으로, 기존 GPU AES 타이밍 공격과 같은 위협 모델에서 AES-128 전체 키를 복원했습니다.
- 은닉 채널: NVIDIA Multi-Process Service(MPS) 아래에서 뱅크 접근과 태그 조회가 각각 프로세스 사이 은닉 채널이 되며, 전송률은 GPU 세대가 바뀔수록 높아졌습니다.
- 성능 방해: MPS 아래에서 워프 하나가 함께 실행되는 cuBLAS 행렬 곱셈을 A100에서 최대 750배, H100에서 최대 563배 느리게 만들었습니다. 어느 쪽이 굶는지는 블록 실행 순서로 정해졌습니다.
- 신빙성: 세 세대의 실제 GPU에서 SASS 수준 마이크로벤치마크로 측정해 근거가 구체적입니다. 다만 NVIDIA GPU만 다뤘고, 공격은 MPS처럼 여러 프로세스가 같은 SM을 나눠 쓰는 환경을 전제합니다. 본문에서 은닉 채널의 구체적인 전송률 수치는 이번 정리에서 확인하지 못했습니다.

#### Comment
- 클라우드에서 GPU를 여러 사용자가 나눠 쓰는 경우가 늘고 있어, MPS 공유 환경의 격리 문제를 정량적으로 보여 준 점에 의미가 있습니다. 특히 750배 수준의 성능 방해는 기밀성보다 가용성 측면에서 실제 위협이 될 수 있습니다.
- 정확한 지연 모델은 방어(상수 시간 GPU 코드 작성, 스케줄링 격리) 설계에도 바로 쓸 수 있는 자료입니다.

# Missing Security-Fix Backporting for GitHub Actions Workflows
> ICSE 2027(제49회 IEEE/ACM 국제 소프트웨어 공학 학회) 채택, arXiv 프리프린트. 싱가포르 경영대학교, 앨버타 대학교
> 2026

GitHub Actions 워크플로의 보안 취약점을 기본 브랜치에서만 고치고, 하위 사용자가 실제로 빌드에 쓰는 릴리스 및 유지보수 브랜치에는 고친 내용을 옮기지 않는 문제를 대규모로 측정한 첫 연구입니다. 예를 들어 actions/checkout을 변경 가능한 태그 대신 불변 커밋 ID로 고정하는 수정을 기본 브랜치에만 하면, 릴리스 브랜치는 태그 바꿔치기 공격(CVE-2025-30066, tj-actions/changed-files 사건)에 계속 노출됩니다. 저자들은 공개 워크플로 이력에서 워크플로를 바꾼 커밋 190만 3,191개를 모아 수정 전후를 정적 분석 도구 zizmor로 검사하고, 그 수정이 각 릴리스 브랜치에 옮겨졌는지 감사했습니다. 이어서 보안 수정을 자동으로 옮기는 기법 WorkflowBP를 제안했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.22519
- arXiv HTML 본문: https://arxiv.org/html/2611.22519
- arXiv PDF: https://arxiv.org/pdf/2611.22519

### Contribution
- 프로젝트 2만 4,238개에서 보안 수정 6만 9,865건을 찾아, 릴리스 브랜치로의 보안 수정 이식 공백을 처음으로 정량화했습니다.
- WorkflowBP는 기본 브랜치의 수정을 Workflow Semantic Patch(WSP)라는 도메인 전용 표현으로 바꾼 뒤, 위치가 아니라 내용으로 작업과 단계를 맞춰 각 브랜치에 적용합니다. 결정적 엔진이 풀지 못하는 크게 갈라진 경우에만 LLM이 WSP를 합성합니다.
- 재검사로 목표 취약점이 고쳐졌고 다른 것이 망가지지 않았음을 확인한 경우에만 이식을 받아들입니다.

### Evaluation
- 실태: 감사한 릴리스 브랜치 47만 4,490개 중 22만 4,392개(47.3%)가 여전히 취약했습니다. 이미 고쳐진 브랜치 7만 8,907개 가운데 의도적인 이식으로 확인된 것은 1만 9,476개뿐이었고, 지연의 중앙값은 243일이었습니다.
- 기법: 실제로 패치되지 않은 워크플로 파일 1만 2,000개에서 WorkflowBP는 67.9%에 대해 검사를 통과한 이식을 만들었습니다. 그대로 복사하기는 18.0%, Dependabot 방식 갱신은 13.0%, LLM만 쓰는 방식은 49.5%였습니다. LLM 비교는 같은 모델(Gemini)을 쓰도록 맞췄습니다.
- 실제 적용: 이식 결과 17건을 실제로 실행해 보았고, 실제 프로젝트에 이슈 176건을 제출해 44건이 개발자에게 확인되거나 수정되었습니다.
- 신빙성: 성공 판정이 같은 정적 분석 도구 재검사에 기대므로, zizmor가 잡지 못하는 취약점이나 기능 회귀는 평가 범위 밖입니다. 그래도 실제 개발자 반응까지 확인해 실무 근거가 있습니다.

#### Comment
- 소프트웨어 공급망 보안에서 "고쳤다"는 기본 브랜치 기준일 뿐이라는 점을 수치로 보여 줍니다. 릴리스 브랜치를 오래 유지하는 오픈소스 프로젝트에 바로 적용할 수 있는 결론입니다.
- ICSE는 소프트웨어 공학 분야 최상위 학회입니다. 저자 다수의 이름이 중국계이지만 소속은 싱가포르 경영대학교(David Lo 연구실)와 캐나다 앨버타 대학교로, 중국 기관 논문에 해당하지 않습니다. 본문에서 도구나 데이터 공개 주소는 확인하지 못했습니다.
- 본문 출처: arXiv PDF(사용자 컴퓨터에서 받음).

# Taking Time Out of TOCTOU: From Race Reproduction to Security Discovery
> arXiv 프리프린트 (심사 전), 코드 공개. 캘거리 대학교
> 2026

검사 시점과 사용 시점 사이의 경쟁 조건(TOCTOU)은 재현이 어렵고, 경쟁에서 지면 취약한 프로그램이 고쳐진 것처럼 보이는 문제가 있습니다. 저자들은 경쟁에 개입하는 시점 조절과 판정 근거를 분리해, 선언된 경쟁에 대해 한 번의 시도로 결론을 내는 보안 회귀 판정기를 만드는 프레임워크 Chronos를 제안했습니다. Chronos는 seccomp 사용자 알림으로 사용 시점의 시스템 호출 직전에 대상 스레드를 붙잡아 두고, 공격자의 변경(예: renameat2로 경로 바꿔치기)이 끝난 뒤에 놓아줍니다. 그러면 몇 마이크로초에 불과하던 경쟁 구간이 사실상 무한히 늘어납니다. 사용자 공간과 커널 명령 지점에는 ptrace와 KVM 게스트 관문으로 같은 일을 합니다. 주로 컨테이너 런타임의 TOCTOU 취약점(CVE-2021-30465, CVE-2025-23359, CVE-2023-27561, CVE-2025-31133)으로 평가했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.21214
- arXiv HTML 본문: https://arxiv.org/html/2611.21214
- arXiv PDF: https://arxiv.org/pdf/2611.21214
- 저자 저장소: https://github.com/hasnainnaeem/chronos

### Contribution
- 붙잡기 방식, 동작, 관찰기, 판정기, 결과 규칙을 조합하는 재사용 가능한 경쟁 명세를 정의해, 결정적 재현, 커밋 이분 탐색, CI 회귀 시험에 같은 명세를 쓰게 했습니다.
- "고쳐짐" 판정에는 보존, 정당한 거부, 확인된 범위 안의 누락 같은 사례별 긍정 근거를 요구하고, 근거가 없거나 모순되면 "판정 불가"로 남겨 거짓 "고쳐짐" 판정을 막았습니다.
- 이 명세를 릴리스, 배포판 패키지, 다른 런타임에 적용해 실제 문제를 새로 찾았습니다.

### Evaluation
- 재현: CVE-2021-30465는 Chronos로 취약 버전 100회 모두에서 공격이 성공했고, Chronos 없이는 2,000회 중 603회 성공했습니다.
- 판정 정확성: 알려진 취약 빌드에서 결과만 보는 검사기는 개입에 실패한 시도에서 800건 넘게 "고쳐짐"으로 잘못 판정했지만 Chronos는 한 건도 없었습니다. 시스템 호출에서 붙잡은 17개 사례 전부와 명령 지점에서 붙잡은 6개 중 4개가 취약과 고쳐짐 라벨을 모두 얻었고, 커널 사례 2개는 한쪽 라벨만 얻었습니다.
- 이분 탐색: 과거 이분 탐색 27건 모두 기대한 경계를 찾았습니다. runc 마스킹 경로 버그에서 고정 재시도와 Git Bayesect는 중앙값 475회와 398회의 실행이 필요했지만, Chronos는 끝점 확인을 포함해 7회로 끝냈습니다.
- 발견: chrony와 rpm의 불완전한 수정, 그리고 추적 시스템에 고쳐졌다고 표시된 Debian rpm 패키지의 문제를 새로 찾았습니다.
- 신빙성: seccomp 방식은 Linux 5.5 이상, 마운트 계열 판정은 Linux 6.8 이상을 요구하고, 대상이 io_uring을 쓰면 시스템 호출 관찰을 우회할 수 있어 쓰지 않는다고 가정합니다. 결과는 "선언된 경쟁"에 대한 것이라 알려지지 않은 경쟁을 찾는 도구는 아닙니다.

#### Comment
- 컨테이너 탈출 계열 취약점의 수정 검증을 확률 게임에서 결정적 시험으로 바꿨다는 점이 실용적입니다. 보안 패치의 회귀 시험을 CI에 넣고 싶은 런타임 유지보수자에게 직접 도움이 됩니다.
- 이전 실행(2026-11-18)에서 arXiv 다운로드 상한으로 미뤄 둔 이월 후보였습니다.
- 본문 출처: arXiv PDF(사용자 컴퓨터에서 받음).

# From Attack Tree to Model Checker: Binding CAPEC Patterns to Verify Robotic System Security
> FMAS 2026(Formal Methods for Autonomous Systems 워크숍) 프로시딩, EPTCS 457권 154-162쪽, DOI 10.4204/EPTCS.457.11. 초록 기반 요약, 본문 미확인
> 2026

자율 시스템과 로봇의 보안 검증은 공격자를 전제로 하지만, 위협 목록에서 검사 가능한 공격자 모델로 가는 과정은 아직 손으로 한다고 저자들은 지적합니다. 이 연구 예고 논문은 그 과정을 기계화하는 파이프라인의 이론과 구성을 제시한다고 합니다. 공격 트리의 각 잎을 CAPEC 공격 패턴에 대응시키고, "공격자의 전제 조건이 공격의 효과를 함의한다"는 1차 논리 규칙으로 적습니다. 규칙의 변수를 특정 시스템의 부품에 묶으면, 선택한 보안 통제 구성에서 전제 조건을 시험할 수 있습니다. 묶인 패턴에서 공격자 모델을 만들고 효과를 시제 논리 속성으로 바꿔, 대응책이 있을 때와 없을 때 시스템에 대해 검사하고 공격을 막는 통제를 보고한다고 합니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.22408

- arXiv PDF: https://arxiv.org/pdf/2611.22408
- EPTCS DOI: https://doi.org/10.4204/EPTCS.457.11

- CAPEC이 로봇 보안 추론을 어떻게 뒷받침할 수 있는지 탐색했다고 합니다.
