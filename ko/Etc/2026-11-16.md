# CrossPloit: A Benchmark for Cross-Version PoC Migration in Python Web Applications
> arXiv 프리프린트 (심사 전). 싱가포르 경영대학교, 하노이 과학기술대학교, 모나시 대학교
> 2026

취약점 데이터베이스에 적힌 "영향받는 버전 범위" 밖의 버전이 실제로는 같은 취약점에 뚫리는지를, 실행 가능한 증거로 확인하는 작업을 벤치마크로 만든 논문입니다. 목록에 있는 버전용 개념 증명(PoC) 익스플로잇이 주어졌을 때, 이를 목록에 없는 이전 버전에서 동작하도록 고치는 것을 "버전 간 PoC 이식"이라고 부릅니다. 저자들은 Django, Flask, FastAPI, Web2py와 그 위에 만든 패키지의 CVE 217개에서 출발해 재현 가능한 기준 PoC 97개를 만들고, 두 명이 각각 독립적으로 이전 버전 이식을 시도한 뒤 결과를 맞춰 127개 이식 사례(CVE 45개)를 확정했습니다. 사례마다 버전을 고정한 컨테이너, 기준 PoC, 취약점별 판정기가 있고, 판정이 공개된 취약점 때문에 성립했는지를 검증자 두 명이 다시 확인합니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.16588
- arXiv HTML 본문: https://arxiv.org/html/2611.16588
- arXiv PDF: https://arxiv.org/pdf/2611.16588

### Contribution
- NVD, OSV, GHSA, Snyk 네 곳 모두의 영향 버전 목록에 빠져 있지만 실제로 취약한 이전 버전 149개를 실행 증거로 확인했습니다. 이 가운데 수정하지 않은 기준 PoC로 뚫리는 것은 22개뿐이어서, 공개 PoC를 다시 돌려 보는 감사로는 6분의 1 정도만 찾을 수 있다는 점을 보였습니다.
- 이식에 필요한 수정 유형(API 변경, 페이로드 조정, 공격 경로 전환, 의존성 복구, 설정 변경)을 분류하고, 보안 수정을 되돌리거나 우회하는 "부정 이식"을 걸러내는 기준을 명시했습니다.
- LLM 에이전트 18개 구성(모델 9종, OpenHands와 SWE-agent 두 하네스)과 기존 실행 추적 기반 도구 VulScope의 이식판을 평가했습니다.

### Evaluation
- 결과: 가장 좋은 구성(OpenHands와 Opus-4.6)이 127개 중 74개(58.3%)를 해결했고, 입력 변형만 하는 VulScope 이식판은 11개(8.7%)에 그쳤습니다. 공격 경로를 바꿔야 하는 사례는 어떤 구성도 37.9%를 넘지 못했습니다.
- 한 구성에서 기준 PoC와 환경 명세를 빼면 해결률이 50.4%에서 15.0%로 떨어져, 제공된 참고 자료의 역할이 크다는 점을 확인했습니다.
- 실패 분석: 성능이 좋은 구성일수록 놓친 API로 인한 실패 비중은 줄고, 방향은 맞게 잡았지만 끝까지 실행하지 못한 실패 비중이 늘었습니다.
- 신빙성: 저자들이 직접 밝혔듯 구성마다 한 번씩만 실행해 실행 간 편차를 재지 않았고, 확인된 취약 버전만 담아 감사 도구로서의 오탐률은 측정하지 않았습니다. 149개는 두 명이 60분 안에 이식하지 못한 경우를 제외한 하한값입니다. 데이터 공개 계획은 본문에서 확인하지 못했습니다.

#### Comment
- 소프트웨어 구성 분석(SCA) 스캐너와 패치 일정이 모두 데이터베이스의 영향 범위를 그대로 믿는다는 점에서, 이미 지원이 끝난 브랜치가 모든 방어 도구의 사각지대가 된다는 지적이 실무적으로 중요합니다. 논문의 Django 4.0 사례처럼 같은 함수가 다른 분기로 여전히 이차 시간 복잡도를 가지는 경우를 기준 PoC 재실행으로는 찾을 수 없습니다.
- 공격자에게도 같은 도구가 n-day 공격 범위를 넓히는 데 쓰일 수 있다는 점을 저자들이 위협 모델에서 명시했습니다.
- 본문 출처: arXiv PDF(사용자 컴퓨터에서 받음).

# IoTPwnBench: A Synthetic Benchmark for IoT Firmware Security Analysis
> arXiv 프리프린트 (심사 전). IMT 루카 고등연구원, 룩셈부르크 대학교 SnT, 제노바 대학교, KU 루뱅
> 2026

IoT 펌웨어 보안 분석 도구를 공정하게 비교할 수 있도록, 약점이 무엇인지 미리 정해 둔 합성 펌웨어를 대량으로 만든 벤치마크입니다. 실제 제품 펌웨어는 결함이 제대로 문서화되어 있지 않고 하드웨어 없이 실행하기 어려워 "도구가 무엇을 찾아야 정답인지"를 정하기 어렵다는 문제에서 출발했습니다. IoTPwnBench는 라우터, IP 카메라, PLC, 건강 모니터, 도어락 등 11개 기기 프로필에 86개 약점 시나리오를 조합해 취약 이미지 716개를 만들고, 각 이미지마다 같은 기기와 서비스를 유지하면서 그 약점만 고친 짝 이미지를 둡니다. 각 기기는 시뮬레이션된 센서와 구동기 값을 HTTP, MQTT, Modbus/TCP로 실제로 내보내므로 동적 분석 도구가 살아 있는 기기 상태를 상대하게 됩니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.15316
- arXiv HTML 본문: https://arxiv.org/html/2611.15316
- arXiv PDF: https://arxiv.org/pdf/2611.15316
- 저자 저장소(벤치마크, 빌드 절차, 시나리오 문서): https://github.com/Mobile-IoT-Security-Lab/IoTPwnBench

### Contribution
- 28개 CWE 분류를 다루는 취약 이미지 716개와 수정본 716개를 제공하고, 각 취약 이미지에 주 CWE, 익스플로잇 페이로드, 약점이 발동했음을 확인하는 관측 신호를 정답으로 붙였습니다.
- 수정본을 함께 두어, 도구가 수정본에서도 같은 약점을 보고하면 오탐으로 셀 수 있게 했습니다. 정답 판정에 평가 대상 도구의 판단을 쓰지 않습니다.
- Yocto 6.0.3 기반 빌드로 리눅스 커널과 ext4 파일시스템 이미지를 만들고, 다섯 가지 QEMU 머신(arm64, arm, x86-64, x86, mips)에서 같은 시나리오를 빌드할 수 있게 했습니다. 같은 소스에서 비트 단위로 같은 결과가 나오는 것을 확인했습니다.

### Evaluation
- 이 논문은 데이터셋 논문으로, 기존 분석 도구의 성능을 측정한 실험은 없습니다. 저자들도 "아직 보고된 사용 사례가 아니라 설계가 지원하는 사용 사례"라고 밝혔습니다.
- 검증: 모든 이미지를 QEMU에서 부팅해 페이로드를 직접 넣고 관측 신호가 문서와 같은지 수작업으로 확인했고, 다르면 모듈을 고쳐 다시 확인했습니다. 기계가 읽을 수 있는 정답 파일은 56개 모듈 중 21개에만 있습니다.
- 구성 편중: 인증, 자격 증명, 암호 관련 이미지가 392개로 절반 이상이고, 메모리 안전 오류는 49개뿐입니다. 86개 시나리오도 56개 모듈의 변형이라, 이미지 수가 독립적인 약점 수를 과대 표현한다고 저자들이 직접 밝혔습니다.

#### Comment
- 정적 분석기, 퍼저, 재호스팅 기반 동적 분석 프레임워크를 같은 정답 위에서 비교할 수 있다는 점이 가장 큰 가치입니다. 같은 약점을 기기 종류, 인터페이스, 아키텍처만 바꿔 가며 시험할 수 있어 "무엇이 탐지를 좌우하는지"를 분리해 볼 수 있습니다.
- 반면 약점이 수집된 것이 아니라 설계된 것이라 실제 분포를 반영하지 않고, 리눅스 기반 이미지만 있어 마이크로컨트롤러와 RTOS 펌웨어는 다루지 않습니다. 의도적으로 취약한 이미지라 517개는 명시적 선택 플래그가 있어야 빌드되도록 막아 두었습니다.
- 본문 출처: arXiv PDF(사용자 컴퓨터에서 받음).

# Beyond the Diff - VulSpot: A Vulnerability Dataset Where No Vulnerability Goes Unlocalized
> arXiv 프리프린트 (심사 중이라고 표기, 5쪽). 몽스 대학교
> 2026

취약점 탐지 모델의 학습과 평가에 쓰는 실제 취약점 데이터셋이 성능을 부풀리는 원인들을 짚고, 이를 고친 "살아 있는" 데이터셋을 제시한 논문입니다. 저자들이 꼽은 문제는 한 번 만들고 갱신하지 않는 데이터셋, 보안과 무관한 변경이 섞인 커밋 때문에 생기는 잘못된 라벨, 거의 같은 코드가 학습과 시험에 동시에 들어가는 분할, 그리고 NULL 검사를 추가하는 것처럼 코드를 더하기만 하는 수정에서 취약 위치가 비어 버리는 문제입니다. VulSpot은 패치가 추가한 코드를 그 코드가 보호하는 기존 문장(예: 검사 없이 포인터를 쓰는 memcpy)에 데이터 흐름으로 연결해 위치를 정하고, 라벨을 버리는 대신 신뢰도 등급을 매기며, 매달 자동으로 갱신됩니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.15737
- arXiv HTML 본문: https://arxiv.org/html/2611.15737
- arXiv PDF: https://arxiv.org/pdf/2611.15737
- 데이터셋(Hugging Face, 논문에 표기): https://huggingface.co/datasets/ods01/VulSpot
- 저자 저장소(논문에 표기): https://github.com/DynaSoumhaneOuchebara/VulSpot-Dataset

### Contribution
- CVE 24,000여 건에서 21개 언어 함수 503,332개를 모았고, C/C++ 취약 함수는 15,932개입니다. 2026년 10월까지의 CVE를 담고 있어 최신 모델의 학습 시점 이후 취약점으로 오염 없는 평가를 할 수 있습니다.
- 추가만 하는 수정으로 기존 데이터셋에서 위치가 비어 있던 함수의 99.3%에 위치를 붙였습니다. 이런 수정은 NULL 역참조(39.6%)와 메모리 누수(42.3%)에서 특히 많아, 빼 버리면 가장 흔한 C/C++ 약점에 대한 평가가 왜곡된다는 점을 보였습니다.
- LLM을 쓰지 않고 계산하는 라벨 신뢰도 등급(높음, 중간, 낮음)과 음성 표본의 출처 유형, 근접 중복 그룹을 고려한 시간순 분할과 프로젝트 단위 분할, AST로 뽑은 호출 대상과 매크로 등 주변 맥락, 계층형 CWE 보기 네 가지를 제공합니다.
- 2024년 리눅스 커널이 CVE 발급 기관이 된 뒤 C/C++ 취약 함수의 75.1%가 커널에서 나온다는 점을 짚고, 커널 비중을 줄인 균형판과 커널 제외 시험 세트를 따로 두었습니다.

### Evaluation
- 데이터셋 논문이라 탐지 모델 성능 실험은 없고, 통계와 구성 방법을 제시합니다. 기준 성능은 앞으로 갱신본마다 공개할 계획이라고 밝혔습니다.
- 위치 지정 품질: 비어 있던 함수의 가장 신뢰도 높은 위치 후보가 강한 규칙(검사와 그 검사가 보호하는 사용 등)으로 정해진 비율은 54.5%이고, 공유 식별자만 보는 약한 규칙이 27.7%, 위치만 보는 대체 방식이 7.6%입니다.
- 신빙성: 신뢰도 등급과 위치 규칙을 사람이 직접 감사하지 않았고 향후 과제로 남겼습니다. CWE 라벨도 NVD를 그대로 믿고 있으며, 여러 커밋에 걸친 수정은 제외했습니다. 99.3%는 위치 후보를 붙인 비율이지 정답률이 아니라는 점을 구분해서 읽어야 합니다.

#### Comment
- PrimeVul처럼 엄격하게 걸러 정확도를 높이는 대신 진짜 취약점까지 버리던 방식과 달리, 신뢰도를 표시해 두고 사용자가 정밀도와 범위를 고르게 한 설계가 실용적입니다.
- 커널 CVE 급증으로 새로 만든 C/C++ 데이터셋이 사실상 리눅스 벤치마크가 된다는 지적은, 최근 발표되는 취약점 탐지 결과를 해석할 때 참고할 만합니다.
- 본문 출처: arXiv PDF(사용자 컴퓨터에서 받음).

# Browser Immune System (BIS): Innate and Adaptive Threat Detection in the Browser with a Cybersecurity Transformer
> arXiv 프리프린트 (심사 전). Alias Robotics, 독립 연구자
> 2026

웹 페이지의 보안 판단을 서버로 보내지 않고 사용자 브라우저 안에서 끝내도록, 40억 매개변수 보안 특화 트랜스포머를 4비트로 양자화해 WebGPU에서 돌리는 브라우저 확장 기능입니다. 모델(alias-web)은 저자들이 이전에 공개한 alias3-micro를 바탕으로 2.44GB 그래프로 컴파일했고, 노트북 GPU에서 유형이 정해진 보안 질문 하나에 약 150ms에 답합니다. 확장 기능은 이를 면역계에 빗대어, 모든 페이지에서 관측 유형에 따라 위협 분류별 예/아니오 질문을 던지는 "선천 반응"과, 사용자가 원할 때만 같은 가중치로 설명 문장을 생성하는 "적응 반응"으로 나눴습니다. 콘텐츠 스크립트는 페이지를 판단 로직 없는 관측 정보로만 줄여 넘깁니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.15302
- arXiv HTML 본문: https://arxiv.org/html/2611.15302
- arXiv PDF: https://arxiv.org/pdf/2611.15302
- 공개 가중치 alias3-web(Hugging Face, 논문에 표기): https://huggingface.co/aliasrobotics/alias3-web
- 기반 모델 alias3-micro(Hugging Face, 논문에 표기): https://huggingface.co/aliasrobotics/alias3-micro-1026

### Contribution
- 보안 특화 언어 모델의 빠른 판정 모드를 브라우저 안에서 처음 구현했다고 밝혔고, 페이지 자료가 기기 밖으로 나가지 않는 구조를 제시했습니다.
- 같은 가중치로 설명 생성(초당 10.5토큰)까지 할 수 있지만 판정 한 번보다 6~39배 비싸다는 점을 재서, 빠른 판정에서 문제가 있을 때만 생성을 쓰는 구조의 근거로 삼았습니다.
- 실제로 악성 동작을 실행하는 합성 사이트 6개(자격 증명 유출, 키로깅, 채굴, 난독화된 드로퍼, 스케어웨어, 핑거프린팅)와 적대적 대조 사이트 2개로 구성한 BISBENCH-8을 만들었고, 연구용 체크포인트를 실제 확장 기능으로 만들기까지 겪은 장애 25가지를 기록했습니다.

### Evaluation
- 결과: BISBENCH-8에서 8개 중 7개 사이트의 페이지 판정이 기대와 같았고(채굴 사이트를 놓침), 대조 사이트 두 곳은 모두 정상으로 판정했습니다. 분류 단위 micro-F1은 0.71, 페이지 검사에는 0.9~6.4초가 걸렸고, Chrome과 Firefox에서 판정이 같았습니다(Firefox가 5.9배 느림).
- 실제 웹: 공개 페이지 11개에 시험한 결과, 일곱 질문 중 두 개가 평범한 스크립트와 로그인 폼에도 "예"라고 답해 실제 웹에서의 특이도가 해결되지 않은 문제라고 저자들이 밝혔습니다.
- 신빙성: 평가가 저자들이 직접 만든 사이트 8개뿐이라 탐지 성능을 일반화할 수 없고, 기존 피싱이나 악성 스크립트 탐지기와의 비교도 없습니다. 측정은 모두 Apple M3 Max 노트북 한 대에서 했습니다. 오류를 모두 공개하고 근거가 아직 뒷받침하지 못하는 부분을 따로 정리한 점은 평가할 만합니다.

#### Comment
- 개인정보를 기기 밖으로 보내지 않는 온디바이스 보안 판단이라는 방향은 의미가 있지만, 현재 상태는 개념 증명에 가깝습니다. 2.44GB 모델을 내려받아야 하는 부담과 실제 웹에서의 오탐 문제가 배포 전에 풀려야 합니다.
- 모델과 논문 저자가 같은 회사여서, 자사 모델 홍보 성격이 있다는 점을 감안해서 읽을 필요가 있습니다.

## 초록 기반 요약 (본문 미확인)

# Batch, Pack, and Prove: More Efficient Verifiable Computation for CKKS
> ASIACRYPT 2026 채택 논문의 전체판(arXiv comment 표기, 92쪽), arXiv 공개본. 초록 기반 요약, 본문 미확인
> 2026

동형암호(HE)로 암호화된 상태에서 수행한 계산이 제대로 되었는지 검증하는 문제를, CKKS 방식에 대해 더 효율적으로 푼 논문이라고 저자들은 설명합니다. 이전 연구(Cascudo et al., CRYPTO 2025)는 환 R_q 위의 산술 회로와 범위 검사를 증명하는 간결 논증을 제시했지만, 다항식 커밋 증명 크기, 범위 증명의 O(N) 부담, 회로 크기에 대해 준선형인 검증 방법의 부재라는 확장성 문제가 남아 있었다고 합니다. 이 논문은 CKKS 계산의 더 효율적인 산술화, 일괄 평가를 지원하는 새 다항식 커밋 BatchFold, 거대한 다항식에 커밋할 필요를 없애는 packing 기법, 회로에 따라 달라지는 희소 다항식의 평가를 증명하는 SparsePack을 제안한다고 밝혔습니다.
