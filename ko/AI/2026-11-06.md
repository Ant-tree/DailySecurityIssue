# Securing Web Agents with the Compile-Then-Execute Paradigm
> arXiv cs.CR 2611.06039 (프리프린트, 심사 전). UC 버클리, 사우디아라비아 킹압둘아지즈 과학기술원(KACST)
> 2026

웹 에이전트는 대부분 ReAct 방식으로 동작합니다. 페이지를 보고, 다음 행동을 고르고, 실행한 뒤 다시 페이지를 보는 과정을 되풀이합니다. 이 구조에서는 판매자 정보처럼 믿을 수 있는 내용과 리뷰나 게시글처럼 누구나 쓸 수 있는 내용이 섞인 화면을 모델이 보는 바로 그 순간에 다음 행동을 결정하므로, 페이지에 심어진 프롬프트 주입이 에이전트의 제어 흐름을 빼앗을 수 있습니다. 이 논문은 계획과 실행을 분리하는 "먼저 컴파일하고 나중에 실행하는" 방식을 웹 에이전트에 적용한 Baya를 제안합니다.

Baya는 실제 웹사이트에 접속하기 전에 사용자의 요청을 Python 프로그램으로 컴파일합니다. 이 프로그램은 사이트별로 미리 만든 "신뢰 웹사이트 API"만 호출하는데, 이 API는 사이트의 REST 엔드포인트와 화면 조작으로만 가능한 기능(Playwright 래퍼)을 하나의 문서화된 인터페이스로 묶은 것입니다. 계획을 세우는 모델은 실제 페이지 내용을 보지 않고, 페이지 내용은 컴파일된 프로그램만 처리합니다. 신뢰할 수 없는 데이터는 변수 값을 채우거나 미리 정해 둔 분기 중 하나를 고를 수는 있지만, 새로운 작업이나 새로운 사이트 조작을 만들어 낼 수는 없습니다. 실행이 실패하면 HTTP 상태 코드와 오류 메시지 정도만 담은 제한된 진단 정보를 컴파일러에 돌려줘 프로그램을 고치게 하고, 리뷰 요약처럼 의미 해석이 필요한 일은 도구 호출 권한이 없는 실행 시점 모델에 맡깁니다.

### Contribution
- CaMeL, FIDES처럼 도구 호출 에이전트에서 검증된 계획과 실행 분리 방식을, 행동 공간이 미리 알려지지 않은 웹 환경으로 넓혔습니다. 그 사이를 잇는 추상화로 사이트별 신뢰 웹사이트 API를 제시했습니다.
- 보호 대상을 "제어 흐름 탈취"로 분명히 한정했습니다. 공격자가 새 행동을 끼워 넣는 것은 막고, 이미 정해진 분기 안에서 결과 값을 흔드는 "결과 조작"은 범위 밖이라고 밝혔습니다.
- 실행 실패를 복구하는 재계획 경로를 두되, 오류 피드백이 공격 통로가 되지 않도록 노출 정보를 제한했습니다.
- 보안을 얻으면서도 유용성이 오히려 높아질 수 있음을 보였습니다. 같은 API와 사이트 안내를 받은 ReAct 에이전트보다 성공률이 높아, 개선이 API 제공 때문만은 아니라는 점을 대조 실험으로 확인했습니다.

### Evaluation
- 유용성: WebArena Verified의 유효 과제 581개(GitLab 154, Shopping 171, Shopping Admin 150, Postmill 106)에서 평가했습니다. 모델은 Claude Sonnet 4.6, Gemini 3.5 Flash, GPT-5.6 Luna 세 가지입니다. Baya의 전체 성공률은 77.8%로, API를 쓰는 ReAct(66.7%)와 브라우저만 쓰는 ReAct(55.1%)보다 높았습니다. Claude Sonnet 4.6 기준으로는 81.9%였습니다. 다만 Shopping과 Shopping Admin에서는 일부 모델에서 API를 쓰는 ReAct가 더 나았습니다.
- 보안: 웹 에이전트용 프롬프트 주입 벤치마크 WASP의 GitLab, Postmill 환경에서 GPT-5.6 Luna 대신 DeepSeek V4 Flash를 넣어 평가했습니다. Baya는 모든 모델과 환경에서 중간 단계 공격 성공률과 최종 공격 성공률이 모두 0%였습니다. ReAct 쪽은 중간 단계 성공률이 최대 52.8%, 최종 성공률이 최대 5.6%였고, 전체 평균은 API를 쓰는 ReAct 16.2%, 브라우저만 쓰는 ReAct 25.5%였습니다. 기존 보안형 에이전트인 UCM(신뢰할 수 없는 콘텐츠 가리기)도 GitLab에서는 0%였지만, 사이트별 가리기 규칙이 필요하고 전체 GitLab 과제 성공률은 Baya보다 17.6%포인트 낮았습니다.
- 비용: 과제당 평균 지연 시간이 327초로, API를 쓰는 ReAct(87초)의 약 3.8배이고 비용도 더 듭니다. UCM보다는 지연 시간이 30.3%, 비용이 82.6% 적었습니다.
- 지표 신빙성: 같은 API와 사이트 안내를 ReAct에도 주고 비교한 점, WebArena의 수작업 검수판을 쓴 점은 설득력이 있습니다. 반면 신뢰 웹사이트 API를 사이트마다 사람이 직접 만들었기 때문에, 이 준비 비용과 품질이 결과에 크게 작용합니다. 보안 평가는 WASP의 정해진 공격에 대한 관측치이며 적응형 공격은 다루지 않았습니다.

#### Comment
- 에이전트 보안을 "모델이 주입을 무시하게 만들기"가 아니라 구조로 해결하려는 흐름의 연장선에 있는 논문입니다. 웹 에이전트에서도 계획과 실행을 분리하면 제어 흐름 탈취는 거의 막을 수 있다는 실증 자료로 쓸 만합니다.
- 한계: 작업 흐름이 미리 정해지지 않는 과제(예: "상사 메일을 찾아 그 내용대로 처리해 줘")는 이 방식으로 처리할 수 없습니다. 신뢰 웹사이트 API를 자동으로 만드는 일은 앞으로의 과제로 남겼고, 자동화 과정에서 마주친 주입이 "신뢰" API에 섞여 들어갈 위험도 저자들이 직접 지적합니다. 결과 조작은 막지 못합니다.
- 신뢰도: 저자진에 David Wagner, Raluca Popa 등 시스템 보안 분야의 대표 연구자가 포함되어 있습니다. 아직 심사 전 원고입니다.

# KVGuard: A KV Cache Safety Checker for LLM Serving Systems
> arXiv cs.CR 2611.06138 (프리프린트, 심사 전). 서울대학교
> 2026

vLLM, SGLang, TensorRT-LLM 같은 LLM 서빙 시스템은 PagedAttention으로 KV 캐시를 관리합니다. GPU 메모리를 cudaMalloc으로 한 번 크게 잡은 뒤 고정 크기 블록으로 나누고, CPU 쪽 할당기가 요청마다 블록을 배정해 블록 테이블로 GPU에 알려 주는 구조입니다. 사실상 응용 수준의 힙 할당기를 하나 더 둔 셈이라, 이중 해제, 해제 후 사용, 범위 밖 접근, 초기화되지 않은 읽기, 권한 위반 같은 할당기 계열 버그가 똑같이 생깁니다. 문제는 이런 버그가 시스템을 멈추게 하지 않고 출력을 조용히 망가뜨리거나 요청 사이의 격리를 깬다는 점입니다.

이 논문은 이 문제를 새로운 메모리 안전성 문제로 정리하고, KV 캐시 블록 단위로 검사하는 KVGuard를 제안합니다. 물리 KV 블록마다 작은 그림자 블록을 두어 요청별 권한과 항목별 초기화 여부를 기록하고, CPU 할당, 블록 테이블 생성과 변환, GPU 쪽 블록 테이블 조회와 KV 항목 접근에 걸쳐 다섯 가지 검사를 합니다. 각 검사는 위반이 처음 생긴 경계에서 바로 걸리도록 배치했습니다. 기존 ASan류 탐지기와 NVIDIA Compute Sanitizer는 CUDA 주소 수준에서 동작해 블록, 요청, 블록 테이블이라는 의미를 모르고, 레드존이나 격리 구역을 두는 방식은 GPU 메모리가 빠듯한 서빙 환경에 맞지 않는다는 것이 저자들의 분석입니다.

### Contribution
- vLLM과 SGLang의 패치 이력에서 KV 캐시 안전성 버그 29건을 모아, 이를 서빙 시스템 고유의 메모리 안전성 버그 부류로 분석했습니다.
- 기존 메모리 오류 탐지기와 GPU 디버깅 도구가 왜 이 버그를 잡지 못하는지 원인을 정리했습니다.
- KV 캐시 관리에 맞춘 첫 체계적인 메모리 안전성 추상화(그림자 블록과 다섯 가지 검사)를 설계해 vLLM과 SGLang에 구현했습니다.
- 실제 서빙 과정에서 이전에 알려지지 않은 안전성 위반 8건을 찾아 수정 요청을 보냈습니다.

### Evaluation
- 탐지 범위: 과거 실제 버그 29건을 모두 재현해 탐지했고, 새 위반 8건을 찾았습니다. 평가한 모든 작업 부하에서 오탐은 없었다고 보고합니다.
- 성능 부담: Qwen 2.5 14B에서 출력 토큰당 시간(TPOT)의 기하 평균 증가가 vLLM 3.0%, SGLang 7.4%이고, 메모리 부담은 KV 캐시의 0.11% 이하로 Compute Sanitizer보다 두 자릿수 낮습니다. Qwen 2.5 14B에서 초당 16요청일 때 중앙값 종단 지연은 vLLM 2.04초에서 2.13초, SGLang 2.60초에서 3.04초로 늘었습니다.
- 작은 모델과 긴 문맥에서는 부담이 큽니다. Llama 3.2 1B에서는 TPOT가 1.83~3.67배(vLLM), 2.02~3.53배(SGLang) 늘었고, 2K~8K 토큰의 LongBench 프롬프트에서는 초당 16요청 기준 7.55배(vLLM), 10.84배(SGLang)까지 늘었습니다. 하이브리드 구조인 Qwen 3.5 4B도 1.09~2.95배였습니다.
- 작업 부하: Llama 3.2 1B, Llama 3.1 8B, Qwen 3.5 4B, Qwen 2.5 14B와 ShareGPT V3를 기본으로, Llama 3.2 1B에는 LongBench와 5-shot MMLU를 추가했습니다.
- 지표 신빙성: 실제 패치 이력의 버그를 하나씩 끝까지 재현해 확인했고, 새로 찾은 버그에는 수정 요청 번호를 함께 적어 검증할 수 있게 했습니다. 다만 초록의 "3.0%, 7.4%"는 가장 유리한 14B 모델 기준이며, 작은 모델과 긴 문맥에서는 수 배의 지연이 생기므로 상시 운영보다는 테스트, 커널 개발, 사고 후 디버깅 용도로 보는 것이 맞습니다. 저자들도 그렇게 위치를 잡습니다.

#### Comment
- KV 캐시 버그는 "다른 사용자의 KV 상태가 섞이는" 요청 간 격리 위반으로 이어질 수 있어, 여러 사용자가 한 서빙 인스턴스를 공유하는 환경에서는 개인정보 유출 경로가 됩니다. LLM 서빙 계층을 보안 관점에서 다룬 드문 시스템 논문입니다.
- 한계: 구현과 평가는 vLLM과 SGLang에 한정됩니다. TensorRT-LLM도 같은 구조라 적용 가능하다고 주장하지만 직접 평가하지는 않았습니다. 그림자 메타데이터를 확인하는 호스트 쪽 작업이 그대로 드러나 작은 모델에서 지연이 큽니다.
- 신뢰도: 서울대학교 이병영 교수 연구실 논문으로, 이 연구실은 시스템 보안 분야 최상위 학회에 꾸준히 논문을 내 왔습니다. 아직 심사 전 원고입니다.

# When File Ingestion Misleads Language Models: Measuring and Mitigating Divergences in Office Documents
> arXiv cs.CR 2611.05806 (프리프린트, 심사 전). 난양공과대학교(싱가포르)
> 2026

Office 문서를 LLM에 올려 요약이나 검토를 맡기는 일이 흔해졌습니다. 그런데 LLM은 사람이 화면에서 보는 문서를 읽는 것이 아니라, 추출기가 문서 안의 OOXML 파일에서 뽑아낸 텍스트를 읽습니다. 추출기는 어떤 XML 부분을 읽고 어떻게 해석하는지가 저마다 달라, 사람이 보는 내용과 모델이 받는 내용이 어긋날 수 있습니다. 예를 들어 슬라이드의 텍스트 상자 위치를 조금만 옮기면 화면은 그대로인데 모델이 읽는 순서가 바뀝니다. 이 논문은 이 "추출 불일치"를 LLM 응용의 공격 표면으로 보고 측정, 공격, 방어를 모두 다룹니다.

정적 소스 분석과 동적 분석을 결합해 markitdown, python-pptx, python-docx, openpyxl, pandas, unstructured, Docling, Apache Tika/POI 등 널리 쓰이는 추출기 열 가지를 조사했습니다. 그 결과 사람에게는 보이지 않는데 추출기는 읽는 통로 19개(슬라이드 밖 텍스트, 숨긴 슬라이드, 발표자 노트, 대체 텍스트, 숨김 서식 등)와, 사람에게는 보이는데 추출기는 버리는 통로 12개(머리글, 바닥글 등)를 찾았습니다. 또 추출기가 숫자 표시 형식과 읽기 순서를 무시해서, 보이는 내용도 다른 형태로 모델에 전달됩니다. 예컨대 셀에 600000이 저장되어 있고 "천 단위 표시" 형식으로 화면에는 $600으로 보이면, 사람과 모델이 서로 다른 예산 총액을 보게 됩니다.

### Contribution
- LLM 응용이 Office 문서를 처리할 때 생기는 추출 불일치를 처음으로 체계적으로 연구했습니다.
- 어떤 추출기가 어떤 통로를 읽는지 알아내는 정적과 동적 결합 분석을 개발해, 열 가지 추출기에서 사람의 화면과 어긋나는 통로 31개를 찾았습니다.
- 지시문을 전혀 넣지 않고도 모델이 사람과 다르게 문서를 해석하게 만드는 다섯 가지 공격 시나리오(숨긴 보안 인증 주장, 숫자 형식, 숨긴 접두어로 단어 뜻 뒤집기, 바닥글 수치 누락, 읽기 순서 바꾸기)를 만들었습니다. 만든 파일은 Office에서 정상적으로 열립니다.
- OOXML 명세로 사람의 화면을 재구성해 모델에 넘기는 방어 Prism을 제안했습니다. 명세로 정해지는 부분은 렌더링 없이 파일에서 바로 풀고, 나머지는 여러 렌더링 엔진의 결과를 비교하는 느린 경로로 넘깁니다.

### Evaluation

# Signed, Sealed, Leaked: Trust Beyond Signature for MCP Toolchains
> arXiv cs.CR 2611.06585 (프리프린트, 심사 전). 툰쿠압둘라만대학교(말레이시아), 타북대학교(사우디아라비아), 싱가포르국립대학교 등
> 2026

AI 에이전트가 쓰는 MCP 서버 같은 외부 도구는 배포자 서명으로 출처를 확인하고, 실행 중에는 접근 가능한 파일과 목적지를 제한하는 정책으로 통제합니다. 이 논문은 서명이 "누가 만들었는지"만 증명할 뿐 "무엇을 하는지"는 보장하지 않는다는 점을 짚습니다. 정상적으로 서명된 OCR 도구가 광고한 기능을 그대로 수행하면서, 앞선 호출에서 받은 자료를 몰래 저장해 두었다가 허용된 목적지로 가는 다음 요청에 덧붙여 보내는 식입니다. 저자들은 실제로 이런 도구를 만들어, Meta의 커널 수준 런타임 방어인 MCPGuard-Dynamic이 같은 실행에서 직접적인 유출 시도는 막으면서도 이 공격은 모든 시행에서 막지 못함을 보였습니다.

해결책으로 "생식 계열 실행(germline execution)"을 제안합니다. 사용자 데이터를 한 번도 가진 적이 없는 깨끗한 원본 프로세스를 두고, 도구를 호출할 때마다 여기서 일회용 사본을 포크합니다. 각 사본은 자신이 연결될 목적지가 볼 수 있도록 허락된 자료만 받습니다. 도구 안에 악성 코드가 있어도, 그 사본이 유출할 수 있는 것은 처음부터 받은 자료로 제한됩니다. 도구 구현을 검사하거나 믿을 필요가 없다는 것이 핵심입니다.

### Contribution
- 호출별 출력 라벨링과 목적지 기반 격리가 공통으로 기대는 가정, 즉 도구가 호출 사이에 상태를 넘기지 않고 한 호출 안의 자료를 섞지 않는다는 "호출 순수성"을 짚어 내고, 그 두 가지 실패 유형을 MCPGuard-Dynamic을 상대로 시연했습니다.
- 사본 격리와 데이터 없는 원본이라는 명시적 가정 아래, 모든 서명 릴리스에 대해 출력 지점 비간섭성을 증명했습니다. 재실행 모델 안에서 결정적인 도구라면, 검증된 증거로 정보 흐름 위반을 입증할 수 있음도 보였습니다.

### Evaluation
- 공격 차단: 153회의 공격 실행에서 생식 계열 실행으로는 허가되지 않은 유출이 한 번도 관측되지 않았습니다. 비교 대상인 기존 방어와 일부 기능을 뺀 변형에서는 5.9~74.5%의 실행에서 유출이 있었습니다. 자동 생성한 변형 91개에서도 유출은 관측되지 않았습니다.
- MCPGuard-Dynamic 비교: 인사, 이사회, 재무, 공개 자료를 다루는 여섯 번의 호출 세션에 최소 권한 정책을 걸고, 일곱 가지 설정에서 세 번씩(총 105회) 시험했습니다. 숨긴 유출은 모든 시행에서 성공했습니다.
- 유용성과 비용: LLM 기반 에이전트가 7개 과제를 모두 완수했고, 사본 하나로 처리되는 호출은 10~49ms가 걸려 매 호출마다 도구를 새로 시작하는 기존 방식보다 2~28배 빨랐습니다.
- 지표 신빙성: 공격 도구와 정책 설정을 저자가 직접 설계했기 때문에, 공격 성공률 수치는 이 시나리오에 대한 것입니다. 보장은 사본 격리와 깨끗한 원본이라는 가정에 기대며, 타이밍 같은 부채널이나 목적지 자체가 공격자인 경우 등은 범위 밖으로 둡니다. MCPGuard의 실패는 구현 결함이 아니라 목적지 기반 격리의 본질적 한계라고 저자들이 분명히 구분한 점은 공정합니다.

# Addition by Subtraction: Toward Mitigating Fragile Safety Alignment in Large Language Models
> arXiv cs.AI 2611.06553, cs.CR 교차 게재 (프리프린트, 심사 전). 뒤스부르크에센대학교(독일)
> 2026

LLM의 안전 정렬은 생각보다 소수의 구성 요소에 몰려 있습니다. 안전에 중요한 뉴런 몇천 개를 잘라 내거나 거절 방향 하나를 지우기만 해도 정렬이 크게 무너진다는 연구가 이어졌습니다. 이 논문은 반대로, 정렬이 그런 소수 구성 요소에 덜 의존하도록 만드는 미세 조정 방법 ABS-Align(Addition by Subtraction)을 제안합니다.

방법은 이름 그대로입니다. 먼저 TwinBreak 방식(해로운 질문과 그와 거의 같은 무해한 질문 쌍의 활성화 차이)으로 안전 핵심 뉴런을 찾습니다. 그다음 DPO 선호 최적화로 미세 조정하면서, 일정 단계마다 중요도가 가장 큰 뉴런부터 점진적으로 잘라 냅니다. 그러면 모델은 잘린 뉴런 없이 다른 부분으로 안전 행동을 다시 익히게 되고, 정렬이 모델 곳곳에 퍼집니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.06553
- arXiv HTML 본문: https://arxiv.org/html/2611.06553
- arXiv PDF: https://arxiv.org/pdf/2611.06553

### Contribution
- 안전 정렬이 희소한 구성 요소에 덜 의존하도록 만드는 첫 시도로, 점진적 가지치기와 선호 최적화를 결합한 미세 조정 방법을 제시했습니다.
- 가지치기 공격을 겨냥해 설계했지만 거절 방향 제거나 블랙박스 탈옥 공격에도 효과가 이어짐을 보였습니다.

- 계속 업데이트되는 모델에서 시간적 멤버십과 그 추론 공격을 처음으로 정식화했습니다.
- 스냅샷 간 신뢰도 궤적을 쓰는 블랙박스 공격 TMIA를 제안했습니다.
- 정적 모델용 방어 세 가지(레이블만 출력, 드롭아웃, 차분 프라이버시)를 연속 업데이트 환경에 맞게 확장해 평가하고, 프라이버시와 유용성의 맞바꿈을 보였습니다.

### Evaluation
- 모델과 데이터: 언어 모델 Pythia-70M, T5, GPT-2 Small과 SST-5, News20, MNLI, 이미지 모델 ResNet-18, SimpleCNN, MobileNet과 CIFAR-10 등 세 가지 이미지 데이터셋입니다. 업데이트는 미세 조정, 데이터 삭제는 NPO 등 언러닝 기법으로 구현했습니다.
- 결과: 시점 단위 추론에서 세 언어 모델 모두 정밀도와 재현율이 80.51% 이상, F1이 83% 이상이었습니다. 구간 단위에서도 Pythia-70M의 세 텍스트 데이터셋에서 F1이 72%를 넘었습니다. 더 큰 생성 언어 모델에서도 효과가 유지된다고 보고합니다.
- 비교 대상: 업데이트 시점마다 기존 멤버십 추론을 적용하는 방식(TS-MIA)과 업데이트 전후 차이를 보는 방식(UP-MIA)입니다. TS-MIA는 거의 모든 시점을 진입으로 예측해 재현율은 높지만 정밀도가 70% 아래였고, UP-MIA는 둘 다 낮았습니다.
- 지표 신빙성: 비교 대상은 이 문제가 새롭기 때문에 저자들이 직접 만든 단순한 기준선입니다. 기본 설정에서 공격자가 모든 스냅샷에 접근하고 확률 벡터를 받는다고 가정하는데, 실제 서비스에서는 이 가정이 강한 편입니다. 일부 스냅샷만 볼 수 있는 경우도 따로 평가했습니다. 모델 크기도 대부분 작습니다.
