# SkillCODER: Towards Auditing and Attribution of Copyright Infringement in LLM Agent Skills
> ACM CCS 2026 채택 논문 (arXiv 프리프린트 판, DOI 10.1145/3830454.3846644)
> 2026

에이전트 스킬은 역할 정의, 제약 조건, 작업 절차를 사람이 읽을 수 있는 긴 문서로 묶은 것이라, 구매자가 무단으로 재배포하거나 공개 스킬을 다른 이름으로 다시 올려도 추적하기 어렵습니다. 기존의 시스템 프롬프트 워터마킹은 모델 그래디언트로 토큰을 바꾸는 방식이어서 스킬처럼 긴 문서에서는 신호가 묽어지고, 읽기 어려운 토큰이 끼어들어 스킬의 가치를 떨어뜨립니다. 이 논문은 스킬을 섹션 단위 중간 표현(SkillIR)으로 나눈 뒤, 자연스러운 조건문 형태의 지시를 여러 구조 노드에 흩어 넣어 평소에는 잠잠하다가 소유자가 설계한 검증 질의에만 정해진 형식의 "캡슐"을 출력하게 만듭니다. 캡슐의 한 필드에는 구매자별로 고른 어휘를 오류 정정 부호로 묶어 넣어, 유출한 구매자까지 특정할 수 있게 했습니다. 검증은 블랙박스 API 출력만으로 이루어집니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.11308
- arXiv HTML 본문: https://arxiv.org/html/2611.11308
- arXiv PDF: https://arxiv.org/pdf/2611.11308
- ACM DOI: https://doi.org/10.1145/3830454.3846644
- 저자 코드 저장소: https://github.com/EonHao/SkillCODER

### Contribution
- 에이전트 스킬의 저작권 감사와 구매자 추적이라는 문제를 처음으로 정식화했습니다. 스킬이 길고 사람이 읽는 문서라는 두 특성이 기존 프롬프트 워터마킹을 무력하게 만든다는 점을 짚었습니다.
- 모델 내부 접근 없이 추론 결과만으로 소유권과 구매자를 동시에 확인할 수 있는 구조를 제안했습니다. 워터마크가 자연어 지시로 들어가므로 스킬의 가독성이 유지됩니다.
- 소유권 증거와 구매자 지문을 하나의 캡슐에 담아 한 번의 검증 질의로 둘 다 확인할 수 있습니다.

### Evaluation
- 코드 리뷰, 데이터 과학, 여행 계획 세 분야의 스킬(Anthropic Skill Creator로 만든 스킬과 공개 커뮤니티 저장소의 실제 스킬)을 대상으로, 공개 모델 4종(Qwen3-1.7B/4B/8B, GLM-Z1-9B)과 상용 API 모델 2종(GPT-5 mini, Claude Haiku 4.5), 에이전트 프레임워크 3종(LangChain, CAMEL, OpenClaw)을 조합한 18개 구성에서 평가했습니다.
- 소유자 검증 정확도는 평균 99.2%로, 비교 대상인 PromptCARE(89.6%)와 PromptCOS(87.5%)보다 높았습니다. 구매자 1순위 식별 정확도는 99.3%로 비교 대상(70.5%, 67.6%)을 크게 앞섰습니다.
- 문장 바꿔 쓰기, 압축, 부가 조항 삭제, 섹션 재배치 공격 아래에서도 공개 모델 기준 소유자 검증이 96.0% 이상 유지됐습니다. 설계를 아는 LLM 정화 공격과 여러 구매자의 공모까지 포함한 적응형 공격 5종에서는 소유권 증거는 유지되고 구매자 식별은 점진적으로 떨어졌다고 보고합니다.
- 비용으로는 워터마크 삽입 후 작업 유용성 점수가 100점 만점에 평균 9.8점 낮아졌습니다. 저자들도 이 손실이 일부 모델과 분야 조합에 몰려 있다고 밝힙니다.
- 비교 대상인 PromptCARE와 PromptCOS는 원래 화이트박스 그래디언트 기반 방법이라, 블랙박스 스킬 환경에 맞게 옮긴 결과와 비교했다는 점은 감안해야 합니다.

#### Comment
- 중국 기관(저장대학교) 중심 논문이라 추가로 확인했습니다. 게재처는 최상위 보안 학회인 ACM CCS 2026이고 본문에 ACM DOI가 실려 있습니다. 저자 가운데 Kui Ren, Zhan Qin, Dacheng Tao(난양공대) 등은 이 분야에서 활동이 확인되는 연구자입니다. 코드 저장소가 GitHub에 공개되어 있고, 상용 API 모델까지 포함해 평가했으며, 유용성 손실도 숨기지 않고 보고했습니다. 수치가 매우 높지만 평가 범위와 손실 보고가 함께 있어 신뢰도에 큰 문제는 없다고 판단했습니다.
- 공동 저자 한 명이 보안 기업(Beijing Chaitin Technology) 소속입니다.
- 스킬 마켓플레이스가 커지면서 실제로 필요해질 기술이지만, 유용성 손실 9.8점은 상업용 스킬에서는 작지 않은 비용입니다.
- 본문 출처: arXiv PDF(사용자 컴퓨터에서 받음).

# CyberBinGym: Can AI Agents Turn Binary Patches into Real Exploits?
> arXiv 프리프린트 (심사 전)
> 2026

보안 패치는 대개 컴파일된 업데이트로 배포되는데, 패치 전후 바이너리를 비교하면 취약점 위치와 공격 방법을 알아낼 수 있습니다(1-day 공격). 이 논문은 AI 에이전트가 소스 코드 없이 패치 전후의 스트립된 바이너리만 받아 실제로 익스플로잇까지 만들 수 있는지 측정하는 벤치마크를 만들었습니다. 53개 오픈소스 프로젝트의 실제 취약점에서 뽑은 100개 과제로 구성되며, 취약점 재현(차등 크래시 테스트)과 실제 익스플로잇(루트 권한 플래그 획득)을 나눠 채점하고, 환경을 직접 뒤지는 식의 보상 해킹은 실행 기록 감사로 걸러 냅니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.10723
- arXiv HTML 본문: https://arxiv.org/html/2611.10723
- arXiv PDF: https://arxiv.org/pdf/2611.10723

### Contribution
- 바이너리만 주어진 1-day 익스플로잇이라는, 기존 벤치마크가 다루지 않던 상황을 측정할 수 있게 했습니다. 기존 벤치마크는 소스 코드를 주거나, 사람이 만든 CTF 문제를 쓰거나, 바이너리 이해만 묻고 실제 공격 결과는 요구하지 않았습니다.
- 공간 메모리 오류, 시간 메모리 오류, 잘못된 포인터 접근, 잘못된 해제, 타입 오류, 초기화 오류의 여섯 가지 취약점 유형과 세 단계 난이도를 고르게 섞었고, 실제 배포 설정으로 컴파일해 정답 PoC로 검증했습니다.
- 패치된 바이너리가 공격에 얼마나 도움이 되는지, 일반적인 바이너리 보호 기법이 켜져 있을 때 어떻게 되는지를 따로 실험했습니다.

### Evaluation
- OpenAI Codex(GPT-5.6), Claude Code(Claude Opus 5), Kimi Code(Kimi K3)를 평가했습니다. 취약점 재현 성공률은 각각 88%, 85%, 64%였지만, 익스플로잇 성공률은 20%, 6%, 0%로 크게 낮았습니다.
- 20개 과제 부분 집합에서 패치된 바이너리를 함께 주면 Codex의 익스플로잇 성공률이 10%에서 25%로 올랐습니다.
- 스택 카나리, PIE, full RELRO, Fortify를 모두 켠 상태에서도 Codex가 원래 성공한 20개 과제 가운데 2개를 여전히 익스플로잇했습니다.
- 과제당 비용과 시간도 함께 보고하며, 패치 바이너리 조건에서는 평균 비용이 약 31달러 수준이었습니다.
- 주요 실험은 안전 장치를 끈 신뢰 접근 프로그램 아래에서 진행했다고 밝히고 있어, 일반 사용자가 쓰는 제품의 능력과는 차이가 있을 수 있습니다.

#### Comment
- 싱가포르국립대, UC 리버사이드, UC 버클리, UC 샌타바버라 공동 연구이며 Dawn Song, Heng Yin, Wenbo Guo 등 이 분야에서 이름이 알려진 연구자가 참여했습니다.
- 취약점을 찾는 능력은 이미 상당하지만, 실제 공격 코드로 이어지는 단계는 아직 불안정하다는 결론입니다. 다만 그 간극이 줄어들수록 패치 배포 지연 기간이 더 위험해진다는 점에서 방어 측에 의미 있는 경고입니다.
- 벤치마크 공개 여부는 본문에서 확인하지 못했습니다.

# Coding Agents Propagate Vulnerabilities in Code Bases
> arXiv 프리프린트 (심사 전)
> 2026

코딩 에이전트는 저장소를 탐색해 기존 코드를 참고하며 새 코드를 쓰는데, 기존 코드에 취약점이 있으면 그것을 본보기 삼아 같은 취약점을 다시 만드는지를 실험으로 확인한 논문입니다. 다른 백엔드 애플리케이션이 이미 있는 저장소에 새 애플리케이션을 구현하는 96개 과제와, 실제 C/C++ 프로젝트에서 메모리 안전과 관련된 코드를 채워 넣는 20쌍의 과제로 나눠, 주변 코드가 안전할 때와 취약할 때의 결과를 비교했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.11455
- arXiv HTML 본문: https://arxiv.org/html/2611.11455
- arXiv PDF: https://arxiv.org/pdf/2611.11455
- 저자 코드 저장소: https://github.com/eth-sri/vulnerability-propagation

### Contribution
- 에이전트가 기여할수록 코드베이스의 보안이 어떻게 변하는지를 처음으로 실증적으로 다뤘습니다.
- 통제된 환경(백엔드 생성)과 현실적인 환경(실제 C/C++ 저장소) 두 가지로 실험을 설계해, 같은 과제에서 주변 코드의 보안 수준만 바꿔 비교했습니다.
- 프롬프트 전략의 영향과, 에이전트가 자신이 넣은 취약점을 알아보는지까지 함께 조사했습니다.

### Evaluation
- 백엔드 과제는 AutoBaxBench에서 일곱 가지 CWE 유형(CWE-20, 22, 78, 79, 89, 522, 863)에 해당하는 24개 시나리오를 골라 만들었고, 실제 익스플로잇으로 보안을 판정했습니다.
- GLM 5.3, Claude Opus 5, GPT-5.6 Sol을 두 설정 모두에서, Claude Opus 5.5와 GPT-6 Astra를 메모리 안전 과제에서 추가로 평가했습니다.
- 취약한 주변 애플리케이션이 있으면 백엔드 코드의 "정확하고 안전한 구현" 비율이 평균 3.4% 떨어졌습니다. C/C++ 저장소 과제에서는 안전한 참고 코드와 취약한 참고 코드 사이의 차이가 평균 35.4%, 모델에 따라 최대 49.0%였습니다.
- 기존 코드 스타일을 따르라는 지시는 전파를 키우고, 보안에 주의하라는 지시는 줄였지만 어느 쪽도 전파를 막지는 못했습니다.
- 구현 이유를 물으면 76.5%의 경우 다른 코드 위치를 따라 했다고 답했고, 취약점 여부를 물으면 69.9%의 경우 스스로 취약점을 알아봤습니다.

#### Comment
- ETH 취리히 SRI 연구실(Martin Vechev) 논문으로, 같은 그룹의 BaxBench 계열 연구를 이어받았습니다. 코드가 공개되어 있습니다.
- "알아볼 수는 있지만 따라 쓴다"는 결과가 핵심입니다. 에이전트 도입이 늘수록 기존 취약점을 먼저 고치지 않으면 같은 패턴이 퍼진다는 실무적 시사점이 큽니다.
- C/C++ 과제가 20쌍으로 많지 않아, 큰 차이 수치는 과제 구성에 따라 달라질 수 있습니다.

# When Experience Becomes a Backdoor: Poisoning Self-Evolving LLM Agents via Failure-Aware Task Optimization
> arXiv 프리프린트 (심사 전)
> 2026

스스로 실행 경험을 스킬로 정리해 다음 작업에 재사용하는 자기 진화형 에이전트를 노린 백도어 공격입니다. 공격자는 스킬 파일을 직접 고칠 수 없고, 진화 학습에 쓰이는 작업만 몰래 끼워 넣을 수 있다고 가정합니다. 그러면 에이전트가 이 작업을 처리하면서 얻은 경험을 정리하는 과정에서 스스로 스킬에 백도어 규칙을 넣게 됩니다. 저자들은 단순히 최종 성공 여부만 보고 오염 작업을 고치면 잘 되지 않는다는 점을 먼저 보이고, 실패를 네 단계(규칙이 스킬에 들어갔는지, 스킬이 불려 왔는지, 규칙을 따랐는지, 원하는 효과가 났는지)로 나눠 진단하고, 나빠진 수정은 되돌리며, 실패한 시도를 기억해 반복하지 않는 BadEvolve를 제안했습니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.10542
- arXiv HTML 본문: https://arxiv.org/html/2611.10542
- arXiv PDF: https://arxiv.org/pdf/2611.10542
- 저자 코드 저장소: https://github.com/ventr1c/BadEvolve

### Contribution
- 스킬을 직접 조작하지 않고 작업만 주입하는 "작업 수준 백도어"라는 현실적인 위협 모델을 제시했습니다.
- 최종 결과만 보는 최적화가 실패하는 이유를 실패 단계 구분 불가와 불안정한 최적화 두 가지로 분석했습니다.
- 단계별 피드백, 되돌리기, 실패 기억을 결합해 공격 성공률을 안정적으로 끌어올렸습니다.

### Evaluation
- SpreadsheetBench, WikiTQ, OfficeQA 세 벤치마크와 네 가지 자기 진화 프레임워크(Trace2Skill, SkillGrad, SkillOpt, A-Evolve), 네 가지 기반 모델(Kimi-K2.5, GPT-OSS-120B, Claude Sonnet 4.6, Qwen3-235B)에서 평가했고, 결과는 세 번 반복 실행 평균입니다.
- 악성 내용 삽입 공격에서 BadEvolve의 평균 공격 성공률은 79.6%(59.3%~100%)로, 비교 대상인 TBA(37.6%)와 TextGrad-Poison(27.8%)보다 크게 높았습니다. 정상 작업 정확도는 오염 없는 경우보다 평균 1.1%포인트만 낮았습니다.
- 답 오염 공격(WikiTQ, A-Evolve)에서는 Kimi-K2.5와 Claude Sonnet 4.6 기준 조건부 성공률이 80.0%와 54.1%로, 가장 좋은 비교 대상(68.5%, 18.0%)보다 높았습니다.

# Mirage: Provable Defense Against LLM KV Cache Timing Side Channels with Topology-Aware Isolation

Mirage는 GPU는 그대로 캐시를 공유해 빠르게 처리하고, 게이트웨이에서 토큰을 내보내는 시점만 늦춰 공격자에게는 캐시 미스처럼 보이게 만듭니다. 어떤 접두어에서 새로운 갈래가 지나치게 많이 생기는지(추측 공격의 특징)를 누적 추적해, 기준을 넘은 접두어에만 지연을 적용합니다.

원문 링크:
- arXiv 초록: https://arxiv.org/abs/2611.10756
- arXiv HTML 본문: https://arxiv.org/html/2611.10756
- arXiv PDF: https://arxiv.org/pdf/2611.10756

### Contribution
- 콘텐츠의 민감도가 아니라 공격자의 탐색 행동을 기준으로 방어를 작동시키는 방식을 제안했습니다.
- 지연을 GPU가 아닌 게이트웨이에서 주므로 캐시 재사용과 처리량을 유지합니다. 스트리밍 응답 전체를 함께 미뤄 버퍼링된 토큰이 한꺼번에 나가는 문제도 처리했습니다.

MCP(Model Context Protocol)는 LLM을 파일 시스템, 데이터베이스, 외부 API에 연결하는 사실상의 표준이 됐지만, MCP 구현체 자체의 소프트웨어 취약점을 체계적으로 모은 데이터셋은 없었습니다. "MCP"라는 약어가 칩 인터커넥트, 리눅스 커널 드라이버 등 무관한 분야에도 쓰여 CVE 검색 결과에 잡음이 많다는 점도 걸림돌입니다. 이 논문은 2026년 2월까지 CVE에서 "MCP"로 검색한 119건을 3단계로 걸러(무관한 72건 제외 등) AI 맥락의 MCP 취약점 24건을 확정하고, 심각도, 유형, 영향 구성 요소(서버, 클라이언트, SDK) 기준으로 분석했습니다. 대표 사례 6건(mcp-server-git의 명령 주입과 경로 조작, Orval 클라이언트의 명령 주입, Dive의 딥링크 설정 변조, TypeScript SDK의 DNS 리바인딩과 UriTemplate ReDoS)의 공격 경로와 수정 방법을 정리했습니다.

### Contribution
- AI 맥락의 MCP 구현 취약점만 모은 첫 정제 데이터셋(2026년 2월 기준 24건 고정 스냅샷)과 검증, 정규화, 보강, 변화 감시 도구를 함께 공개했습니다.
- 약어 혼동을 다루는 필터링 절차를 명시하고, 제외 판단 표본을 두 사람이 따로 검토해 일치율을 보고했습니다.
- 서버 쪽은 도구 인자를 셸이나 파일 경로로 그대로 넘기는 입력 검증 실패, 클라이언트 쪽은 외부 데이터 처리와 확인 절차 부족, SDK 쪽은 안전하지 않은 기본값이 주된 원인이라는 구분을 제시하고, 각각에 대응하는 방어 권고(라이브러리 API 사용과 허용 목록 검증, 경로 정규화 후 포함 여부 검사, 최소 권한 실행, DNS 리바인딩 보호 기본 활성화 등)를 정리했습니다.

### Evaluation
- 데이터: 119건 중 24건 확정. 제외 판단 표본 감사의 평가자 간 일치율 96.7%. JFrog, Trend Micro 보고서와 GitHub 보안 권고와 대조해 공개된 고위험 MCP 사례가 모두 포함됐는지 확인했습니다.
- 분포: 심각 14건(58.3%), 높음 7건(29.2%), 보통 2건, 낮음 1건으로 심각 또는 높음이 87.5%입니다. 명령 주입, 원격 코드 실행, 경로 조작이 66.7%이고, 구성 요소별로는 서버 11건(45.8%), 클라이언트 8건(33.3%), SDK 5건(20.8%)입니다.
- 지표의 신빙성: 탐지 도구나 벤치마크를 평가하는 논문이 아니라 측정과 분류 연구입니다. 표본이 24건으로 작고 CVE가 발급된 사례만 대상이라, 비율 수치는 생태계 전체의 분포가 아니라 공개 CVE 기준의 초기 관찰로 보는 것이 맞습니다. 저자들도 포괄적 벤치마크가 아니라고 밝혔습니다.
